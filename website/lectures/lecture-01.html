2. Limitations ("Weaknesses") of Relational DBMSs

Why this matters: This section is the motivation for OODBMSs — every weakness discussed here is later solved by an OODBMS feature (see Section 11).

2.1 Weakness 1 — Poor Representation of "Real World" Entities

  • Normalization leads to relations (tables) that do not correspond directly to entities in the "real world."
  • This causes fragmentation of the "real world" — a single real-world object (e.g., a member of staff) ends up scattered across multiple normalized tables.
  • Information is most commonly obtained from the DB through performing a JOIN (an intensive computation) of 2 or more tables.

📌 Example — The JOIN Problem (from the slides)

To see a staff member's name together with their branch's address, two separate tables must be joined:

Staff table

staffNo sName position salary branchNo
SL21 John White Manager 30000 B005
SG37 Ann Beech Assistant 12000 B003
SG14 David Ford Supervisor 18000 B003
SA9 Mary Howe Assistant 9000 B007
SG5 Susan Brand Manager 24000 B003
SL41 Julie Lee Assistant 9000 B005

Branch table

branchNo bAddress
B005 22 Deer Rd, London
B007 16 Argyll St, Aberdeen
B003 163 Main St, Glasgow
  • To answer "What is the address of the branch where John White works?" the DBMS must JOIN Staff and Branch on branchNo — an expensive relational-algebra operation — even though, conceptually, "a staff member works at a branch with an address" is a single real-world fact.

📌 Additional Example (added for clarity)

A university database with Student, Registration, and Module tables must JOIN all three tables just to answer "Which modules is student S12345 registered for, and what are their names?" — even though this is one simple real-world question ("what is this student currently studying?").

2.2 Weakness 2 — Semantic Overloading

  • The relational model has a single construct for representing both data AND data relationships: the relation (table).
  • There is no mechanism to distinguish between:
    • relations vs. relationships, or
    • different types of relationships (e.g., one-to-one vs. one-to-many vs. many-to-many; composition vs. association).
  • This means the relational model is semantically overloaded — one construct is forced to carry multiple different meanings.

📌 Example — ERD Semantic Overloading (from the slides)

Consider the ERD: Student — (is written in) → Registration — (is found in) → Module

  • Registration is both a relation (table) AND a relationship (it represents the many-to-many association between Student and Module) — the relational model cannot express that duality directly.
  • The relationship "is written in" is not recorded/labelled anywhere in the Relational DB — it's implicit.
  • The relationship "is found in" is likewise not recorded in the Relational DB.

📌 Additional Example (added for clarity)

Consider a Manages relationship between Employee and Department. In a relational schema, this becomes just another table with two foreign keys — indistinguishable, at the schema level, from a genuine independent entity like Orders. The type of relationship (1:1 management vs. 1:* employment) is not explicitly modelled — it can only be inferred from constraints.

2.3 Weakness 3 — Limited Operations

  • RDBMSs only have a fixed set of operations (using SQL) which cannot be extended, i.e., operations are limited to those defined by the Relational calculus & algebra on sets of tuples.
  • It is not possible for software developers to specify new operations — this is in contrast to OOP methods, where developers can define arbitrary new behaviour on objects.
  • BUT: Database programmers can create stored procedures on the server side as a workaround.

2.4 Weakness 4 — Homogeneous Data Structure

  • Horizontal and vertical homogeneity is restrictive for representing "real world" objects.
    • Horizontal homogeneity: each tuple (row) is composed of the same attributes.
    • Vertical homogeneity: values of an attribute (column) come from the same domain.
  • The intersection of a row and column must be atomic — this means it is not possible to store an object that can be decomposed into its components (i.e., no nested/composite values).
  • Note: it is possible to store a BLOB or CLOB (a pointer to a file containing the object) for viewing purposes only — but the DBMS cannot query/decompose the internal structure of that BLOB/CLOB.

📌 Example (from the slides)

A simple position/salary table:

position salary
Manager 30000
Assistant 12000
Supervisor 18000
Assistant 9000
Manager 24000
Assistant 9000

Every cell (e.g., "Manager", 30000) is atomic — there is no way to store, say, a salary cell that itself contains a structured sub-object like {basic: 25000, bonus: 5000} without breaking First Normal Form.

2.5 Weakness 5 — Impedance (Mismatch)

  • Impedance (Physics analogy): a measure of the opposition (resistance) to the flow of a current in an electrical circuit: I = V / R.
  • Impedance (Software Engineering): a measure of the opposition (difficulty) caused by differences between two programming paradigms — e.g., the set-based, declarative paradigm of SQL vs. the object-based, imperative paradigm of Java/C++.
  • Embedded SQL:
    • Used for applications that access database data from within a host programming language.
    • The SQL standard provides "embedded SQL."
    • This creates the problem of impedance mismatch for software developers: mixing different programming paradigms within one application (e.g., relational rows/tables vs. objects/classes).

2.6 Weakness 6 (part 1) — Example of Impedance Mismatch: JDBC Code

📌 Coding Example 1 — JDBCSample.java (from the slides, reproduced in full)

This program demonstrates the impedance mismatch: Java (OOP) code has to embed textual SQL strings, and results come back as generic ResultSet rows rather than typed Java objects.

import java.sql.*

public class JDBCSample {
    public static void main( String args[ ]) {
        String connectionURL =
            "jdbc:postgresql://localhost:5432/movies;user=java;password=samples";
        try {
            Class.forName("org.postgresql.Driver");
            Connection con = DriverManager.getConnection(connectionURL);
            Statement stmt = con.createStatement();
            ResultSet rs =
                stmt.executeQuery("SELECT moviename, releasedate FROM movies");
            while (rs.next())
                System.out.println("Name= " + rs.getString("moviename")
                                    + " Date= " + rs.getString("releasedate"));
        } finally {
            con.close();
        }
    }
}

Step-by-step walkthrough:

  1. Import the JDBC API — import java.sql.* gives access to Connection, Statement, ResultSet, etc.
  2. Build a connection URL — a plain string specifying the driver protocol (jdbc:postgresql://), host, port, database name (movies), and credentials.
  3. Load the driver class — Class.forName("org.postgresql.Driver") registers the PostgreSQL JDBC driver with the DriverManager.
  4. Open a connection — DriverManager.getConnection(connectionURL) returns a live Connection object to the database.
  5. Create a Statement — con.createStatement() gives an object that can execute raw SQL text.
  6. Execute a query — stmt.executeQuery("SELECT moviename, releasedate FROM movies") sends a string of SQL to the database and returns a ResultSet (a cursor over relational rows, not Java objects).
  7. Iterate the result set — while (rs.next()) moves the cursor row by row; each column must be manually extracted by name and type (rs.getString("moviename")) and reassembled by the programmer — this is the impedance mismatch in action: the programmer must manually translate between rows/columns and any meaningful Java object.
  8. Clean up — con.close() in a finally block releases the database connection.

📌 Coding Example 2 (added for step-by-step clarity)

A minimal JDBC example inserting a row, showing the same mismatch in the opposite direction (Java object → SQL string):

import java.sql.*;

public class InsertStudent {
    public static void main(String[] args) throws Exception {
        // Step 1: Load driver
        Class.forName("org.postgresql.Driver");

        // Step 2: Open connection
        Connection con = DriverManager.getConnection(
            "jdbc:postgresql://localhost:5432/university", "java", "samples");

        // Step 3: Prepare an SQL statement with placeholders
        PreparedStatement ps = con.prepareStatement(
            "INSERT INTO Student (studentNo, sName) VALUES (?, ?)");

        // Step 4: Manually map Java field values into the SQL statement
        ps.setString(1, "S12345");
        ps.setString(2, "Thabo Mokoena");

        // Step 5: Execute the update
        ps.executeUpdate();

        // Step 6: Close connection
        con.close();
    }
}

Why this illustrates impedance mismatch: a Student object in Java naturally has fields (studentNo, sName), but to persist it, the programmer must manually flatten it into an SQL string with positional ? placeholders — there is no automatic translation between the Java class and the relational table.

2.7 Weakness 6 (part 2) — RDBMS Supports Only Short-Lived Transactions

  • A transaction is: an indivisible sequence of DB operations.
BEGIN TRANSACTION
    SQL statements for transaction go here
END TRANSACTION
  • RDBMS transactions are designed to be short-lived (business) transactions (e.g., "transfer money between two accounts," completing in milliseconds), as opposed to long-duration (design) transactions (e.g., a CAD engineer working on a design for several days) which RDBMSs handle poorly.

2.8 Weakness 7 — Schema Changes Create Problems

  • A database schema change requires corresponding program changes.
  • Example of a change: adding new attributes (columns) to a table — every piece of application code that reads/writes that table may need to be updated to account for the new column, and existing rows must be back-filled or given defaults.

3. Storing Objects in Relational Databases (Object–Relational Mapping)

  • Storing objects in a relational DB is one approach to achieving persistence with an OOP language: use an RDBMS as the underlying storage engine.
  • This requires mapping class instances (i.e., objects) to one or more rows distributed over one or more relations — the programmer must write code to convert between objects and rows.
  • Object–Relational Mapping (ORM) Adds Complexity.

📌 Example (from the slides)

A STUDENT registers for COURSES for a DEGREE PROGRAM.

  • ⇒ The data for a single STUDENT object ends up stored across 3 separate tables (e.g., Student, Registration, Module/DegreeProgram) — reconstructing one Student object back into memory requires multiple JOINs, which is exactly the ORM complexity/impedance-mismatch problem described above.

📌 Additional Example (added for clarity)

A Book object with an internal List<Author> (multiple authors per book) requires at least two tables in an RDBMS: Book and Author, linked via a BookAuthor join table for the many-to-many relationship — the single conceptual Book object is fragmented across three relations.

4. Introduction to Object-Oriented Databases

4.1 Origins — Design Data Characteristics

Some common characteristics of design data that motivated OODBs:

  • Design has many parts & interdependent subsystems.
  • Large number of types & small number of instances — this is the opposite of the relational world, where there are typically few relations but many tuples.
  • OODBs originate from Engineering & design domains.
    • e.g., CAD (Computer Aided Design) databases store data relating to engineering designs.
    • Examples of designs: (1) Cars, (2) Buildings.
    • Realised today using CAD, BIM (Building Information Modelling), Digital Twins, Engineering Simulation, etc.
  • Note: the OODBMS market is relatively small compared with the RDBMS market.

📌 Example (added for clarity)

An automotive CAD system might model a Car design with thousands of distinct part types (bolt, gasket, sensor, ECU, bracket, etc. — each its own class/type) but only a handful of design instances (one master design per car model). This is the inverse of, say, a Sales relational database, which has very few table types (Customer, Order, Product) but millions of row instances.

4.2 Object Databases / Object Data Management Systems

  • Object databases (ODB) / Object data management systems (ODMS) are designed to:
    • Meet some of the needs of more complex applications.
    • Specify:
      • The structure of complex objects.
      • The operations that can be applied to these objects.

5. OO Database Terminology

Term Definition
OO data model A (logical) data model that captures the semantics of objects (classes) supported in object-oriented programming.
OO database A persistent, sharable collection of objects defined by an OO data model.
OODBMS The manager (software) of an OODB.

📌 Example (added for clarity)

For a real-estate agency system: the OO data model defines classes like PropertyForRent, Client, Branch; the OO database is the actual persistent, shared collection of PropertyForRent, Client, and Branch object instances stored on disk; the OODBMS is the software (e.g., ObjectDB or ObjectStore) that manages creating, storing, querying, and retrieving those objects.

6. OODB and OODBMS — How They Relate

  • The OO data model defines the contents of the OODB.
  • Diagram structure (from the slides):
    • A Database system contains Sales application programs and Contracts application programs, each with their own "Data entry and reports" modules, used by Sales staff and Contracts staff respectively.
    • Both sets of application programs communicate with a central DBMS — labelled here as the Object-oriented DBMS (OODBMS).
    • The OODBMS in turn manages the Database itself — labelled as the Object-oriented database (OODB) — which, in the slide's real-estate example, stores PropertyForRent, PrivateOwner, Client, and Lease details + file definitions.
    • The OO data model is what "defines the contents of" both the OODBMS logic and the OODB data.
  • OO data model: (logical) data model that captures the semantics of objects (classes) supported in object-oriented programming.

8. Strategies for Developing an OODBMS

There are 5 strategies in total (strategies 1–2 are core content; strategies 3–5 are marked "additional reading for the student"):

Strategy 1 — Extend an Existing Object-Oriented Programming Language

  • Add traditional database capabilities to an existing OOP language.
  • e.g., Smalltalk, C++, Java.
  • e.g., GemStone extended Smalltalk, C++, Java.

Strategy 2 — Provide an Extensible OODBMS Library

  • No extensions to the OOP language are needed.
  • Instead, provide a persistence framework/library.
  • The library provides persistence and database capabilities.
  • Developers work in a known programming language with the same compiler (no special compiler required).
  • Examples: ObjectStore (for C++) and ObjectDB (for Java).

Strategy 3 — Imbed OODB Language Constructs in a Conventional Host Language (additional reading)

  • e.g., O2 : extensions for C.

Strategy 4 — Extend an Existing Database Language (SQL) with Object-Oriented Capabilities (additional reading)

  • Object-oriented features were introduced in SQL:1999 and remain supported by many modern DBMSs, including PostgreSQL.
  • There is an Object SQL standard by ODMG.
  • Ontos and Versant provide a version of Object SQL.

Strategy 5 — Develop a Novel Database Data Model/Language (additional reading)

  • No history / baggage — start from scratch.
  • No installed base, no skills (a downside — nobody already knows it).
  • Example: Semantic Information Manager (SIM).

📌 Example (added for clarity)

  • Strategy 1 in practice: GemStone/S adds persistence keywords directly into the Smalltalk language itself, so a Smalltalk programmer writes almost no "extra" database code — persistence is baked into the language.
  • Strategy 2 in practice: ObjectDB requires no changes to the Java language or compiler — a normal javac-compiled program simply imports the javax.persistence (JPA) library, annotates classes with @Entity, and calls library methods like em.persist(obj) to get database behaviour (this is explored fully in Section 9).

9. Case Study: ObjectDB for Java

9.1 What is ObjectDB?

  • ObjectDB is a powerful Object-Oriented Database Management System (ODBMS).
  • It provides all the standard database management services — storage and retrieval, transactions, lock management, query processing, etc. — in a way that makes development easier and applications faster.

9.2 ObjectDB Features

  • 100% pure Java Object-Oriented Database Management System (ODBMS).
  • No proprietary API — managed only by standard Java APIs (JPA 2 / JDO 2).
  • Suitable for database files ranging from kilobytes to terabytes.
  • Supports both Client-Server mode and Embedded mode.
  • Single JAR with no external dependencies.
  • Database is stored as a single file.
  • Advanced querying and indexing capabilities.
  • Effective in heavy loaded multi-user environments.
  • Can easily be embedded in applications of any type and size.

9.3 Object Identifier (OID)

  • One goal of an OODB is to maintain a direct correspondence between real-world and database objects so that objects do not lose their integrity and identity and can easily be identified and operated upon.
  • Hence, a unique identity is assigned to each independent object stored in the database.
  • This unique identity is typically implemented via a unique, system-generated object identifier (OID).

9.4 Defining a JPA Entity Class

  • Jakarta Persistence API (JPA) — formerly Java Persistence API — defines a standard for management of persistence and object/relational mapping in Java environments.
  • A JPA entity class is a POJO (Plain Old Java Object) class — i.e., an ordinary Java class that is marked (annotated) as having the ability to represent objects in the database.
  • Common implementations include: Hibernate, EclipseLink, and ObjectDB.

9.5 The Point Entity Class — Coding Example 1

The following Point class, which represents points in a plane, is marked as an entity class. It provides the ability to store Point objects in the database and retrieve Point objects from the database.

package com.objectdb.tutorial;

import javax.persistence.Entity;

@Entity
public class Point {
    // Persistent Fields:
    private int x;
    private int y;

    // Constructor:
    Point (int x, int y) {
        this.x = x;
        this.y = y;
    }

    // Accessor Methods:
    public int getX() { return this.x; }
    public int getY() { return this.y; }

    // String Representation:
    @Override
    public String toString() {
        return String.format("(%d, %d)", this.x, this.y);
    }
}

Step-by-step walkthrough:

  1. Package declaration — package com.objectdb.tutorial; — normal Java package organisation, no persistence meaning.
  2. Import the annotation — import javax.persistence.Entity; brings in the JPA @Entity annotation.
  3. Annotate the class — @Entity marks Point as a persistent entity class — this single annotation is what tells ObjectDB "instances of this POJO can be stored in and retrieved from the database." No special base class or interface needs to be implemented (unlike some older persistence frameworks).
  4. Declare persistent fields — private int x; and private int y; are the class's persistent fields; by default JPA persists all non-static, non-transient fields of an @Entity class.
  5. Constructor — Point(int x, int y) is a normal Java constructor used to create Point instances in memory before they are persisted.
  6. Accessor methods — getX() and getY() are plain getters — no special persistence logic needed here; JPA can use field or property access.
  7. toString() override — a normal Java convenience method for readable printing of a Point; unrelated to persistence, included to show that entity classes remain ordinary Java classes (POJOs) — they are not required to be "database-only" objects.

📌 Coding Example 2 (added for step-by-step clarity) — A Student Entity Class

Applying the exact same pattern to a different domain object, to reinforce the "POJO + @Entity" recipe:

package com.university.demo;

import javax.persistence.Entity;
import javax.persistence.Id;

@Entity
public class Student {
    // Persistent Fields:
    @Id
    private String studentNo;
    private String name;
    private double gpa;

    // Constructor:
    public Student(String studentNo, String name, double gpa) {
        this.studentNo = studentNo;
        this.name = name;
        this.gpa = gpa;
    }

    // No-arg constructor required by JPA:
    public Student() {}

    // Accessor Methods:
    public String getStudentNo() { return this.studentNo; }
    public String getName() { return this.name; }
    public double getGpa() { return this.gpa; }

    @Override
    public String toString() {
        return String.format("%s (%s) — GPA: %.2f", name, studentNo, gpa);
    }
}

Step-by-step walkthrough:

  1. @Entity marks the class as persistent — identical role to the Point example.
  2. @Id marks studentNo as the primary/identifying field for this entity (an addition beyond the slide's simpler Point example, showing how identity can also be application-defined alongside the system-generated OID).
  3. A no-argument constructor is added — JPA implementations require this so they can reconstruct objects from stored data via reflection.
  4. The rest of the class (fields, accessors, toString) follows exactly the same POJO pattern as Point.

9.6 Database Connections in ObjectDB

  • In JPA, a database connection is represented by the EntityManager interface.
  • Therefore, in order to manipulate an ObjectDB database, we need an EntityManager instance.
  • Operations that modify database content also require an EntityTransaction instance.

9.7 Obtaining an EntityManagerFactory

  • Obtaining an EntityManager instance consists of two steps:
    1. Obtain an instance of EntityManagerFactory that represents the relevant database.
    2. Use that factory instance to get an EntityManager instance.
EntityManagerFactory emf =
    Persistence.createEntityManagerFactory(
        "objectdb:$objectdb/db/points.odb");

9.8 Obtaining an EntityManager

  • Once we have an EntityManagerFactory, we can easily obtain an EntityManager instance:
EntityManager em = emf.createEntityManager();
  • The EntityManager instance represents a connection to the database.
  • When using JPA, every operation on a database is associated with an EntityManager.

9.9 Using an EntityTransaction

  • Operations that modify database content, such as store, update, and delete, should only be performed within an active transaction.
  • Given an EntityManager, em, you begin a transaction like this:
em.getTransaction().begin();
  • There is a one-to-one relationship between an EntityManager instance and its associated EntityTransaction instance (the one returned by getTransaction()).

9.10 CRUD Operations Using ObjectDB — Coding Example 1

Given an EntityManager, em, that represents a JPA connection to the object database, we can use it to store, retrieve, update and delete database objects as follows:

Operation Example
1. Storing New Entity Objects em.getTransaction().begin(); for (int i = 0; i < 1000; i++) { Point p = new Point(i, i); em.persist(p); } em.getTransaction().commit();
2. Reading Entity Objects Query q1 = em.createQuery("SELECT COUNT(p) FROM Point p"); System.out.println("Total Points: " + q1.getSingleResult());
3. Delete Entities em.getTransaction().begin(); em.remove(p); // delete entity em.getTransaction().commit();
4. Update Entities em.getTransaction().begin(); p.setX(p.getX() + 100); // update entity em.getTransaction().commit();

Step-by-step walkthrough of the full CRUD lifecycle:

  1. Create (Store):
    1. Begin a transaction — em.getTransaction().begin();.
    2. Loop and construct 1000 in-memory Point objects — new Point(i, i).
    3. Mark each object for persistence — em.persist(p); (this schedules the object to be written to the DB).
    4. Commit the transaction — em.getTransaction().commit(); — this is when the objects are actually flushed to the database file, and each is assigned an OID.
  2. Read:
    1. Create a JPQL query — em.createQuery("SELECT COUNT(p) FROM Point p") counts all Point entities.
    2. Execute and retrieve a single scalar result — q1.getSingleResult() runs the query and returns the count.
  3. Update:
    1. Begin a transaction.
    2. Mutate a managed object directly — p.setX(p.getX() + 100); — note there is no explicit SQL UPDATE statement; because p is a managed entity (retrieved via em), simply changing its field is enough.
    3. Commit — ObjectDB automatically detects the change and writes it to the database.
  4. Delete:
    1. Begin a transaction.
    2. Call em.remove(p); to mark the entity for deletion.
    3. Commit — the object is removed from the database file.

📌 Coding Example 2 (added for step-by-step clarity) — Full CRUD Program for Student

Combining everything above into one complete, runnable-style program using the Student entity from Section 9.5:

EntityManagerFactory emf =
    Persistence.createEntityManagerFactory("objectdb:$objectdb/db/university.odb");
EntityManager em = emf.createEntityManager();

// --- CREATE ---
em.getTransaction().begin();
Student s1 = new Student("S12345", "Thabo Mokoena", 3.8);
em.persist(s1);
em.getTransaction().commit();

// --- READ ---
Query q = em.createQuery("SELECT s FROM Student s WHERE s.gpa > 3.5");
List<Student> topStudents = q.getResultList();
for (Student s : topStudents) {
    System.out.println(s);
}

// --- UPDATE ---
em.getTransaction().begin();
s1.getClass(); // (s1 is already a managed entity)
// Suppose gpa is updated after a re-mark:
// s1.gpa = 3.9;  (would require a setter in a real class)
em.getTransaction().commit();

// --- DELETE ---
em.getTransaction().begin();
em.remove(s1);
em.getTransaction().commit();

em.close();
emf.close();

Step-by-step walkthrough:

  1. Obtain the factory and manager exactly as in Section 9.7–9.8, pointing at a different database file (university.odb).
  2. Create: begin → construct → persist() → commit, identical pattern to the Point loop.
  3. Read: this time using a JPQL WHERE clause (s.gpa > 3.5) instead of COUNT, and getResultList() instead of getSingleResult() since multiple rows may come back.
  4. Update: shown conceptually — any field mutation on a managed entity between begin() and commit() is automatically saved.
  5. Delete: identical remove() pattern as the Point example.
  6. Close resources — em.close() and emf.close() — good practice not explicitly shown on the slide, added here for completeness.

10. Case Study: ObjectStore for C++

  • ObjectStore is a Commercial OODBMS.
  • It uses heap-allocated objects.

10.1 What is ObjectStore? (Architecture)

  • ObjectStore is a "pure" object database.
  • It stores C++ objects in the same format as they are used in memory.
  • Objects are accessed and updated using the same C++ syntax as heap-allocated objects — i.e., there is almost no impedance mismatch for the C++ programmer, because persistent objects "look like" ordinary in-memory C++ objects.
  • Architecture (Client Side vs. Server Side):
    • Client Side: a C++ Client holds "Persistent objects used by client" — an in-memory tree/graph of linked objects.
    • Server Side: an ObjectStore Server manages "Persistent objects in ObjectStore database" stored on disk.
    • The client and server communicate: the client sends requests and receives objects back from the server; the server's database persists the equivalent object graph on disk.

10.2 ObjectStore is Distributed

  • A client can access objects in different remote databases in the same transaction.
  • Architecture: multiple Clients connect (via a network) to multiple osserver (ObjectStore server) processes, each of which manages one or more DB files.
  • This means a single logical transaction on the client side can span object data physically stored on several different remote database servers simultaneously.

10.3 ObjectStore C++ Client — Detailed Architecture

  • The C++ client is the program you write.
  • It is linked with the ObjectStore libraries.
  • It opens databases and runs transactions against them.
  • It allocates objects, calls methods on them, and deletes them.
  • Pages are fetched automatically from the DB as needed.
  • ObjectStore automatically maintains a cache of recently accessed pages.
  • Client is a C++ application program.
  • Architecture components (from the slide diagram):
    • Client Side: memory is organised into Heap → PSR → Stack; within it sits the C++ Client process, which contains a Session object, and connects to a Cache Manager, a Commseg (communication segment), and a Client Cache.
    • Server Side: the ObjectStore Server communicates with the Cache Manager (client side), writes to a Txn Log (transaction log, for recovery), and manages one or more Databases.

📌 Example (added for clarity)

A CAD application built with ObjectStore might have a C++ class Car3DModel containing pointers to thousands of Part sub-objects. In an RDBMS, saving this would require flattening the object graph into many rows across many tables (see Section 3). With ObjectStore, the entire in-memory pointer graph of Car3DModel and its Part objects can be made persistent with a single call, using ordinary C++ pointer syntax (car->parts[i]->name) to navigate it — both while it's in memory and after retrieving it from disk.

11. How OODBMSs Overcome the Limitations of RDBMSs

This section directly answers the recap question posed in Lecture 3: "How does OODBMSs e.g. ObjectDB overcome the limitations discussed previously?" It maps back one-to-one onto Section 2.

11.1 Recap — Weaknesses 1 & 2

1. Poor representation of "real world" entities

  • Normalization leads to relations that do not correspond to entities in the "real world."
  • Joins are needed to obtain information from relations (tables).

2. Semantic Overloading

  • Single construct for representing data and data relationships: the relation.
  • No mechanism to distinguish between relations & relationships, or between different types of relationships.

11.2 Solution to Weakness 1 — Representation of "Real World" Entities

  • OOP constructs are used: classes, inheritance, composition, etc. — these map directly onto real-world entities and their structure.
  • Joins are not used (there are no tables in the DB) — since a real-world object is stored as one object, not fragmented across relations, there is nothing to "join" back together.

11.3 Solution to Weakness 2 — No Semantic Overloading

  • Object identifier (OID) is generated by the DBMS for every object, giving every object a unique, unambiguous identity — separate from its data.
    • Logical OID: independent of physical location on disk.
    • Physical OID: points to an actual location on disk.
  • Representation of relationships (business rules):
    • One-to-one, one-to-many, many-to-many relationships (object composition) are done using OIDs (rather than foreign keys embedded in flat tables).
  • Representation of inheritance relationships:
    • Done through class definitions — inheritance is a first-class OOP construct, unlike in the relational model.

  • Method of locating objects: Lookup a virtual memory pointer (in the ROT) with each object access.
  • OIDs are obtained from the DBMS, typically using constructors & an overloaded new operator.

11.8 Recap — Weakness 3 (Limited Operations)

3. Limited Operations

  • RDBMSs only have a fixed set of operations which cannot be extended, i.e., operations on relations (sets of tuples) & tuples.
  • Not possible to specify new operations (BUT: can use stored procedures).
  • How do OODBMSs e.g. ObjectDB overcome the above limitations?

11.9 Solution to Weakness 3 — OOP Methods Defined for Classes

  • Solution: OOP methods are defined for classes.

📌 Coding Example 1 — The Pilot Class for OODB (from the slides, reproduced in full)

//package com.db4o.f1.chapter1;

public class Pilot
{
    private String name;
    private int points;

    public Pilot(String name, int points)
    {
        this.name = name;
        this.points = points;
    }

    public int getPoints()
    {
        return points;
    }

    public void addPoints(int points)
    {
        this.points += points;
    }

    public String getName()
    {
        return name;
    }

    public String toString()
    {
        return name + "/" + points;
    }
}

Step-by-step walkthrough:

  1. Fields — name (String) and points (int) hold the pilot's identifying data and score.
  2. Constructor — Pilot(String name, int points) initialises a new in-memory Pilot object.
  3. getPoints() — a simple accessor operation.
  4. addPoints(int points) — a custom, user-defined operation/method (this.points += points;) — this is exactly the kind of new operation that RDBMSs could not support natively (Weakness 3) but is trivially expressed as a method directly on the Pilot class in an OODBMS.
  5. getName() — another accessor.
  6. toString() — overridden for display, formats the object as "name/points".
  • This directly demonstrates the fix for Weakness 3: instead of being limited to SQL's fixed relational operators, the developer can attach arbitrary behaviour (like addPoints) directly to the persistent class — this new operation travels with every Pilot object stored in the OODB.

📌 Coding Example 2 (added for step-by-step clarity) — Extending Pilot with a Business-Rule Method

public class Pilot {
    private String name;
    private int points;
    private static final int CHAMPIONSHIP_THRESHOLD = 100;

    public Pilot(String name, int points) {
        this.name = name;
        this.points = points;
    }

    public void addPoints(int points) {
        this.points += points;
    }

    // New custom operation — not expressible as a fixed SQL operator
    public boolean isChampionshipContender() {
        return this.points >= CHAMPIONSHIP_THRESHOLD;
    }

    public String toString() {
        return name + "/" + points;
    }
}

Step-by-step walkthrough:

  1. A new static constant, CHAMPIONSHIP_THRESHOLD, encodes a business rule directly in the class.
  2. The new method isChampionshipContender() performs a domain-specific computation (points >= 100) that a plain relational SELECT statement could express only via a WHERE clause external to the data — here, it is encapsulated inside the object itself, so any part of the application can call pilot.isChampionshipContender() without re-writing that business logic elsewhere.
  3. This reinforces Weakness 3's solution: OOP methods let the data and its behaviour travel together as one persistent unit.

11.10 Storing and Executing Methods

There are two approaches to storing/executing the methods (behaviour) associated with persistent objects:

1. Store methods in external files

  • Link libraries into the application at compile / link time.
  • Architecture: CLIENT (Application + Object manager) exchanges Requests / Objects with the SERVER (Object server), which is backed by an Object store; the Object manager on the client side is linked at compile-time to external method files (File1, File2, File3) — i.e., "Methods in files (bound at compile and link time)."

2. Store methods in database

  • Dynamically bound to the application at run-time.
  • Architecture: identical Client/Server structure, but this time — "Methods dynamically bound to application" — the method code itself resides in the Object store alongside the data, and is fetched/bound to the running application at run-time rather than at compile-time.

Benefits (apply especially to storing methods in external files / libraries):

  • Eliminates redundant code.
  • Simplifies modifications.
  • Methods are more secure.
  • Methods can be shared concurrently.
  • Improved integrity.

📌 Example (added for clarity)

Approach 1 is analogous to a Java application that is compiled against a .jar library containing the Pilot class's methods — if the method logic changes, the whole application must be recompiled/relinked. Approach 2 is analogous to a stored-procedure-like model where the OODBMS itself stores the bytecode/logic for addPoints() inside the database, so different client applications connecting to the database at run-time automatically get the current version of the method without needing to be recompiled.

13. JPA Query API

  • The JPA Query Language (JPQL) is defined as an object-oriented version of SQL.
  • Users familiar with SQL find JPQL very easy to learn and use.
  • Topics to be discussed:
    • JPA Query API
    • JPA Query Structure (JPQL/Criteria)
    • JPA Query Expressions (JPQL/Criteria)

13.1 The Two Query Interfaces

Queries are represented in JPA 2 by two interfaces:

  • The old Query interface: the only interface available for representing queries in JPA 1.
  • The new TypedQuery interface: introduced in JPA 2. The TypedQuery interface extends the Query interface.

📌 Coding Example — Query vs. TypedQuery (from the slides)

Query q1 = em.createQuery("SELECT c FROM Country c");

TypedQuery<Country> q2 =
    em.createQuery("SELECT c FROM Country c", Country.class);

Step-by-step comparison:

  1. Line 1 (Query) — em.createQuery("SELECT c FROM Country c") returns a raw, untyped Query object. Any result retrieved from q1 must be manually cast to Country by the developer (e.g., (Country) q1.getSingleResult();).
  2. Line 2 (TypedQuery<Country>) — passing the extra Country.class argument returns a TypedQuery<Country>, meaning the compiler and IDE know the result type is Country — no manual casting needed, and type errors are caught at compile time.
  3. Why it matters: TypedQuery is generally preferred in modern JPA/ObjectDB code because it is safer (compile-time type checking) and more convenient (q2.getSingleResult() returns a Country directly).

14. JPA Query Structure (JPQL / Criteria)

  • The syntax of the Java Persistence Query Language (JPQL) is very similar to the syntax of SQL.
  • The main difference between SQL and JPQL is that SQL works with relational database tables, records and fields, whereas JPQL works with Java classes and objects.

14.1 The Six JPQL Clauses

As with SQL, a JPQL SELECT query consists of up to 6 clauses, in the following format:

SELECT ... FROM ...
[WHERE ...]
[GROUP BY ... [HAVING ...]]
[ORDER BY ...]

Additionally, JPQL also supports:

DELETE FROM ... [WHERE ...]
UPDATE ... SET ... [WHERE ...]

📌 Example (added for clarity) — All Clauses in One Query

TypedQuery<Country> q = em.createQuery(
    "SELECT c FROM Country c " +
    "WHERE c.population > 1000000 " +
    "GROUP BY c.continent " +
    "HAVING COUNT(c) > 3 " +
    "ORDER BY c.name",
    Country.class);

Step-by-step breakdown:

  1. SELECT c FROM Country c — selects whole Country objects (aliased c), analogous to SELECT * FROM Country in SQL but returning objects, not rows.
  2. WHERE c.population > 1000000 — filters which Country objects are considered, exactly like a SQL WHERE clause but referencing an object attribute (c.population) rather than a column.
  3. GROUP BY c.continent — groups the filtered countries by their continent attribute.
  4. HAVING COUNT(c) > 3 — keeps only groups (continents) that have more than 3 matching countries.
  5. ORDER BY c.name — sorts the final result set alphabetically by the country's name attribute.

15. JPA Query Expressions

  • Query expressions are the foundations on which JPQL and criteria queries are built.
  • Every query consists of clauses — SELECT, FROM, WHERE, GROUP BY, HAVING and ORDER BY — and each clause consists of JPQL query expressions.

📌 Example (added for clarity)

In the query WHERE c.population > 1000000 AND c.continent = 'Africa', each of the following is a query expression:

  • c.population — a path expression (navigation from variable c to its population attribute).
  • 1000000 — a literal expression.
  • c.population > 1000000 — a comparison expression (combining two smaller expressions with the > operator).
  • c.continent = 'Africa' — another comparison expression.
  • The whole ... AND ... construct — a logical expression combining two comparison expressions.

📌 Example (added for clarity)

  • In SQL: SELECT * FROM Country returns rows — plain sets of column values, with no behaviour attached.
  • In JPQL: SELECT c FROM Country c returns Country objects — each result is a fully-formed Java object (with any methods the Country class defines) rather than a disconnected row of values. This mapping is the conceptual key to understanding every JPQL query: mentally substitute "table" → "entity/class," "row" → "object," and "column" → "attribute" when translating SQL knowledge to JPQL.

17. JPA Atomic Query Expressions, Operators & Functions

17.1 Atomic Query Expressions

  • The atomic query expressions are:
    • JPQL / Criteria Variables — e.g., Range (e.g., the alias c in FROM Country c).
    • JPQL / Criteria Parameters — e.g., named, ordinal (bound parameters passed into a query, e.g., :countryName or ?1).
    • JPQL / Criteria Literals — e.g., NULL, Boolean, etc.
  • Every query expression consists of at least one atomic component. More complex query expressions are built by combining atomic expressions with operators and functions.

17.2 JPA Operators and Functions

  • JPQL / Criteria queries support the following operators (in order of decreasing precedence):
Precedence Operator Category Operators
(1) Navigation operator .
(2) Arithmetic operators * (multiplication), / (division), + (addition), - (subtraction)
(3) Comparison operators =, <>, <, <=, >, >=, IS [NOT] NULL, [NOT] BETWEEN, plus Collection operators: [NOT] IN, IS [NOT] EMPTY, [NOT] MEMBER [OF], and the [NOT] LIKE operator
(4) Logical operators AND, OR, NOT

📌 Example (added for clarity) — Using Parameters and Operators Together

TypedQuery<Student> q = em.createQuery(
    "SELECT s FROM Student s " +
    "WHERE s.gpa >= :minGpa AND s.name LIKE :namePattern",
    Student.class);
q.setParameter("minGpa", 3.0);
q.setParameter("namePattern", "T%");
List<Student> results = q.getResultList();

Step-by-step breakdown:

  1. :minGpa and :namePattern are named parameters (an atomic query expression type) — placeholders that get filled in at run-time.
  2. s.gpa >= :minGpa uses the comparison operator >= (precedence level 3) between the navigation expression s.gpa (precedence level 1, i.e., resolved first) and the parameter.
  3. s.name LIKE :namePattern uses the LIKE collection/string operator (also precedence level 3) for pattern matching ("T%" matches any name starting with "T").
  4. The two comparisons are joined with the logical operator AND (precedence level 4, evaluated last).
  5. q.setParameter(...) binds actual values to the named parameters before execution.
  6. q.getResultList() executes the query and returns a List<Student> of all matching objects.

18. Questions & Memo

Section 1 — Administrative

Q1: What percentage of a student's semester mark comes from Semester Test 2, and what is the minimum semester mark required to write the exam?

A1: Semester Test 2 contributes 50% of the semester mark. A student needs a minimum 40% semester mark AND must have completed at least 3 practical assignments to be permitted to write the final exam.

Section 2 — Limitations of RDBMSs

Q2: List all seven weaknesses of RDBMSs discussed in the lecture.

A2:

  1. Poor representation of "real world" entities.
  2. Semantic overloading.
  3. Limited operations.
  4. Homogeneous data structure.
  5. Impedance (mismatch).
  6. RDBMS supports only short-lived transactions.
  7. Schema changes create problems.

Q3: Explain why a JOIN is needed to see a staff member's name together with their branch's address in a relational database, and why this is considered a weakness.

A3: Because normalization splits the "real world" fact (a staff member works at a branch with an address) across two separate relations, Staff (which stores branchNo as a foreign key) and Branch (which stores bAddress). To reconstruct the combined real-world fact, the DBMS must perform a JOIN — an intensive computational operation — on branchNo. This is a weakness because it means a single conceptual real-world entity requires expensive cross-relation computation just to view together, rather than being stored/retrieved as one coherent unit.

Q4: What is "semantic overloading" in the relational model, and how does the Student–Registration–Module ERD example illustrate it?

A4: Semantic overloading means the relational model has only one construct — the relation — to represent both data and relationships between data, with no way to distinguish relations from relationships, or different relationship types from each other. In the ERD example, Registration functions simultaneously as a relation (a table storing registration data) and as the relationship connecting Student and Module. Furthermore, the semantic labels on the relationships themselves ("is written in," "is found in") are not recorded anywhere in the relational database — that meaning exists only in the ERD diagram, not in the stored data.

Q5: Give an example of "homogeneous data structure" being a limitation, using the intersection-must-be-atomic rule.

A5: In a position/salary table, every cell must hold a single atomic value (e.g., "Manager", 30000). It is not possible to store a composite/decomposable object in a single cell — e.g., a salary cell cannot directly hold a structured value like {basic: 25000, bonus: 5000}. The only relational workaround is storing a BLOB/CLOB pointer to an external file, but that file's internal structure cannot be queried by the DBMS — it is only useful for viewing.

Q6: In the JDBC code example, identify two specific points at which the "impedance mismatch" between Java (OOP) and SQL (relational) is visible.

A6:

  1. The SQL query itself is embedded as a plain string literal — stmt.executeQuery("SELECT moviename, releasedate FROM movies") — meaning SQL syntax is not checked by the Java compiler and is essentially "foreign" code living inside Java source.
  2. Extracting results requires manual, per-column, per-type extraction from the generic ResultSet — rs.getString("moviename") — the programmer must manually map relational columns back into meaningful application data; there is no automatic object reconstruction.

Q7: Distinguish between a short-lived (business) transaction and a long-duration (design) transaction, and state which one RDBMSs are best suited for.

A7: A short-lived (business) transaction completes quickly (e.g., transferring money between two bank accounts in milliseconds), while a long-duration (design) transaction may remain open for extended periods (e.g., an engineer working on a CAD design over several days). RDBMSs are optimised for and best suited to short-lived (business) transactions; they handle long-duration design transactions poorly.

Section 3 — Storing Objects in Relational Databases

Q8: Why does storing objects in a relational database "add complexity," and how does the STUDENT/COURSES/DEGREE PROGRAM example demonstrate this?

A8: Because achieving persistence for OOP objects using an RDBMS as the storage engine requires mapping class instances to one or more rows distributed over one or more relations, and the developer must manually write conversion code between objects and rows (Object-Relational Mapping). In the example, a single conceptual STUDENT object (registering for courses in a degree program) ends up with its data spread across 3 separate tables, so reconstructing one Student object back into an application requires multiple JOINs and manual object-assembly code.

Section 4 — Introduction to OODBs

Q9: How does the typical ratio of "types" to "instances" in design/engineering data differ from that of relational data, and why does this matter for OODB origins?

A9: Design/engineering data (the origin domain of OODBs, e.g., CAD) typically has a large number of types and a small number of instances — many distinct part/component classes but relatively few actual design instances. This is the opposite of the relational world, which typically has few relations (types) but many tuples (instances). This mismatch is part of why the relational model (optimised for many rows of few table types) was a poor fit for engineering/design applications, motivating the development of OODBMSs.

Q10: What two things does an Object Data Management System (ODMS) need to specify for complex objects?

A10: An ODMS needs to specify: (1) the structure of complex objects, and (2) the operations that can be applied to these objects.

Section 5 & 6 — Terminology and OODB/OODBMS Relationship

Q11: Define "OO data model," "OO database," and "OODBMS," and explain how they relate to one another using the real-estate example.

A11:

  • OO data model: a (logical) data model that captures the semantics of objects (classes) supported in object-oriented programming.
  • OO database (OODB): a persistent, sharable collection of objects defined by an OO data model.
  • OODBMS: the manager (software) of an OODB.

They relate as follows: the OO data model defines the classes (e.g., PropertyForRent, Client, Branch) and their structure. The OODBMS (the software) uses that data model to manage the actual stored data. The OODB is the resulting persistent collection of object instances (e.g., actual PropertyForRent, PrivateOwner, Client, and Lease records) that the OODBMS manages.

Section 7 & 8 — Vendors and Development Strategies

Q12: Name one commercial and one open-source OODBMS, and identify which programming language each is most associated with (per the case studies).

A12: ObjectStore (commercial) is most associated with C++; ObjectDB (open source) is most associated with Java.

Q13: Compare Strategy 1 ("Extend an existing OOP language") and Strategy 2 ("Provide an extensible OODBMS library") for building an OODBMS.

A13: Strategy 1 modifies/extends the OOP language itself to add database capabilities (e.g., GemStone extending Smalltalk, C++, or Java) — this typically requires a special compiler/language variant. Strategy 2 makes no changes to the OOP language; instead it provides an "off-the-shelf" persistence library that developers use with a completely standard compiler and language (e.g., ObjectStore for C++, ObjectDB for Java). Strategy 2 is generally less invasive because developers keep working in their normal, unmodified language and tooling.

Section 9 — ObjectDB Case Study

Q14: What is an Object Identifier (OID) and why is it necessary in an OODB?

A14: An OID is a unique, system-generated identifier assigned to each independent object stored in the database. It is necessary because one of the core goals of an OODB is to maintain a direct correspondence between real-world and database objects, so that objects retain their integrity and identity and can be easily identified and operated upon — the OID provides that stable, unique identity, independent of the object's changing data values.

Q15: What annotation marks a POJO as a JPA entity class, and what does "POJO" stand for?

A15: The @Entity annotation marks a POJO as a JPA entity class. POJO stands for Plain Old Java Object — i.e., an ordinary Java class with no special base class or interface requirements, simply annotated to gain database persistence capability.

Q16 (Code Tracing): Given the Point class from Section 9.5, what would be printed by System.out.println(new Point(3, 4));?

A16: (3, 4) — because the constructor sets x = 3 and y = 4, and the overridden toString() method returns String.format("(%d, %d)", this.x, this.y), which formats those two field values inside parentheses separated by a comma and space.

Q17: Describe the two steps required to obtain an EntityManager instance in ObjectDB.

A17: Step 1: Obtain an instance of EntityManagerFactory representing the relevant database, via Persistence.createEntityManagerFactory("objectdb:$objectdb/db/points.odb");. Step 2: Use that factory instance to get an EntityManager instance, via EntityManager em = emf.createEntityManager();.

Q18: Why must operations like store, update, and delete in ObjectDB be performed within an active transaction, but not read (query) operations?

A18: Store, update, and delete operations modify database content, and transactions ensure such modifications are applied atomically and consistently — either the whole set of changes commits, or none of them do, preserving database integrity. Read/query operations do not modify data, so they do not require the same atomic-commit guarantee and can typically be executed directly against the EntityManager without wrapping them in a transaction.

Q19 (Code Tracing): Given the CRUD table in Section 9.10, what Java statement is used to persist a new Point object, and what statement is used to delete an existing entity p?

A19: To persist a new object: em.persist(p); (called between em.getTransaction().begin(); and em.getTransaction().commit();). To delete an existing entity: em.remove(p); (also wrapped in a begin/commit transaction block).

Section 10 — ObjectStore Case Study

Q20: Explain what it means that "ObjectStore stores C++ objects in the same format as they are used in memory," and why this reduces impedance mismatch.

A20: It means persistent ObjectStore objects on disk have the same internal layout/representation as the equivalent objects would have while sitting in a running C++ program's memory (heap). Because of this, the C++ programmer can access and update persistent objects using the exact same C++ syntax as ordinary heap-allocated objects (pointer dereferencing, member access, etc.) — there is no need to translate between a "database format" and an "in-memory format," which is precisely what reduces/eliminates the impedance mismatch problem described in Weakness 5.

Q21: What does it mean that "ObjectStore is distributed," and give the specific benefit stated in the slides?

A21: It means a client can connect to multiple osserver processes, each managing its own database(s), across a network. The specific stated benefit is that a client can access objects in different remote databases within the same (single) transaction — i.e., one atomic transaction can span multiple physically separate databases.

Section 11 — How OODBMSs Solve RDBMS Weaknesses

Q22: Explain, step by step, how OODBMSs eliminate the need for JOINs when representing real-world entities.

A22: OODBMSs use OOP constructs (classes, inheritance, composition) so that a real-world entity is stored as one coherent object, rather than fragmented across multiple normalized tables — this directly addresses Weakness 1. Relationships between objects are then represented using Object Identifiers (OIDs) as direct reference attributes (e.g., Branch stores a manager: OID6 attribute referencing the Manager object). Since there are no tables in the database at all, retrieving a related object is a matter of directly dereferencing its OID (a pointer lookup, e.g., via the Resident Object Table) rather than performing a relational JOIN — this is computationally far cheaper and conceptually matches how the real-world objects actually relate.

Q23: Distinguish between a Logical OID and a Physical OID.

A23: A Logical OID is independent of the object's physical location on disk (it is an abstract, stable identifier that survives object relocation). A Physical OID points directly to an actual location on disk (faster to dereference, but breaks if the object physically moves without updating all references).

Q24 (Worked Calculation/Tracing): Using the Resident Object Table (ROT) example in Section 11.4, if the application needs to find the street address of the branch that David Ford (Staff: OID4) works at, describe the sequence of OID lookups required (no joins allowed).

A24:

  1. Start at Staff: OID4 (David Ford) and read its branch attribute, which stores the reference OID1.
  2. Take OID1 and look it up in the Resident Object Table (ROT) to find its current memory address.
  3. Follow that memory address to load the Branch: OID1 object into memory (if not already resident).
  4. Read the street attribute of Branch: OID1, which is 163 Main St. This is achieved purely through direct OID/pointer dereferencing — no relational JOIN operation is performed at any step.

Q25: For a 1:1 relationship between two objects A and B in an OODB, how many reference attributes are added, and where?

A25: Two reference attributes are added — one to each object. Object A gets a reference attribute (an OID) pointing to Object B, and Object B gets a reference attribute (an OID) pointing back to Object A. (Worked example: Branch: OID1 stores manager: OID6, and Manager: OID6 stores branch: OID1.)

Q26: For a 1:* relationship (e.g., one Branch has many Properties for rent), what needs to be added on each side, and how does this differ from the 1:1 case?

A26: One object (PropertyForRent, the "many" side) gets a single reference attribute pointing to the "one" side (branch: OID1). The other object (Branch, the "one" side) gets an attribute containing a set of references to all the related "many"-side objects (property: {OID2, OID3, ...}). This differs from the 1:1 case in that only one side stores a set of references — in 1:1, both sides store a single, individual reference.

Q27: For a many-to-many (:) relationship (e.g., Client views many PropertyForRent, and a property is viewed by many clients), what needs to be added on each side?

A27: Both objects need an attribute containing a set of references to the other — each Client stores a set of references to the PropertyForRent objects it has viewed, and each PropertyForRent stores a set of references (viewers) to all the Client objects that have viewed it.

Q28: Referring to the Pilot class example, explain how OODBMSs solve Weakness 3 (Limited Operations).

A28: RDBMSs are restricted to a fixed set of relational-algebra operations (via SQL) and cannot have new operations defined by developers (aside from stored procedures). OODBMSs solve this because OOP methods can be defined directly on persistent classes — e.g., the Pilot class defines a custom method addPoints(int points) that mutates the object's state in a domain-specific way. Because this method is part of the class definition itself, every stored Pilot object automatically has this custom operation available, something impossible to express as a native, extensible operator in the relational model.

Q29: Compare the two approaches to storing and executing methods in an OODBMS, and list the four benefits attributed to the file-based approach.

A29: Approach 1 — Store methods in external files: the method code is compiled and linked into the application at compile/link time (static binding). Approach 2 — Store methods in the database: the method code is stored alongside the data and dynamically bound to the application at run-time. The four benefits attributed (to storing methods in shared external files/libraries) are: (1) eliminates redundant code, (2) simplifies modifications, (3) methods are more secure, (4) methods can be shared concurrently — with an additional note of improved integrity.

Section 12–17 — JPA / JPQL Querying

Q30: What does JPQL stand for, and what is the single main difference between SQL and JPQL?

A30: JPQL stands for Java Persistence Query Language. The main difference is that SQL works with relational database tables, records, and fields, whereas JPQL works with Java classes and objects.

Q31: Explain the difference between the Query and TypedQuery interfaces, with reference to the Country example.

A31: Query is the original, untyped interface (the only one available in JPA 1); results retrieved via Query must be manually cast to the expected type (e.g., (Country) q1.getSingleResult()). TypedQuery<T> was introduced in JPA 2 and extends Query; by supplying the target class (Country.class) when creating the query, results come back already typed as Country, giving compile-time type safety and removing the need for manual casts.

Q32: List, in order, the six possible clauses of a JPQL query.

A32: SELECT ... FROM ..., [WHERE ...], [GROUP BY ... [HAVING ...]], [ORDER BY ...] — plus the two data-modification forms: DELETE FROM ... [WHERE ...] and UPDATE ... SET ... [WHERE ...].

Q33: Complete the SQL-to-JPQL terminology mapping table: Table → ?, Row → ?, Column → ?, SELECT * → ?

A33: Table → Entity; Row → Object; Column → Attribute; SELECT * → SELECT e (where e is the entity alias).

Q34: Name the three types of JPA atomic query expressions, with an example of each.

A34:

  1. JPQL/Criteria Variables — e.g., a range variable such as c in FROM Country c.
  2. JPQL/Criteria Parameters — e.g., named parameters (:minGpa) or ordinal parameters (?1).
  3. JPQL/Criteria Literals — e.g., NULL, Boolean literals (TRUE/FALSE), numeric or string literals.

Q35: List the four categories of JPA operators in order of decreasing precedence, and give one example operator from each category.

A35:

  1. Navigation operator (highest precedence) — . (e.g., c.name).
  2. Arithmetic operators — *, /, +, -.
  3. Comparison operators (including collection operators) — e.g., =, <>, [NOT] BETWEEN, [NOT] IN, IS [NOT] EMPTY, [NOT] MEMBER [OF], [NOT] LIKE.
  4. Logical operators (lowest precedence) — AND, OR, NOT.

Q36 (Code Tracing): Given TypedQuery<Student> q = em.createQuery("SELECT s FROM Student s WHERE s.gpa >= :minGpa", Student.class); q.setParameter("minGpa", 3.0);, explain what type of atomic query expression :minGpa is, and what precedence-level operator is used to compare it against s.gpa.

A36: :minGpa is a named parameter (a type of atomic query expression). It is compared against s.gpa using the comparison operator >=, which sits at precedence level (3) — evaluated after the navigation operator (. used to resolve s.gpa, precedence level 1) but before any logical operators would be applied.
