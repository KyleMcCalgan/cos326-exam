2. Introduction — Databases as Data Sources for Web Applications

  • Databases function as data sources for Web applications.
  • HTML:
    • Used in static Web pages.
  • XML, JSON:
    • Self-describing documents.
    • Used in dynamic Web pages.
  • Chapter focus: the XML data model and languages.
  • Note: While XML remains foundational, JSON and YAML are now more common in RESTful APIs and microservices.

Example (added for clarity)

A static company "About Us" page is typically hand-written or template-generated HTML with fixed content. A dynamic e-commerce product page, by contrast, might be generated on-the-fly by a web server that fetches XML or JSON data (e.g., current price, stock level, reviews) from a database and injects it into an HTML template at request time — illustrating why XML/JSON (self-describing, structured data formats) are needed in addition to plain HTML for dynamic content.

3. Structured, Semi-Structured, and Unstructured Data

3.1 Structured Data

  • Has a well-defined, predictable schema.
  • Usually organised into tables, records, fields, etc.
  • Relational databases are a common example.

3.2 Semi-Structured Data

  • Not all data has identical structure.
  • Schema information mixed in with the data itself.
  • Self-describing.
  • Directed graph model (see Section 5).
  • Often stored in NoSQL databases (e.g., MongoDB, Neo4j, Couchbase).

3.3 Unstructured Data

  • Limited data type indication.
  • Example: Web pages in HTML.

Example (added for clarity)

A Staff relational table with fixed columns staffNo, fName, lName, salary is structured data — every row must conform to exactly that schema. A staff_list.xml file (explored throughout this module) where each <STAFF> element may or may not include every possible sub-element, and where the structure is described inline via tags, is semi-structured data. A raw scanned .txt transcript of a phone call, with no tags, fields, or type indicators at all, is unstructured data.

4. Semi-Structured Data in Detail

  • Definition: data that may be irregular or incomplete and have a structure that may change rapidly or unpredictably.
  • Examples: XML documents, JSON documents.
  • May have a structure, but that structure may change.
  • aka "schema-flexible" or "self-describing."
    • Structure may be embedded in the data itself.
    • A separate schema may be absent, optional, or defined using technologies such as DTD/XSD.
    • Structure can vary between documents.
  • Contrast with relational, object-oriented, object-relational DBMSs:
    • These require a pre-defined schema — the opposite philosophy to semi-structured data.

Worked Example — staff_list.xml (from the slides)

This is the actual sample XML file referenced throughout Lecture 10 (staff_list.xml, available on ClickUP), and it is used here to illustrate exactly what "self-describing, schema-flexible" data looks like in practice:

<?xml version="1.0" encoding="UTF-8"?>
<STAFFLIST>
    <STAFF branchNo="B002">
        <STAFFNO>SL20</STAFFNO>
        <NAME>
            <FNAME>Thando</FNAME>
            <LNAME>Mandela</LNAME>
        </NAME>
        <POSITION>Manager</POSITION>
        <DOB>1-Oct-98</DOB>
        <SALARY>30000</SALARY>
    </STAFF>
    <STAFF branchNo="B003">
        <STAFFNO>SL21</STAFFNO>
        <NAME>
            <FNAME>Marlize</FNAME>
            <LNAME>Kruger</LNAME>
        </NAME>
        <POSITION>Accountant</POSITION>
        <SALARY>12000</SALARY>
        <DOB>31-Nov-02</DOB>
        <SALARY>27000</SALARY>
    </STAFF>
    <STAFF branchNo="B003">
        <STAFFNO>SL22</STAFFNO>
        <NAME>
            <FNAME>Lerato</FNAME>
            <LNAME>Mpho</LNAME>
        </NAME>
        <POSITION>Administrator</POSITION>
        <SALARY>25000</SALARY>
        <DOB>12-Jan-01</DOB>
        <SALARY>30000</SALARY>
    </STAFF>
    <!-- Additional <STAFF branchNo="B004"> elements exist further in the file,
         e.g. staff with last names 'Bakwena' and 'Luke', and a staff member
         with first name 'James' — confirmed by the query results in Section 16 -->
</STAFFLIST>

Step-by-step reading of this example:

  1. The root element is <STAFFLIST>, which contains multiple <STAFF> child elements — one per staff member.
  2. Each <STAFF> element has an attribute, branchNo (e.g., "B002"), directly identifying which branch that staff member belongs to — attribute data attached directly to the element tag, not as a nested child.
  3. Notice the second <STAFF> element (SL21, Marlize Kruger) has <SALARY> appearing twice (12000 and, later, 27000) — this is a clear, concrete illustration of "semi-structured" behaviour: the structure is irregular, since not every <STAFF> element necessarily has exactly the same sequence or count of sub-elements, unlike a strict relational schema where every row of a Staff table would have exactly one salary column value.
  4. <NAME> is itself a complex, nested element, containing its own child elements <FNAME> and <LNAME> — demonstrating the hierarchical (tree) nature of XML data (fully explored in Section 10).
  5. Because the structure (tag names, nesting, attributes) is embedded directly in the document itself, a reader (human or program) can understand the data's meaning without consulting a separate, mandatory schema document — this is the essence of "self-describing" data.

5. The Directed Graph Model for Semi-Structured Data

  • Semi-structured data (including XML) can be represented conceptually as a directed graph.

Worked Example — Figure 13.1: Representing Semistructured Data as a Graph (from the slides)

                     Company projects
                    /                \
              Project              Project
               /                      \
              •  ─────────────────┐    •
   Name  Number  Location  Worker  Worker
    ↓      ↓        ↓         ↓        ↓
'Product X' 1   'Bellaire'    •        •
                          Ssn Last_name Hours    Ssn First_name Hours
                           ↓    ↓        ↓        ↓     ↓         ↓
                      '123456789' 'Smith' 32.5 '435435435' 'Joyce' 20.0

Step-by-step reading of this example:

  1. The root node represents "Company projects" — a graph node with no incoming edges.
  2. From the root, two labelled directed edges (both labelled Project) lead to two separate project nodes.
  3. The left project node has multiple outgoing edges labelled Name, Number, Location, Worker, Worker — leading to leaf values ('Product X', 1, 'Bellaire') and to two separate worker nodes (since a project can have multiple workers).
  4. Each worker node further branches into Ssn, Last_name/First_name, and Hours edges, leading to concrete leaf values (e.g., '123456789', 'Smith', 32.5).
  5. Why a graph, not a strict tree: unlike a rigid table schema, this structure can have varying numbers and types of child edges at each node (e.g., the right-hand Project node's sub-structure is left unspecified/collapsed in the figure, showing that different Project nodes need not have identical structure) — this directly embodies the "structure may be irregular/incomplete" definition of semi-structured data from Section 4.

6. XML (eXtensible Markup Language)

  • XML is a meta-language — a language for describing other languages.
  • It enables developers to create their own customized tags.
  • It provides functionality not available with HTML.
  • XML remains widely used in SOAP, configuration files, and document formats like Microsoft's DOCX and XLSX.
  • History:
    • 1998: XML 1.0 published by the World Wide Web Consortium (W3C).
    • XML (1.0) Fifth Edition – 2008 — a widely used standard.
  • Impact: XML has impacted many types of systems, e.g.:
    • Distributed systems.
    • Database management, etc.
  • XML is the de facto standard for data communication, replacing EDI (Electronic Data Interchange).

Example (added for clarity)

A modern .docx Word document is, internally, a ZIP archive full of XML files (this directly illustrates "XML remains widely used in ... document formats like Microsoft's DOCX and XLSX") — e.g., document.xml inside a .docx file uses custom XML tags (like <w:p> for a paragraph, <w:t> for text runs) defined by Microsoft's Office Open XML schema, demonstrating XML's role as a meta-language that lets an organisation define its own tag vocabulary for a specific purpose.

9. XML vs JSON

Feature XML JSON
Syntax Verbose, tag-based Lightweight, key-value pairs
Schema XSD, DTD JSON Schema
Typical use SOAP, enterprise/document exchange, configuration REST APIs, web/mobile applications, configuration

Example (added for clarity)

The same staff record could be represented in XML (verbose, tag-based, as seen in staff_list.xml in Section 4) or in JSON:

{
  "staffNo": "SL20",
  "name": { "fName": "Thando", "lName": "Mandela" },
  "position": "Manager",
  "salary": 30000
}

The JSON version is noticeably more compact (no closing tag repetition), which is part of why, per Section 2's note, JSON has become more common than XML for lightweight REST API payloads — even though XML remains dominant in enterprise/document contexts like SOAP and DOCX/XLSX.

10. XML Hierarchical (Tree) Data Model

  • Basic object: the XML document.
  • Element:
    • Can be Simple or Complex.
    • A Schema document defines element names.
  • Attribute — data attached directly to an element's tag (e.g., branchNo on <STAFF> in Section 4's example).
  • Document types (categorising how an XML document is primarily used):
    • Data-centric — XML acts like a digital transfer file. It is primarily built for machines to read and exchange information smoothly.
    • Document-centric — XML functions as a digital book or article. It is primarily designed to be read by humans.
    • Hybrid — combines features from both of the categories above. Used for storing records that require a mix of rigid data fields and long narrative descriptions.

Example (added for clarity)

staff_list.xml (Section 4) is a clear example of a data-centric document — it exists purely to represent structured staff records for machine processing (e.g., by BaseX queries), with no free-form prose. A user manual marked up in XML with <chapter>, <paragraph>, and <emphasis> tags would be document-centric — meant primarily for human reading, with the XML structure mainly supporting presentation/semantics of prose. A patient medical record combining rigid fields (<patientID>, <bloodType>) and a long free-text <doctorNotes> narrative would be a hybrid document.

11. XML Schema (XSD)

11.1 What is XML Schema?

  • The XML schema language is commonly known as XML Schema Definition (XSD).
  • It specifies document structure.
  • XSD allows for strong typing, constraints, and extensibility in XML documents.
  • It uses the same syntax rules as XML documents themselves (i.e., an XSD file is itself valid XML).
  • It defines: elements, attributes, keys, references, and identifiers.
  • (Example: Figure 13.5 in the recommended textbook.)

11.2 XML Namespaces

  • An XML namespace provides a unique namespace URI for XML names.
  • It prevents naming conflicts/collisions between different XML vocabularies.
  • Used through namespace prefixes, such as xs: for annotations, documentation, and the schema language used.
  • Note: Modern DBMSs like BaseX, PostgreSQL, and Oracle support XML storage and querying via XPath/XQuery.

11.3 Elements and Types (in XSD)

  • Root element.
  • First-level elements.
  • Specifying element type and min and max occurrences.

11.4 Coding Example 1 — A Complete XSD Schema (from the slides)

<?xml version = "1.0" encoding = "UTF-8"?>
<xs:schema xmlns:xs = "http://www.w3.org/2001/XMLSchema">
   <xs:element name = "contact">
      <xs:complexType>
         <xs:sequence>
            <xs:element name = "name" type = "xs:string" />
            <xs:element name = "company" type = "xs:string" />
            <xs:element name = "phone" type = "xs:int" />
         </xs:sequence>
      </xs:complexType>
   </xs:element>
</xs:schema>

Step-by-step walkthrough:

  1. <?xml version="1.0" encoding="UTF-8"?> — the standard XML declaration, since an XSD file is itself an XML document.
  2. <xs:schema xmlns:xs="http://www.w3.org/2001/XMLSchema"> — declares the root <xs:schema> element and binds the namespace prefix xs: to the official W3C XML Schema namespace URI — this is a direct, concrete illustration of the "XML namespace" concept from Section 11.2: every xs:-prefixed tag in this document unambiguously refers to the W3C schema vocabulary, preventing collisions with any other vocabulary that might also define an element called, e.g., element.
  3. <xs:element name="contact"> — declares that valid documents using this schema must have (or may have) an element named contact.
  4. <xs:complexType><xs:sequence>...</xs:sequence></xs:complexType> — specifies that contact is a complex type (see Section 12.2), whose children must appear in the given sequence.
  5. <xs:element name="name" type="xs:string" />, company (xs:string), phone (xs:int) — declare the three required child elements of contact, each with a simple type (xs:string or xs:int).

  6. A valid contact XML document conforming to this schema would look like:

    xml <contact> <name>Thabo Mokoena</name> <company>Acme Corp</company> <phone>27125551234</phone></contact>

11.5 Coding Example 2 (added for step-by-step clarity) — An XSD Schema for staff_list.xml

Applying the same schema-writing pattern to the staff_list.xml example from Section 4:

<?xml version = "1.0" encoding = "UTF-8"?>
<xs:schema xmlns:xs = "http://www.w3.org/2001/XMLSchema">
   <xs:element name = "STAFFLIST">
      <xs:complexType>
         <xs:sequence>
            <xs:element name = "STAFF" maxOccurs = "unbounded">
               <xs:complexType>
                  <xs:sequence>
                     <xs:element name = "STAFFNO"  type = "xs:string" />
                     <xs:element name = "NAME">
                        <xs:complexType>
                           <xs:sequence>
                              <xs:element name = "FNAME" type = "xs:string" />
                              <xs:element name = "LNAME" type = "xs:string" />
                           </xs:sequence>
                        </xs:complexType>
                     </xs:element>
                     <xs:element name = "POSITION" type = "xs:string" />
                     <xs:element name = "SALARY"   type = "xs:decimal" />
                     <xs:element name = "DOB"      type = "xs:string" />
                  </xs:sequence>
                  <xs:attribute name = "branchNo" type = "xs:string" />
               </xs:complexType>
            </xs:element>
         </xs:sequence>
      </xs:complexType>
   </xs:element>
</xs:schema>

Step-by-step walkthrough:

  1. The root element STAFFLIST is declared as a complex type containing a sequence of STAFF elements.
  2. maxOccurs="unbounded" on STAFF specifies that there can be any number of STAFF elements (min/max occurrence specification, per Section 11.3) — matching the real file, which has multiple <STAFF> children.
  3. Each STAFF element is itself a nested complex type, containing its own sequence: STAFFNO, a nested NAME complex type (with FNAME/LNAME), POSITION, SALARY, DOB.
  4. <xs:attribute name="branchNo" type="xs:string" /> declares the branchNo XML attribute (not a child element) on STAFF, matching the real file's <STAFF branchNo="B002"> syntax.
  5. This demonstrates how deeply nested complex types (Section 12.2) can mirror an arbitrarily deep XML tree structure, directly matching the hierarchical model from Section 10.

11.6 Keys and Complex Elements

  • Keys — constraints that correspond to relational database concepts:
    • Primary key.
    • Foreign key.
  • Complex elements — declared using xsd:complexType.
  • Composite (compound) attributes — attributes made up of multiple sub-parts.
  • XSD allows for strong typing, constraints, and extensibility in XML documents (repeated emphasis from the slides).

Example (added for clarity)

XSD's key/keyref mechanism lets a schema enforce that every branchNo attribute value used inside a <STAFF> element must correspond to an actual branchNo declared elsewhere in a <BRANCH> element — directly mirroring a relational foreign key constraint, but expressed in XML Schema terms (<xs:key> and <xs:keyref> elements, referencing XPath selectors).

12. XML Schema Definition Types

  • XML schema elements can be defined in the following ways:
    1. Simple Types.
    2. Complex Types.
    3. Global Types.

12.1 Simple Type

  • A simple type element is used only in the context of the text (i.e., it holds only a plain text/scalar value, no child elements or attributes).
  • Some predefined simple types: xs:integer, xs:boolean, xs:string, xs:date.

Coding Example 1 — A Simple Type Element (from the slides)

<xs:element name = "phone_number" type = "xs:int" />
  • This declares an element named phone_number whose content must be a valid xs:int — nothing more (no children, no attributes).

Coding Example 2 (added for step-by-step clarity) — Additional Simple Type Elements

<xs:element name = "isManager"  type = "xs:boolean" />
<xs:element name = "dateOfBirth" type = "xs:date" />
<xs:element name = "staffName"   type = "xs:string" />

Step-by-step walkthrough:

  1. isManager is restricted to xs:boolean — only true/false (or 1/0) values are valid content.
  2. dateOfBirth is restricted to xs:date — content must be a validly formatted date (e.g., YYYY-MM-DD), directly enforcing type-correctness that raw untyped XML text could not guarantee on its own.
  3. staffName uses xs:string, the most general simple type, for free-form text content.

12.2 Complex Type

  • A complex type is a container for other element definitions.
  • This allows you to specify which child elements an element can contain, and to provide some structure within your XML documents.

Coding Example 1 — A Complex Type Element (from the slides)

<!-- Only <Address> can use this structure -->
<xs:element name = "Address">
   <xs:complexType>
      <xs:sequence>
         <xs:element name = "name" type = "xs:string" />
         <xs:element name = "company" type = "xs:string" />
         <xs:element name = "phone" type = "xs:int" />
      </xs:sequence>
   </xs:complexType>
</xs:element>
  • Note the slide's comment: "Only <Address> can use this structure" — i.e., this complex type is declared anonymously, locally inside the Address element definition, so it cannot be reused by any other element (this limitation motivates Global Types, Section 12.3).

Coding Example 2 (added for step-by-step clarity) — A Complex Type for STAFF (Attributes + Children)

<xs:element name = "STAFF">
   <xs:complexType>
      <xs:sequence>
         <xs:element name = "STAFFNO" type = "xs:string" />
         <xs:element name = "POSITION" type = "xs:string" />
      </xs:sequence>
      <xs:attribute name = "branchNo" type = "xs:string" />
   </xs:complexType>
</xs:element>

Step-by-step walkthrough:

  1. Like the Address example, STAFF is declared with an anonymous, local <xs:complexType>, meaning this exact structure cannot be reused for another element elsewhere in the schema without repeating the definition.
  2. The <xs:sequence> specifies the ordered child elements STAFFNO and POSITION.
  3. The <xs:attribute name="branchNo" .../> demonstrates that a complex type can define both nested child elements AND attributes simultaneously — reflecting the real staff_list.xml structure exactly (<STAFF branchNo="...">).

12.3 Global Type

  • A global type allows you to define a single type in your document, which can be used by all other references.
  • It is designed to avoid repeating structure definitions across different elements.
  • How: define it immediately under <xs:schema>, and give it a name attribute so it can be referenced by name elsewhere.

Coding Example 1 — A Reusable AddressType Global Type (from the slides)

<!-- Defined globally once -->
<xs:complexType name="AddressType">
    <xs:sequence>
        <xs:element name="city" type="xs:string" />
    </xs:sequence>
</xs:complexType>

<!-- Reused by multiple elements -->
<xs:element name="BillingAddress" type="AddressType" />
<xs:element name="ShippingAddress" type="AddressType" />

Step-by-step walkthrough:

  1. <xs:complexType name="AddressType"> — because this complex type is declared directly under <xs:schema> (globally) and given a name, it becomes a reusable, named type, unlike the anonymous, local complex types from Section 12.2.
  2. <xs:element name="BillingAddress" type="AddressType" /> and <xs:element name="ShippingAddress" type="AddressType" /> — both elements reference the same AddressType by name, rather than each needing to redeclare the full <xs:sequence> structure independently.
  3. Benefit: if the address structure ever needs to change (e.g., adding a postcode field), it only needs to be edited once, in the single global AddressType definition, and both BillingAddress and ShippingAddress automatically inherit the change.

Coding Example 2 (added for step-by-step clarity) — A Reusable NameType for staff_list.xml-style Data

<xs:complexType name="NameType">
    <xs:sequence>
        <xs:element name="FNAME" type="xs:string" />
        <xs:element name="LNAME" type="xs:string" />
    </xs:sequence>
</xs:complexType>

<xs:element name="StaffName"  type="NameType" />
<xs:element name="ClientName" type="NameType" />

Step-by-step walkthrough:

  1. NameType is declared once, globally, capturing the FNAME/LNAME structure seen inside <NAME> in staff_list.xml.
  2. Both StaffName and ClientName elements reuse NameType by reference — avoiding having to redefine the FNAME/LNAME sequence twice, exactly as the AddressType example does for BillingAddress/ShippingAddress.

12.4 Complex Type vs. Global Type — Comparison

Dimension Complex Type Global Type
Primary Purpose Defines structure and content (e.g., nesting child elements like name, company, phone). Defines reusability and scope across the entire XML schema.
Reusability Limited to one element when written anonymously/locally inside an <xs:element>. Reusable anywhere in the document by referencing its name.
Role in Schema Determines whether an element contains nested sub-elements, attributes, or simple text. Acts as a shared blueprint or template for multiple distinct elements.

13. Storing and Extracting XML Documents from Databases

There are several general approaches:

  1. Use a file system or DBMS to store documents as text.
  2. Use a DBMS to store document contents as data elements.
  3. Design a specialized system to store XML data (e.g., a native XML database — see Section 19, BaseX).
  4. Create or publish custom XML documents from pre-existing relational databases.

This approach is explored further in section 13.6 of the recommended textbook.

Example (added for clarity)

Approach 1 ("store documents as text") is what a simple file server does when it saves staff_list.xml as a flat file on disk with no XML-aware indexing. Approach 3 ("specialized system") is exactly what BaseX provides (Section 19) — a database engine purpose-built to store, index, and query XML natively (rather than treating it as an opaque blob of text), enabling efficient XPath/XQuery queries like those explored in Section 16.

14. XML Languages Overview — XPath and XQuery

  • Query language standards, managed by W3C:
    • XPath — computes specific locations or values within an ordered tree representation of a single document. It functions similarly to local file paths, but targeting XML or JSON nodes.
    • XQuery — designed to query and transform collections of structured and unstructured data, primarily in the form of XML.
  • Specifying XPath expressions in XML:
    • Returns a sequence of items satisfying certain pattern(s):
      • Values, elements, or attributes.
    • Qualifier conditions.
    • Separators:
      • Single slash / or double slash //.

Example (added for clarity)

Just as a Windows/Unix file path like C:\Users\Thabo\Documents\report.docx (or /home/thabo/report.docx) navigates a directory tree to locate one specific file, an XPath expression like //STAFFLIST/STAFF[1]/STAFFNO navigates an XML element tree to locate one specific node — this is precisely the "functions similarly to local file paths" comparison made in the slides.

15. XML Path Language (XPath)

  • XPath is a declarative query language.
  • It works by specifying a directory-like path, possibly with conditions placed in the path.
  • It retrieves collections of elements.
  • It treats the XML document as a logical tree of nodes.

15.1 XPath Query Components

Query component Description
context node starting point
location path path from one point in document to another, composed of steps
step consists of basis and predicates
basis axis and node test
axis direction, e.g., grandparent, parent, child, etc.
node test identifies node type, e.g., element name or function text()
predicate in square brackets after the basis

15.2 Worked Example — Anatomy of an XPath Query (from the slides)

Query: "Details of 1st staff member?"

child::STAFF[1]     or     /child::STAFF[position()=1]

Breaking down the components (as annotated on the slide):

   basis
┌─────────┐
child::STAFF [1]
 └──┬──┘ └─┬──┘ └┬┘
  axis  node test  predicate
  • child — the axis (direction: "child" of the context node).
  • STAFF — the node test (identifies the node type/name: element named STAFF).
  • child::STAFF together — the basis (axis + node test).
  • [1] (or, equivalently, [position()=1]) — the predicate, in square brackets after the basis, filtering to just the first matching node.

15.3 XPath Location Path Reference Table (from the slides)

Location path Selects…
. …context node
.. …parent of context node
/ …root node, or separator between steps in path
// …descendants of current node
/child::STAFF or /STAFF …STAFF elements that are children of the root
child::STAFF or STAFF …STAFF element children of context node
attribute::branchNo or @branchNo …branchNo attribute of context node
attribute::* or @* …all attributes of context node
child::STAFF[3] …third STAFF element that is a child of the context node
/child::STAFF[@branchNo="B005"] …STAFF elements that have attribute branchNo with value B005
/child::STAFF[@branchNo="B005"][position()=1] …first STAFF elements that have attribute branchNo with value B005

Coding Example 1 — Combining a Predicate with an Attribute Filter (from the table above)

/child::STAFF[@branchNo="B005"][position()=1]

Step-by-step walkthrough:

  1. /child::STAFF — starts from the root and selects all STAFF elements that are direct children of the root (basis: axis child, node test STAFF).
  2. [@branchNo="B005"] — the first predicate, filtering down to only those STAFF elements whose branchNo attribute equals "B005".
  3. [position()=1] — a second, chained predicate, further filtering to just the first element remaining after the first filter was applied.
  4. Result: the very first STAFF element (in document order) belonging to branch B005.

Coding Example 2 (added for step-by-step clarity) — Selecting All Attributes of a Node

//STAFFLIST/STAFF[1]/attribute::*

Step-by-step walkthrough:

  1. //STAFFLIST/STAFF[1] — navigates to the first STAFF element under STAFFLIST (using the double-slash // to search for STAFFLIST as a descendant from anywhere, then a single / to its first STAFF child).
  2. attribute::* (equivalently @*) — selects all attributes of that context node.
  3. Result (applied to the staff_list.xml example from Section 4): this would return the branchNo="B002" attribute of the first <STAFF> element.

These worked examples use the tree structure of staff_list.xml (Section 4), and are visualised as trees in the original slides. The tree layout is reproduced below in outline form.

16.2 Query 1 — Details of All Staff

Question: "Details of all staff?"

//STAFFLIST/child::STAFF     or     //STAFFLIST/STAFF

Step-by-step walkthrough:

  1. //STAFFLIST finds the STAFFLIST element (searching descendants from the document, here effectively the root).
  2. /child::STAFF (or the shorthand /STAFF) selects all STAFF elements that are direct children of STAFFLIST — since there is no [n] predicate, all matching STAFF nodes are returned, not just one.
  3. Result: every <STAFF>...</STAFF> element (and its full sub-tree) in the document.

16.3 Query 2 — Details of the First Staff Member

Question: "Details of 1st staff?"

//STAFFLIST/child::STAFF[1]   or   //STAFFLIST/STAFF[1]   or   //STAFFLIST/child::STAFF[position()=1]

Step-by-step walkthrough:

  1. Same navigation as Query 1, down to STAFF children of STAFFLIST.
  2. The predicate [1] (equivalently [position()=1]) restricts the result to only the first STAFF element encountered, in document order.
  3. Result: the entire sub-tree of the first <STAFF> element only (e.g., the SL20/Thando Mandela record from Section 4's sample file).

16.4 Query 3 — Staff Number of the First Staff Member

Question: "Staff number of 1st staff?"

//STAFFLIST/STAFF[1]/STAFFNO

Step-by-step walkthrough:

  1. //STAFFLIST/STAFF[1] — as in Query 2, selects the first STAFF element only.
  2. /STAFFNO — an additional step, navigating one level deeper to that STAFF element's STAFFNO child.
  3. Result: just the <STAFFNO> element (and its text content) of the first staff member.

16.5 Query 4 — Name of the First Staff Member

Question: "Name of 1st staff?"

//STAFFLIST/STAFF[1]/NAME

Step-by-step walkthrough:

  1. Identical pattern to Query 3, but navigating to the NAME child instead of STAFFNO.
  2. Result: the entire <NAME> sub-tree of the first staff member — i.e., both <FNAME> and <LNAME> together (since NAME is a complex/nested element, not a simple leaf value).
  3. Contrast: if only the first name was wanted, an additional step would be needed: //STAFFLIST/STAFF[1]/NAME/FNAME.

17. XML Query Languages and XQuery

  • XML Query languages (historical context): XML-QL, UnQL, XQL, XQuery, …
  • XQuery was developed by the W3C XML Query Working Group, with contributions from:
    • The database community.
    • The document community.
    • The programming language community.
  • Note: SQL alone is not designed specifically for hierarchical XML data; XQuery provides XML-oriented querying capabilities.

Example (added for clarity)

This "SQL alone is not designed for hierarchical XML data" note directly connects back to the ORDBMS lectures: while PostgreSQL supports storing XML/JSON data (recall JSONB from the ORDBMS notes), plain SQL's SELECT/WHERE/JOIN syntax is fundamentally built around flat relational tables — it has no native concept of "navigate down three levels of nesting, then across to a sibling," which is exactly the kind of hierarchical navigation XPath/XQuery are purpose-built for.

17.1 XQuery Characteristics

  • XQuery is a functional language:
    • Meaning: a query is represented as an expression.
    • Nested expressions are possible.
  • XQuery uses:
    • Path expressions (use the syntax of XPath).
    • FLWOR expressions (see Section 18).
  • The queries:
    • Operate on single documents.
    • Operate also on fixed collections of documents.
    • Select sub-trees of documents.

18. XQuery FLWOR Expressions

  • FLWOR stands for the five clauses of the expression:
FOR    <variable bindings to individual nodes (elements)>
LET    <variable bindings to collections of nodes (elements)>
WHERE  <qualifier conditions>
ORDER BY <ordering specifications>
RETURN <query result specification>
  • Variables are preceded with $.
  • FOR — assigns a variable to a range (binds a variable to individual nodes, one at a time).
  • WHERE — specifies additional conditions.
  • ORDER BY — specifies the order of result elements.
  • RETURN — specifies the elements for retrieval.
  • (LET, per the syntax box, binds a variable to a collection of nodes, rather than iterating one at a time like FOR.)

Coding Example 1 (added for step-by-step clarity) — A FLWOR Query Over staff_list.xml

FOR $s IN //STAFFLIST/STAFF
WHERE $s/SALARY > 20000
ORDER BY $s/SALARY DESCENDING
RETURN $s/NAME/FNAME

Step-by-step walkthrough:

  1. FOR $s IN //STAFFLIST/STAFF — binds the variable $s to each STAFF element in the document, one at a time (an XPath path expression, per Section 17.1, is used to specify the range).
  2. WHERE $s/SALARY > 20000 — filters, keeping only iterations where the current staff member's SALARY exceeds 20000.
  3. ORDER BY $s/SALARY DESCENDING — sorts the surviving results by salary, highest first.
  4. RETURN $s/NAME/FNAME — for each remaining, sorted $s, returns just that staff member's first name.
  5. Applied to the sample data from Section 4 (Thando: 30000; Marlize: 27000 [second <SALARY>]; Lerato: 30000): all three would pass the WHERE filter (>20000), and would be returned in descending salary order.

Coding Example 2 (added for step-by-step clarity) — A FLWOR Query Using LET

FOR $s IN //STAFFLIST/STAFF
LET $fullname := concat($s/NAME/FNAME, " ", $s/NAME/LNAME)
WHERE $s/@branchNo = "B003"
RETURN $fullname

Step-by-step walkthrough:

  1. FOR $s IN //STAFFLIST/STAFF — as before, iterates over each STAFF element.
  2. LET $fullname := concat(...) — demonstrates the LET clause: it binds a computed value (here, the concatenation of first and last name) to a new variable $fullname, for reuse later in the query.
  3. WHERE $s/@branchNo = "B003" — filters to only staff belonging to branch B003 (using @branchNo to access the attribute, per the XPath attribute syntax from Section 15.3).
  4. RETURN $fullname — returns the pre-computed full name for each matching staff member.
  5. Applied to the sample data: this would match Marlize Kruger (SL21, B003) and Lerato Mpho (SL22, B003), returning "Marlize Kruger" and "Lerato Mpho".

19. Introduction to BaseX

  • BaseX is an open source, robust, high-performance XML database engine.
  • It was created by Christian Grün in 2005 at the University of Konstanz in Germany.
  • It is specialised in storing, querying, and visualizing large XML documents and collections.
  • It serves as an excellent framework for building complex data-intensive web applications.
  • It comes with interactive user interfaces (desktop, web-based), giving great insight into semi-structured data.
  • It supports both the XPath and XQuery languages.

Example (added for clarity)

BaseX is a concrete, practical instance of the "specialized system to store XML data" approach mentioned in Section 13 — rather than treating staff_list.xml as a flat text file, BaseX imports it into an internally indexed database structure, allowing fast, repeated XPath/XQuery lookups (like all the examples in Section 20) without needing to re-parse the entire XML file from scratch on every query.

Section 3 & 4 — Structured, Semi-Structured, Unstructured Data

Q3: Classify each of the following as structured, semi-structured, or unstructured data, with a justification: (a) a Branch relational table, (b) staff_list.xml, (c) a plain-text customer complaint email body.

A3: (a) Structured — a Branch relational table has a well-defined, predictable schema, with every row conforming to the same fixed set of columns. (b) Semi-structured — staff_list.xml is self-describing (structure embedded in the tags themselves), but its structure is irregular (e.g., the observed duplicate <SALARY> element in one STAFF record) and does not require a separate mandatory schema. (c) Unstructured — a plain-text email body has limited/no data type indication and no embedded tags describing its internal structure, similar to the slides' HTML web page example.

Q4: Name two NoSQL databases mentioned as commonly storing semi-structured data.

A4: Any two of: MongoDB, Neo4j, Couchbase.

Section 5 — Directed Graph Model

Q5: Referring to Figure 13.1 (Section 5), why is a directed graph, rather than a strict relational table, an appropriate way to model "Company projects" data with workers?

A5: Because each Project node can have a varying number of Worker sub-nodes (and, implicitly, Worker records could have varying attributes), and the overall structure is not required to be perfectly uniform across all Project nodes — this variability and irregularity is exactly what a rigid relational table (with a single fixed schema for every row) cannot naturally express, but a directed graph, where each node can have its own distinct set of outgoing edges, can.

Section 6 — Introduction to XML

Q6: In what year was XML 1.0 published by the W3C, and what does XML replace as "the de facto standard for data communication"?

A6: XML 1.0 was published by the W3C in 1998. XML is described as replacing EDI (Electronic Data Interchange) as the de facto standard for data communication.

Section 9 — XML vs JSON

Q7: According to the comparison table, what schema technologies are associated with XML, and which with JSON? What is a typical use case for each format?

A7: XML's schema technologies are XSD and DTD; JSON's schema technology is JSON Schema. A typical XML use case is SOAP, enterprise/document exchange, or configuration; a typical JSON use case is REST APIs, web/mobile applications, or configuration.

Section 10 — Hierarchical Data Model

Q8: Distinguish between a "data-centric," "document-centric," and "hybrid" XML document, giving an example of each.

A8: A data-centric document (e.g., staff_list.xml) is built primarily for machines to read and exchange structured information. A document-centric document (e.g., an XML-marked-up user manual) is built primarily for humans to read, more like a digital book or article. A hybrid document (e.g., a patient medical record with both rigid fields and long free-text notes) combines both characteristics.

Section 11 & 12 — XML Schema

Q9 (Code Tracing): Given the XSD snippet <xs:element name="phone_number" type="xs:int" />, would the XML fragment <phone_number>012-555</phone_number> be considered valid against this schema? Why or why not?

A9: No — 012-555 is not a valid xs:int value (it contains a hyphen and would likely also be treated as having a leading-zero/format issue), so an XML document containing this fragment would fail validation against a schema requiring phone_number to be of type xs:int. It would need to be reformatted purely as digits, e.g., 012555, to validate as an integer (though even then, care is needed since a leading zero may cause other type/format issues depending on the validator).

Q10: What is the key limitation of an anonymous, locally-declared complex type (Section 12.2), and how does a Global Type (Section 12.3) solve it?

A10: An anonymous, locally-declared complex type (declared directly inside a specific <xs:element>) is limited to that one element only — it cannot be reused elsewhere in the schema without being fully rewritten. A Global Type solves this by being declared once, directly under <xs:schema>, with a name, so that any number of different elements can reference it by name (e.g., both BillingAddress and ShippingAddress referencing the same AddressType), avoiding repeated/duplicated structure definitions.

Q11: Complete this comparison: Complex Type's primary purpose is to define __, while Global Type's primary purpose is to define ____.

A11: Complex Type's primary purpose is to define structure and content (e.g., which nested child elements, attributes, or simple text an element contains). Global Type's primary purpose is to define reusability and scope across the entire XML schema (acting as a shared blueprint/template for multiple distinct elements).

Section 13 — Storing XML in Databases

Q12: List the four general approaches given for storing and extracting XML documents from databases.

A12:

  1. Use a file system or DBMS to store documents as text.
  2. Use a DBMS to store document contents as data elements.
  3. Design a specialized system to store XML data.
  4. Create or publish custom XML documents from pre-existing relational databases.

Section 14 & 15 — XPath

Q13: Explain the difference between XPath and XQuery, in one sentence each, per the slides' definitions.

A13: XPath computes specific locations or values within an ordered tree representation of a single document, functioning similarly to a file path but targeting XML/JSON nodes. XQuery is designed to query and transform collections of structured and unstructured data, primarily in the form of XML (and can itself make use of XPath path expressions internally).

Q14 (Code Tracing): Break down the XPath expression child::STAFF[1] into its basis, axis, node test, and predicate components.

A14: Axis: child (direction — children of the context node). Node test: STAFF (identifies the element name to match). Basis: child::STAFF (axis + node test combined). Predicate: [1] (in square brackets after the basis, filtering to the first matching node).

Q15 (Code Tracing): Using the location path reference table (Section 15.3), what does /child::STAFF[@branchNo="B005"] select?

A15: It selects STAFF elements (that are children of the root) that have an attribute branchNo with the value "B005".

Section 16 — XPath Worked Examples

Q16 (Code Tracing): Write the XPath expression to select the last name (LNAME) of the first staff member in staff_list.xml, building on the pattern shown in the lecture examples.

A16: //STAFFLIST/STAFF[1]/NAME/LNAME — navigating to the first STAFF element, then into its NAME child, then to LNAME.

Q17: What is the effect of omitting a [1] (or any positional) predicate from a query such as //STAFFLIST/STAFF/NAME/FNAME, compared to including one?

A17: Omitting the positional predicate means the query matches all STAFF elements (and thus returns the FNAME of every staff member), rather than restricting the result to just a single specific staff member's record — this is exactly the distinction between the "details of all staff" query (Section 16.2) and the "details of 1st staff" query (Section 16.3).

Section 17 & 18 — XQuery and FLWOR

Q18: List the five clauses of a FLWOR expression, and state which one is used to assign a variable to a range of individual nodes.

A18: The five clauses are FOR, LET, WHERE, ORDER BY, RETURN. FOR is used to assign a variable to a range (binding it to individual nodes/elements one at a time).

Q19 (Code Tracing): In the FLWOR query FOR $s IN //STAFFLIST/STAFF WHERE $s/SALARY > 20000 ORDER BY $s/SALARY DESCENDING RETURN $s/NAME/FNAME (Section 18), explain the purpose of each clause used.

A19: FOR $s IN //STAFFLIST/STAFF iterates the variable $s over every STAFF element (using an XPath path expression to define the range). WHERE $s/SALARY > 20000 filters to keep only staff earning more than 20000. ORDER BY $s/SALARY DESCENDING sorts the remaining results by salary, highest first. RETURN $s/NAME/FNAME specifies that only each qualifying staff member's first name should be returned in the final result.

Section 20 — Practical BaseX Queries

Q22 (Code Tracing): Given the query //STAFFLIST/STAFF[@branchNo="B004"]/NAME/LNAME/text() returning the result "2 Results, 13 b: Bakwena, Luke," explain step by step what each part of the query is doing.

A22:

  1. //STAFFLIST/STAFF[@branchNo="B004"] — finds all STAFF elements (anywhere the STAFFLIST descendant path leads) whose branchNo attribute equals "B004" — there is no positional predicate, so potentially multiple matches are kept (here, two).
  2. /NAME/LNAME — for each matching STAFF, steps down into its NAME child element, then further into that NAME's LNAME child.
  3. /text() — extracts just the plain text content of each LNAME element (rather than the surrounding XML tags).
  4. Result: the two last names of the staff members at branch B004 — Bakwena and Luke.

Q23: Why does the query //STAFFLIST/STAFF/NAME/FNAME/text() return 4 results, while a query like //STAFFLIST/STAFF[1]/NAME/FNAME/text() would return only 1 result?

A23: The first query has no [n] predicate after STAFF, so it matches every STAFF element in the document (four, based on the BaseX screenshot results: Thando, Marlize, Lerato, James), returning one FNAME text value per match. The second query includes the [1] predicate, restricting the match to only the first STAFF element, so only a single FNAME value would be returned.
