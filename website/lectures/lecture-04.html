2. XQuery — FLWOR Expressions

2.1 Construction of a FLWOR Expression (from the slides)

  • FLWOR ("flower") expression construction:
    1. Starts with one or more FOR or LET clauses (any order).
    2. Followed by an optional WHERE clause.
    3. Optional ORDER BY clause.
    4. Required RETURN clause.

General form (syntax box from the slides):

FOR       forVar    IN    inExpression
LET       letVar    :=    letExpression
[WHERE    filterExpression ]
[ORDER BY orderSpec ]
RETURN    expression

Clause-by-clause definition of the syntax box:

Part Meaning
forVar A variable (starts with $) bound to each item in turn.
inExpression The expression (usually an XPath) that supplies the items to loop over.
letVar := letExpression A variable bound once to the whole value of an expression.
[WHERE filterExpression] Optional condition that restricts the tuples.
[ORDER BY orderSpec] Optional ordering of the tuples.
RETURN expression Required — builds what goes into the result.

The square brackets in the syntax box mean "optional"; they are not typed in a real query.

2.2 Figure — Flow of a FLWOR Expression (from the slides)

┌──────────────────────┐
│    FOR/LET clauses   │
└──────────┬───────────┘
           ▼        list of tuples of bound variables
┌──────────────────────┐
│ WHERE clause         │
│ (optional)           │
└──────────┬───────────┘
           ▼        restricted list of tuples of bound variables
┌──────────────────────┐
│ ORDER BY clause      │
│ (optional)           │
└──────────┬───────────┘
           ▼        sort the tuples in the tuple stream
┌──────────────────────┐
│ RETURN clause        │
└──────────┬───────────┘
           ▼        instance of XML query data model

(In the slide image the last label is partly clipped; it reads "instance of XML query data model".)

Step-by-step reading of this figure:

  1. FOR/LET clauses produce a list of tuples of bound variables — each tuple is one combination of values for the variables (for example, one $S per STAFF).
  2. The WHERE clause (optional) discards the tuples that fail the condition, leaving a restricted list of tuples.
  3. The ORDER BY clause (optional) sorts the tuples in the tuple stream.
  4. The RETURN clause is evaluated for each remaining tuple, in that order. Its output is an instance of the XML query data model (a sequence of nodes and/or values).
  5. Because WHERE and ORDER BY are optional, the shortest legal FLWOR is for … return … or let … return … (see Section 4.3).

Example (added for clarity) — the pipeline as a conveyor belt

Think of a factory line at a bakery. FOR puts every loaf on the belt, WHERE removes the burnt ones, ORDER BY arranges the rest by size, and RETURN wraps each remaining loaf in a box. The "tuple stream" is the belt.

2.3 Comparison — FLWOR vs SQL (added for clarity)

FLWOR clause Closest SQL idea Difference
for $S in //STAFF FROM Staff S for iterates over nodes of a tree, not rows of a table.
let $sal := 30000 a constant / subquery value / WITH alias let binds the whole value once (no iteration).
where $S/SALARY > 10000 WHERE salary > 10000 The condition navigates with XPath.
order by $S/STAFFNO ORDER BY staffNo Same idea.
return $S/NAME SELECT name return can construct new XML elements, not just pick columns.

3. FLWOR Clauses in Detail

3.1 The FOR Clause (from the slides)

  • Example: for $S in //STAFF
  • Iteration: associates variable $S with each expression value.
  • The result is a tuple stream.

Example (added for clarity)

for $S in //STAFF binds $S to the first <STAFF> node, then to the second, and so on. With the four staff of Lecture 11 the tuple stream has 4 tuples: $S = SL20, $S = SL21, $S = SL22, $S = SL23. Everything after for (where, order by, return) is applied once per tuple.

3.2 The LET Clause (from the slides)

  • Example: let $sal := 30000
  • Binds one or more variables to one or more expressions.
  • Without iteration (single binding for each variable).

Example (added for clarity)

let $S := //STAFF binds $S to the entire sequence of four STAFF nodes in a single tuple. Then count($S) returns 4, whereas for $S in //STAFF return count($S) returns 1 1 1 1 (one count per staff, each of a single node).

3.3 FOR vs LET — Comparison (added for clarity)

Dimension for let
Operator in :=
Iteration Yes — one tuple per item No — one binding
Variable holds A single item at a time The whole sequence
Typical use Loop over elements (//STAFF) Name a constant, or a group/aggregate (avg(...))
Effect on tuple count Multiplies the tuples Leaves the tuples unchanged

3.4 The WHERE Clause (from the slides)

  • Example: where $S/SALARY > 10000
  • One or more conditions to restrict tuples generated by FOR and LET (optional).

Example (added for clarity)

where $S/SALARY > 10000 and $S/@branchNo = "B002" keeps only the tuples where both conditions hold. Conditions are combined with and / or, exactly as in SQL.

3.5 The ORDER BY Clause (from the slides)

  • Example: order by $S/STAFFNO descending
  • Order of the tuple stream.
  • Determines the order in which the RETURN clause is evaluated.

Example (added for clarity)

order by $S/STAFFNO descending makes the tuple for SL23 first and SL20 last. Because return is evaluated in that order, the result also appears in that order. ascending is the default direction.

3.6 The RETURN Clause (from the slides)

  • Example: return $S
  • Evaluated once for each tuple in the tuple stream.
  • Results concatenated to form the final result.

Example (added for clarity)

If four tuples survive and return $S/STAFFNO is used, return runs four times, producing four <STAFFNO> elements that are concatenated into one result sequence of four items. (In BaseX this appears as "4 Results".)

3.7 Summary of Clause Rules

  1. A FLWOR expression must begin with for or let (one or more, in any order).
  2. where and order by are optional.
  3. return is required and is always last.
  4. Variable names start with $ and are case-sensitive (see Section 4.3).
  5. Keywords are written in lowercase in BaseX 12.4 (see Section 4.1).

4. Examples 1–5 — FLWOR in BaseX 12.4

4.1 Example 1 — List the Names of All Staff (from the slides)

for  $N  in  //STAFF/NAME  return $N

Note (from the slide): XQuery keywords are case-sensitive. Use the standard lowercase forms: for, let, where, order by, return.

Result (from the slide's BaseX screenshot):

4 Results, 346 b
<NAME>
        <FNAME>Thando</FNAME>
        <LNAME>Mandela</LNAME>
</NAME>
<NAME>
        <FNAME>Marlize</FNAME>
        <LNAME>Kruger</LNAME>
</NAME>
<NAME>
        <FNAME>Lerato</FNAME>
        <LNAME>Bakwena</LNAME>
</NAME>
<NAME>
        <FNAME>James</FNAME>
        <LNAME>Luke</LNAME>
</NAME>

Step-by-step walkthrough:

  1. for $N in //STAFF/NAME — the path //STAFF/NAME selects the NAME child of every STAFF element. for binds $N to each NAME node in turn (4 iterations).
  2. There is no where and no order by, so no tuple is removed and the order stays document order.
  3. return $N — returns the whole NAME element, including both FNAME and LNAME children, once per iteration.
  4. Result: 4 Results, 346 b — Thando Mandela, Marlize Kruger, Lerato Bakwena, James Luke.
  5. Equivalence: this FLWOR returns exactly what the XPath //STAFF/NAME returns. FLWOR is not needed here, but the form is the starting point for the later examples.

Note for students: in the Lecture 9–10 notes the example FLWOR keywords were written in capitals (FOR, WHERE, …) following the textbook. In BaseX 12.4 use the lowercase forms stated on this slide.

4.3 Example 3 — List Staff with Salary = R30,000 (from the slides)

let $SAL := 30000
return //STAFF[SALARY = $SAL]

Note (from the slide, marked **Note): - Variable names are case sensitive. - A FLWOR expression does not have to contain every clause. for or let must initiate the expression, and return is required. - Other operators: eq, ne, lt, le, gt, ge — value comparison operators.

Result (from the slide's BaseX screenshot):

2 Results, 511 b
<STAFF branchNo="B002">
      <STAFFNO>SL20</STAFFNO>
      <NAME>
         <FNAME>Thando</FNAME>
         <LNAME>Mandela</LNAME>
      </NAME>
      <POSITION>Manager</POSITION>
      <DOB>1-Oct-98</DOB>
      <SALARY>30000</SALARY>
   </STAFF>
<STAFF branchNo="B004">
      <STAFFNO>SL22</STAFFNO>
      <NAME>
         <FNAME>Lerato</FNAME>
         <LNAME>Mpho</LNAME>
      </NAME>
      <POSITION>Administrator</POSITION>
      <DOB>12-Jan-01</DOB>
      <SALARY>30000</SALARY>
   </STAFF>

Step-by-step walkthrough:

  1. let $SAL := 30000 — binds $SAL once to the number 30000. There is no iteration, so there is exactly one tuple.
  2. return //STAFF[SALARY = $SAL] — //STAFF selects all staff; the predicate [SALARY = $SAL] keeps only STAFF elements whose SALARY child equals 30000.
  3. This FLWOR has only let + return — it demonstrates the note that not every clause is required.
  4. Result: 2 Results, 511 b — SL20 (Thando Mandela, B002) and SL22 (Lerato, B004).
  5. Variable case-sensitivity: $SAL and $sal are different variables; writing $sal in the predicate would raise an error because it was never bound.
  6. Value comparison operators: eq, ne, lt, le, gt, ge mean equal, not equal, less than, less than or equal, greater than, greater than or equal. They are the value-comparison versions of =, !=, <, <=, >, >= (the latter are general comparisons).

Note for students: this screenshot shows the surname Mpho for SL22, while the other Lecture 11 screenshots show Bakwena for the third staff member (see Section 1.3). Reproduced exactly as shown.

Comparison — General vs Value Comparison Operators (added for clarity)

Dimension General: = != < <= > >= Value: eq ne lt le gt ge
Operands Sequences of any length Single items (an error if a sequence has more than one item)
Meaning True if some pair of items satisfies it (existential) The two single values satisfy it
Typical use in the slides $S/SALARY > 15000, [SALARY = $SAL] $S/SALARY eq 30000

Coding Example 2 (added for step-by-step clarity) — let with a constant

let $C := 16
return //MODULE[CREDITS = $C]/NAME/text()

Step-by-step walkthrough:

  1. let $C := 16 binds the constant once.
  2. //MODULE[CREDITS = $C] keeps the modules whose CREDITS equals 16.
  3. /NAME/text() extracts the names. Result (verified): Database Systems, Computer Organisation.

Coding Example 3 (added for step-by-step clarity) — What goes wrong with eq on untyped data

for $M in //MODULE
where $M/CREDITS eq 16
return string($M/@code)

Step-by-step walkthrough:

  1. CREDITS holds untyped text (there is no schema attached), and eq is a value comparison. Under the XQuery rules the untyped value is treated as a string, which cannot be compared with the integer 16.
  2. The query therefore fails with a type error (verified with Saxon: XPTY0004 — Values are not comparable).
  3. Fix 1: use the general comparison $M/CREDITS = 16, which converts the untyped value for you.
  4. Fix 2: cast explicitly: where xs:integer($M/CREDITS) eq 16. Result (verified): COS326, COS284.

5. Example 6 — Aggregates and Constructed XML

5.1 Example 6 — List Each Branch Office and the Average Salary at the Branch (from the slides)

for $B in  distinct-values(//@branchNo)
let $avgSalary :=
               avg(//STAFF[@branchNo = $B]/SALARY)
return
    <BRANCH>
        <BRANCHNO>{$B }</BRANCHNO>
        <AVGSALARY>{ $avgSalary }</AVGSALARY>
    </BRANCH>

Note (from the slide): Functions for aggregates are: avg, etc. Homework (flagged on this slide — see Section 9.1).

Result (from the slide's BaseX screenshot):

3 Results, 227 b
<BRANCH><BRANCHNO>B002</BRANCHNO><AVGSALARY>30000</AVGSALARY></BRANCH>
<BRANCH><BRANCHNO>B003</BRANCHNO><AVGSALARY>27000</AVGSALARY></BRANCH>
<BRANCH><BRANCHNO>B004</BRANCHNO><AVGSALARY>29333.333333333332</AVGSALARY></BRANCH>

(The slide screenshot is partly overlapped by the text box; the first result row, for B002, and the "3 Results, 227 b" header are visible, and the B003 and B004 rows are read from the lower part of the screenshot.)

Step-by-step walkthrough:

  1. distinct-values(//@branchNo) — //@branchNo returns every branchNo attribute in the document; distinct-values removes duplicates, leaving B002, B003, B004. This is the XQuery way of doing "group by branch".
  2. for $B in … — one tuple per distinct branch (3 tuples). $B holds one branch number at a time.
  3. let $avgSalary := avg(//STAFF[@branchNo = $B]/SALARY) — for the current $B, the path selects the SALARY of every staff at that branch, and avg computes their average. let is used because avg(...) needs the whole group at once, not one value at a time.
  4. return <BRANCH>…</BRANCH> — return constructs a new XML element BRANCH for each tuple, with child elements BRANCHNO and AVGSALARY.
  5. { $B } and { $avgSalary } — curly braces mean "evaluate this expression and insert the value here". Without braces the text $B would be copied literally.
  6. Result: 3 Results, 227 b. B002 averages 30000, B003 averages 27000, B004 averages 29333.333333333332.
  7. Why B004 is not a round number: 29333.333333333332 is 88000 ÷ 3. This means the average at B004 was taken over three SALARY values, even though only two staff (Lerato and James) are visible at B004 in the Lecture 11 results. That is consistent with some STAFF elements holding more than one SALARY element, the irregular (semi-structured) structure seen in the Lecture 9–10 sample file. The individual salaries are not visible on the slide, so this is an inference.
  8. Why the output has no line breaks between the child elements: BRANCH is constructed by the query, so BaseX prints it as written.

Coding Example 2 (added for step-by-step clarity) — Total and average credits per department

for $D in distinct-values(//@dept)
let $total := sum(//MODULE[@dept = $D]/CREDITS)
return
    <DEPT>
        <NAME>{ $D }</NAME>
        <TOTAL>{ $total }</TOTAL>

Step-by-step walkthrough:

  1. distinct-values(//@dept) yields CS and STA (2 tuples).
  2. For CS: //MODULE[@dept = "CS"]/CREDITS is 16, 32, 16, so sum = 64. For STA: only 12, so sum = 12.
  3. return builds one DEPT element per department.
  4. Result (verified): <DEPT><NAME>CS</NAME><TOTAL>64</TOTAL></DEPT> and <DEPT><NAME>STA</NAME><TOTAL>12</TOTAL></DEPT>.
  5. Replacing sum by avg gives 21.333333333333332 for CS (64 ÷ 3) and 12 for STA (verified), another example of a non-round average like the slide's B004.

Coding Example 3 (added for step-by-step clarity) — Several aggregates in one query

for $D in distinct-values(//@dept)
return
    <DEPT>
        <NAME>{ $D }</NAME>
        <COUNT>{ count(//MODULE[@dept = $D]) }</COUNT>
        <MAX>{ max(//MODULE[@dept = $D]/CREDITS) }</MAX>
    </DEPT>

Step-by-step walkthrough:

  1. The aggregate calls count and max can be written directly inside the braces, so a let is optional.
  2. Result (verified): CS → COUNT 3, MAX 32; STA → COUNT 1, MAX 12.

Key takeaway: for over distinct-values(...) + an aggregate function over the matching nodes is the XQuery pattern for SQL's GROUP BY.

6. Example 7 — Quantifiers (some / every)

6.1 Example 7 — List Branches with at Least One Member of Staff with Salary > R15,000 (from the slides)

for $B in distinct-values(//@branchNo)
let $S := //STAFF[@branchNo = $B]
   where some $sal in $S/SALARY
             satisfies ($sal > 15000)
   return <BRANCHNO>{ $B}</BRANCHNO>

Annotations on the slide:

  • some: existential qualifier.
  • every: universal qualifier.
  • The let … where … part is labelled "sub-query."

Result (from the slide's BaseX screenshot):

3 Results, 79 b
<BRANCHNO>B002</BRANCHNO>
<BRANCHNO>B003</BRANCHNO>
<BRANCHNO>B004</BRANCHNO>

Step-by-step walkthrough:

  1. for $B in distinct-values(//@branchNo) — one tuple per branch (B002, B003, B004).
  2. let $S := //STAFF[@branchNo = $B] — binds $S to all staff at that branch (a sequence, because let does not iterate).
  3. where some $sal in $S/SALARY satisfies ($sal > 15000) — the existential qualifier: the condition is true if at least one SALARY value of the group is greater than 15000. Inside the quantifier, $sal ranges over each salary.
  4. return <BRANCHNO>{ $B}</BRANCHNO> — for each branch that passes, construct a BRANCHNO element holding the branch number.
  5. Result: 3 Results, 79 b — all three branches qualify.
  6. some vs every: every $sal in $S/SALARY satisfies ($sal > 15000) is the universal qualifier — it would be true only if all salaries at the branch exceeded 15000.
  7. Link to Example 4: the general comparison $S/SALARY > 15000 is also existential, so where $S/SALARY > 15000 has the same effect as the explicit some … satisfies …. The explicit form makes the quantifier visible and is the only way to write every.

Comparison — some vs every (added for clarity)

Dimension some … satisfies … every … satisfies …
Name Existential qualifier Universal qualifier
True when At least one item meets the test All items meet the test
Empty sequence false true
Logic analogue ∃ (there exists) ∀ (for all)

Coding Example 2 (added for step-by-step clarity) — Departments where every module has at least 16 credits

for $D in distinct-values(//@dept)
let $M := //MODULE[@dept = $D]
where every $C in $M/CREDITS satisfies ($C >= 16)
return <DEPT>{ $D }</DEPT>

Step-by-step walkthrough:

  1. CS group credits: 16, 32, 16 → all are ≥ 16 → every is true → CS is returned.
  2. STA group credits: 12 → 12 < 16 → every is false → STA is rejected.
  3. Result (verified): <DEPT>CS</DEPT>.
  4. With some $C in $M/CREDITS satisfies ($C < 16) instead, only STA is returned (verified): there exists a module below 16 credits in STA, but none in CS.

7. Joining Two Documents

Both examples join staff_list.xml to nok.xml (next of kin) on the staff number, as in a relational join of Staff and NextOfKin on staffNo. The next-of-kin NAME is a simple text value (for example Xolani Mandela), while the staff NAME has FNAME/LNAME children. The internal structure of nok.xml is not shown on the slides; the queries show that each NOK element has a STAFFNO and a NAME.

7.1 Example 1 — Joining Two Documents with Two for Variables (from the slides)

Task: List names of staff and names of their next of kin.

for $S in //STAFF,
    $NOK in //NOK
where $S/STAFFNO = $NOK/STAFFNO
return
    <STAFFNOK>
     { $S/NAME, $NOK/NAME }
    </STAFFNOK>

Result (from the slide's BaseX screenshot):

4 Results, 533 b
<STAFFNOK><NAME>
        <FNAME>Thando</FNAME>
        <LNAME>Mandela</LNAME>
    </NAME><NAME>Xolani Mandela</NAME></STAFFNOK>
<STAFFNOK><NAME>
        <FNAME>Marlize</FNAME>
        <LNAME>Kruger</LNAME>
    </NAME><NAME>Johan Kruger</NAME></STAFFNOK>
<STAFFNOK><NAME>
        <FNAME>Lerato</FNAME>
        <LNAME>Bakwena</LNAME>
    </NAME><NAME>Tumelo Bakwena</NAME></STAFFNOK>
<STAFFNOK><NAME>
        <FNAME>James</FNAME>
        <LNAME>Luke</LNAME>
    </NAME><NAME>Martha Luke</NAME></STAFFNOK>

Step-by-step walkthrough:

  1. for $S in //STAFF, $NOK in //NOK — two variables in one for clause (separated by a comma). The tuple stream contains every pair ($S, $NOK): a Cartesian product (every staff paired with every next-of-kin record).
  2. where $S/STAFFNO = $NOK/STAFFNO — the join condition. Only pairs whose staff numbers match survive, so each staff member is paired with his or her own next of kin.
  3. return <STAFFNOK> { $S/NAME, $NOK/NAME } </STAFFNOK> — constructs a wrapper element STAFFNOK and, inside the braces, places the staff NAME followed by the next-of-kin NAME (a comma-separated sequence).
  4. Result: 4 Results, 533 b: Thando Mandela / Xolani Mandela, Marlize Kruger / Johan Kruger, Lerato Bakwena / Tumelo Bakwena, James Luke / Martha Luke.
  5. Why this is a join: the two documents have no declared relationship. The only link is the shared STAFFNO value, exactly like a foreign key in SQL.

7.2 Example 2 — Joining Two Documents with a Correlated Sub-query (from the slides)

Task: List names of staff and names of their next of kin.

for $S in //STAFF
return <STAFFNOK>
{ $S/NAME }
    { for $NOK in //NOK
    where $S/STAFFNO    =$NOK/STAFFNO
return $NOK/NAME }
</STAFFNOK>

The slide labels the inner for … where … return as a correlated sub-query.

Result (from the slide's BaseX screenshot): identical to Example 1 — 4 Results, 533 b, with the same four STAFFNOK elements.

Step-by-step walkthrough:

  1. for $S in //STAFF — the outer loop has one tuple per staff.
  2. return <STAFFNOK> … — for each staff, a STAFFNOK element is built.
  3. { $S/NAME } — the staff name is inserted first.
  4. { for $NOK in //NOK where $S/STAFFNO = $NOK/STAFFNO return $NOK/NAME } — an inner FLWOR nested in the braces. It is correlated because its where clause refers to $S, the variable of the outer query, so it is re-evaluated for each outer tuple.
  5. Result: the same output as Example 1.

Note for students: Examples 1 and 2 give the same result on this data but are not equivalent in general. If a staff member has no next of kin, Example 1 drops that staff member, whereas Example 2 still returns a STAFFNOK containing the staff NAME only (like a relational outer join). This is verified below on modules.xml.

Comparison — Example 1 vs Example 2 (added for clarity)

Dimension Example 1 (two for variables) Example 2 (correlated sub-query)
Structure One flat FLWOR Outer FLWOR with an inner FLWOR inside return
Join condition in Outer where Inner where
Unmatched staff Omitted Kept (with no next-of-kin name)
SQL analogue INNER JOIN LEFT OUTER JOIN / correlated subquery

9.2 Summary & Takeaways (from Lecture 11)

The Lecture 11 slides do not contain a separate summary slide. The following is a consolidation of the lecture content (added for clarity):

  1. A FLWOR expression is for/let → where → order by → return; only return and at least one of for/let are compulsory.
  2. for iterates (tuple stream); let binds once (no iteration).
  3. where filters tuples; order by fixes the order in which return runs; return runs once per tuple and the results are concatenated.
  4. BaseX 12.4: keywords and variable names are case-sensitive and keywords are lowercase.
  5. text() extracts values; { } inserts expressions into constructed XML; distinct-values + aggregate functions (avg, count, max, sum) give grouping.
  6. some = existential, every = universal.
  7. Joins are done by two for variables with a where condition, or by a correlated sub-query.
  8. Functions can be inline (function($x,$y){…}) or built-in references (math:pow#2).

9.3 Outstanding Discussion Question (added for clarity)

The slides pose no discussion question. A useful one: In Example 7, the query where $S/SALARY > 15000 returns the same branches as where some $sal in $S/SALARY satisfies ($sal > 15000). Why, and when would you have to use some/every explicitly? (Answer: general comparison is already existential; every has no general-comparison equivalent.)

Section 2 — FLWOR Construction

Q3: What does FLWOR stand for, and which clauses are compulsory?

A3: FLWOR is pronounced "flower" and stands for for, let, where, order by, return. The expression must start with one or more for or let clauses (any order) and must end with the return clause. where and order by are optional.

Q4: Describe the stages of the FLWOR flow figure, naming what each stage hands to the next.

A4: (1) for/let clauses produce a list of tuples of bound variables. (2) The optional where clause produces a restricted list of tuples. (3) The optional order by clause sorts the tuples in the tuple stream. (4) The return clause is evaluated for each tuple and produces an instance of the XML query data model.

Q5: Map each FLWOR clause to its nearest SQL counterpart and state one thing FLWOR can do that SQL's SELECT cannot.

A5: for ≈ FROM, let ≈ a named value/subquery, where ≈ WHERE, order by ≈ ORDER BY, return ≈ SELECT. Unlike SELECT, return can construct new XML elements (for example <BRANCH>…</BRANCH>) and navigate trees with XPath.

Section 3 — FLWOR Clauses

Q6: Distinguish between for and let.

A6: for $S in //STAFF iterates: $S takes one item at a time, producing one tuple per item (a tuple stream). let $sal := 30000 binds the variable once to the whole expression value, without iteration, so the number of tuples is unchanged. for uses in, let uses :=.

Q7 (Code Tracing): Using the four staff of Lecture 11, give the result of (a) for $S in //STAFF return count($S) and (b) let $S := //STAFF return count($S).

A7:

  1. (a) for creates 4 tuples; in each, $S is a single STAFF, so count($S) is 1 each time.
  2. return is evaluated four times and the results are concatenated: 1 1 1 1.
  3. (b) let binds $S once to the sequence of all four STAFF nodes, so there is one tuple and count($S) is evaluated once.
  4. Result: 4.

Q8 (Code Tracing): Trace the query for $x in (1,2,3) let $y := $x * 2 where $y > 2 order by $y descending return $y.

A8:

  1. Tuple 1: $x = 1, $y = 2 → where 2 > 2 is false → removed.
  2. Tuple 2: $x = 2, $y = 4 → 4 > 2 is true → kept.
  3. Tuple 3: $x = 3, $y = 6 → 6 > 2 is true → kept.
  4. order by $y descending sorts the kept tuples: $y = 6, then $y = 4.
  5. return $y runs in that order. The final result is 6 4 (verified).

Q9: What does order by determine about the return clause, and what is the default sort direction?

A9: order by sets the order of the tuple stream, which determines the order in which the return clause is evaluated, so it controls the order of the result. The default direction is ascending.

Section 4 — Examples 1–5 in BaseX

Q10: In BaseX 12.4 the query FOR $n IN //STAFF RETURN $n/STAFFNO fails. Why, and how is it fixed?

A10: XQuery keywords are case-sensitive and the standard forms are lowercase (for, let, where, order by, return). The query must be written for $n in //STAFF return $n/STAFFNO. (Variable names are also case-sensitive: $n and $N are different variables.)

Q11: What is the difference between the results of Example 1 (for $N in //STAFF/NAME return $N) and Example 2 (for $N in //STAFF/NAME/LNAME/text() return $N)?

A11: Example 1 returns the whole NAME elements, including FNAME and LNAME and their tags (4 Results, 346 b). Example 2 uses text() to extract only the surname values — Mandela, Kruger, Bakwena, Luke (4 Results, 30 b).

Q12: Explain why Example 3 (let $SAL := 30000 return //STAFF[SALARY = $SAL]) is a valid FLWOR expression although it has no for, where or order by.

A12: A FLWOR expression does not have to contain every clause: it must be initiated by for or let and must have return. Here let binds $SAL once and return selects the STAFF elements with SALARY = 30000. The result is 2 Results, 511 b (staff SL20 and SL22).

Q13: List the value comparison operators mentioned on the Example 3 slide and state what each means. Why might $M/CREDITS eq 16 raise an error on untyped XML data?

A13: eq (equal), ne (not equal), lt (less than), le (less than or equal), gt (greater than), ge (greater than or equal). On untyped XML the CREDITS text is treated as a string by a value comparison and cannot be compared with the integer 16, so a type error is raised (verified: XPTY0004). Use the general comparison = or cast: xs:integer($M/CREDITS) eq 16.

Q14 (Code Tracing): Example 4 is for $S in //STAFF where $S/SALARY > 15000 and $S/@branchNo = "B004" return $S/NAME. Explain what each clause does and give the result shown in the lecture.

A14:

  1. for $S in //STAFF — four tuples, one per staff.
  2. where $S/SALARY > 15000 — keeps staff earning more than 15000.
  3. and $S/@branchNo = "B004" — also requires the branchNo attribute (@) to equal "B004".
  4. return $S/NAME — returns each surviving staff member's NAME element.
  5. Result: 2 Results, 170 b — Lerato Bakwena and James Luke.

Q15 (Code Tracing): Using the four staff of Lecture 11, what does Example 5 return, and what changes if ascending is replaced by descending?

A15: Example 5 (for $S in //STAFF order by $S/STAFFNO ascending return $S/STAFFNO) returns 4 Results, 98 b: SL20, SL21, SL22, SL23. With descending the same four elements are returned in the order SL23, SL22, SL21, SL20.

Q16 (Write the Code): Write a FLWOR query that lists the first names of staff at branch B003, ordered by last name.

A16:

for $S in //STAFF
where $S/@branchNo = "B003"
order by $S/NAME/LNAME
return $S/NAME/FNAME/text()

for iterates over staff, where keeps those with attribute branchNo = "B003", order by sorts on the LNAME child, and return extracts the first-name text.

Section 6 — Quantifiers

Q22: Distinguish the existential and the universal qualifier, and state which keyword Example 7 uses.
