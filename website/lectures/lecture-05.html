1. Lecture Overview and Where This Fits

  • Lectures 9–10 introduced XML itself: the data model, XSD, XPath, XQuery/FLWOR and a native XML database (BaseX).
  • Lecture 12 asks a different question: what if our data lives in a relational (RDB) or object-relational (ORDB) database such as PostgreSQL, and we need to store, produce and query XML there?
  • Topics covered:
    • XML databases and SQL.
    • Storing XML data in an RDB or ORDB (four approaches).
    • XML and SQL standards.
    • Creating a DB table using the XML data type.
    • SQL/XML functions, operators and mapping functions.
    • PostgreSQL and XML data (including xpath() and unnest).
    • Importing XML data into a PostgreSQL DB.

Example (added for clarity)

Contrast the two worlds. In BaseX (Lectures 9–10) the whole database is XML and you query it with //STAFFLIST/STAFF[1]/STAFFNO. In PostgreSQL (this lecture) the database is relational, XML is just one column type among others, and you must combine SQL with XPath: SELECT xpath('/STAFF/STAFFNO', staffData) FROM XMLStaff;.

2. Storing XML Data in an RDB or ORDB — Four General Approaches

  1. Store the XML document as the value of a column in one row or several rows.
  2. Store the XML document in a shredded form across a number of columns and tables.
  3. Store the XML document in a schema-independent form.
  4. Store the XML document in a parsed (internal) form.

The slides give detail for approaches 1–3. Approach 4 is only listed (the DBMS keeps its own internal parsed representation).

2.1 Approach 1 — Storing XML in a Table Column

Conceptual Example (from the slides)

docNo docDate XMLdoc (whole doc or fragment)
D001 2020-05-20 <STAFFLIST><STAFF branchNo="B002"> ... </STAFF></STAFFLIST>
  • The XML is stored raw in a column; the other columns (docNo, docDate) are ordinary relational attributes.
  • Data types used for XML data:
    • CLOB (character large object) — used in the past.
    • Native XML data type: xml (PostgreSQL) or XMLType (Oracle).
Advantages Disadvantages
Efficient to insert documents into the database General query performance is poor — the XML must be parsed on the fly every time it is queried
Efficient to retrieve documents (whole) Updates: the entire XML document is replaced (more recently, an XML document can be updated using SQL)
Easy to apply full-text indexing to documents

Example (added for clarity)

An archive of invoices received as XML (never edited, always fetched whole by invoice number) suits Approach 1 perfectly — fast to insert, fast to retrieve. If staff later asked "total salary across all documents", every document would have to be parsed again to dig the <SALARY> values out, which is exactly the poor-query-performance weakness.

2.2 Approach 2 — Storing XML in Shredded Form

  • The XML is decomposed ("shredded") into its constituent elements.
  • The data is distributed over a number of attributes (columns) in one or more relations.
  • Pros / cons:
    • Easier to index the values of individual elements.
    • Need additional data capturing the hierarchical nature of the XML so the original document can be recomposed.
    • XML updates are more involved.
    • You have to create an appropriate database structure from the schema (relational or object-relational).
  • (Reading for the student: Chapter 13.6.)

Example (from the slides) — staff_list.xml shredded into a table

BRANCHNO STAFFNO NAME FNAME LNAME
B002 SL20 Thando Mandela
B003 SL21 Marlize Kruger

Reading the example:

  1. Each <STAFF> element becomes one row.
  2. The branchNo attribute, <STAFFNO>, and the leaf elements <FNAME>/<LNAME> each become a column.
  3. The NAME column is empty — <NAME> is a complex element with no text of its own; it only groups FNAME and LNAME. This is the loss of hierarchy that the "additional data" bullet warns about: the tree structure (NAME contains FNAME and LNAME) is no longer stored explicitly.
  4. Because the values now sit in normal columns, a query like WHERE LNAME = 'Mandela' can use an ordinary index — impossible if the XML were one opaque blob.

2.3 Approach 3 — Schema-Independent Representation

  • Idea: create a relation (table) from the Document Object Model (DOM) of the XML document, so the table stores the tree itself (nodes and their relationships) rather than the specific element names as columns.
  • It works for any XML document without needing to know its schema in advance.
  • Slide illustration: the DOM tree of the first staff record:
<STAFFLIST>
  <STAFF branchNo="B002">
    <STAFFNO>SL20</STAFFNO>
    <NAME>
      <FNAME>Thando</FNAME>
      <LNAME>Mandela</LNAME>
    </NAME>
    <POSITION>Manager</POSITION>
    <DOB>1-Oct-98</DOB>
    <SALARY>30000</SALARY>
  </STAFF>

Example (added for clarity)

A generic node table could look like this (node, parent, type, name, value) for the record above:

nodeID parentID nodeType name value
1 NULL element STAFFLIST
2 1 element STAFF
3 2 attribute branchNo B002
4 2 element STAFFNO SL20
5 2 element NAME
6 5 element FNAME Thando
7 5 element LNAME Mandela

Any XML document fits this one table (flexible), but reconstructing or querying it needs many self-joins on parentID. (Table is an illustration of the idea, not from the slides.)

2.4 Comparison of the Approaches

Dimension Approach 1: Column Approach 2: Shredded Approach 3: Schema-independent
Storage Whole document in one column Elements spread over columns/tables Generic table built from the DOM
Insert / retrieve whole doc Very efficient Must decompose / recompose Must decompose / recompose
Query & index individual elements Poor (parse on the fly) Good Possible but join-heavy
Needs a schema up front? No Yes No
Typical fit Documents handled as a unit Data-centric XML, frequently queried Many different/unknown XML structures

3. XML and SQL Standards

  • Introduced in SQL:2003, and carried through SQL:2008 and SQL:2011 (SQL/XML):
    • A native XML data type: XML.
    • A set of XML/SQL operators for the type.
    • A set of XML/SQL functions.
    • A set of mappings from relational data to XML.

Example (added for clarity)

Because SQL/XML is part of the SQL standard, a function such as XMLELEMENT is available (with small dialect differences) in PostgreSQL, Oracle and SQL Server-style systems — the same idea of "build XML from table rows" carries across vendors.

4. Creating a Table Using the XML Data Type

4.1 Coding Example 1 — XMLStaff (from the slides)

CREATE TABLE XMLStaff (
    docNo     CHAR(4) PRIMARY KEY,
    docDate   DATE,
    staffData XML );

INSERT INTO XMLStaff VALUES ('D001',
    DATE '2023-08-31',
    XML ('<STAFF branchNo  =    "B002">
            <STAFFNO>   SL20        </STAFFNO>
            <POSITION>  Manager   </POSITION>
            <DOB>       1998-10-01   </DOB>
            <SALARY>    30000        </SALARY>  </STAFF>') );

SELECT * FROM XMLStaff;

Result (pgAdmin, partially displayed):

docno [PK] character docdate date staffdata xml
D001 2023-08-31 <STAFF branchNo = "B002"> …

Step-by-step walkthrough:

  1. staffData XML — the third column is declared with the native XML data type, so the DBMS stores an XML value (and checks it is well-formed), rather than plain text.
  2. docNo CHAR(4) PRIMARY KEY and docDate DATE — ordinary relational columns sitting next to the XML column: this is Approach 1 (Section 2.1) in action.
  3. INSERT ... XML('<STAFF ...>...</STAFF>') — the XML fragment is passed in as a string and converted to the XML type. A single <STAFF> element (not a whole <STAFFLIST>) is stored.
  4. Note the stray whitespace inside the tags (<STAFFNO> SL20 </STAFFNO>): the XML type preserves it. This matters later — when we query this row with xpath() the value comes back with those extra spaces (Section 8.3).
  5. SELECT * — pgAdmin only shows the start of the XML value; double-click the cell to see all of it.

4.2 Coding Example 2 — A Second Row (from the slides)

INSERT INTO XMLStaff VALUES ('D002', DATE '2023-08-31',
    XML('<STAFF branchNo = "B003">
            <STAFFNO>SL21</STAFFNO>
            <POSITION>Accountant</POSITION>
            <DOB>2002-11-02</DOB>
            <SALARY>27000</SALARY> </STAFF>') );

SELECT * FROM XMLStaff;
  • Adds D002: Marlize's record (SL21, branch B003, Accountant, salary 27000). The table now holds two documents (D001 and D002) — used by all the xpath() examples in Section 8.
  • Note the second document has clean values (no extra spaces) while the first does not.
  • Also note the date format is ISO (2002-11-02), unlike the 31-Nov-02 style in staff_list.xml from Lectures 9–10 (which is not even a real date).

5. SQL/XML Functions (Reading for the Student)

Function What it does
XMLFOREST Generates a sequence (forest) of XML elements from the supplied values.
XMLCONCAT Concatenates a list of XML values.
XMLPARSE Performs a non-validating parse of a character string to produce an XML value.
XMLROOT Creates an XML value by modifying the properties of the root item of another XML value.
XMLCOMMENT Generates an XML comment.
XMLPI Generates an XML processing instruction.
XMLSERIALIZE Generates a character or binary string from an XML value (the opposite of XMLPARSE).
XMLAGG Aggregates XML values across rows into a single XML value.

Examples (added for clarity — not on the slides)

-- XMLFOREST: one element per supplied value, element name = alias
SELECT XMLFOREST(staffNo AS id, lName AS surname) FROM staff;
-- → <id>SL20</id><surname>Mandela</surname>

-- XMLPARSE: string → xml
SELECT XMLPARSE(DOCUMENT '<a>1</a>');

-- XMLSERIALIZE: xml → text
SELECT XMLSERIALIZE(CONTENT '<a>1</a>'::xml AS text);

-- XMLAGG: many rows → one XML value
SELECT XMLAGG(XMLELEMENT(NAME staff, lName)) FROM staff;
-- → <staff>Mandela</staff><staff>Kruger</staff>

Memory aid: Parse = text → XML; Serialize = XML → text; Agg = many rows → one value; Forest/Concat = build/join several elements.

6. SQL/XML Operators — Generating XML from Relational Data

6.1 The Source Table (from the slides)

CREATE TABLE staff (
    staffNo  CHAR(4), fName CHAR(10),
    lName    CHAR(10), branchNo CHAR(4) );

INSERT INTO staff VALUES ('SL20', 'Thando',  'Mandela', 'B002');
INSERT INTO staff VALUES ('SL21', 'Marlize', 'Kruger',  'B003');
SELECT * FROM staff;
staffno fname lname branchno
SL20 Thando Mandela B002
SL21 Marlize Kruger B003

This is the reverse direction to Sections 4 and 8: here the data starts relational and we generate XML from it.

6.2 XMLELEMENT — Generate an Element

  • Generates an XML value with a single element as a child of its root item.
SELECT xmlelement( NAME staffname, concat(fName, lName) )
FROM Staff;

Result:

xmlelement (xml)
<staffname>Thando Mandela </staffname>
<staffname>Marlize Kruger </staffname>

Step-by-step walkthrough:

  1. xmlelement( NAME staffname, ... ) — NAME staffname gives the tag name of the new element.
  2. concat(fName, lName) — the second argument is the element content; here the first and last name joined together.
  3. The query runs once per row of Staff, so two rows give two <staffname> elements.
  4. Why the odd spacing? fName and lName are declared CHAR(10), which is blank-padded to 10 characters. The padding is carried into the XML. (Use VARCHAR, or trim(), to avoid it.) Also, concat does not insert a space itself.

6.3 XMLATTRIBUTES — Give the Element Attributes

  • An element can have zero or more attributes, specified in the XMLATTRIBUTES sub-clause.
SELECT xmlelement( NAME staff,
                   xmlattributes( branchNo AS "branchNo" ) )
FROM Staff;

Result:

xmlelement (xml)
<staff branchNo="B002"/>
<staff branchNo="B003"/>

Walkthrough:

  1. NAME staff → the element is called staff.
  2. xmlattributes( branchNo AS "branchNo" ) → takes the column value branchNo and makes it an attribute; the alias in double quotes is the attribute name (quotes preserve the capital N — otherwise PostgreSQL would fold it to lowercase).
  3. No content was supplied, so each element is self-closing (<staff .../>).

6.4 Combining Attributes and Content (from the slides)

Task: List all staff as XML elements with name and branch number as an attribute.

SELECT staffNo,
       xmlelement( NAME staff,
                   xmlattributes( branchNo AS "branchNo" ),
                   concat(fName, lName)
       ) AS staffXMLCol
FROM Staff;

Result:

staffno character(4) staffxmlcol xml
SL20 <staff branchNo="B002">Thando Mandela </staff>
SL21 <staff branchNo="B003">Marlize Kruger </staff>

Walkthrough:

  1. Argument order inside xmlelement: NAME first, then xmlattributes(...), then the content expression(s).
  2. staffNo is selected as a normal relational column beside the generated XML column, and the XML column is named with AS staffXMLCol.
  3. This is the table → XML direction: every row becomes one XML element.

Additional Example (added for clarity) — Nesting Elements

XMLELEMENT calls can be nested to build a hierarchy like the staff_list.xml structure:

SELECT xmlelement( NAME "STAFF",
           xmlattributes( branchNo AS "branchNo" ),
           xmlelement( NAME "STAFFNO", staffNo ),
           xmlelement( NAME "NAME",
               xmlelement( NAME "FNAME", trim(fName) ),
               xmlelement( NAME "LNAME", trim(lName) ) ) )
FROM Staff;
-- <STAFF branchNo="B002"><STAFFNO>SL20</STAFFNO><NAME><FNAME>Thando</FNAME><LNAME>Mandela</LNAME></NAME></STAFF>

Wrapping all of them in XMLELEMENT(NAME "STAFFLIST", XMLAGG(...)) would produce a full <STAFFLIST> document.

7. SQL/XML Mapping Functions

  • SQL/XML defines functions for mapping from tables to XML documents.
  • The mapping produces two types of XML document:
    1. Mapped table data — e.g., PostgreSQL: table_to_xml.
    2. An XML Schema describing the mapped table data — e.g., PostgreSQL: table_to_xmlschema.

7.1 The Demonstration Table (from the slides)

CREATE TABLE numbers( num1 int, num2 int );
INSERT INTO NUMBERS VALUES (1,2);
INSERT INTO NUMBERS VALUES (3,4);
INSERT INTO NUMBERS VALUES (5,6);
SELECT * FROM NUMBERS;
num1 num2
1 2
3 4
5 6

(Reference: PostgreSQL 18 documentation, "Functions for converting tables to XML".)

7.2 Generating XML from a Table — table_to_xml / query_to_xml

SELECT table_to_xml('Numbers', false, false, '');
-- OR:
SELECT query_to_xml('SELECT num1, num2 FROM Numbers', false, false, '');

Output (when table_to_xml is used):

<numbers xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance">
  <row> <num1>1</num1> <num2>2</num2> </row>
  <row> <num1>3</num1> <num2>4</num2> </row>
  ...

Walkthrough:

  1. The root element is named after the table (<numbers>); each row becomes a <row> element; each column becomes a child element (<num1>, <num2>).
  2. table_to_xml(tbl, nulls, tableforest, targetns) — the four arguments are:
    • tbl — the table name ('Numbers').
    • nulls — false = omit NULL columns; true = include them with xsi:nil="true".
    • tableforest — false = one document with a single root wrapping all rows (as shown); true = a "forest": one element per row, no wrapper.
    • targetns — the target namespace ('' = none).
  3. query_to_xml does the same for the result of any query (first argument is the query string), so you can choose columns or filter rows.
  4. The output is a single xml value in one cell — the whole table as one document.

7.3 Generating the XML Schema — table_to_xmlschema / query_to_xmlschema

SELECT table_to_xmlschema('Numbers', false, false, '');
-- OR:
SELECT query_to_xmlschema('SELECT num1, num2 FROM Numbers', false, false, '');

Output (partial listing):

<xsd:schema xmlns:xsd="http://www.w3.org/2001/XMLSchema">

  <xsd:simpleType name="INTEGER">
    <xsd:restriction base="xsd:int">
      <xsd:maxInclusive value="2147483647"/>
      <xsd:minInclusive value="-2147483648"/>
    </xsd:restriction>
  </xsd:simpleType>

  <xsd:complexType name="RowType.StaffList.public.numbers">
    <xsd:sequence>
      <xsd:element name="num1" type="INTEGER" minOccurs="0"></xsd:element>
      <xsd:element name="num2" type="INTEGER" minOccurs="0"></xsd:element>
    </xsd:sequence>
  </xsd:complexType>

  <xsd:complexType name="TableType.StaffList.public.numbers">
    <xsd:sequence>
      <xsd:element name="row" type="RowType.StaffList.public.numbers" minOccurs="0" maxOccurs="unbounded"/>
    </xsd:sequence>
  </xsd:complexType>

  <xsd:element name="numbers" type="TableType.StaffList.public.numbers"/>
</xsd:schema>

Step-by-step reading (links straight back to Lectures 9–10, XSD):

  1. xsd:simpleType name="INTEGER" — a simple type (Section 12.1 of L9–10) restricting xsd:int to PostgreSQL's integer range (−2147483648 to 2147483647).
  2. RowType...numbers — a named (global) complex type with an xsd:sequence of num1 and num2, both of type INTEGER. minOccurs="0" because a column value may be NULL.
  3. TableType...numbers — a global complex type containing row elements: minOccurs="0" and maxOccurs="unbounded" (zero or more rows).
  4. xsd:element name="numbers" — the root element, of type TableType....
  5. Notice the schema is built entirely from global types — exactly the reuse pattern from the Global Type section of L9–10. The schema describes the table_to_xml output from Section 7.2, so the data can be validated against it.
  6. The type names contain StaffList.public.numbers = database name . schema name . table name (this database is called StaffList).

8. PostgreSQL and XML — SQL + XPath Queries

8.1 The xpath() Function

  • Syntax: xpath('xpath_expression', colname)
  • PostgreSQL's xpath() evaluates XPath 1.0 expressions and returns an xml[] array (an array of XML values, because an XPath expression can match many nodes).
  • Use the text() function in the path to strip the tags and return only the content.
  • It combines the two query languages: SQL decides which rows and which columns; XPath digs inside the XML value.

Reminder: the XMLStaff table has two rows: D001 (SL20, B002, Manager, 1998-10-01, 30000 — with extra spaces) and D002 (SL21, B003, Accountant, 2002-11-02, 27000).

8.2 Query (4a) — Selecting an Element

SELECT xpath('/STAFF/STAFFNO', staffData) AS StaffNumberXML
FROM XMLStaff;

Result:

staffnumberxml xml[]
{<STAFFNO> SL20 </STAFFNO>}
{<STAFFNO>SL21</STAFFNO>}

Walkthrough:

  1. /STAFF/STAFFNO — from the root STAFF element, select its STAFFNO child. (The root of each stored document is <STAFF>, not <STAFFLIST>, so the path starts /STAFF.)
  2. The query runs once per table row; each result is an xml[] array (hence the xml[] column type) holding the matching element(s).
  3. Without text(), the tags are kept (<STAFFNO>...</STAFFNO>) and the spaces from D001's insert are visible.

8.3 Query (4b) — Using text() and @ for Several Columns

SELECT docNo, docDate,
    xpath('/STAFF/@branchNo',         staffData) AS BranchNumber,
    xpath('/STAFF/STAFFNO/text()',    staffData) AS StaffNumber,
    xpath('/STAFF/POSITION/text()',   staffData) AS Position,
    xpath('/STAFF/DOB/text()',        staffData) AS DOB,
    xpath('/STAFF/SALARY/text()',     staffData) AS Salary
FROM XMLStaff;

Result (each XML column has type xml[]):

docno docdate branchnumber xml[] staffnumber xml[] position xml[] dob xml[] salary xml[]
D001 2023-08-31 B002 SL20 Manager 1998-10-01 30000
D002 2023-08-31 B003 SL21 Accountant 2002-11-02 27000

Walkthrough:

  1. Relational + XML in one query: docNo and docDate are ordinary columns; the other five columns are extracted from inside the XML column.
  2. /STAFF/@branchNo — @ selects an attribute (recall attribute::branchNo = @branchNo from L9–10).
  3. /text() — returns just the text content, no tags.
  4. Each result is still an array (xml[]), shown as {SL20} in pgAdmin; it contains one element because each document has exactly one STAFF.

8.4 Query (5) — Flattening Arrays with unnest

  • unnest converts an array into a table-like structure (one row per array element) — so the xml[] arrays become plain xml values.
SELECT docNo, docDate,
    unnest(xpath('/STAFF/@branchNo',       staffData)) AS BranchNumber,
    unnest(xpath('/STAFF/STAFFNO/text()',  staffData)) AS StaffNumber,
    unnest(xpath('/STAFF/POSITION/text()', staffData)) AS Position,
    unnest(xpath('/STAFF/DOB/text()',      staffData)) AS DOB,
    unnest(xpath('/STAFF/SALARY/text()',   staffData)) AS Salary
FROM XMLStaff;

Result: same values as 8.3, but the column types are now xml (not xml[]) — no more curly-brace array wrappers.

Walkthrough:

  1. xpath(...) returns an array; unnest(...) expands it to one row per element.
  2. Here each array has one element, so the row count stays at 2. If a document had several matches (e.g., a <STAFFLIST> with 4 <STAFF> children), unnest would produce 4 rows instead.
  3. Caution: several unnest calls in the same SELECT list expand in parallel (PostgreSQL 10+), so they only line up correctly when every array has the same length.

Additional Example (added for clarity)

To get only the names of staff earning more than 28000, combine SQL's WHERE with a cast:

SELECT (xpath('/STAFF/STAFFNO/text()', staffData))[1]::text AS staffNo
FROM XMLStaff
WHERE ((xpath('/STAFF/SALARY/text()', staffData))[1]::text)::int > 28000;
-- → SL20

[1] picks the first array element, ::text turns xml into text, and ::int makes the comparison numeric.

9. PostgreSQL Server-Side File Access

  • pg_read_file() and pg_ls_dir() access files on the machine hosting the PostgreSQL server (not the client/PC running pgAdmin).
  • Relative paths are resolved relative to the PostgreSQL cluster/data directory.
  • PostgreSQL restricts these functions by default, and they can expose files accessible to the database server.

Security note (from the slides): these are server-side file access functions restricted by PostgreSQL privileges. They should not be granted casually because they can expose files accessible to the database server.

Example (added for clarity)

If a normal user could run SELECT pg_read_file('postgresql.conf');, they could read the server's configuration (and with absolute paths, other files the server process can read). That is why access is limited to superusers or roles explicitly granted it (e.g., the built-in pg_read_server_files role).

10. Importing XML Data into a PostgreSQL Database

Workflow: place the file where the server can see it → list files to confirm → read the file as text → cast to xml → store in a table → use xpath to break it up.

10.1 Step 1 — Place the File Where the Server Can Read It

  • The current working directory (cwd) for pgAdmin4/the server is C:\Program Files\PostgreSQL\18\data.
  • Create a folder under data and store your XML files there, e.g., MyXMLfiles.
  • For this demonstration, the XML file is placed in a directory accessible to the PostgreSQL server.

10.2 Step 2 — List Files with pg_ls_dir

SELECT pg_ls_dir('.');               -- files/folders under the cwd (data)
SELECT pg_ls_dir('./MyXMLfiles');    -- files/folders in the sub-folder MyXMLfiles
  • '.' = the cwd (the data folder); the second query lists the contents of MyXMLfiles (it should show staff_list.xml). One file/folder name is returned per row.

10.3 Step 3 — Read the File as Text with pg_read_file

SELECT pg_read_file('./MyXMLfiles/staff_list.xml');
  • Reads the contents of the file and returns it as text type — the XML is just a string at this point; PostgreSQL has not parsed it.

10.4 Step 4 — Present the Contents as xml Type

SELECT CAST( pg_read_file('./MyXMLfiles/staff_list.xml') AS xml );
  • CAST(... AS xml) converts the text into the xml data type. This parses the string and fails with an error if the XML is not well-formed.

10.5 Step 5 — Create a Table and Load the File Contents

SELECT ( CAST( pg_read_file('./MyXMLfiles/staff_list.xml') AS xml ) )
       AS xmldata
INTO   NewXMLtable;

SELECT * FROM NewXMLtable;

Walkthrough:

  1. SELECT ... AS xmldata INTO NewXMLtable — SELECT ... INTO creates a new table NewXMLtable with one column xmldata of type xml and inserts the result into it. This is a quick way to create a (temporary-style) XML table without writing CREATE TABLE.
  2. The table has one row containing the entire staff_list.xml — Approach 1 (whole document in a column) again.
  3. SELECT * FROM NewXMLtable shows that single row.

10.6 Step 6 — Use xpath to Split into <STAFF> Elements

SELECT xpath('//STAFF', xmldata) AS XMLcol
FROM NewXMLtable;

Query result (one cell, an xml[] array with one array element per <STAFF> element):

{ "<STAFF branchNo=\"B002\">
     <STAFFNO>SL20</STAFFNO>
     <NAME><FNAME>Thando</FNAME><LNAME>Mandela</LNAME></NAME>
     <POSITION>Manager</POSITION>
     <DOB>1998-10-01</DOB>
     <SALARY>30000</SALARY>
   </STAFF>",
  "<STAFF branchNo=\"B003\">
     <STAFFNO>SL21</STAFFNO>
     <NAM (...)  " }

Walkthrough:

  1. //STAFF — the double slash selects STAFF elements anywhere in the document.
  2. The result is one row whose single value is an array of all the <STAFF> elements (curly braces, comma-separated, each element quoted with escaped inner quotes \").
  3. This is the stepping-stone to shredding (Approach 2): the array still sits in one cell and must be spread out into rows.

HOMEWORK (from the slides): Write a PL/pgSQL function to store the array elements into a table, with one element per row.

Hint / Sketch for the Homework (added for clarity — not a memo)

CREATE TABLE StaffRows ( staffXML xml );

CREATE OR REPLACE FUNCTION split_staff() RETURNS void AS $$
DECLARE
    arr xml[];
    el  xml;
BEGIN
    SELECT xpath('//STAFF', xmldata) INTO arr FROM NewXMLtable;
    FOREACH el IN ARRAY arr LOOP
        INSERT INTO StaffRows VALUES (el);
    END LOOP;
END;
$$ LANGUAGE plpgsql;

This reuses FOREACH ... IN ARRAY from the PL/pgSQL lectures (5–8). (Alternative without PL/pgSQL: INSERT INTO StaffRows SELECT unnest(xpath('//STAFF', xmldata)) FROM NewXMLtable;.) Check it against your own understanding before relying on it.

11. Further Reading

  • PostgreSQL also provides XMLTABLE for converting XML content into relational rows and columns.

Example (added for clarity)

XMLTABLE does in one step what Section 8.3/8.4 did with several xpath/unnest calls:

SELECT x.*
FROM NewXMLtable,
     XMLTABLE('//STAFF' PASSING xmldata
        COLUMNS branchNo text PATH '@branchNo',
                staffNo  text PATH 'STAFFNO',
                fname    text PATH 'NAME/FNAME',
                lname    text PATH 'NAME/LNAME') AS x;

It turns each matching <STAFF> element into one relational row — effectively shredding (Approach 2) on the fly.

13. Questions & Memo

Section 2 — Storing XML in an RDB/ORDB

Q1: List the four general approaches for storing XML data in a relational or object-relational database.

A1:

  1. Store the XML document as the value of a column in one row or several rows.
  2. Store the XML document in a shredded form across a number of columns and tables.
  3. Store the XML document in a schema-independent form.
  4. Store the XML document in a parsed (internal) form.

Q2: State two advantages and two disadvantages of storing XML as a value in a table column (Approach 1).

A2: Advantages (any two): efficient to insert documents; efficient to retrieve documents; easy to apply full-text indexing. Disadvantages (any two): general query performance is poor because the XML must be parsed on the fly; updates replace the entire document (although XML documents can now be updated using SQL).

Q3: What is meant by "shredding" an XML document, and what extra information is needed?

A3: Shredding means decomposing the XML into its constituent elements and distributing the data over a number of attributes (columns) in one or more relations. Extra data is needed to capture the hierarchical nature of the XML (e.g., which elements are children of which) so the original document can be recomposed.

Q4: Name the native XML data type in (a) PostgreSQL and (b) Oracle, and the type that was used in the past.

A4: (a) xml; (b) XMLType; in the past a CLOB (character large object) was used.

Q5 (Scenario): A company stores thousands of XML purchase orders. They are always inserted once and retrieved whole by order number, and are never searched internally. Which storage approach is most appropriate, and why? Which approach would you choose if analysts must frequently query individual elements such as the total amount?

A5: Approach 1 (whole document in an XML column) — inserting and retrieving whole documents is efficient, and the weak query performance does not matter if documents are never searched internally. If individual elements (e.g., total amount) are queried often, Approach 2 (shredding) is better: values are in ordinary columns that are easy to index, avoiding on-the-fly parsing.

Q6: Which SQL standards introduced the XML data type, and what four things did they add?

A6: SQL:2003 (continuing in SQL:2008 and SQL:2011) added: a native XML data type, a set of XML/SQL operators, a set of XML/SQL functions, and a set of mappings from relational data to XML.

Section 4 — The XML Data Type

Q7 (Code Tracing): Given CREATE TABLE XMLStaff (docNo CHAR(4) PRIMARY KEY, docDate DATE, staffData XML); — what would happen if you tried to insert 'D003' with the value XML('<STAFF><STAFFNO>SL22</STAFFNO>') (no closing </STAFF>)? Why?

A7: The INSERT fails with an error because the value is not well-formed XML — the XML data type parses the string and rejects it. A plain VARCHAR/TEXT column would have accepted it, which is an advantage of the native XML type.

Q8: In Coding Example 1 the <STAFFNO> contained SL20 with extra spaces. What effect does this have on an xpath() query?

A8: The XML type preserves the whitespace, so xpath('/STAFF/STAFFNO', staffData) returns <STAFFNO> SL20 </STAFFNO> with the spaces, and .../text() returns SL20 — which would not equal 'SL20' in a comparison unless trimmed.

Section 6 — SQL/XML Operators

Q9 (Code Tracing): What does the following return for the Staff table (rows: SL20 Thando Mandela B002; SL21 Marlize Kruger B003)?

SELECT xmlelement( NAME staff, xmlattributes( branchNo AS "branchNo" ) ) FROM Staff;

A9: Two rows, each a self-closing element with a branchNo attribute: <staff branchNo="B002"/> and <staff branchNo="B003"/>. No content was supplied, so there is no closing tag.

Q10 (Code Writing): Write a query that lists all staff as XML elements named member, with staffNo as an attribute and the last name as content.

A10:

SELECT xmlelement( NAME member,
                   xmlattributes( staffNo AS "staffNo" ),
                   lName )
FROM Staff;
-- <member staffNo="SL20">Mandela   </member> ...

Q11: Why does concat(fName, lName) in the XMLELEMENT example produce extra spaces between the names?

A11: fName and lName are declared CHAR(10), which pads values with blanks to 10 characters. concat joins the padded strings (and adds no separator of its own), so the padding appears inside the generated element.

Q12: Match each function to its purpose: XMLPARSE, XMLSERIALIZE, XMLAGG, XMLFOREST.

A12: XMLPARSE — non-validating parse of a character string to produce an XML value. XMLSERIALIZE — generates a character/binary string from an XML value. XMLAGG — aggregates XML values across rows into a single XML value. XMLFOREST — generates a sequence (forest) of XML elements from the supplied values.

Section 7 — Mapping Functions

Q13: What two kinds of XML document do the SQL/XML mapping functions produce? Give the PostgreSQL function for each.

A13: (1) The mapped table data — table_to_xml; (2) an XML Schema describing the mapped table data — table_to_xmlschema. (Query-based versions: query_to_xml, query_to_xmlschema.)

Q14 (Code Tracing): For table numbers(num1, num2) holding (1,2), (3,4), (5,6), describe the structure of the output of SELECT table_to_xml('Numbers', false, false, '');.

A14: A single XML value whose root element is <numbers>, containing one <row> element per table row, each with <num1> and <num2> children holding that row's values (e.g., <row><num1>1</num1><num2>2</num2></row>).

Q15: In table_to_xmlschema, why do the generated num1 and num2 elements have minOccurs="0", and why does row have maxOccurs="unbounded"?

A15: minOccurs="0" because column values may be NULL (an omitted element). row has maxOccurs="unbounded" because a table can have any number of rows; minOccurs="0" there allows an empty table.

Q16: What is the difference between table_to_xml and query_to_xml?

A16: table_to_xml maps an entire named table; query_to_xml maps the result of any SQL query passed as a string, so specific columns/rows can be selected.

Section 8 — SQL + XPath in PostgreSQL

Q17: What does PostgreSQL's xpath() return, and which XPath version does it evaluate?

A17: It returns an xml[] array (array of XML values) and evaluates XPath 1.0 expressions.

Q18 (Code Tracing): Explain the difference in output between xpath('/STAFF/POSITION', staffData) and xpath('/STAFF/POSITION/text()', staffData).

A18: The first returns the whole element including tags, e.g. {<POSITION>Manager</POSITION>}. The second uses the text() node test to return only the text content, {Manager}.

Q19 (Code Writing): Write a query returning docNo and the branch number (as plain text, one row per document) from XMLStaff.

A19:

SELECT docNo,
       unnest( xpath('/STAFF/@branchNo', staffData) ) AS BranchNumber
FROM XMLStaff;

@branchNo selects the attribute; unnest converts the resulting array into ordinary values (type xml).

Q20: What does unnest do, and why was it needed in the lecture example?

A20: unnest converts an array into a table-like structure (one row per element). xpath() returns arrays (xml[]); applying unnest yields plain xml values/rows instead of arrays, giving a more table-like result (and producing multiple rows if the XPath matches multiple nodes).

Q21: In the query xpath('/STAFF/@branchNo', staffData), what does @ mean, and what would /STAFF/branchNo return instead?

A21: @ selects an attribute. /STAFF/branchNo looks for a child element called branchNo, which does not exist (it is an attribute), so it returns an empty array {}.

Sections 9 & 10 — Importing XML Files

Q22: What do pg_ls_dir() and pg_read_file() do, and why should access to them be restricted?

A22: pg_ls_dir() lists files/folders and pg_read_file() reads a file's contents, both on the machine hosting the PostgreSQL server, with relative paths resolved against the cluster/data directory. They are restricted by default because they can expose any file the database server can access, so privileges to use them must not be granted casually.

Q23 (Ordering): Put the following in the correct order for loading an XML file into a table: (a) xpath('//STAFF', xmldata); (b) place the file in a folder under the data directory; (c) CAST(... AS xml); (d) pg_read_file(...); (e) SELECT ... INTO NewXMLtable.

A23: (b) → (d) → (c) → (e) → (a). Place the file; read it as text; cast it to xml; store it in a table (INTO); then split it with xpath.

Q24 (Code Tracing): What does SELECT (CAST(pg_read_file('./MyXMLfiles/staff_list.xml') AS xml)) AS xmldata INTO NewXMLtable; do?

A24: It reads the file as text, casts it to the xml type (error if not well-formed), and creates a new table NewXMLtable with one xml column named xmldata, containing one row with the entire document.

Q25: What does SELECT xpath('//STAFF', xmldata) FROM NewXMLtable; return when the file holds four <STAFF> elements — one row or four? Why?

A25: One row, containing one xml[] array with four elements (one per <STAFF>). xpath returns an array in a single cell. To get four rows, apply unnest (or loop over the array, as in the homework).

Q26 (Homework recap): What was the homework task set in this lecture?

A26: Write a PL/pgSQL function that stores the elements of the <STAFF> array (result of xpath('//STAFF', xmldata)) into a table, with one element per row.

Q27: Which PostgreSQL feature is mentioned for further reading to convert XML content directly into relational rows and columns?

A27: XMLTABLE.

Comparison Questions

Q28: Compare using BaseX (native XML database) with storing XML in PostgreSQL's XML type, in terms of how queries are written.

A28: In BaseX the entire database is XML and queries are pure XPath/XQuery (e.g., //STAFFLIST/STAFF[1]/STAFFNO). In PostgreSQL the XML sits in a column of a relational table; SQL selects rows/columns and xpath() (XPath 1.0 only, returning arrays) queries inside the XML value (e.g., SELECT xpath('/STAFF/STAFFNO', staffData) FROM XMLStaff;). PostgreSQL therefore lets you mix XML with relational data in one query, while BaseX offers full XQuery (FLWOR) over XML collections.
