2. What is Big Data?

  • Definition: datasets whose scale, complexity, speed, or diversity creates challenges for conventional data-management approaches.
  • Key idea: big data is huge in volume, yet growing exponentially with time. It is so large and complex that traditional data management tools struggle to efficiently store and process it.

2.1 The 5 Vs of Big Data

V Meaning (from the slides)
Volume Data at the scale of terabytes to petabytes (now even yottabytes).
Velocity Data in motion → need to analyse streaming data to enable decisions within fractions of a second.
Variety Data in many forms: structured, semi-structured, unstructured, text, multimedia.
Value Value usually comes from insight discovery and pattern recognition that lead to more effective operations, stronger customer relationships, etc.
Veracity The "truth" / accuracy of data and information assets — determines the accuracy, reliability and trustworthiness of the data.

Example (added for clarity)

A national retailer's point-of-sale + website + social-media data illustrates all five Vs at once: millions of transactions per day (volume); live fraud-detection on card payments, decided in milliseconds (velocity); sales tables, JSON order logs, customer-review text and product photos (variety); spotting that rainy-day sales of a product spike, which drives stock decisions (value); and discarding fake reviews or duplicated sensor/log records so the analysis can be trusted (veracity).

3. Sources of Big Data

3.1 A. Web-generated structured & unstructured data

  1. Click-stream data — website browsing activities.
  2. E-commerce purchasing histories — feed recommender systems.
  3. Social network services — social media platforms generate enormous volumes of text, images, video, interaction and behavioural data.

3.2 B. Sensor data

  1. Modern connected vehicles: GPS/location, vehicle diagnostics, driver-assistance sensors, battery/energy data, telemetry.
  2. Other sources, e.g., wireless sensor networks.

3.3 C. Mobile devices

  • e.g., smartphones (GPS, etc.).

3.4 D. Business data

  1. Stock exchange — stock trading continues 24/7.
  2. Smart transport systems — traffic sensors, vehicle GPS data, toll/road monitoring systems, public transport tracking.

Example (added for clarity)

A single connected car is a walking big-data source: every second it emits GPS position, engine diagnostics and battery readings (sensor data + velocity). Multiply that by millions of cars, and the manufacturer has a volume problem that a single relational server cannot comfortably ingest — which motivates Section 4.

4. Databases for Big Data — Why NoSQL?

4.1 The Problem

  • Traditional relational database architectures may struggle when workloads require:
    • Massive horizontal scaling.
    • Flexible schemas.
    • Very high write throughput.
    • Distributed processing across large clusters.

4.2 The Solution — NoSQL Database Systems

  • NoSQL = "Not Only SQL".
  • NoSQL systems:
    • Are distributed, non-relational DBs.
    • Are designed for large-scale distributed processing and analytics.
    • Support massively parallel data processing using a large number of low-cost servers → scalability, availability & fault tolerance.
    • Can support thousands or millions of interactive users.

4.3 Who Uses NoSQL?

  • Arose alongside major Internet businesses that had difficulty storing and processing huge quantities of data: Google, Amazon, Facebook, Twitter (now X), Microsoft, Apple, etc.
  • Today: used by organisations that collect large amounts of semi-structured & unstructured data for analysis, e.g., social media data (X, Facebook).

4.4 AI and NoSQL

  • AI organisations and AI-powered businesses increasingly use NoSQL as part of the data layer supporting:
    • Generative AI applications.
    • Retrieval-Augmented Generation (RAG).
    • Vector / semantic search.
    • AI agents and agent memory.
    • Real-time personalised AI applications.

Example (added for clarity)

"Scale up vs. scale out": a relational server is typically scaled up (buy a bigger, costlier machine). NoSQL is designed to scale out — when load doubles, add more cheap servers to the cluster and the data is spread across them. If one server fails, replicas on other servers keep the system available (fault tolerance).

5. The CAP Theorem (Section 24.2)

  • Replicated data items can have various levels of consistency.
    • Enforcing serializability is the strongest form of consistency, but has high overhead — it can reduce read/write performance.
  • CAP = Consistency, Availability, Partition tolerance.
  • CAP theorem: it is not possible to guarantee all three simultaneously in a distributed system with data replication.
    • More precisely: when a network partition occurs, a distributed system cannot simultaneously guarantee both strong consistency and availability.
  • Systems therefore make different consistency/availability trade-offs depending on their requirements.
  • In big-data systems, guaranteeing availability and partition tolerance is often more important → eventual consistency is often adopted.

Example (added for clarity)

A social network keeps copies of your profile on servers in two data centres. The link between them breaks (partition). Option A (favour availability): both data centres keep accepting reads/writes, so for a short time a friend may see your old profile photo — data is eventually consistent. Option B (favour consistency): one data centre refuses requests until the link is restored, so nobody sees stale data but some users get errors (not available). Most big-data/web systems choose A; a bank transferring money would lean towards B.

5.1 Reading for the Student — PACELC

Flagged on the slides: "Read about the PACELC model and explain how it extends the CAP theorem by considering trade-offs when there is no network partition."

  • Summary (self-study aid — verify against your own reading): PACELC says: if there is a Partition (P), choose between Availability (A) and Consistency (C) — exactly as in CAP — Else (E), when the system is running normally, choose between Latency (L) and Consistency (C).
  • Why it matters: CAP only describes behaviour during a partition. PACELC recognises that even without a partition, replication forces a trade-off: waiting for all replicas to agree gives stronger consistency but higher latency; answering from one replica is faster but possibly stale.

6. Querying NoSQL Databases & Classification

  • No unified query standard (unlike SQL for relational DBs).
  • NoSQL DBMSs provide a native API with simple data-access commands, or a native query language, e.g.:
    • MongoDB → mongosh, a JavaScript-based shell, plus drivers for application languages.
    • Neo4j → Cypher query language and a REST API (get, put, post).

6.1 Classification of NoSQL Databases (five categories)

  1. Key-value stores.
  2. Document databases.
  3. Wide-column stores.
  4. Graph databases.
  5. Time series databases.

7. NoSQL Data Models for Big Data

7.1 Key-Value Stores

  • Key — uniquely identifies a data item.
  • Value — a word, number, or complex structure with unique semantics (e.g., lists, sets).
  • Data searches: data is primarily accessed using keys or key-based access patterns. Query capabilities depend on the specific system.
  • Primary use: very fast & highly scalable retrieval of values needed for application tasks, e.g., retrieving product names (Amazon's DynamoDB).
  • Example DBs: DynamoDB (Amazon), Redis (LinkedIn), RocksDB (Meta Platforms).

Worked Example — Slide figure: "Key/Value Store" (Car)

Key Value (attributes)
1 Make: Nissan, Model: Pathfinder, Color: Green, Year: 2003
2 Make: Nissan, Model: Pathfinder, Color: Blue, Color: Green, Year: 2005, Transmission: Auto

Step-by-step reading:

  1. The key (1, 2) uniquely identifies each item; the database retrieves a whole value by that key.
  2. The value is opaque to the DB's data model — it is simply "whatever the application stored."
  3. Notice key 2 has two Color entries and an extra Transmission attribute, while key 1 does not → values need not share a common structure (no fixed schema).
  4. To find "all green cars" you would typically have to scan values in the application — the model is optimised for "give me the value for key X", not complex searching.

7.2 Document Databases

  • Designed to store documents.
  • Documents are encoded in a standard data-exchange format, e.g., XML, JSON (JavaScript Object Notation), BSON (Binary JSON).
  • Documents contain field-value pairs and can include nested documents and arrays → complex hierarchical data is represented naturally.
  • The number & type of attributes can vary from document to document.
  • Both keys and values are searchable (a key difference from plain key-value stores).
  • Primary use: storing text documents, e-mail messages, XML documents.
  • Example DBs: MongoDB, Apache's CouchDB, Google's Firebase Firestore, Amazon's DocumentDB.

Worked Example — Slide figure: "Document DB" (orders)

Key 101:
{
  "ID": "1001",
  "ItemsOrdered": [
    { "ItemID": "1",    "Quantity": "2", "cost": "1000" },
    { "ItemID": "1001", "Quantity": "2", "cost": "1000" }
  ],
  "OrderDate": "05/11/2019"
}

Key 102:
{
  "ID": "1002",
  "ItemsOrdered": [
    { "ItemID": "2890", "Quantity": "11", "cost": "10000" }
  ],
  "OrderDate": "05/11/2019"
}

Step-by-step reading:

  1. Each document is stored under a key (101, 102) — so a document DB is, in effect, a key-value store whose values are structured, searchable documents.
  2. ItemsOrdered is an array of nested documents — one order holds many line items inside the same document.
  3. In a relational design this would need two tables (Order and OrderItem) joined by a foreign key; here the order and its items are stored together and retrieved in one read.
  4. Order 101 has two items and order 102 has one → the structure varies per document without any schema change.

7.3 Wide-Column (Column-Family) Stores

  • Data is stored in rows identified by keys, with columns grouped into column families.
  • Different rows may contain different columns.
  • Designed for distributed, highly scalable workloads.
  • Example DBs: Google's Bigtable, Apache's HBase, Apache Cassandra (distributed wide-column DB used in large-scale applications), Amazon's Keyspaces, Microsoft Azure's Cosmos DB.

Worked Example — Slide figure: Column family UserProfile

Row key Column 1: Name Column 2: ContactInfo Column 3
ID: 101 First Name: John, Last Name: Doe Email: email1@ex.com, Phone#: 4084006666 Age: 40
ID: 102 First Name: John, Last Name: Doe, Title: Dr. Email: email1@ex.com Country: US

Step-by-step reading:

  1. The whole structure is the column family UserProfile; each row is found by its row key (101, 102).
  2. Row 101 has an Age column; row 102 has a Country column instead → different rows contain different columns.
  3. Even inside the Name column, row 102 has an extra Title — so the sub-columns also vary.
  4. Contrast with a relational table: there, every row would carry all columns (with NULLs for the unused ones).

7.4 Graph Databases

  • Represent data as nodes, relationships (edges), and properties → well suited to highly connected data.
  • A graph is an object-oriented network of:
    • Nodes (entities).
    • Edges (relationships between nodes).
    • Properties (object attributes, expressed as key-value pairings).
  • Primary uses: social networks, recommendations, forensic investigations.
  • Example DBs: Neo4j, Amazon Neptune, Amazon Neptune Analytics / other modern graph offerings.

Worked Example — Slide figure: Graph DB (Matrix characters)

Step-by-step reading:

  1. Nodes are the characters (e.g., Neo {age: 29, name: Neo}, Morpheus {occupation, rank}, Trinity, Cypher, Agent Smith, The Architect).
  2. Edges are the labelled, directed relationships: Neo KNOWS Morpheus, Neo LOVES Trinity, Agent Smith CODED_BY The Architect.
  3. Edges can carry properties too — e.g., a KNOWS edge with age: 12 years or disclosure: public/secret.
  4. This is the same directed-graph idea as Figure 13.1 in the semi-structured data notes, but with a database engine built around it — queries like "who knows whom, and how?" follow edges directly instead of using joins.

7.5 Time Series Databases

  • Designed to store and retrieve data records sequenced by time — sets of data points associated with timestamps, stored in time-sequence order.
  • Make it easy to measure how measurements or events change over time, e.g., temperature readings from weather sensors or intraday stock prices.

Worked Example — Slide figure: time-series data model

  1. Database → Table → Series → Record is the hierarchy.
  2. A series is identified by dimensions (e.g., Region: us-west, Host: Server1) plus a measure name (e.g., CPU).
  3. Each record in the series is a timestamp + measure value — e.g., 2019-02-18 8:01 PST → 55%, 8:02 PST → 65%.
  4. Different series can have different dimensions (Series 3 also has a NIC dimension) — again a flexible schema.

7.6 Summary — Comparing the Five NoSQL Models

Model Data structure Typical use Example DBs
Key-value Unique key → value (simple or complex) Very fast key lookups (e.g., product names) DynamoDB, Redis, RocksDB
Document Documents (JSON/BSON/XML) with nested fields & arrays; keys and values searchable Text documents, e-mails, XML MongoDB, CouchDB, Firestore, DocumentDB
Wide-column Rows + column families; rows may have different columns Large-scale distributed workloads Bigtable, HBase, Cassandra, Keyspaces, Cosmos DB
Graph Nodes, edges, properties Social networks, recommendations, forensics Neo4j, Amazon Neptune
Time series Timestamped records in time order Sensor readings, stock prices (slide gives no named examples)

8. MongoDB — Document Database

8.1 Definitions

  1. MongoDB is a document-oriented database providing:
    • High performance.
    • High availability.
    • High scalability.
  2. It works on the concepts of collections and documents: records are stored as documents (specifically BSON documents), which are gathered together in collections.
  3. A MongoDB database is a logical container for one or more collections.
  4. A MongoDB DBMS (deployment) can contain one or more databases and may be deployed as a standalone server, replica set, or sharded cluster.

Hierarchy: Deployment → Database → Collection → Document → Field-value pairs

8.2 The MongoDB Document

  • A BSON document consisting of field-value pairs; can contain nested documents and arrays.
  • BSON has additional data types such as ObjectId and Date.
  • Has a dynamic schema: MongoDB uses a flexible schema by default, but schema validation rules can be applied when required.

Worked Example — Slide figure 3.1: A MongoDB document

{
  name: "sue",
  age: 26,
  status: "A",
  groups: [ "news", "sports" ]
}
  • Each line is a field: value pair; groups holds an array value.

8.3 Sample MongoDB Document (blog data)

The slide's sample is reproduced below with the braces tidied up (the slide's layout places some braces in the wrong positions; the content is unchanged):

{
  _id: ObjectId("507f1f77bcf86cd799439011"),
  title: 'MongoDB Overview',
  description: 'MongoDB is no sql database',
  by: 'tutorials point',
  url: 'http://www.up.ac.za',
  tags: ['mongodb', 'database', 'NoSQL'],
  likes: 100,
  comments: [
    {
      user: 'user1',
      message: 'My first comment',
      dateCreated: new Date(2021, 1, 20),
      likes: 0
    },
    {
      user: 'user2',
      message: 'My second comments',
      dateCreated: new Date(2022, 1, 20),
      likes: 5
    }
  ]
}

Homework from the slide — "Identify data types in this document"

Field Value Data type
_id ObjectId("507f…") ObjectId (BSON-specific; unique document identifier)
title, description, by, url text in quotes String
tags ['mongodb','database','NoSQL'] Array (of strings)
likes (top level) 100 Number (integer)
comments [ {…}, {…} ] Array of embedded (nested) documents
user, message (inside a comment) text String
dateCreated new Date(2021, 1, 20) Date (BSON-specific)
likes (inside a comment) 0, 5 Number (integer)

Step-by-step notes:

  1. _id is the primary key of the document; ObjectId is a BSON type that doesn't exist in plain JSON.
  2. comments is the key nested-structure feature: instead of a separate Comment table with a foreign key (relational), the comments live inside the blog document.
  3. Watch out: in JavaScript's new Date(year, month, day), the month is zero-based, so new Date(2021, 1, 20) is 20 February 2021, not 20 January.
  4. likes appears twice — once at blog level and once per comment; this is fine because they are in different (nested) scopes.

8.4 The MongoDB Collection

  • A group of MongoDB documents.
  • Approximately the same purpose as an RDBMS table.
  • Does not enforce a schema.
  • Documents within a collection can have different fields.
  • Typically, all documents in a collection are of a similar or related purpose.
  • Slide figure 3.2: a collection drawn as a stack of documents (each with name, age, status, groups).

8.5 Relational vs MongoDB — Terminology Mapping (added for clarity)

Relational (RDBMS) MongoDB
Database Database
Table Collection
Row / tuple Document
Column / attribute Field
Fixed schema enforced Flexible schema (optional validation)
Joins / foreign keys across tables Nested documents & arrays (embedding)
Primary key _id

8.6 The MongoDB Database Environment (Software)

Software Function
mongod DBMS server (the Mongo server process).
mongo Client (older shell; replaced by mongosh in current versions).
mongoimport & mongoexport Tools for importing and exporting JSON documents into/out of the DB.
MongoDB Atlas Fully managed cloud database service for deploying, scaling and managing MongoDB across AWS, Azure and Google Cloud.
mongosh JavaScript-based shell (a JavaScript/Node.js REPL) for interacting with MongoDB. Applications use drivers for Java, Python, C#, JavaScript/Node.js, etc.

8.7 Basic MongoDB Statements (typed in the client window)

Operation Example MongoDB statement
CREATE a database or open an existing database use mydb
CREATE a collection mydb.createCollection("myCollection")
Store data in the database (create/insert a document) db.myCollection.insertOne({name: "value", x: 3})
READ db.myCollection.find({ x: 3 })

Coding Example (added for step-by-step clarity)

use mydb                                   // 1
db.createCollection("myCollection")        // 2
db.myCollection.insertOne({ name: "value", x: 3 })   // 3
db.myCollection.insertOne({ name: "other", x: 7, tags: ["a","b"] }) // 4
db.myCollection.find({ x: 3 })             // 5

Step-by-step walkthrough:

  1. use mydb — switches to the database mydb; if it doesn't exist, MongoDB creates it when data is first stored. (It both "creates or opens", as the slide says.)
  2. createCollection — explicitly creates the collection. In mongosh, after use mydb, this is normally called on the current database object db (the slide writes mydb.createCollection(...); check which form your practical setup accepts).
  3. insertOne({...}) — stores a single document (a JSON-like object) in the collection. MongoDB automatically adds a unique _id (an ObjectId) if you don't supply one.
  4. The second document has a different shape (extra tags array) — allowed, because a collection does not enforce a schema.
  5. find({ x: 3 }) — returns every document whose field x equals 3 (here, only the first document). The argument { x: 3 } is the filter/query condition; compare with SELECT * FROM myCollection WHERE x = 3 in SQL.

9. Questions & Memo

Section 2 — Big Data

Q1: List the 5 Vs of Big Data and give a one-line description of each.

A1: Volume — terabytes to petabytes and beyond. Velocity — data in motion, needing near-instant analysis of streams. Variety — structured, semi-structured, unstructured, text and multimedia. Value — insight and pattern discovery that improve operations and customer relationships. Veracity — the accuracy, reliability and trustworthiness of the data.

Q2: A ride-hailing company records GPS pings from every vehicle each second, and must decide within milliseconds which driver to assign to a rider. Which two Vs are most prominent, and why?

A2: Velocity (data in motion; decisions needed within fractions of a second) and Volume (millions of pings per minute, accumulating over time). (Variety could also be argued if ratings, text and maps are combined.)

Section 3 — Sources of Big Data

Q3: Name the four categories of big-data sources given in the lecture and one example of each.

A3: (A) Web-generated data — click-stream data, e-commerce histories, social networks. (B) Sensor data — connected-vehicle telemetry, wireless sensor networks. (C) Mobile devices — smartphone GPS. (D) Business data — stock exchange trading, smart transport systems.

Section 4 — Why NoSQL

Q4: What does "NoSQL" stand for, and what problems of traditional relational architectures does it address?

A4: Not Only SQL. It addresses difficulties with massive horizontal scaling, flexible schemas, very high write throughput, and distributed processing across large clusters — using distributed, non-relational DBs on many low-cost servers for scalability, availability and fault tolerance.

Q5: Give two reasons AI-powered businesses use NoSQL databases.

A5: Any two of: supporting generative AI applications, RAG, vector/semantic search, AI agents and agent memory, real-time personalised AI applications.

Section 5 — CAP Theorem

Q6: State the CAP theorem and explain which two properties many big-data systems prioritise.

A6: In a distributed system with data replication, it is not possible to guarantee Consistency, Availability and Partition tolerance simultaneously. When a partition occurs, a system cannot guarantee both strong consistency and availability. Many big-data systems prioritise availability and partition tolerance and adopt eventual consistency.

Q7: Why is enforcing serializability not always desirable in a replicated distributed system?

A7: It is the strongest form of consistency but carries high overhead, which can reduce read/write performance.

Q8: How does PACELC extend CAP?

A8: CAP only covers behaviour during a network partition. PACELC adds that Else (no partition) the system must still trade off Latency vs Consistency.

Section 6 & 7 — NoSQL Classification and Data Models

Q9: Name the five categories of NoSQL databases and one example DB for each.

A9: Key-value (DynamoDB / Redis / RocksDB); Document (MongoDB / CouchDB / Firestore / DocumentDB); Wide-column (Bigtable / HBase / Cassandra / Keyspaces / Cosmos DB); Graph (Neo4j / Amazon Neptune); Time series (e.g., temperature sensor or stock-price data stores).

Q10: Why is there "no unified query standard" for NoSQL, and how do MongoDB and Neo4j each get queried?

A10: Each NoSQL system has its own native API or query language. MongoDB uses mongosh (JavaScript-based shell) plus language drivers; Neo4j uses the Cypher query language and a REST API.

Q11: What is the main difference between a key-value store and a document database in terms of searching?

A11: In a key-value store data is primarily accessed via the key; in a document database both keys and values (fields inside documents) are searchable, and documents hold structured, nested content.

Q12 (Classification): Match each scenario to the best NoSQL model: (a) shopping-cart lookups by session ID, (b) "people you may know" suggestions, (c) CPU readings from servers every minute, (d) blog posts with nested comments.

A12: (a) Key-value. (b) Graph. (c) Time series. (d) Document.

Q13: What do the terms "column family" and "row key" mean in a wide-column store, and how does this differ from a relational table?

A13: Data is stored in rows identified by a row key, with columns grouped into column families. Different rows may contain different columns, unlike a relational table where every row has the same fixed columns.

Q14: What are the three building blocks of a graph database?

A14: Nodes (entities), edges (relationships between nodes), properties (attributes of nodes/edges, as key-value pairs).

Section 8 — MongoDB

Q15: Define a MongoDB document, collection and database, and state the RDBMS equivalent of a collection.

A15: A document is a BSON record of field-value pairs (can contain nested documents and arrays). A collection is a group of documents (RDBMS equivalent: a table, but with no enforced schema). A database is a logical container for one or more collections.

Q16: What is BSON and how does it differ from JSON?

A16: BSON = Binary JSON. It is the binary-encoded format MongoDB uses to store documents and has additional data types such as ObjectId and Date.

Q17 (Code Tracing): Given db.myCollection.insertOne({name: "value", x: 3}) followed by db.myCollection.find({ x: 3 }), what does the find return, and what extra field will the returned document contain?

A17: It returns the document { name: "value", x: 3 } plus an automatically generated _id field (an ObjectId), because the insert didn't supply one.

Q18: Does MongoDB force every document in a collection to have the same fields? Can a schema be enforced?

A18: No — documents in a collection can have different fields (flexible/dynamic schema by default). Schema validation rules can be applied when required.

Q19: List three ways a MongoDB deployment can be set up, and name the cloud service that manages MongoDB for you.

A19: Standalone server, replica set, sharded cluster. The managed cloud service is MongoDB Atlas (on AWS, Azure and Google Cloud).

Q20: Match each software component to its function: mongod, mongosh, mongoimport/mongoexport, Atlas.

A20: mongod — DBMS server process. mongosh — JavaScript-based client shell. mongoimport/mongoexport — import/export JSON documents. Atlas — fully managed cloud MongoDB service.

Q21 (Homework): Identify the data types of _id, tags, comments and dateCreated in the sample blog document.

A21: _id — ObjectId; tags — array of strings; comments — array of embedded documents; dateCreated — Date.

Q22: Why would the blog sample (Section 8.3) need at least two tables in a relational design, but only one document in MongoDB?

A22: Comments are a one-to-many child of a blog post, so a relational design needs a Blog table and a Comment table linked by a foreign key (and tags would need a third). MongoDB embeds the comments (array of nested documents) and tags (array) inside the blog document, so a single read retrieves everything.
