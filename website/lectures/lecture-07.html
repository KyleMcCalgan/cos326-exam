2. MongoDB Document Database

2.1 Definition of MongoDB

  1. MongoDB is a:
    • Document-oriented database designed to support high-performance, highly available and horizontally scalable applications.
    • Database that works on the concepts of collections and documents.
  2. A MongoDB database is a logical container for collections.
  3. A MongoDB DBMS can run on a single server or be distributed across clusters for horizontal scaling.

2.2 Collections

  1. A MongoDB collection is a:
    • Group of MongoDB documents.
    • Exists within a single database.
    • Does not enforce a schema.
    • Documents within a collection can have different fields.
    • Typically all documents in a collection are of similar or related purpose.
    • Analogous to tables in relational databases, but MongoDB uses a flexible schema by default.

📌 Example (from the slides) — A Collection of Documents

Each document is a set of field: value pairs; values can be strings, numbers, arrays, etc.:

{
  name:   "al",
  age:    18,
  status: "D",
  groups: [ "politics", "news" ]
}

The slide stacks three such documents (each with fields name, age, status, groups) to show a collection = a group of documents.

2.3 Terminology — Relational vs. MongoDB (added for clarity)

Relational MongoDB
Database Database (logical container for collections)
Table Collection
Row / tuple Document
Column / attribute Field
Fixed schema (all rows same columns) Flexible schema (documents may differ)
Primary key _id field (automatically added if omitted)
Atomic values only (1NF) Arrays and embedded documents allowed

📌 Example (added for clarity)

In one students collection these two documents are both valid — the second has an extra field and the first does not:

{ name: "Thando", age: 20 }
{ name: "Marlize", age: 21, modules: ["COS326", "COS332"] }

A relational Student table would force both rows to have identical columns (and modules would need a separate table to stay in 1NF).

2.4 MongoDB Atlas — Cloud Database Platform

  • MongoDB Atlas is MongoDB's fully managed cloud database service, designed for scalability, security and global distribution.
  • Key features:
    • Multi-cloud support: deploy on AWS, Azure or Google Cloud.
    • Built-in security: encryption, access controls and auditing.
    • Scalability: horizontal scaling and global clusters.
    • Automation: automated backups, monitoring, deployment and scaling.
    • Integrated capabilities: Compass, Charts, Atlas Search and Atlas Services.
  • Use cases: real-time analytics; mobile and web apps; IoT and telemetry; forensic data pipelines (e.g., secure evidence storage, audit trails).
  • Getting started: sign up at mongodb.com/atlas → create a free-tier cluster → connect via Compass, mongosh or application drivers.

3. MongoDB Data Types

3.1 Data Types (1)

Type Description (from the slides)
String Most commonly used type. Must be UTF-8 valid.
Integer 32-bit (Int32) and 64-bit (Int64) integer BSON types.
Boolean true / false.
Double Floating-point values.
Array Arrays/lists/multiple values under one key.
Timestamp BSON type primarily used internally by MongoDB (replication/oplog). Use Date for application date/time values.

3.2 Data Types (2)

Type Description (from the slides)
Embedded document Used for documents nested inside other documents.
ObjectId Used for the unique _id identifier of a document (see note below).
Null Stores a null value.
Date Stores date/time values. In mongosh use new Date() or ISODate() to create BSON Date values.
Binary data Stores binary data.
Code Stores JavaScript code in a document. Rare and discouraged for security reasons.
Regular expression Stores a regular expression.

⚠️ Note on the slide: the slide's description of ObjectID reads "used to store a document nested inside another document" — that is actually the definition of an embedded document (the line above it). ObjectId is the 12-byte unique identifier MongoDB generates for _id (e.g., ObjectId("64f77f99cf3b7de1d4d48756"), as seen in the demo output). Know the correct meaning for the exam.

📌 Example (added for clarity) — One Document Using Many Types

{
  _id:      ObjectId("507f1f77bcf86cd799439011"),   // ObjectId
  name:     "Thando Mandela",                        // String
  age:      25,                                      // Integer (Int32)
  gpa:      3.7,                                     // Double
  enrolled: true,                                    // Boolean
  dob:      ISODate("2000-10-01"),                   // Date
  modules:  ["COS326", "COS332"],                    // Array
  address:  { city: "Pretoria", code: "0002" },      // Embedded document
  notes:    null                                     // Null
}

4. CRUD Operations

4.1 CRUD Summary — MongoDB vs. Relational (from the slides)

Operation MongoDB Relational equivalent
Select database use mydb Select database/schema
Create collection db.createCollection("students") CREATE TABLE students (...)
Insert document db.students.insertOne({...}) INSERT INTO students ...
Read documents db.students.find(...) SELECT ... WHERE ...
Update document(s) updateOne() / updateMany() UPDATE ... WHERE ...
Delete document(s) deleteOne() / deleteMany() DELETE ... WHERE ...

Note (from the slide): these are conceptual equivalents, not exact one-to-one translations.

4.2 CREATE — Documents and Collections

Task Example
Create a document (a JavaScript object in a variable) doc = { name: "value", x: 3 }
Create a collection explicitly, then insert db.createCollection("myCollection") then db.myCollection.insertOne({ name: "value", x: 3 })
Implicitly create a collection (no createCollection needed) db.myCollection.insertOne(doc) or db.myCollection.insertOne({ name: "value", x: 3 })
Drop a collection db.myCollection.drop()

Walkthrough:

  1. A document is just a JSON-like object; assigning it to a variable (doc = {...}) does not store it in the database.
  2. createCollection is optional — inserting into a collection that does not exist creates it automatically.
  3. drop() removes the whole collection (all its documents).

📌 Demo Output (from the slide screenshot)

db> db.myCollection.insertOne({name: "mongo", x:3})
{ acknowledged: true,
  insertedId: ObjectId("64f77f99cf3b7de1d4d48756") }
  • acknowledged: true — the server confirmed the write.
  • insertedId — the _id MongoDB generated automatically because we did not supply one.

4.3 INSERT — insertOne() and insertMany()

  • Inserts into a specific collection; if the collection doesn't exist, it is created.
  • You can specify a unique ID (_id), or MongoDB assigns one.
  • Multiple documents can be inserted using array notation [ {...}, {...} ].
// 1. MongoDB assigns the _id
db.myCollection.insertOne( { name: "mongo", x: 3 } )

// 2. We supply our own _id
db.myCollection.insertOne( {
    _id:  ObjectId("507f1f77bcf86cd799439011"),
    name: "mongo",
    x:    3 } )

// 3. Several documents at once (array of documents)
db.myCollection.insertMany( [
    { name: "mongo", x: 3 },
    { name: "Neo4j", x: 4 }
] )

Walkthrough:

  1. insertOne(doc) takes one document; insertMany([ ... ]) takes an array of documents.
  2. Every document needs a unique _id (the primary key). Supplying a duplicate _id gives an error; omitting it lets MongoDB generate an ObjectId.
  3. (Slide tip: in the shell, placing the cursor on a bracket highlights its matching bracket — useful for spotting mismatched { } and [ ] in longer inserts.)
  4. Slide typo: the second slide example is missing a comma after the _id line. Fields in a document must be comma-separated.

📌 Demo Result — what the collection holds after the lecture inserts

db> db.myCollection.find()
[
  { _id: ObjectId("64f77f32cf3b7de1d4d48755"), name: 'value', x: 3 },
  { _id: ObjectId("64f77f99cf3b7de1d4d48756"), name: 'mongo', x: 3 },
  { _id: ObjectId("64f77fa7cf3b7de1d4d48757"), name: 'Neo4j', x: 4 }
]

(These three documents are the dataset for all the query examples that follow.)

5. Querying (READ) — find()

5.1 find() Basics

  • List a collection's contents: db.myCollection.find()
  • If _id is omitted, MongoDB/drivers automatically generate one, typically an ObjectId.
  • Use it (shell helper) to show more results when find() returns more documents than fit on the screen.
  • findOne(...) returns only one document (the first match) instead of a cursor of many.

5.2 Relational (Comparison) Operators

General form: db.myCollection.find( <selection criterion> )

Operation Syntax Example
Equality { <key>: <value> } db.myCollection.find({ x: 3 })
Less than { <key>: { $lt: <value> } } db.myCollection.find({ x: { $lt: 3 } })
Less than or equal { <key>: { $lte: <value> } } db.myCollection.find({ x: { $lte: 3 } })
Greater than { <key>: { $gt: <value> } } db.myCollection.find({ x: { $gt: 3 } })
Greater than or equal { <key>: { $gte: <value> } } db.myCollection.find({ x: { $gte: 3 } })
Not equal { <key>: { $ne: <value> } } db.myCollection.find({ x: { $ne: 3 } })

Applied to the demo data (x values: value→3, mongo→3, Neo4j→4):

Query Documents returned
find({ x: 3 }) value, mongo
find({ x: { $lt: 3 } }) none
find({ x: { $lte: 3 } }) value, mongo
find({ x: { $gt: 3 } }) Neo4j
find({ x: { $gte: 3 } }) all three
find({ x: { $ne: 3 } }) Neo4j

Reading the syntax: the first { } is the filter document; inside it, a field name maps to either a plain value (equality) or an operator document ({ $gt: 3 }). Operators always start with $.

5.3 Logical Operators — AND, OR, $in

Operation Syntax Example
AND $and: [ {<key1>:<value1>}, {<key2>:<value2>}, ... ] db.myCollection.find({ $and: [ { name: "mongo" }, { x: 3 } ] })
OR $or: [ {<key1>:<value1>}, {<key2>:<value2>}, ... ] db.myCollection.find({ $or: [ { name: "mongo" }, { name: "Neo4j" } ] })
Alternative OR (same field, several values) { <key>: { $in: [ val1, val2, ... ] } } db.myCollection.find({ name: { $in: [ "mongo", "Neo4j" ] } })

Walkthrough:

  1. $and / $or take an array of condition documents.
  2. $and example → documents where name is "mongo" and x is 3 → returns the mongo document only.
  3. $or example → name is "mongo" or "Neo4j" → returns two documents.
  4. $in is a shorthand for an OR over one field with a list of allowed values — equivalent to the $or above, and shorter.

📌 Additional Example (added for clarity)

A comma-separated filter is an implicit AND: find({ name: "mongo", x: 3 }) does the same as the $and example. $and is needed mainly when you must repeat the same field, e.g. { $and: [ { x: { $gt: 1 } }, { x: { $lt: 4 } } ] }.

5.4 Projection — Choosing Which Fields to Return

Syntax:

db.myCollection.find( { <criterion> },
                      { <field1>: <selector>, <field2>: <selector>, ... } )
  • Selector = 1 → include the field.
  • Selector = 0 → exclude the field.
  • Rule: you generally cannot mix inclusion and exclusion in the same projection, except for _id.

Example (from the slide):

db.myCollection.find( { x: { $gt: 2 } }, { name: 1, _id: 0 } )

Walkthrough:

  1. First argument { x: { $gt: 2 } } — filter: only documents with x > 2.
  2. Second argument { name: 1, _id: 0 } — projection: return the name field and suppress _id (which is otherwise always included by default).
  3. Mixing name: 1 (include) with _id: 0 (exclude) is allowed because _id is the exception.
  4. Result on the demo data: { name: 'value' }, { name: 'mongo' }, { name: 'Neo4j' }.
  5. SQL analogy: projection ≈ the SELECT column list; the filter ≈ WHERE.

5.5 Sorting

Syntax:

<find query>.sort( { <field1>: <order>, <field2>: <order>, ... } )
  • Order = 1 → ascending.
  • Order = -1 → descending.

Example (from the slide):

db.myCollection.find( { x: { $gt: 2 } } ).sort( { name: 1 } )
  • Finds documents with x > 2 and sorts them by name ascending (≈ SQL ORDER BY name ASC).
  • Several fields can be listed; earlier fields take priority (e.g., .sort({ x: -1, name: 1 }) = highest x first, ties broken by name A→Z).

6. CRUD Operations: UPDATE

Syntax (as on the slide):

updateOne( { <field>: { <criterion> } },
           { $set: { <action> } } )
  • First argument = filter (which document(s)).
  • Second argument = update operation; $set modifies specific fields.
  • updateOne() affects the first matching document.
  • updateMany() modifies all matching documents.
db.myCollection.updateOne ( { x: 3 }, { $set: { name: "mongodb" } } )
db.myCollection.updateMany( { x: 3 }, { $set: { name: "mongodb" } } )

Walkthrough on the demo data (two documents have x: 3):

  • updateOne → only the first x: 3 document (value) gets name: "mongodb".
  • updateMany → both x: 3 documents (value and mongo) become name: "mongodb".
  • $set changes only the named field(s); other fields are left alone. (Without $set, a plain replacement document would overwrite the whole document — a common beginner error.)

Note on the slide: the syntax box shows a { multi: <selector> } option (selector true = more than one document). That belongs to the older update() method. With updateOne / updateMany you simply choose the method — no multi option is needed.

7. CRUD Operations: DELETE

  • deleteOne( { <criterion> } ) — deletes one (the first matching) document.
  • deleteMany( { <criterion> } ) — deletes all matching documents.
  • deleteMany( { } ) with an empty filter — deletes all documents in the collection (the collection itself and its indexes remain).
// statement 1: delete one document
db.myCollection.deleteOne( { x: 3 } )

// statement 2: delete all documents (empty filter matches everything)
db.myCollection.deleteMany( { } )

⚠️ Don't confuse: deleteMany({}) empties the collection but keeps it; drop() (Section 4.2) removes the collection itself. Relational analogy: DELETE FROM t; vs DROP TABLE t;.

📌 Example (added for clarity)

db.myCollection.deleteMany( { x: { $lt: 4 } } ) — deletes every document with x < 4 (here both x: 3 documents), leaving Neo4j.

8. Indexing

  • Indexes can be created on collections to improve the performance of frequently used queries.
  • Indexes:
    • Speed up find, update and remove queries.
    • Speed up sort queries.
    • Improve performance and scalability.
  • Trade-off: indexes improve read performance but add storage and write overhead. (Every insert/update must also maintain the index.)

8.1 Creating Indexes — createIndex()

Index type Example
Single-field, ascending (1) db.myCollection.createIndex( { name: 1 } )
Single-field, descending (-1) db.myCollection.createIndex( { name: -1 } )
Composite (several fields) db.myCollection.createIndex( { name: 1, x: -1 } )
  • 1 = ascending, -1 = descending.
  • A composite index orders by name ascending first, then by x descending within equal names. It supports queries on name alone or on name and x, and sorts matching that order.

8.2 Checking Whether an Index Is Used — explain()

db.myCollection.find( { name: "mongo" } ).explain("executionStats")
  • explain() shows the query plan and whether an index is being used.
  • Recommended to check whether a query performs an index scan (IXSCAN) rather than a collection scan (COLLSCAN — reads every document).

📌 Example (added for clarity)

With 1 000 000 documents, find({ name: "mongo" }) without an index must examine all 1 000 000 documents (collection scan). After createIndex({ name: 1 }), MongoDB jumps straight to the matching entries (index scan) and explain("executionStats") shows a tiny number of documents examined. The cost: the index takes extra disk space, and each insert/update/delete must also update it.

10. Questions & Memo

(Dataset for the code-tracing questions: collection myCollection holds {name:'value', x:3}, {name:'mongo', x:3}, {name:'Neo4j', x:4}.)

Section 2 — Concepts

Q1: Define MongoDB and state what a MongoDB database and a collection are.

A1: MongoDB is a document-oriented database designed for high-performance, highly available, horizontally scalable applications, built on collections and documents. A database is a logical container for collections. A collection is a group of documents within a single database; it does not enforce a schema, so documents in it can have different fields.

Q2: Give three differences between a MongoDB collection and a relational table.

A2: Any three: a collection does not enforce a schema (flexible; a table has a fixed schema); documents in a collection can have different fields (all table rows have the same columns); documents can contain arrays and embedded documents (table values must be atomic); collections are created implicitly on first insert (tables need CREATE TABLE).

Q3: Name two ways MongoDB can be deployed/scaled, and mention three features of MongoDB Atlas.

A3: MongoDB can run on a single server or be distributed across clusters for horizontal scaling. Atlas features (any three): multi-cloud support (AWS, Azure, Google Cloud); built-in security (encryption, access control, auditing); horizontal scaling/global clusters; automation (backups, monitoring, deployment, scaling); integrated tools (Compass, Charts, Atlas Search).

Q4: What is MongoDB Compass, and what is mongosh?

A4: Compass is a free, source-available GUI for querying, aggregating and analysing data visually (macOS, Windows, Linux). mongosh is the command-line shell using JavaScript-style helpers (show, use, db, help).

Q5: Give the JavaScript equivalent of use mydb and of show collections, and explain why they exist.

A5: use mydb ≡ db = db.getSiblingDB('mydb'); show collections ≡ db.getCollectionNames(). The shell helpers only work interactively; the JavaScript equivalents work in scripts and application code.

Q6: When is a database actually created after use mydb?

A6: When data is first stored in it. use only switches to (or names) the database; MongoDB creates it on first insert.

Section 3 — Data Types

Q7: Which type should you use for application date/time values — Timestamp or Date? Why?

A7: Date (created with new Date() or ISODate()). The Timestamp BSON type is primarily internal to MongoDB (replication/oplog).

Q8: Distinguish an embedded document from an ObjectId.

A8: An embedded document is a document nested inside another document (e.g., address: { city: "Pretoria" }). An ObjectId is the unique identifier MongoDB generates for a document's _id when one isn't supplied.

Q9: Why is the Code data type discouraged?

A9: Storing executable JavaScript in documents is rare and discouraged for security reasons.

Sections 4 & 5 — Create and Read

Q10: Must you call createCollection before inserting? Explain.

A10: No. insertOne/insertMany on a non-existent collection creates it implicitly. createCollection is optional.

Q11: What is the difference between insertOne and insertMany, and what happens if you omit _id?

A11: insertOne inserts one document; insertMany takes an array of documents. If _id is omitted, MongoDB automatically generates a unique _id (an ObjectId). A supplied _id must be unique.

Q12 (Code Tracing): What does db.myCollection.find({ x: { $gt: 3 } }) return?

A12: Only the Neo4j document (x: 4). The x: 3 documents are excluded because 3 is not strictly greater than 3.

Q13 (Code Tracing): What does db.myCollection.find({ x: { $ne: 3 } }) return, and what does find({ x: { $lt: 3 } }) return?

A13: $ne: 3 → the Neo4j document. $lt: 3 → nothing (an empty result), since no document has x below 3.

Q14 (Code Writing): Write queries for (a) documents where name is "mongo" and x is 3; (b) documents named "mongo" or "Neo4j" using $or; (c) the same as (b) using $in.

A14:

// (a)
db.myCollection.find({ $and: [ { name: "mongo" }, { x: 3 } ] })
// (b)
db.myCollection.find({ $or: [ { name: "mongo" }, { name: "Neo4j" } ] })
// (c)
db.myCollection.find({ name: { $in: [ "mongo", "Neo4j" ] } })

Q15 (Code Tracing): What does db.myCollection.find({ x: { $gt: 2 } }, { name: 1, _id: 0 }) return?

A15: The name field only (no _id) of every document with x > 2 — all three: {name:'value'}, {name:'mongo'}, {name:'Neo4j'}.

Q16: Explain the rule about mixing 1 and 0 in a projection.

A16: You generally cannot mix inclusion (1) and exclusion (0) in one projection, except for _id, which can be excluded (_id: 0) while other fields are included.

Q17 (Code Writing): Return all documents with x >= 3, sorted by name in descending order, showing only name and x.

A17:

db.myCollection.find( { x: { $gte: 3 } }, { name: 1, x: 1, _id: 0 } )
                .sort( { name: -1 } )

Q18: What does findOne() do and how does it differ from find()?

A18: findOne() returns a single document (the first match); find() returns a cursor over all matching documents (use it in the shell to see more).

Sections 6 & 7 — Update and Delete

Q19 (Code Tracing): After db.myCollection.updateOne({ x: 3 }, { $set: { name: "mongodb" } }), how many documents change? What if updateMany is used?

A19: updateOne changes one document — the first with x: 3. updateMany changes both x: 3 documents.

Q20: What does $set do, and what would happen if you omitted it and passed a plain document?

A20: $set modifies only the specified fields and leaves the rest intact. Without an update operator (plain replacement), the whole document would be replaced — or the update rejected, depending on the method used — so $set is the safe way to change individual fields.

Q21: Distinguish deleteMany({}), deleteOne({ x: 3 }) and drop().

A21: deleteOne({ x: 3 }) deletes one matching document. deleteMany({}) deletes all documents (empty filter matches everything) but leaves the (empty) collection. drop() removes the entire collection.

Section 8 — Indexing

Q22: State three benefits and one cost of indexes.

A22: Benefits: speed up find, update and remove; speed up sort; improve performance and scalability. Cost: extra storage and write overhead (indexes must be maintained on every write).

Q23 (Code Writing): Create (a) an ascending index on name; (b) a composite index on name ascending and x descending.

A23:

db.myCollection.createIndex( { name: 1 } )
db.myCollection.createIndex( { name: 1, x: -1 } )

Q24: How do you check whether a query uses an index, and what two outcomes might you see?

A24: Use .explain("executionStats"), e.g. db.myCollection.find({ name: "mongo" }).explain("executionStats"). The plan shows an index scan (index used — efficient) or a collection scan (every document read — slow on large collections).

Comparison Question

Q25: Compare MongoDB's find with SQL's SELECT: map the filter, projection and sort.

A25: Filter (first argument) ≈ WHERE (e.g., { x: { $gt: 3 } } ≈ WHERE x > 3). Projection (second argument) ≈ the SELECT column list ({ name: 1, _id: 0 } ≈ SELECT name). .sort({ f: 1 }) ≈ ORDER BY f ASC (-1 ≈ DESC). These are conceptual equivalents, not exact translations.
