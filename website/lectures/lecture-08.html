2. Cursors & Iteration

  • Cursor: an object used to iterate over the documents returned by a query.
  • find() does not hand back all documents as one big value; it returns a cursor that you step through.

2.1 Cursor Methods

Method Purpose
hasNext() Returns true if another document is available.
next() Returns the next document from the cursor.
printjson() Prints a value in a readable JSON-like format.
toArray() Converts the remaining cursor results into an array.

2.2 Coding Example 1 — Iterating Over a Cursor (from the slides)

Action JavaScript statement
1. Query testCollection and assign the resulting cursor to variable c const c = db.testCollection.find()
2. Print the full result set using a while loop while ( c.hasNext() ) printjson(c.next())
3. Manipulate the cursor as an array, e.g., print the document at array index 4 const documents = c.toArray() then printjson(documents[4])

Step-by-step walkthrough:

  1. const c = db.testCollection.find() — runs the query; c now holds a cursor, not an array.
  2. while ( c.hasNext() ) — loop condition: keep going as long as another document remains.
  3. printjson( c.next() ) — each pass fetches the next document (advancing the cursor) and prints it nicely.
  4. c.toArray() — pulls the remaining documents into a normal JavaScript array so they can be accessed by index (documents[4] is the 5th document, since indexes start at 0).
  5. Important: a cursor is consumed as you iterate. After the while loop in step 2, the cursor is exhausted, so calling toArray() on the same c would return an empty array — re-run find() to get a fresh cursor.

Note from the slides

Use explicit cursor iteration when you need to process or display returned documents individually.

3. Embedded (Nested) Documents

  • An embedded (nested) document is a document inside another document.

3.1 Coding Example — Creating the users Collection (from the slides)

doc = { username: "gooduser",
        contact: { phone: "012 420 1234", email: "champion@mybusiness.co.za" },
        access:  { level: 5, group: "dev" } }
db.users.insertOne(doc)

doc = { username: "serioususer",
        contact: { phone: "012 420 5678", email: "worker@mybusiness.co.za" },
        access:  { level: 3, group: "dev" } }
db.users.insertOne(doc)

Step-by-step walkthrough:

  1. Each user document has one simple field (username) and two embedded documents: contact (phone, email) and access (level, group).
  2. insertOne(doc) stores each as a separate document in the users collection; MongoDB adds an _id (ObjectId) to each automatically.
  3. Relational equivalent: this would normally be three tables (User, Contact, Access) linked by foreign keys; here everything about a user lives in one document.

3.2 Querying the Collection (from the slides)

use db
db.users.find()

Result (from the slide's mongosh screenshot): both documents are returned, each showing its auto-generated _id: ObjectId("..."), username, contact: { phone, email } and access: { level, group } — gooduser has level: 5, serioususer has level: 3.

3.3 Querying with Iteration & printjson (from the slides)

var c = db.users.find()
while (c.hasNext()) printjson(c.next())
  • Same documents, but printed one at a time in formatted JSON — the cursor pattern from Section 2.

3.4 Querying Embedded Documents — Two Approaches

Approach 1 — Match the whole embedded document (from the slides)

var c = db.users.find( { access: { level: 5, group: "dev" } } )
while ( c.hasNext() ) printjson( c.next() )

Step-by-step walkthrough:

  1. The query value for access is a complete embedded document: { level: 5, group: "dev" }.
  2. MongoDB matches only documents whose access field is exactly this sub-document — same fields, same values, same field order.
  3. Result: only gooduser (level: 5, group: "dev"); serioususer has level: 3, so it fails.
  4. Caution (from the slides): "Exact embedded-document matching considers the embedded document as a whole." So { group: "dev", level: 5 } (different order) or { level: 5 } (missing group) would not match.

Approach 2 — Match a specific field using dot notation (from the slides)

var c = db.users.find( { "access.level": 5 } )
while ( c.hasNext() ) printjson( c.next() )

Step-by-step walkthrough:

  1. "access.level" uses dot notation to reach inside the embedded document: field level of access.
  2. The quotes are required around a dotted field name.
  3. Only that one field is compared; other fields in access (e.g., group) are ignored, and order does not matter.
  4. Result: gooduser again — but this approach is more flexible (e.g., { "access.level": { $gt: 3 } } is possible; whole-document matching cannot do this).

Comparison

Aspect Whole-document match Dot notation
Syntax { access: { level: 5, group: "dev" } } { "access.level": 5 }
Matches on The entire embedded document One field inside it
Field order / extra fields Must match exactly Irrelevant
Typical use Rare — exact structure known Usual choice

4. Operations on Arrays

  • If a field holds an array, you can query for:
    1. An exact array match, or
    2. Specific values in the array.
  • If the array holds embedded documents, you can query specific fields in those documents using dot notation.
  • Sample inventory document: { "_id": 5, "type": "food", "item": "cake", "ratings": [5, 8, 9] }

4.1 Exact Match on an Array

  • The array field must match exactly the specified values AND element order.
db.inventory.find({ ratings: [ 5, 8, 9 ] })
  • Returns documents whose ratings is exactly [5, 8, 9] in that order. [9, 8, 5] or [5, 8, 9, 10] would not match.

4.2 Match an Array Element

db.inventory.find( { ratings: 5 } )
  • Returns documents where ratings contains 5 as one of its elements (e.g., [5, 8, 9], [2, 5], [5]).
  • Note the difference from 4.1: ratings: 5 (a scalar) = "contains"; ratings: [5, 8, 9] (an array) = "equals exactly."

4.3 Multiple Criteria on Array Elements — $gt / $lt Combined

db.inventory.find( { ratings: { $gt: 5, $lt: 9 } } )
  • Matches if one element satisfies > 5 and another element satisfies < 9, or a single element satisfies both.
  • Each condition can be met by a different element.

4.4 Multiple Criteria — $elemMatch

db.inventory.find( { ratings: { $elemMatch: { $gt: 5, $lt: 9 } } } )
  • Matches if the array contains at least one element that is BOTH greater than 5 AND less than 9 (i.e., a single element must meet all conditions).

Worked Example (added for step-by-step clarity) — { $gt: 5, $lt: 9 } vs $elemMatch

Test two documents: A ratings: [5, 8, 9] and B ratings: [5, 9].

Document Plain { $gt: 5, $lt: 9 } $elemMatch: { $gt: 5, $lt: 9 }
A [5, 8, 9] Match — 8 is >5 (and <9); also 5 is <9 Match — element 8 is both >5 and <9
B [5, 9] Match — 9 satisfies >5, and 5 satisfies <9 (different elements) No match — 5 is not >5, 9 is not <9; no single element satisfies both

Take-away: plain operators let different elements satisfy different conditions; $elemMatch forces one element to satisfy all of them.

4.5 Arrays of Embedded Documents (from the slides)

Sample document:

{ _id: 100, type: "food", item: "xyz", qty: 25, price: 2.5,
  ratings: [ 5, 8, 9 ],
  memos: [ { memo: "on time",  by: "shipping" },
           { memo: "approved", by: "billing"  } ] }

Query 1 — Any element with by: "shipping"

db.inventory.find( { 'memos.by': 'shipping' } )
  • Selects documents where memos is an array containing an embedded document whose by field equals 'shipping' (in any position).

Query 2 — First element specifically (array index in the path)

db.inventory.find( { 'memos.0.by': 'shipping' } )
  • Selects documents where the first element (index 0) of memos is a document whose by field is 'shipping'.

Step-by-step walkthrough (applied to the sample document):

  1. memos has two embedded documents: index 0 = {memo: "on time", by: "shipping"}, index 1 = {memo: "approved", by: "billing"}.
  2. Query 1 ('memos.by'): checks every element's by → index 0 matches → document returned.
  3. Query 2 ('memos.0.by'): checks only index 0 → by is 'shipping' → document returned.
  4. Contrast: 'memos.1.by': 'shipping' would not match this document, because index 1 has by: 'billing'; but 'memos.by': 'shipping' still would.

4.6 Summary of Array Query Forms

Goal Query form
Array equals exactly (values + order) { ratings: [5, 8, 9] }
Array contains a value { ratings: 5 }
Conditions met by any elements (possibly different) { ratings: { $gt: 5, $lt: 9 } }
Conditions met by one same element { ratings: { $elemMatch: { $gt: 5, $lt: 9 } } }
Field inside any embedded document in array { 'memos.by': 'shipping' }
Field inside embedded document at a specific index { 'memos.0.by': 'shipping' }

5. Aggregation

5.1 Example Collection — blogs

Listing of the blogs collection without _id (projection):

db.blogs.find( { }, { _id: 0, title: 1, likes: 1 } )
title likes
NoSQL 400
MongoDB 100
MongoDB 150
MongoDB 50
Neo4j 50
Neo4j 150
Neo4j 250

Step-by-step reading of the find:

  1. First argument { } — the filter; empty = all documents.
  2. Second argument { _id: 0, title: 1, likes: 1 } — the projection: 1 = include the field, 0 = exclude it. _id is shown by default, so it is explicitly switched off here.
  3. Totals worth remembering for later queries: NoSQL = 400; MongoDB = 100 + 150 + 50 = 300; Neo4j = 50 + 150 + 250 = 450.

5.2 Aggregation Functions (accumulators)

Function Purpose
$sum compute the sum
$avg compute the average
$min find the minimum value
$max find the maximum value
  • aggregate() method — syntax: db.COLLECTION_NAME.aggregate(AGGR_OPERATION)

5.3 The Aggregation Pipeline

  • An aggregation pipeline consists of one or more stages that process documents:
    • Each stage performs an operation on the input documents — e.g., filter documents, group documents, calculate values.
    • The documents output from a stage are passed to the next stage.
  • A pipeline can return results for groups of documents — e.g., total, average, maximum, minimum values.

Pipeline syntax:

db.collection.aggregate([
  { $match: <document criterion> },
  { $group: <group specification> },
  { $sort:  <sort specification> }
])
Stage Role SQL analogy (added for clarity)
$match Filters documents by a condition WHERE (before grouping) / HAVING (after grouping)
$group Groups documents by _id and computes accumulators GROUP BY + SUM/AVG/MIN/MAX
$sort Orders documents (1 = ascending, -1 = descending) ORDER BY

Reading tip: the pipeline is an array [ ... ] of stage objects { ... }, executed left-to-right / top-to-bottom; the order of stages matters.

5.4 Coding Example 1 — $sum: Total Likes per Title (from the slides)

db.blogs.aggregate( [
  { $group: {
      _id: "$title",
      num_likes: { $sum: "$likes" }
  } }
] )

Result (from the slide's screenshot):

{ _id: 'NoSQL',   num_likes: 400 }
{ _id: 'MongoDB', num_likes: 300 }
{ _id: 'Neo4j',   num_likes: 450 }

Step-by-step walkthrough:

  1. $group gathers documents into groups; _id: "$title" says "group by the value of the title field." (The $ prefix means "the value of this field.")
  2. num_likes: { $sum: "$likes" } creates a new output field num_likes = the sum of likes across every document in the group.
  3. The three groups: NoSQL (400), MongoDB (100+150+50 = 300), Neo4j (50+150+250 = 450).
  4. SQL equivalent: SELECT title, SUM(likes) AS num_likes FROM blogs GROUP BY title;
  5. Note: with no $sort, the order of groups is not guaranteed.

5.5 Coding Example 2 — $match then $group: Likes for One Title (from the slides)

Query: total number of likes for the title 'Neo4j'.

db.blogs.aggregate( [
  { $match: { title: "Neo4j" } },
  { $group: { _id: "$title", num_likes: { $sum: "$likes" } } }
] )

Result: [ { _id: 'Neo4j', num_likes: 450 } ]

Step-by-step walkthrough:

  1. Stage 1 — $match: { title: "Neo4j" }: filters the 7 documents down to the 3 Neo4j documents (likes 50, 150, 250).
  2. Stage 2 — $group: receives only those 3 documents, groups by title (one group) and sums likes → 450.
  3. SQL equivalent: SELECT title, SUM(likes) FROM blogs WHERE title = 'Neo4j' GROUP BY title;

5.6 Coding Example 3 — $group then $sort: Ascending Order (from the slides)

Query: total likes per title, shown in ascending order of number of likes.

db.blogs.aggregate( [
  { $group: { _id: "$title", num_likes: { $sum: "$likes" } } },
  { $sort:  { "num_likes": 1 } }
] )

Result (from the slide's screenshot):

{ _id: 'MongoDB', num_likes: 300 }
{ _id: 'NoSQL',   num_likes: 400 }
{ _id: 'Neo4j',   num_likes: 450 }

Step-by-step walkthrough:

  1. $group produces the three totals (as in 5.4).
  2. $sort: { "num_likes": 1 } — sorts those group results by num_likes; 1 = ascending (use -1 for descending).
  3. Result order: 300 → 400 → 450.
  4. Key idea: $sort works on the output of the previous stage (the new num_likes field), which only exists after $group.

5.7 Coding Example 4 — Three Stages: Group, Filter Totals, Sort (from the slides)

Query: total likes per title, only those with a total > 300, in ascending order.

db.blogs.aggregate([
  { $group: { _id: "$title", num_likes: { $sum: "$likes" } } },
  { $match: { num_likes: { $gt: 300 } } },
  { $sort:  { num_likes: 1 } }
])

Result: [ { _id: 'NoSQL', num_likes: 400 }, { _id: 'Neo4j', num_likes: 450 } ]

Step-by-step walkthrough:

  1. $group: NoSQL = 400, MongoDB = 300, Neo4j = 450.
  2. $match: { num_likes: { $gt: 300 } }: keeps groups with total greater than 300 → MongoDB (exactly 300) is excluded ($gt is strictly greater-than).
  3. $sort ascending: NoSQL (400) then Neo4j (450).
  4. Why the stage order matters: this $match comes after $group, so it filters on the computed total, not on individual documents. Placed before $group, it could only filter on the original fields (title, likes).

Highlighted on the slide

"The $match [after $group] is equivalent to the SQL HAVING."

SQL equivalent of the whole pipeline:

SELECT title, SUM(likes) AS num_likes
FROM   blogs
GROUP  BY title
HAVING SUM(likes) > 300
ORDER  BY num_likes ASC;

Note: the slide's screenshot shows the pipeline beginning with an empty { $match: { } } stage (which matches all documents and has no effect); the code listing on the slide omits it — both give the same result.

5.8 $match Before vs After $group — Comparison (added for clarity)

Position Filters on SQL equivalent Example
Before $group Original document fields WHERE { $match: { title: "Neo4j" } }
After $group Computed group values HAVING { $match: { num_likes: { $gt: 300 } } }

6. Data Model Design (refer to the MongoDB manual)

  • Key design decision: use embedded documents OR use references.

6.1 The Two Models

Aspect Embedded data model Referenced (normalised) data model
Where related data lives Within the same document In separate documents / collections
Relationship representation Nesting (sub-documents, arrays) References (e.g., a user_id field holding another document's _id)
Retrieval Often a single database operation Retrieve related documents separately, or use $lookup where appropriate
Best for Data frequently accessed together Avoiding duplication, complex relationships
SQL analogy Denormalised Foreign key / normalised

6.2 When to Use Embedded Data Models

  • You have "contains" or "has" relationships between entities.
  • You have one-to-many relationships where the "many" (child) documents always appear with / are viewed in the context of the "one" (parent) document.
  • Avoid embedding unbounded or continually growing arrays — MongoDB documents have a 16 MiB size limit.

Worked Example — Slide figure 4.3: Embedded model (user)

{
  _id: <ObjectId1>,
  username: "123xyz",
  contact: { phone: "123-456-7890", email: "xyz@example.com" },   // embedded sub-document
  access:  { level: 5, group: "dev" }                              // embedded sub-document
}
  • All related information about the user is in one document → one read returns username, contact and access.
  • This is the same structure as the users collection in Section 3.

6.3 When to Use Normalised (Referenced) Data Models

Use normalised data models:

  1. When embedding would result in duplication of data but would not provide sufficient read-performance advantages to outweigh the implications of the duplication.
  2. To represent more complex many-to-many relationships.
  3. To model large hierarchical data sets.

Worked Example — Slide figure: Normalised model (user, contact, access)

// user document
{ _id: <ObjectId1>, username: "123xyz" }

// contact document
{ _id: <ObjectId2>, user_id: <ObjectId1>, phone: "123-456-7890", email: "xyz@example.com" }

// access document
{ _id: <ObjectId3>, user_id: <ObjectId1>, level: 5, group: "dev" }

Step-by-step reading:

  1. The same information is now split into three documents (usually in three collections: user, contact, access).
  2. The user_id field in contact and access holds the _id of the user document (ObjectId1) — this reference (the highlighted field on the slide) plays the role of a foreign key.
  3. To assemble a full user profile the application must make extra queries (or use $lookup) — more work on read, but each piece of data is stored once, with no duplication.
  4. Compare with the embedded figure: same data, different trade-off — read speed & simplicity (embedded) vs no duplication & flexibility for many-to-many (referenced).

6.4 Decision Guide (added for clarity)

Situation Choose
User → their contact details & access level (always viewed together, one-to-one) Embed
Blog post → its comments (child always viewed with parent; bounded size) Embed
Blog post → millions of comments that keep growing Reference (risk of exceeding the 16 MiB document limit)
Students ↔ Courses (many-to-many) Reference
Same data would be copied into many documents with little read benefit Reference (normalise)

7. Questions & Memo

Section 2 — Cursors

Q1: What is a cursor in MongoDB, and what do hasNext(), next(), printjson() and toArray() do?

A1: A cursor is an object used to iterate over the documents returned by a query. hasNext() returns true if another document is available; next() returns the next document; printjson() prints a value in readable JSON format; toArray() converts the remaining cursor results into an array.

Q2 (Code Tracing): Explain what this code does and what documents[4] refers to: const c = db.testCollection.find(); const documents = c.toArray(); printjson(documents[4]).

A2: find() returns a cursor c; toArray() loads all its documents into an array documents; documents[4] is the 5th document (array indexes start at 0), which printjson prints. If c had already been iterated with next(), only the remaining documents would be in the array.

Section 3 — Embedded Documents

Q3: Distinguish between db.users.find({ access: { level: 5, group: "dev" } }) and db.users.find({ "access.level": 5 }).

A3: The first matches the entire embedded document — access must be exactly { level: 5, group: "dev" } (same fields, values and order). The second uses dot notation to match only the level field inside access; other fields (e.g., group) and field order are irrelevant.

Q4 (Code Tracing): In the users collection (gooduser: level 5; serioususer: level 3), which documents does db.users.find({ "access.level": 3 }) return?

A4: Only serioususer (its access.level is 3).

Q5: Why must the dotted field name in { "access.level": 5 } be written in quotes?

A5: Because access.level is not a valid plain JavaScript property name in an object literal; quoting it makes it a string key that MongoDB interprets as a path into the embedded document.

Section 4 — Arrays

Q6: Using { "_id": 5, "type": "food", "item": "cake", "ratings": [5, 8, 9] }, state whether it is returned by each query: (a) { ratings: [5, 8, 9] }, (b) { ratings: [9, 8, 5] }, (c) { ratings: 5 }, (d) { ratings: { $gt: 5, $lt: 9 } }, (e) { ratings: { $elemMatch: { $gt: 5, $lt: 9 } } }.

A6: (a) Yes — exact values and order. (b) No — order differs. (c) Yes — 5 is an element. (d) Yes — e.g., 8 satisfies both (and other elements can satisfy either). (e) Yes — element 8 is both > 5 and < 9.

Q7: What is the difference between { ratings: { $gt: 5, $lt: 9 } } and { ratings: { $elemMatch: { $gt: 5, $lt: 9 } } }? Give an array that matches the first but not the second.

A7: In the first, different elements may satisfy each condition; in the second, a single element must satisfy both. The array [5, 9] matches the first (9 > 5, 5 < 9) but not the second (no element is both > 5 and < 9).

Q8 (Code Tracing): Given memos: [ { memo: "on time", by: "shipping" }, { memo: "approved", by: "billing" } ], will { 'memos.0.by': 'shipping' } match? What about { 'memos.1.by': 'shipping' }? What about { 'memos.by': 'billing' }?

A8: 'memos.0.by': 'shipping' — Yes (index 0 has by: 'shipping'). 'memos.1.by': 'shipping' — No (index 1 has by: 'billing'). 'memos.by': 'billing' — Yes (any element's by is 'billing').

Q9: Write a query to list all inventory documents where an element of memos has by equal to 'shipping'.

A9: db.inventory.find( { 'memos.by': 'shipping' } )

Section 5 — Aggregation

Q10: Name the four accumulator functions in the lecture and describe an aggregation pipeline.

A10: $sum, $avg, $min, $max. An aggregation pipeline is made of one or more stages; each stage performs an operation (filter, group, calculate) on its input documents and passes its output to the next stage.

Q11 (Code Tracing): Using the blogs data, what does this return? db.blogs.aggregate([ { $group: { _id: "$title", num_likes: { $sum: "$likes" } } } ])

A11: One document per distinct title with total likes: { _id: 'NoSQL', num_likes: 400 }, { _id: 'MongoDB', num_likes: 300 }, { _id: 'Neo4j', num_likes: 450 } (order not guaranteed).

Q12 (Code Tracing): What does db.blogs.aggregate([ { $match: { title: "Neo4j" } }, { $group: { _id: "$title", num_likes: { $sum: "$likes" } } } ]) return?

A12: [ { _id: 'Neo4j', num_likes: 450 } ] — $match keeps the three Neo4j documents (50, 150, 250), and $group sums them.

Q13: In { $sort: { "num_likes": 1 } }, what does 1 mean and what would -1 do?

A13: 1 sorts in ascending order; -1 sorts in descending order.

Q14 (Code Tracing): What does the three-stage pipeline [ $group (sum likes by title), $match { num_likes: { $gt: 300 } }, $sort { num_likes: 1 } ] return for the blogs data, and why is MongoDB not in the result?

A14: [ { _id: 'NoSQL', num_likes: 400 }, { _id: 'Neo4j', num_likes: 450 } ]. MongoDB's total is exactly 300, and $gt: 300 means strictly greater than, so it is excluded.

Q15: Which SQL clause is equivalent to a $match placed after a $group stage? Explain how it differs from a $match placed before it.

A15: HAVING. A $match after $group filters on computed group results (e.g., num_likes); a $match before $group filters the original documents (like WHERE).

Q16: Write a pipeline to return the average likes per title, highest average first.

A16:

db.blogs.aggregate([
  { $group: { _id: "$title", avg_likes: { $avg: "$likes" } } },
  { $sort:  { avg_likes: -1 } }
])

(Result for the sample data: Neo4j 150, NoSQL 400, MongoDB 100 → sorted: NoSQL 400, Neo4j 150, MongoDB 100.)

Q17: Explain the projection db.blogs.find( { }, { _id: 0, title: 1, likes: 1 } ).

A17: The empty filter { } selects all documents; the projection excludes _id (0) and includes only title and likes (1).

Section 6 — Data Model Design

Q18: What is the key design decision for the structure of a MongoDB database?

A18: Whether to use embedded documents or references between documents.

Q19: State two situations in which an embedded model is appropriate and one in which it should be avoided.

A19: Appropriate: "contains/has" relationships; one-to-many relationships where the child documents are always viewed with the parent. Avoid: embedding unbounded or continually growing arrays, because of the 16 MiB document size limit.

Q20: List the three situations in which a normalised (referenced) model is recommended.

A20: (1) When embedding would cause duplication without sufficient read-performance advantage; (2) to represent complex many-to-many relationships; (3) to model large hierarchical data sets.

Q21: In the normalised user/contact/access figure, what is the purpose of the user_id field, and how can related documents be retrieved together?

A21: user_id holds the _id of the related user document — a reference (like a foreign key) linking the contact/access documents to the user. Related documents can be fetched with separate queries or combined using $lookup.

Q22 (Scenario): A blog application stores posts and their comments. Comments are always displayed with their post, and each post gets at most a few dozen comments. Embed or reference? How would your answer change if posts received millions of comments?

A22: Embed the comments as an array of nested documents in the post — a bounded one-to-many "has" relationship where children are viewed with the parent, allowing one read to retrieve everything. With millions of comments, use references (a separate comments collection with a post_id), since an ever-growing array risks exceeding the 16 MiB document limit.

Revision Tip: The exam is likely to test (a) tracing queries against a small sample collection — dot notation on embedded documents, exact array match vs element match, $gt/$lt vs $elemMatch, and 'memos.0.by'-style paths; (b) tracing aggregation pipelines stage by stage ($match → $group → $sort), including the $match ≈ HAVING point and strict $gt boundaries; (c) writing a pipeline from a plain-English requirement (e.g., total/average per group, filtered and sorted); and (d) embed vs reference design decisions with justification (one-to-many "has" → embed; many-to-many / duplication / unbounded growth → reference; 16 MiB limit). Operator Parameters Purpose Example filter

7. Aggregation functions and operators

Accumulators inside $group

Operator Parameters Purpose Example inside $group
$sum "$field" Sum a field total:{$sum:"$grade"}

Complete aggregation example

db.students.aggregate([
  { $match: { year: 2 } },

  { $group: {
      _id: "$course",
      averageGrade: { $avg: "$grade" },
      totalStudents: { $sum: 1 },
      highestGrade: { $max: "$grade" }
  }},

  { $sort: { averageGrade: -1 } }
])

Filters second-year students, groups by course, calculates statistics and sorts by average grade.
