4. Function Examples

4.1 Predicate EXISTS (from the slides)

Query: list all nodes with a name property and true/false indicating whether they follow someone.

MATCH (n)
WHERE (n.name) IS NOT NULL
RETURN n.name AS name, EXISTS( (n)-[:FOLLOWS]->() ) AS isAfollower

Result (slide screenshot):

name isAfollower
"Thandi" true
"Johan" true
"Neo" false
"Melanie" true

Step-by-step walkthrough:

  1. MATCH (n) — every node; WHERE (n.name) IS NOT NULL keeps only nodes that have a name property.
  2. EXISTS( (n)-[:FOLLOWS]->() ) — a predicate that tests whether at least one outgoing FOLLOWS relationship exists from n (end node anonymous ()); returns true/false.
  3. AS isAfollower — names the output column.
  4. Result: Thandi (follows Johan & Neo), Johan (follows Thandi), Melanie (follows Johan) → true; Neo has no outgoing FOLLOWS → false.
  5. Note: in newer Neo4j versions the pattern-test form is written with braces — EXISTS { (n)-[:FOLLOWS]->() } — check which form your installed version accepts.

4.2 Scalar Function LENGTH (from the slides)

Query: for all paths of length 2, list the node names and the path length.

MATCH p = (a)-->(b)-->(c)
RETURN a.name, b.name, c.name, length(p);

Result (slide screenshot):

a.name b.name c.name length(p)
"Johan" "Thandi" "Neo" 2
"Johan" "Thandi" "Johan" 2
"Melanie" "Johan" "Thandi" 2
"Thandi" "Johan" "Thandi" 2

Step-by-step walkthrough:

  1. p = (a)-->(b)-->(c) — assigns the whole path to variable p; the pattern is two directed hops (any relationship type).
  2. length(p) — a scalar function returning the number of relationships in the path → always 2 here.
  3. Why four rows? Following the arrows in the graph:
    • Johan → Thandi → Neo; Johan → Thandi → Johan (back again).
    • Melanie → Johan → Thandi.
    • Thandi → Johan → Thandi (back again).
    • Thandi → Neo → (nothing: Neo has no outgoing relationship); so no path.
  4. Key rule: within one path Cypher never uses the same relationship twice, but nodes may repeat (that is why "Johan → Thandi → Johan" is allowed: two different relationships).

4.3 Collection Function NODES (from the slides)

Query: for all paths of length 2 between Melanie and Thandi, show the nodes in the path p.

MATCH p = (a)-->(b)-->(c)
WHERE a.name = "Melanie" AND c.name = "Thandi"
RETURN nodes(p)

Result (slide screenshot): one path — nodes Melanie → Johan → Thandi.

Step-by-step walkthrough:

  1. The same 2-hop pattern, but WHERE forces the start node to be Melanie and the end node to be Thandi.
  2. The only matching path is Melanie → Johan → Thandi.
  3. nodes(p) returns the list of nodes along the path p (Melanie, Johan, Thandi) — a collection function.
  4. Equivalent query (shown on the slide): RETURN a, b, c returns the same three nodes, as separate columns instead of one list.
  5. Related collection functions: relationships(p) (the relationships in the path), labels(n) (a node's labels).

4.4 Mathematical Function abs (from the slides)

MATCH (a), (b)
WHERE a.name = "Thandi" AND b.name = "Neo"
RETURN a.age, b.age, abs(a.age - b.age);

Result (slide screenshot):

a.age b.age ageDifference
20 22 2

Step-by-step walkthrough:

  1. MATCH (a), (b) — two separate node patterns (no relationship between them required).
  2. WHERE picks Thandi as a and Neo as b.
  3. abs(a.age - b.age) — absolute value of the age difference: |20 − 22| = 2.
  4. (The slide screenshot labels the column ageDifference, which implies an alias AS ageDifference — the code on the slide omits it; without an alias the column header would be the expression text.)

4.5 String Function toUpper (from the slides)

MATCH (psn:Person)
RETURN toUpper(psn.name) AS upperCaseName;

Result (slide screenshot): "THANDI", "JOHAN", "NEO", "MELANIE".

  • toUpper returns the original strings in uppercase; related: toLower, substring, trim.

5. Database Operations — Patterns & Paths

5.1 Variable-Length Patterns (from the slides)

Query: all Persons that are 1 or 2 links away from Melanie.

MATCH (psM:Person {name:"Melanie"})-[*1..2]-(psn)
RETURN DISTINCT psn.name;

Result (slide screenshot): Johan, Thandi.

Step-by-step walkthrough:

  1. -[*1..2]- — a variable-length relationship pattern: a path of 1 to 2 relationships, of any type.
  2. No arrowhead (- … -) → relationships can be traversed in either direction.
  3. Melanie's 1-hop neighbour: Johan. 2 hops: Johan's neighbour Thandi. (Neo is 3 hops away — Melanie → Johan → Thandi → Neo — so he is excluded.)
  4. RETURN DISTINCT removes duplicate names (the same person can be reached by more than one route).

Variable-length syntax cheat-sheet (added for clarity)

Pattern Meaning
-[*]- Any number of relationships (1 or more)
-[*2]- Exactly 2
-[*1..2]- Between 1 and 2
-[*..5]- Up to 5 (maximum 5)
-[*3..]- 3 or more
-[:FOLLOWS*1..3]-> Between 1 and 3 FOLLOWS relationships, following direction

5.2 shortestPath (from the slides)

Query: the shortest path from Johan to Neo.

MATCH p = shortestPath(
  (psJ:Person {name:"Johan"})-[*]-(psN:Person {name:"Neo"})
)
RETURN p

Result (slide screenshot): a graph showing Johan – Thandi – Neo (Johan ⇄ Thandi, Thandi → Neo).

Step-by-step walkthrough:

  1. shortestPath( … ) finds the path with the fewest relationships between the two start/end nodes.
  2. -[*]- — any length, either direction (no arrowheads). Here the arrows happen to line up (Johan → Thandi → Neo), but ignoring direction is the general approach for "how connected are these two?"
  3. RETURN p returns all nodes and relationships on the path.
  4. Only one shortest path exists: Johan → Thandi → Neo, length 2.

5.3 shortestPath with a Search Limit (from the slides)

MATCH p = shortestPath(
  (psJ:Person {name:"Johan"})-[*..5]-(psN:Person {name:"Neo"})
)
RETURN psJ.name, psN.name, length(p)

Result (slide screenshot):

psJ.name psN.name length(p)
"Johan" "Neo" 2
  • [*..5] limits the search to paths of at most 5 relationships — important in large graphs to avoid expensive unbounded searches.
  • length(p) = 2 — the number of relationships in the shortest path.

7. Importing Data into Neo4j (CSV)

  • Reference: Neo4j documentation — Importing CSV files with Cypher (LOAD CSV).
  • Tutorial files:
    • persons.csv — a list of persons.
    • movies.csv — a list of movies.
    • roles.csv — the roles played by persons in each movie.
  • Where the CSV can be: on the database server, accessed with a file:/// URL, or over HTTPS, HTTP or FTP.
  • In Neo4j Desktop: CSV files can be imported using the import tool feature.

7.1 Importing Persons (from the slides)

persons.csv (sample): header id, name → 1, Charlie Sheen; 2, Oliver Stone; 3, Michael Douglas; 4, Martin Sheen; 5, Morgan Freeman.

// Create constraint for uniqueness
CREATE CONSTRAINT person_id_unique IF NOT EXISTS
FOR (person:Person) REQUIRE person.id IS UNIQUE;

LOAD CSV WITH HEADERS FROM "file:///persons.csv" AS csvLine
MERGE (person:Person {id: toInteger(csvLine.id)})
SET person.name = csvLine.name;

Step-by-step walkthrough:

  1. CREATE CONSTRAINT … IF NOT EXISTS — makes id unique among Person nodes; IF NOT EXISTS avoids an error if the constraint was already created.
  2. LOAD CSV WITH HEADERS FROM "file:///persons.csv" AS csvLine — reads the file one row at a time; WITH HEADERS means the first line holds column names, so each row is a map accessed as csvLine.id, csvLine.name.
  3. MERGE (person:Person {id: toInteger(csvLine.id)}) — match or create a person by id. toInteger() is needed because CSV values are read as strings.
  4. SET person.name = csvLine.name — sets the name property.
  5. Why MERGE and not CREATE? Re-running the import doesn't create duplicates (and the uniqueness constraint would reject them anyway).

7.2 Importing Movies (from the slides)

movies.csv (sample): header id, title, country, year → 1, Wall Street, USA, 1987; 2, The American President, USA, 1995; 3, The Shawshank Redemption, USA, 1994.

CREATE CONSTRAINT movie_id_unique IF NOT EXISTS
FOR (movie:Movie) REQUIRE movie.id IS UNIQUE;

// Optional: index for Country name
CREATE INDEX country_name_index IF NOT EXISTS
FOR (country:Country) ON (country.name);

LOAD CSV WITH HEADERS FROM "file:///movies.csv" AS csvLine
MERGE (country:Country {name: csvLine.country})
MERGE (movie:Movie {id: toInteger(csvLine.id)})
SET movie.title = csvLine.title,
    movie.year  = toInteger(csvLine.year)
MERGE (movie)-[:MADE_IN]->(country);

Step-by-step walkthrough:

  1. A uniqueness constraint on Movie.id, plus an optional index on Country.name (for efficient lookup).
  2. For each CSV row: MERGE (country:Country {name: …}) — create the country once (the three USA rows share one Country node).
  3. MERGE (movie:Movie {id: …}) + SET — create the movie and set its title and year (year converted with toInteger).
  4. MERGE (movie)-[:MADE_IN]->(country) — creates the relationship (also idempotent).
  5. Result for the sample rows: 3 Movie nodes, 1 Country {name:"USA"} node, 3 MADE_IN relationships.
  6. Design note: the country was a column in the CSV, but is modelled as a separate node — a typical graph modelling decision (it lets you traverse movie → country and count/group by country).

7.3 Importing Roles (from the slides)

roles.csv (sample): header personId, movieId, role → 1, 1, Bud Fox; 4, 1, Carl Fox; 2, 1, Gordon Gekko; 4, 2, A.J. MacInerney.

CREATE CONSTRAINT person_id_unique IF NOT EXISTS
FOR (person:Person) REQUIRE person.id IS UNIQUE;
CREATE CONSTRAINT movie_id_unique IF NOT EXISTS
FOR (movie:Movie) REQUIRE movie.id IS UNIQUE;

LOAD CSV WITH HEADERS FROM "file:///roles.csv" AS csvLine
MATCH (person:Person { id: toInteger(csvLine.personId) }),
      (movie:Movie   { id: toInteger(csvLine.movieId)  })
MERGE (person)-[:PLAYED {role: csvLine.role}]->(movie);

Step-by-step walkthrough:

  1. This file contains no new entities, only links — so for each row it MATCHes the existing person and movie (using the ids imported earlier).
  2. MERGE (person)-[:PLAYED {role: …}]->(movie) creates a PLAYED relationship carrying the role as a relationship property.
  3. Order matters: import persons and movies first, then roles — otherwise the MATCH finds nothing and no relationships are created.
  4. Relational analogy: roles.csv looks like a junction (many-to-many) table with two foreign keys (personId, movieId) plus an attribute (role). In the graph it becomes a relationship with a property — no join table needed.
  5. Sample result: Martin Sheen (id 4) gets two PLAYED relationships — to Wall Street (as Carl Fox) and to The American President (as A.J. MacInerney).

7.4 CSV → Graph Mapping Summary (added for clarity)

CSV file Becomes Cypher pattern

movies.csv Movie nodes + Country nodes + MADE_IN relationships MERGE ×3

8. Homework 1 — Movie Graph Queries

After importing the three CSV files, write Cypher for the following. The answers below are suggested solutions (added) — verify them in your own database.

Basic Entity Exploration

// 1. List all persons
MATCH (p:Person) RETURN p;                       // or RETURN p.name

// 2. List all movies
MATCH (m:Movie) RETURN m;                        // or RETURN m.title

// 3. List all countries associated with movies
MATCH (m:Movie)-[:MADE_IN]->(c:Country)
RETURN DISTINCT c.name;

Relationship Exploration

// 4. Who played which role in which movie
MATCH (p:Person)-[r:PLAYED]->(m:Movie)
RETURN p.name, r.role, m.title;

// 5. How many roles each person played
MATCH (p:Person)-[r:PLAYED]->(:Movie)
RETURN p.name, count(r) AS roles;

// 6. All movies Morgan Freeman acted in
MATCH (:Person {name:"Morgan Freeman"})-[:PLAYED]->(m:Movie)
RETURN m.title;

Graph Structure & Traversal

// 7. Full path from actor to country via movie
MATCH path = (p:Person)-[:PLAYED]->(m:Movie)-[:MADE_IN]->(c:Country)
RETURN path;

// 8. Actors who appeared in movies made in the USA
MATCH (p:Person)-[:PLAYED]->(:Movie)-[:MADE_IN]->(c:Country {name:"USA"})
RETURN DISTINCT p.name;

Aggregation & Analysis

// 9. Number of movies per country
MATCH (m:Movie)-[:MADE_IN]->(c:Country)
RETURN c.name, count(m) AS movies;

// 10. Most frequent role name
MATCH ()-[r:PLAYED]->()
RETURN r.role, count(*) AS uses
ORDER BY uses DESC
LIMIT 1;

Notes on the solutions:

  1. Query 3 uses DISTINCT because the pattern returns one row per movie, so a country shared by several movies (e.g., USA) would otherwise appear several times.
  2. Query 5 groups by p.name implicitly (Lecture 18 aggregation); people with no roles don't appear (use OPTIONAL MATCH to include them with 0).
  3. Query 6 depends on the full data files — the sample rows shown on the slides don't include a Morgan Freeman role.
  4. Query 7 returns paths, which the graph view draws as Person → Movie → Country.
  5. Query 10: ORDER BY … DESC LIMIT 1 returns one top row; if several roles tie, the others are not shown.

9. Homework 2 — Meaning of Four MATCH Patterns

Pattern Meaning
MATCH (psn:Person)-->(psm) A Person with any outgoing relationship of any type to any node psm.
MATCH (psn:Person)-[:FOLLOWS]-(followed) A Person connected by a FOLLOWS relationship in either direction (no arrowhead — psn follows them or they follow psn). The variable name followed is misleading here since direction is ignored.
MATCH (psn:Person)-[:FOLLOWS]->(followed) Outgoing FOLLOWS: psn follows followed.
MATCH (psn:Person)<-[:FOLLOWS]-(follower) Incoming FOLLOWS: follower follows psn (the arrow points to psn).

Applied to Thandi in this lecture's graph: outgoing FOLLOWS → Johan, Neo; incoming FOLLOWS → Johan; undirected FOLLOWS → Johan (twice, once per direction) and Neo.

10. Data Models for Graph Databases

10.1 The Property Graph Model

  • Information is modelled using three basic building blocks:
    1. Node (a.k.a. vertex).
    2. Relationship (edge, with direction & type; labelled and directed).
    3. Property (a.k.a. attribute) on nodes and relationships.
  • More specifically, the graph model is a labelled and directed multigraph:
    • Labelled graph: a label (type) for each edge.
    • Directed graph: edges with fixed direction.
    • Multigraph: multiple edges are allowed between two nodes.
  • Many graph-theory algorithms are available, e.g., shortest path, closeness, betweenness.
  • Neo4j uses the property graph model.

📌 Example — Multigraph (added for clarity)

In this lecture's graph, Thandi → Johan and Johan → Thandi are two edges between the same two nodes (opposite directions). A multigraph would also allow two FOLLOWS edges in the same direction between them (e.g., a follow, an unfollow and a re-follow, each with its own since).

10.2 Neo4j Graph Data Modelling — The Reference Example

  • Reference: Neo4j "Graph database concepts" appendix.

📌 Worked Example — Slide figures: entities & relationships

(:Person:Actor { name: 'Tom Hanks', born: 1956 })
      -[:ACTED_IN { roles: ['Forrest'] }]->
(:Movie { title: 'Forrest Gump', released: 1994 })
      <-[:DIRECTED]-
(:Person { name: 'Robert Zemeckis', born: 1951 })

Step-by-step reading:

  1. Three nodes: two with label Person (Tom Hanks also has the second label Actor → a node can have multiple labels) and one Movie.
  2. Two relationships: ACTED_IN (Tom Hanks → Forrest Gump) and DIRECTED (Robert Zemeckis → Forrest Gump).
  3. Relationship properties: ACTED_IN carries roles: ['Forrest'] — a list-valued property on a relationship.
  4. Direction (highlighted on the slide): the Tom Hanks node has an outgoing relationship, while the Forrest Gump node has an incoming relationship (and note Forrest Gump has two incoming relationships).
  5. Types vs labels: labels (Person, Actor, Movie) classify nodes; relationship types (ACTED_IN, DIRECTED) name relationships; properties hold the details.

10.3 NoSQL Data Models — Size vs Complexity

  • Slide diagram (Neo Technology) positions the main NoSQL categories on size (vertical) vs complexity (horizontal):
Category Size Complexity
Key-value stores Highest Lowest
Bigtable clones (wide-column) ↓ ↓
Document databases ↓ ↓
Graph databases Lower ("still billions of nodes & relationships") Highest
  • Message: as you move from key-value → wide-column → document → graph, the data model gets richer/more complex while the maximum scale is somewhat lower — but graph databases still handle billions of nodes and relationships, which covers the large majority of use cases (the diagram's dashed line marks "90% of use cases").

11. Homework 3 — Weaknesses of Relational DBs and How Neo4j Avoids Them

11.1 The Four Weaknesses (from the slide)

  1. Normalisation leads to relations that do not correspond to entities in the "real world"; information is obtained by joining two or more tables.
  2. Semantic overloading: no mechanism to distinguish between relations and relationships, or between different types of relationships.
  3. Schema changes are difficult: a database change requires program changes.
  4. Designed for content-based associative access — poor for navigational access: movement between records is not supported (except through stored procedures).

11.2 How Neo4j Avoids Them — Suggested Answer (added; check against your own notes/reading)

Relational weakness How Neo4j addresses it
1. Normalised tables ≠ real-world entities; joins needed Each real-world entity is one node (with its properties), and its connections are stored as relationships — related data is reached by traversing relationships, not by joins (e.g., Person –PLAYED→ Movie –MADE_IN→ Country).
2. Semantic overloading Relationships are first-class, each with an explicit type (FOLLOWS, ACTED_IN, MADE_IN), a direction and properties, while labels classify nodes — so entities and different kinds of relationship are clearly distinguished.
3. Schema changes are difficult Flexible schema: nodes can have different properties; new labels, relationship types or properties can be added without restructuring the whole database or rewriting existing queries. (Constraints/indexes are optional.)
4. Poor navigational access Graph databases are built for navigation: relationships are stored with the nodes, so you can move from node to node along relationships natively — and Cypher has variable-length patterns and shortestPath (Section 5) — without stored procedures.

Section 5 & 6 — Patterns, Paths, Algorithms

Q9 (Code Tracing): Explain MATCH (psM:Person {name:"Melanie"})-[*1..2]-(psn) RETURN DISTINCT psn.name; and give its result.

A9: It finds every node reachable from Melanie via 1 or 2 relationships of any type, in either direction (no arrowheads), returning each name once (DISTINCT). Result: Johan (1 hop) and Thandi (2 hops); Neo is 3 hops away so is excluded.

Q10: Explain the notations [*], [*2], [*..5], [*3..].

A10: [*] — any length; [*2] — exactly 2 relationships; [*..5] — at most 5; [*3..] — at least 3.

Q11 (Code Tracing): What does the shortestPath query from Johan to Neo return, and what is its length?

A11: The path Johan – Thandi – Neo, containing the nodes and relationships along it; length(p) = 2.

Q12: Why add a limit such as [*..5] inside shortestPath?

A12: It limits the search to paths of at most 5 relationships, keeping the search efficient in large graphs.

Q13: Name three algorithms from Neo4j's graph data science library.

A13: Any three of: shortest path, all paths, all simple paths, Dijkstra, A* search.

Section 7 — Importing Data

Q14: Where can CSV files for LOAD CSV be located?

A14: On the database server (via a file:/// URL) or via HTTPS, HTTP or FTP; in Neo4j Desktop the import tool can also be used.

Q15 (Code Tracing): Explain each line: LOAD CSV WITH HEADERS FROM "file:///persons.csv" AS csvLine MERGE (person:Person {id: toInteger(csvLine.id)}) SET person.name = csvLine.name;

A15: LOAD CSV WITH HEADERS … AS csvLine reads the file row by row, using the header row as field names; MERGE matches or creates a Person node with that integer id (toInteger converts the string from the CSV); SET sets its name property from the same row.

Q16: Why is toInteger() used on csvLine.id and csvLine.year?

A16: LOAD CSV reads every value as a string; toInteger converts it to a number so the property is stored as an integer (and comparisons/sorting work numerically).

Q17: Why use MERGE rather than CREATE in imports, and what is the purpose of CREATE CONSTRAINT … IF NOT EXISTS?

A17: MERGE avoids duplicate nodes/relationships if the import is run more than once (and for shared values like the USA country). The constraint enforces unique ids; IF NOT EXISTS prevents an error if the constraint already exists.

Q18 (Code Tracing): After importing movies.csv (three rows, all USA), how many Country nodes and MADE_IN relationships exist?

A18: 1 Country node (MERGE reuses it) and 3 MADE_IN relationships (one per movie).

Q19: Why must roles.csv be imported after the persons and movies, and what does it create?

A19: Because it uses MATCH to find the existing person and movie by id — if they don't exist yet, nothing matches and no relationships are created. It creates PLAYED relationships with a role property.

Section 8 & 9 — Homework

Q20: Write a query that shows each person with the number of roles they played.

A20: MATCH (p:Person)-[r:PLAYED]->(:Movie) RETURN p.name, count(r) AS roles;

Q21: Write a query for the actors who appeared in movies made in the USA.

A21: MATCH (p:Person)-[:PLAYED]->(:Movie)-[:MADE_IN]->(:Country {name:"USA"}) RETURN DISTINCT p.name;

Q22: Distinguish between (psn:Person)-->(psm), (psn:Person)-[:FOLLOWS]-(x), (psn:Person)-[:FOLLOWS]->(x) and (psn:Person)<-[:FOLLOWS]-(x).

A22: (1) any outgoing relationship of any type; (2) FOLLOWS in either direction; (3) outgoing FOLLOWS — psn follows x; (4) incoming FOLLOWS — x follows psn.

Section 10 — Data Models

Q23: Describe the property graph model and explain "labelled and directed multigraph".

A23: Built from nodes, relationships (with direction and type) and properties (on nodes and relationships). Labelled — each edge has a label/type; directed — edges have a fixed direction; multigraph — multiple edges may exist between the same two nodes.

Q24: In the Tom Hanks / Forrest Gump example, identify the node labels, relationship types, a relationship property and the direction of each relationship.

A24: Labels: Person, Actor (Tom Hanks has both), Movie. Relationship types: ACTED_IN and DIRECTED. Relationship property: roles: ['Forrest'] on ACTED_IN. Direction: ACTED_IN goes from Tom Hanks to the movie (outgoing for Tom, incoming for the movie); DIRECTED goes from Robert Zemeckis to the movie.

Q25: According to the Neo Technology diagram, how do graph databases compare with other NoSQL categories on size and complexity?

A25: They handle the most complex data model but at somewhat lower size than key-value/wide-column/document stores — yet still billions of nodes and relationships, enough for the vast majority of use cases.

Section 11 — Relational Weaknesses

Q26: List the four weaknesses of relational DB systems from the homework.

A26: (1) Normalisation → relations don't match real-world entities; joins needed. (2) Semantic overloading — no way to distinguish relations from relationships or relationship types. (3) Schema changes are difficult and require program changes. (4) Poor for navigational access (designed for content-based associative access).

Q27 (Scenario): A social network needs to find "friends of friends" up to three levels away. Explain why a graph database is more suitable than a relational database and write the Cypher.

A27: In a relational DB each extra level requires another self-join of a large "friendships" table (expensive as depth grows); in a graph DB the relationships are stored with the nodes and traversed directly, so depth costs little. Cypher:

MATCH (me:Person {name:"Thandi"})-[:FOLLOWS*1..3]-(other:Person)
WHERE other <> me
RETURN DISTINCT other.name;
