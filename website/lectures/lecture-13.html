2. Introduction to NewSQL

  • NewSQL is a term for a class of modern database management systems designed to support high-performance OLTP while retaining:
    • the relational data model,
    • SQL querying, and
    • strong transactional guarantees (ACID) associated with traditional relational systems.
  • The problem with traditional relational DBs: mature SQL support and reliable transactions, but scaling very large transactional workloads across multiple servers introduces architectural and operational challenges.
  • The NoSQL response: emerged to address flexible data models, distributed storage and horizontal scalability — but NoSQL systems differ considerably in their query languages, data models and transaction guarantees.
  • NewSQL aims to combine the strengths of relational databases with the scalability and distributed processing needed by modern applications.
  • The central idea: NewSQL seeks to provide relational data management, SQL support, ACID transactions and improved horizontal scalability within a modern database architecture.

Example (added for clarity)

Think of a bank. A traditional relational DBMS on one big server gives you SQL and safe transfers, but one server eventually can't keep up with millions of customers. A typical NoSQL store scales out easily but may offer weaker transaction guarantees. NewSQL is the attempt to get both — safe SQL transactions spread over many servers.

3. ACID Transactions and OLTP

3.1 The ACID Properties

Property Meaning (from the slides)
A — Atomicity A transaction is completed entirely, or its changes are rolled back.
C — Consistency A transaction preserves the database's defined integrity constraints and consistency rules.
I — Isolation Concurrent transactions behave according to the database's specified isolation guarantees.
D — Durability Once committed, changes persist despite failures covered by the system's durability guarantees.

Worked Example (added) — Transferring R500 from Account A to Account B

BEGIN;
UPDATE Account SET balance = balance - 500 WHERE accNo = 'A';
UPDATE Account SET balance = balance + 500 WHERE accNo = 'B';
COMMIT;

Step-by-step walkthrough:

  1. Atomicity: if the server crashes after the debit but before the credit, the whole transaction is rolled back — the R500 does not vanish.
  2. Consistency: rules such as "balance ≥ 0" or "total money in the system is unchanged" must hold after the transaction.
  3. Isolation: while the transfer runs, another transaction reading A's and B's balances must not see the half-finished state (debited but not yet credited).
  4. Durability: after COMMIT, the transfer survives a power failure (via logging/replication).

3.2 Online Transaction Processing (OLTP)

  • OLTP = processing operational transactions generated by applications and users.
  • These transactions are typically short, frequent and executed concurrently.
  • Examples (from the slides):
    • Transferring money between bank accounts.
    • Registering students for university courses.
    • Processing online shopping orders.
    • Updating inventory after a purchase.
    • Recording payments and bookings.

3.3 Why ACID and OLTP Matter to NewSQL

  • NewSQL systems aim to support demanding transactional workloads while preserving reliable transaction processing across distributed database infrastructure.

OLTP vs OLAP (added for clarity)

Aspect OLTP (this lecture's focus) OLAP (analytical processing)
Workload Many short read/write transactions Fewer, long complex read queries
Example "Process this order" "Total sales per region over 5 years"
Priority Correctness + speed per transaction Throughput over large data volumes

(TiDB's HTAP, Section 7.4, tries to serve both.)

4. Why Do We Need NewSQL? — Scaling

4.1 Vertical Scaling ("scale up")

  • Increasing the resources of an existing server — processing power, memory or storage.
  • Can improve performance without distributing the database over more servers.
  • Limited by hardware capacity, cost, and the architecture of the database system.

4.2 Horizontal Scaling ("scale out")

  • Adding more servers/nodes and distributing data or processing across them.
  • Increases total capacity of a deployment; supports larger workloads and distributed applications.
  • Introduces challenges: data distribution, transaction coordination, network communication and consistency.
Aspect Vertical scaling Horizontal scaling
Method Bigger server More servers
Limit Hardware ceiling & cost Coordination & network overhead
Complexity Lower (still one machine) Higher (distributed system)
Failure Single point of failure Can tolerate node failures (with replication)

4.3 The NewSQL Objective — and a Warning

  • Objective: retain SQL and reliable relational transactions while supporting distributed architectures that scale across multiple servers.
  • "Horizontal scaling does not automatically guarantee linear performance improvements." Results depend on the workload, data distribution, network latency and coordination required between nodes.

Example (added for clarity)

Doubling from 4 to 8 nodes does not double throughput if most transactions touch data on several nodes: each such transaction needs network round-trips to coordinate, so part of the extra capacity is spent on coordination.

5. Key Features of NewSQL Databases

# Feature Description
1 SQL & relational data management SQL access to tables, relationships, constraints, queries.
2 ACID transactions Aim to preserve A, C, I, D — including in distributed environments.
3 Horizontal scalability Distribute data and processing across multiple nodes for growing workloads.
4 Distributed transaction processing A transaction may involve data on more than one node; the DB coordinates the operations to preserve guarantees.
5 Partitioning & data distribution Data divided into partitions spread across nodes; supports parallel processing and workload distribution.
6 Replication & high availability Data copied across nodes/locations for fault tolerance and recovery.
7 Concurrency control Mechanisms coordinate simultaneous transactions to protect integrity and enforce isolation.
8 Indexing & query optimisation Indexes + query optimisers locate and process data efficiently. Indexes need extra storage and may increase update cost.
9 Crash recovery & durability Logging, replication and recovery mechanisms restore a consistent state after failures.
10 Distributed deployment Deployment across multiple servers, data centres or geographic regions.

Important consideration (slide): not every NewSQL product implements these features in the same way — architecture, consistency guarantees, replication mechanisms and scaling behaviour depend on the specific system.

5.1 Partitioning vs Replication (added for clarity)

Aspect Partitioning (sharding) Replication
What happens Data split into pieces; each piece lives on different node(s) The same data copied onto several nodes
Main goal Scalability — spread load & storage, enable parallelism Availability / fault tolerance — survive node failure; recovery
Cost Queries/transactions spanning partitions need coordination Copies must be kept consistent; extra storage
Together Each partition is usually also replicated

Worked Example (added) — A banking table across 3 nodes

  • Partition the Account table by account number: accounts 1–1M on Node 1, 1M–2M on Node 2, 2M–3M on Node 3 → each node handles a third of the load.
  • Replicate each partition on two other nodes → if Node 1 fails, its data is still available from a copy.
  • A transfer from account 500 (Node 1) to account 1,500,000 (Node 2) is a distributed transaction: both nodes must commit together or both roll back (atomicity across nodes) — this coordination is the main cost of horizontal scaling.

6. Comparison — SQL vs NoSQL vs NewSQL

Feature Traditional relational SQL NoSQL NewSQL / distributed SQL
Data model Relational tables Key-value, document, graph, wide-column and others Usually relational tables
Query interface SQL Depends on the system; may include SQL-like languages or APIs SQL
Schema Typically structured and defined Flexible or schema-dependent Typically structured and defined
Transactions ACID support is common Varies by product and transaction scope Designed to retain ACID guarantees
Scaling Vertical common; some also scale horizontally Horizontal scaling common in distributed systems Horizontal scaling is a key design goal
Distribution Depends on architecture/deployment Common in distributed NoSQL systems Designed for distributed deployment
Typical use cases Enterprise applications, reporting, transactional systems Applications needing particular data models or distributed access patterns Transaction-intensive applications needing SQL + distributed scalability

Link to earlier lectures (added)

  • MongoDB (document) and Neo4j (graph) from Lectures 13–19 are NoSQL examples — different data models, different query languages (find/aggregation pipeline; Cypher).
  • Lecture 13's CAP theorem trade-off (consistency vs availability under partition) is exactly the tension NewSQL systems must manage when they promise ACID across nodes (e.g., CockroachDB favours strong consistency).
  • Slide 16 reminder: NoSQL databases vary in data models, query interfaces and transaction guarantees — they should not be treated as one uniform category.

7. Advantages and Limitations of NewSQL

7.1 Advantages

Advantage Explanation
SQL support Developers use familiar SQL and relational structures.
Transactional reliability ACID transactions maintain data integrity (banking, order processing).
Horizontal scalability Distributed architectures increase capacity by adding nodes.
High availability Replication and fault-tolerance reduce the impact of certain failures.
Relational integrity Tables, keys, constraints and relationships support structured data management.
Distributed processing Workloads spread across nodes, depending on architecture.

7.2 Limitations and Challenges

Limitation Explanation
Operational complexity Distributed deployments need monitoring, configuration, backup planning and failure management.
Coordination overhead Distributed transactions need communication between nodes, increasing latency.
Network dependency Network failures and delays affect distributed operations.
Cost Infrastructure, licensing, networking and expertise may be expensive.
Migration effort Moving from an existing DB may require changes to schemas, queries, applications and operational processes.
Workload dependence Performance depends on architecture and workload; NewSQL is not necessarily faster than every traditional SQL or NoSQL system.

8. Examples of NewSQL / Distributed SQL Databases

8.1 VoltDB

  • Designed for high-throughput transactional applications; in-memory, distributed architecture for rapid transaction processing.
  • Features: high-speed transactional workloads; in-memory processing to reduce access latency; distributed transaction processing & partitioned data; reliable updates; integration with streaming platforms (e.g., Apache Kafka); replication and recovery (depending on configuration).
  • Applications: financial transaction processing, telecommunications event processing, real-time operational applications, high volumes of incoming events.
  • Scenario: a telecom provider processes a high volume of customer usage events and must process them quickly while keeping reliable records for billing.

8.2 CockroachDB

  • A distributed SQL database providing relational data management, SQL, ACID transactions and horizontal scalability.
  • Features: SQL + relational structures; distributes and replicates data across a cluster; ACID and strong consistency; replication + distributed coordination tolerate certain failures; scales by adding nodes (data distribution and rebalancing managed by the system); serializable isolation (the strongest standard isolation level).
  • Applications: financial/payment systems, e-commerce, business applications needing distributed transactions, multi-server/multi-region deployments.
  • Scenario: an online retailer serving customers in multiple regions must process orders and update inventory reliably while transaction volume grows.

8.3 NuoDB

  • A distributed SQL DBMS supporting relational data, SQL and ACID across distributed deployments.
  • Features: SQL relational data management; ACID; scale-out across multiple database processes and hosts; continuous availability and resilience; cloud and on-premises deployment; geographically distributed deployments.
  • Applications: enterprise transactional systems; applications needing relational consistency plus distributed deployment / scale-out.
  • Scenario: a company runs one business application across several sites, needing SQL access to shared data and reliable transactions as it grows.

8.4 TiDB

  • An open-source distributed SQL database for large-scale transactional and analytical workloads; compatible with the MySQL protocol and many MySQL features.
  • Features: SQL + relational; horizontal scalability; strong consistency and distributed transactions; high availability via replication; supports HTAP — Hybrid Transactional and Analytical Processing; separates key functions across components (distributed storage, query processing, cluster management).
  • Applications: high-volume OLTP; e-commerce/financial apps; distributed SQL + strong consistency; workloads combining operational transactions with analytics.
  • Scenario: a retailer processes orders while analysing recent sales in the same broader architecture.

8.5 Altibase

  • An RDBMS known for a hybrid architecture combining in-memory processing with disk-based storage.
  • Features: SQL and relational management; in-memory tables for rapid-access data; disk-based tables for persistent storage and larger datasets; both within one hybrid architecture; transaction, logging and recovery mechanisms; replication and high-availability configurations.
  • Advantages of hybrid storage: frequently accessed data in memory (lower latency); larger/less-used data on disk; balances performance, capacity and cost.
  • Scenario: a telecom needs rapid access to current operational data while retaining large volumes of historical records.
  • Important distinction (slide): Altibase illustrates hybrid in-memory/disk architecture — this does not mean all NewSQL systems share the same storage design.

8.6 Summary Table of Examples (added for clarity)

System Standout characteristic Typical application
VoltDB In-memory, distributed, very high throughput; Kafka integration Telecom events, financial transactions
CockroachDB Distributed SQL, strong consistency, serializable isolation, auto-rebalancing, multi-region Payments, e-commerce
NuoDB Scale-out across processes/hosts; cloud + on-premises; geo-distributed Enterprise transactional systems
TiDB MySQL-compatible, open source, HTAP, separated components OLTP + analytics (retail, finance)
Altibase Hybrid in-memory + disk storage Telecom (hot + historical data)

9. Case Study — Database Selection for an Online Banking System

Scenario: a bank is building an online banking platform for millions of accounts and a growing number of transactions. It must:

  • Process transfers reliably; prevent inconsistent balances; support many concurrent transactions;
  • Stay available when certain servers fail; scale as customers/transactions grow;
  • Support SQL queries and relational integrity constraints.

9.1 Suggested Answers to the Slide's Questions (added — check against your own reasoning)

  1. Why are ACID transactions important?
    • Atomicity: a transfer's debit and credit happen together or not at all.
    • Consistency: balances respect constraints (e.g., no overdraft beyond limit; money is conserved).
    • Isolation: concurrent transactions don't see/overwrite each other's partial work (prevents inconsistent balances).
    • Durability: a committed transfer survives failures.
  2. Vertical vs horizontal scaling here? Vertical: buy a bigger server for the bank's database — simple, but limited by hardware/cost and a single point of failure. Horizontal: add more servers and spread accounts/processing across them — handles millions of customers, but needs partitioning, coordination and consistency management.
  3. How could partitioning and replication help? Partitioning (e.g., by account number/region) spreads load and storage and enables parallel processing. Replication keeps copies of each partition on other nodes, so the system stays available when a server fails and can recover.
  4. Challenges when a transaction spans nodes? Needs coordination between nodes (all commit or all roll back); added latency from network communication; network failures/delays may leave a transaction in doubt; concurrency control across nodes; keeping replicas consistent.
  5. Why a distributed SQL DB might be suitable? It aims to combine SQL + relational integrity constraints + ACID transactions + horizontal scalability + replication-based availability — matching every requirement on the list.
  6. Two factors to evaluate before choosing a product (any two): consistency requirements/guarantees; transaction latency; recovery mechanisms; security; cost; operational complexity; migration effort.

Discussion point (slide): a distributed SQL DB may be suitable because it aims to combine relational data management, transactional guarantees and horizontal scalability — but the bank must still evaluate consistency requirements, transaction latency, recovery mechanisms, security, cost and operational complexity.

10. Summary (from the slides)

  • NewSQL = database systems supporting relational data management and SQL while addressing the scalability needs of demanding transactional workloads.
  • ACID properties matter for applications needing reliable transaction processing.
  • Horizontal scaling distributes data/processing across servers; vertical scaling increases a single server's resources.
  • Partitioning, replication, concurrency control and recovery help distributed databases manage workloads and failures.
  • NoSQL databases vary in data models, query interfaces and transaction guarantees — not a single uniform category.
  • NewSQL/distributed SQL can benefit transactional applications but add coordination, network and operational challenges.
  • Database selection should rest on workload requirements, transaction guarantees, scalability, availability, cost and operational needs.

11. Homework — Suggested Answers (added)

The slides pose four homework tasks; the answers below are suggested outlines drawn from the lecture content.

H1. Discuss at least four advantages and three limitations of NewSQL.

  • Advantages: (1) familiar SQL and relational structures; (2) ACID reliability for banking/orders; (3) horizontal scalability by adding nodes; (4) high availability through replication; (5) relational integrity (keys, constraints); (6) distributed processing of workloads.
  • Limitations: (1) operational complexity (monitoring, backup, failure management); (2) coordination overhead/latency for distributed transactions; (3) network dependency; (4) cost; (5) migration effort; (6) workload dependence — not always faster than SQL or NoSQL.

H2. Compare SQL, NoSQL and NewSQL (data models, query interfaces, transactions, scalability) — answer with the Section 6 table: relational tables / varied models (key-value, document, graph, wide-column) / relational tables; SQL / system-specific APIs or languages / SQL; ACID common / varies / ACID retained; vertical (some horizontal) / horizontal common / horizontal a key goal.

H3. Explain how horizontal scaling, partitioning and replication support a distributed transactional database.

  • Horizontal scaling adds nodes so total capacity and throughput grow.
  • Partitioning divides data across nodes so each handles part of the load (parallel processing); transactions touching one partition stay cheap.
  • Replication keeps copies across nodes → fault tolerance, availability and recovery.
  • Together with concurrency control and distributed transaction coordination, they keep ACID guarantees while spreading the workload; the price is coordination overhead and network dependency (Section 4.3).

H4. Justify whether a distributed SQL DB suits the banking case study; identify two challenges.

  • Suitable: it offers SQL + relational integrity + ACID + horizontal scalability + replication — matching the bank's requirements (Section 9.1, Q5).
  • Challenges (any two): cross-node transaction latency/coordination; network failures/delays; operational complexity; cost; migration from existing systems; ensuring security and consistency requirements are met.

12. Questions & Memo

Q1: Define NewSQL and state its central idea.

A1: A class of modern DBMSs for high-performance OLTP that retain the relational model, SQL and strong (ACID) transactional guarantees. Central idea: provide relational data management, SQL, ACID transactions and improved horizontal scalability in a modern architecture.

Q2: What problem do traditional relational DBs face that motivated NewSQL, and what weakness of NoSQL does NewSQL address?

A2: Scaling very large transactional workloads across multiple servers is architecturally/operationally difficult for traditional relational systems. NoSQL scales out but systems differ widely in query languages, data models and transaction guarantees — NewSQL keeps SQL and ACID while scaling out.

Q3: State the four ACID properties and give an example of each in a funds transfer.

A3: Atomicity — debit and credit both happen or neither. Consistency — integrity rules (e.g., no negative balance) still hold. Isolation — other transactions don't see the half-done transfer. Durability — a committed transfer survives a crash.

Q4: What is OLTP? Give three examples.

A4: Processing of operational transactions from applications/users — short, frequent, concurrent. Examples: bank transfers, course registration, online orders, inventory updates, payments/bookings.

Q5: Distinguish vertical and horizontal scaling, with one limitation of each.

A5: Vertical — add resources (CPU, memory, storage) to one server; limited by hardware, cost and architecture. Horizontal — add more servers/nodes and distribute work; brings data distribution, coordination, network and consistency challenges.

Q6: Why does horizontal scaling not guarantee linear performance gains?

A6: Gains depend on workload, data distribution, network latency and the coordination required between nodes — distributed transactions spend part of the extra capacity on coordination.

Q7: Differentiate partitioning from replication and state the main benefit of each.

A7: Partitioning splits data across nodes → scalability and parallelism. Replication copies data to several nodes → availability, fault tolerance and recovery.

Q8: What is a distributed transaction and why is it a challenge?

A8: A transaction that involves data on more than one node; the DB must coordinate the operations so ACID is preserved (all commit or all roll back), which adds latency, network dependency and complexity.

Q9: List five key features of NewSQL systems.

A9: Any five of: SQL/relational management; ACID transactions; horizontal scalability; distributed transaction processing; partitioning; replication/high availability; concurrency control; indexing/query optimisation; crash recovery/durability; distributed deployment.

Q10: Why can indexes be a trade-off?

A10: They help locate/process data efficiently but need additional storage and may increase the cost of updates.

Q11: Compare SQL, NoSQL and NewSQL on data model and transactions.

A11: SQL: relational tables; ACID common. NoSQL: many models (key-value, document, graph, wide-column); transactions vary by product. NewSQL: usually relational tables; designed to retain ACID while scaling horizontally.

Q12: State three advantages and three limitations of NewSQL.

A12: Advantages: SQL support; ACID reliability; horizontal scalability (also availability, relational integrity). Limitations: operational complexity; coordination overhead/latency; network dependency (also cost, migration effort, workload dependence).

Q13: Is NewSQL always faster than traditional SQL or NoSQL? Explain.

A13: No — performance depends on architecture and workload; coordination overhead can reduce speed for some workloads.

Q14: Match each system to its distinguishing feature: VoltDB, CockroachDB, NuoDB, TiDB, Altibase.

A14: VoltDB — in-memory, high-throughput, Kafka integration. CockroachDB — distributed SQL with strong consistency/serializable isolation. NuoDB — scale-out across processes/hosts, cloud & on-premises. TiDB — MySQL-compatible, HTAP. Altibase — hybrid in-memory + disk storage.

Q15: What does HTAP stand for and why is it useful?

A15: Hybrid Transactional and Analytical Processing — it lets one platform handle operational transactions and analytics (e.g., processing orders while analysing recent sales).

Q16: Why is Altibase's design not representative of all NewSQL systems?

A16: It illustrates hybrid in-memory/disk storage, but NewSQL systems differ in storage design, consistency guarantees, replication and scaling behaviour.

Q17 (Scenario): A telecom must process millions of usage events per minute with reliable billing records. Which example system fits best and why?

A17: VoltDB — designed for high-throughput transactional workloads with in-memory, distributed processing, partitioned data, transaction guarantees, and streaming (Kafka) integration — matching the telecom scenario on the slides. (Altibase's hybrid design is an alternative if historical data must also be retained.)

Q18 (Scenario): An online retailer sells in several regions, needs reliable order/inventory updates and growth in volume. Which system illustrates this and which features matter?

A18: CockroachDB (slide scenario) — SQL, ACID with strong consistency/serializable isolation, replication across a cluster, scale by adding nodes with automatic rebalancing, multi-region deployment.

Q19 (Scenario): List four factors a bank should evaluate before choosing a distributed SQL product.

A19: Consistency requirements; transaction latency; recovery mechanisms; security; cost; operational complexity (also migration effort, workload fit).
