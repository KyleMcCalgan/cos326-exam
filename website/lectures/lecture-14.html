2. Introduction — What Is Big Data?

  • Exponential growth in data from:
    • Social media, IoT sensors, satellite imagery.
    • App telemetry, eSIM, cloud logs.
    • Business intelligence and user analytics.
  • Definition: Big Data refers to datasets whose size, speed of generation, diversity, or complexity requires scalable approaches to data storage, processing, management and analysis beyond what traditional data-processing approaches can efficiently support.
  • Important qualification: the suitability of a solution depends on the data characteristics, workload, performance requirements and available infrastructure — there is no single "best" big-data technology.

4. Hadoop — Legacy Components and Lessons

4.1 Hadoop Legacy Components

Component Role
HDFS Distributed file system for large datasets
MapReduce Batch-oriented programming model
YARN Resource management: ResourceManager + NodeManager

MapReduce — a short worked example (added for step-by-step clarity; not detailed on the slides)

Task: count how often each word appears in a very large set of text files.

  1. Map phase: each node reads its part of the data and emits (word, 1) pairs — e.g., "to be or not to be" → (to,1), (be,1), (or,1), (not,1), (to,1), (be,1).
  2. Shuffle/sort: the system groups all pairs with the same key and sends each group to one reducer.
  3. Reduce phase: each reducer adds up the values for its keys → (to,2), (be,2), (or,1), (not,1).
  4. Why it scales: map tasks run in parallel on many machines, each working on local data; intermediate results are written to disk between phases (the source of the limitations below).

4.2 Limitations of Traditional Hadoop MapReduce

  1. Intermediate results are commonly written to disk, which can increase processing overhead.
  2. Iterative algorithms may incur substantial overhead because successive stages repeatedly read and write data.
  3. MapReduce is primarily designed for batch processing, not low-latency, interactive analytics.
  4. These limitations encouraged the adoption of engines such as Apache Spark and specialised stream-processing frameworks.

Note from the slide: Hadoop is an ecosystem of technologies. Its limitations should not be attributed equally to HDFS, YARN and every Hadoop-related tool (the disk-write limitation is about MapReduce, not HDFS itself).

Example (added for clarity)

A machine-learning algorithm that repeats 50 passes over the same dataset would, under MapReduce, read from and write to disk 50 times; an engine that keeps the data in memory between passes (Spark) avoids most of that overhead.

5. Apache Spark — The Modern Alternative

  • Apache Spark is a distributed processing engine designed for large-scale data analytics.
  • Through its ecosystem it supports:
    • SQL queries
    • Batch processing
    • Structured streaming
    • Machine learning
    • Graph processing
  • Uses directed acyclic graphs (DAGs) to represent and schedule processing stages.
  • Can cache data in memory when beneficial — but can also use disk storage.
  • Can process data stored in HDFS and supported cloud object stores: Amazon S3, Azure Blob Storage, Google Cloud Storage.
  • Key advantage: Spark can reduce processing overhead for many iterative and interactive workloads compared with traditional disk-intensive MapReduce jobs.

Example (added for clarity)

DAG: a job such as read logs → filter errors → group by server → count → write results is represented as a graph of stages (nodes) with one-way dependencies (edges), no cycles. Spark can schedule and optimise the stages together, rather than treating each step as a separate disk-to-disk job.

5.1 MapReduce/Hadoop vs Spark (added comparison)

Aspect Hadoop MapReduce Apache Spark
Execution model Map → shuffle → reduce stages DAG of stages
Intermediate data Commonly written to disk Cached in memory when beneficial (disk also used)
Best for Batch processing Batch, iterative, interactive, streaming, ML, graph, SQL
Latency Higher Lower for many workloads
Status in lecture Foundational but largely legacy Modern, widely used

8. Apache Flink — Stateful Stream Processing

  • A distributed processing framework designed primarily for stateful stream processing.
  • Supports event-time processing, state management and event-time window operations.
  • Typical applications: fraud detection, IoT monitoring, real-time analytics.
  • Also supports batch-style processing.
  • Related technologies: Kafka Streams, Spark Structured Streaming (architectures and capabilities differ).
  • Example (slide): a bank uses Flink to analyse incoming transactions and flag suspicious activity within seconds.

Terms explained (added)

  • Stateful: the engine remembers information between events (e.g., "how many transactions has this card made in the last 5 minutes?").
  • Event time: the time the event actually happened, not the time it arrived — important when events arrive late or out of order.
  • Window: a slice of the stream (e.g., the last 5 minutes) over which results are computed.

10. Modern File Formats

Type Formats Characteristics
Columnar formats Apache Parquet, Apache ORC Store data by column; often effective for analytical queries that read selected columns from large datasets
Row-oriented serialization Apache Avro Useful for record-oriented data exchange and schema-based serialization
Table formats for data lakes Delta Lake, Apache Iceberg, Apache Hudi Add table-level capabilities: metadata management, schema evolution, transactional operations (exact features depend on implementation/configuration)

Example — why columnar? (added)

A table of 100 columns and 1 billion rows: a query that only needs amount and date reads just those two columns from a columnar file (Parquet/ORC); a row-oriented file would force reading all 100 columns of every row. Conversely, Avro (row-oriented) suits writing/exchanging whole records, e.g., messages between systems.

11. Workflow Orchestration

  • Tools: Airflow, Prefect, Dagster.
  • Purpose: manage ETL, dependencies, scheduling and monitoring of data pipelines.

Example (added)

A nightly pipeline: extract sales → clean → load into warehouse → refresh report. An orchestrator runs the steps in order, retries failures, waits for dependencies and alerts you if a step fails.

12. Streaming & Real-Time Analytics

Technology Description
Apache Kafka Distributed event-streaming platform that stores and distributes event records through topics
Apache Pulsar An alternative distributed messaging/event-streaming platform
Amazon Kinesis; Google Cloud Pub/Sub Managed cloud services for streaming ingestion and distribution
Apache Flink; Spark Structured Streaming Stream-processing engines that process incoming events for real-time or near-real-time results
  • Streaming systems can support event replay, continuous processing and event-driven applications; the processing model depends on the platform and application design.

Division of labour (added)

Kafka moves and stores the events (the "pipe"); Flink / Spark Structured Streaming compute on them (the "brain"). A typical pipeline: sensors → Kafka → Flink → alert/dashboard.

14. Data Governance, Security, Ethics & Legal Considerations

  • Big data systems must protect data throughout its lifecycle: collection → storage → processing → sharing → deletion.
Area Requirement (from the slides)
Access control Role-based (RBAC) or attribute-based (ABAC) access control, following the principle of least privilege
Encryption Protect sensitive data in transit and at rest
Auditing & monitoring Record access and administrative activities for accountability and incident investigation
Data governance Maintain data catalogues, ownership information, data lineage, retention policies and quality controls
Privacy & legal compliance Apply relevant laws, including South Africa's POPIA (Protection of Personal Information Act) and, where applicable, the EU GDPR

Examples (added for clarity)

  • RBAC: a "call-centre agent" role may view a customer's name and plan, but not their full location history; a "fraud analyst" role may.
  • Least privilege: give each user/service only the permissions it needs, nothing more.
  • Data lineage: being able to trace where a number in a report came from (which source tables and transformations produced it).

14.1 Discussion Question (from the slide)

What risks arise when a company combines location data, purchasing histories and social media activity to predict individual behaviour?

Suggested points (added):

  1. Privacy / re-identification: combining datasets can identify individuals even if each dataset alone seems anonymous, and can reveal sensitive inferences (health, religion, relationships, home/work).
  2. Legal compliance: processing personal information needs a lawful basis, purpose limitation and consent under POPIA/GDPR; profiling and automated decisions attract extra scrutiny.
  3. Bias and discrimination: predictions may disadvantage groups (e.g., credit or insurance decisions).
  4. Security: large combined datasets are an attractive target for breaches.
  5. Accuracy (veracity): wrong inferences can harm individuals.
  6. Surveillance and manipulation: behavioural prediction can be used to manipulate choices; users may be unaware their data is combined.

17. Homework — Telecom Case Study

Scenario: a telecom collects millions of network events every hour and needs to: (1) store historical events for long-term analysis; (2) identify suspicious activity as events arrive; (3) run ML models on historical data; (4) control access to sensitive subscriber information.

Suggested Answers (added — check against your own reasoning)

a. Storage technology for historical data? Cloud object storage (e.g., Amazon S3, Azure Data Lake Storage, Google Cloud Storage) forming a data lake, optionally with columnar formats (Parquet/ORC) and a table format (Delta Lake/Iceberg). Why: capacity scales through the service without cluster capacity planning; usage-based cost suits growing history; API access from many analytics tools (Spark, Trino, BigQuery). Alternative: HDFS if the company already runs an on-premises Hadoop cluster.

b. Processing framework for real-time detection? Apache Flink (stateful, event-time stream processing — fraud/IoT monitoring) or Spark Structured Streaming, fed by Kafka (or Kinesis/Pub-Sub) for event ingestion.

c. How can Spark contribute to historical analysis and ML? Spark processes the stored historical data (from HDFS or object stores) with Spark SQL for batch analysis, and Spark MLlib to train models at scale; its DAG engine and in-memory caching make iterative ML training and interactive analysis faster than disk-heavy MapReduce.

d. Two security/privacy controls? (1) Access control (RBAC/ABAC, least privilege) so only authorised roles see subscriber data; (2) Encryption in transit and at rest. (Also: auditing/monitoring, data governance such as retention and lineage, POPIA/GDPR compliance, anonymisation/masking.)

e. Why can a single technology not be sufficient? The four requirements have different characteristics: long-term, low-cost, scalable storage (object store/HDFS); low-latency, stateful stream processing (Flink/Kafka); large-scale batch analytics and ML (Spark); and governance/security (access control, encryption, catalogues, audit) cutting across everything. No single tool is optimised for all; modern architectures combine specialised components — and, as the introduction stresses, suitability depends on workload, performance requirements and infrastructure.

18. Questions & Memo

Q1: Define Big Data and list the five Vs with a brief description of each.

A1: Datasets whose size, speed of generation, diversity or complexity requires scalable approaches to storage, processing, management and analysis beyond traditional approaches. Volume (terabytes→zettabytes), Velocity (real-time ingestion/processing), Variety (structured, semi-structured, unstructured), Veracity (trustworthiness/quality), Value (business/analytical relevance).

Q2: Place in chronological order and describe: Spark, MapReduce, cloud-native, Hadoop v1/v2 (YARN).

A2: MapReduce (2004) — parallel batch processing on clusters → Hadoop v1/v2 with YARN — resource management + HDFS → Spark (2014+) — in-memory, DAG-based, faster → Cloud-native — serverless, autoscaling, object storage.

Q3: Name the three legacy Hadoop components and state each one's role.

A3: HDFS — distributed file system; MapReduce — batch programming model; YARN — resource management (ResourceManager + NodeManager).

Q4: State three limitations of traditional Hadoop MapReduce.

A4: Intermediate results are written to disk (overhead); iterative algorithms repeatedly read/write data; designed for batch, not low-latency/interactive analytics.

Q5: Why should Hadoop's limitations not be attributed equally to all its components?

A5: Hadoop is an ecosystem; for example, the disk-intensive intermediate processing is a characteristic of MapReduce, not of HDFS or YARN.

Q6: Describe Apache Spark and explain what a DAG is in this context.

A6: A distributed processing engine for large-scale analytics supporting SQL, batch, structured streaming, ML and graph processing. A DAG (directed acyclic graph) represents and schedules the processing stages with one-way dependencies and no cycles.

Q7: Is Spark purely in-memory? Where can it read data from?

A7: No — it can cache data in memory when beneficial but can also use disk. It reads from HDFS and cloud object stores (S3, Azure Blob Storage, Google Cloud Storage).

Q8: Compare HDFS and cloud object storage on storage model, scaling and cost.

A8: HDFS: distributed file system; scaling needs cluster capacity planning; cost = infrastructure, storage and operations. Object storage: objects in buckets/containers; capacity scales via the cloud service; usage-based pricing with possible request and data-transfer charges.

Q9: Match legacy tools to modern alternatives: Pig, Hive, Sqoop, HBase.

A9: Pig → Spark SQL, dbt; Hive → Trino, BigQuery; Sqoop → NiFi, Airbyte; HBase → Cassandra, Google Cloud Bigtable.

Q10: What is Apache Flink primarily designed for? Give an example application.

A10: Stateful stream processing (event-time processing, state management, windows). Example: a bank flagging suspicious transactions within seconds.

Q11: Distinguish Kafka from Flink.

A11: Kafka is a distributed event-streaming platform that stores and distributes event records through topics; Flink is a stream-processing engine that processes those events to produce real-time results.

Q12: Name one storage, one integration and one analytics service from each of AWS and Google Cloud.

A12: AWS: S3 (storage), Glue (integration), Redshift/EMR (analytics/processing). Google Cloud: Cloud Storage (storage), Dataflow/Pub/Sub (processing/messaging), BigQuery (analytics).

Q13: Why are columnar formats such as Parquet effective for analytics? Where is Avro more suitable?

A13: They store data by column, so queries reading selected columns from large datasets read less data. Avro is row-oriented, suited to record-oriented data exchange and schema-based serialization.

Q14: What do Delta Lake, Iceberg and Hudi add to a data lake?

A14: Table-level capabilities — metadata management, schema evolution and transactional operations (features depend on implementation/configuration).

Q15: What do workflow orchestrators such as Airflow do?

A15: Manage ETL pipelines — dependencies, scheduling and monitoring.

Q16: List four governance/security measures for big data systems.

A16: Access control (RBAC/ABAC, least privilege); encryption in transit and at rest; auditing and monitoring; data governance (catalogues, ownership, lineage, retention, quality); and privacy/legal compliance (POPIA, GDPR).

Q17 (Scenario): A retailer wants to combine location, purchase history and social-media data to predict customer behaviour. Identify three risks.

A17: Any three of: privacy/re-identification; non-compliance with POPIA/GDPR (consent, purpose limitation); bias/discrimination; security/breach risk; inaccurate inferences; manipulation/surveillance (see Section 14.1).

Q18 (Scenario): Why might a company use both Kafka/Flink and Spark rather than one tool?

A18: The workloads differ: Kafka/Flink handle low-latency, real-time event ingestion and stateful stream processing, while Spark is strong at large-scale batch analytics and ML over historical data. Suitability depends on workload, performance requirements and infrastructure.
