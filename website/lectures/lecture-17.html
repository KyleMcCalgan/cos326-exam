2. Recap — ROLAP Structure

  • Dimension tables and a fact table for a data mart (the star schema).
  • Hierarchies: a dimension may have more than one hierarchy — e.g., TIME may have a calendar_rollup and a fiscal_rollup.
  • ROLAP uses a relational structure to implement a dimensional schema for OLAP.
  • Surrogate keys: keys generated by the system (e.g., Time_Key, Hotel_Key, Room_Key).
  • Slide figure (hotel star schema):
Table Columns
OCCUPANCY_FACTS Time_Key, Hotel_Key, Room_Key, Occupied_rooms, Vacant_rooms, Revenue
HOTEL Hotel_Key, Hotel_ID, Hotel_Line, Province, Branch
RM_TYPE Room_Key, Room_ID, Room_Type, Size
TIME Time_Key, Time_ID, Year, Quarter, Month
  • Key point (slide): surrogate keys allow a dimension to maintain multiple historical versions of the same business entity (see slowly changing dimensions, Section 4).

📌 Example (added)

Hotel_ID is the business key from the source system (e.g., "H0017"); Hotel_Key is the surrogate key (e.g., 12345) generated by the warehouse. If the hotel is later reclassified, a new row with a new Hotel_Key but the same Hotel_ID can be added without disturbing historical facts.

Note (slide): CREATE DIMENSION is Oracle SQL functionality, not a universally supported SQL statement.

3.1 CREATE SEQUENCE (added example — slide lists the statement only)

CREATE SEQUENCE hotel_key_seq START WITH 1 INCREMENT BY 1;

INSERT INTO HOTEL (Hotel_Key, Hotel_ID, ...)
VALUES (hotel_key_seq.NEXTVAL, 'H0017', ...);
  • The sequence hands out 1, 2, 3, … so every new dimension row gets a unique surrogate key automatically.

3.2 CREATE DIMENSION (from the slides)

-- 1. First create the table
CREATE TABLE HOTEL ( ... );

-- 2. Then declare the dimension
CREATE DIMENSION HOTELS_DIM
  LEVEL Hotel     IS HOTEL.Hotel_ID
  LEVEL Province  IS HOTEL.Province_ID
  LEVEL Hotelline IS HOTEL.Hotelline_ID
  HIERARCHY Hotel_Rollup
    ( Hotel CHILD OF Province CHILD OF Hotelline )
  ATTRIBUTE Hotel     DETERMINES (Hotel_name, Hotel_address, Hotel_city, ...)
  ATTRIBUTE Province  DETERMINES Province_name
  ATTRIBUTE Hotelline DETERMINES Hotelline_desc;

Step-by-step walkthrough:

  1. The HOTEL table (slide example) has columns: Hotelline_ID, Hotelline_desc, Province_ID, Province_name, Hotel_key, Hotel_ID, Hotel_name, Hotel_address, Hotel_city, Hotel_manager, Hotel_size.
  2. LEVEL … IS … names each level and the column that identifies it.
  3. HIERARCHY Hotel_Rollup (Hotel CHILD OF Province CHILD OF Hotelline) — the roll-up path from lowest to highest level.
  4. ATTRIBUTE … DETERMINES … — functional dependencies: e.g., Province_ID determines Province_name.
  5. The statement declares metadata; it does not create or move data. (It helps the optimiser — e.g., for materialised views and roll-up query rewrite.)

4. Slowly Changing Dimensions (SCDs)

  • A data warehouse stores historical data for a long period, so data in dimension tables may change over time — e.g., a customer's marital status.
  • ⇒ We need a strategy to handle the changes.

4.1 The Three Strategies

Type Rule (from the slides) Effect on history
Type 1 The changed attribute value is overwritten History lost — only the current value is kept
Type 2 The changed value causes a new record to be created Full history preserved — one row per version
Type 3 The changed value causes an alternate attribute (column) to be created, so old and new values are in the same record Limited history — previous + current value only

Example table on the slide: CUSTOMER(Cust_Key, Cust_ID, Cust_sname, Marital_stat, etc.).

4.2 Worked Example — Type 2 Change (slide)

Event: a customer's marital status changes from Single to Married (and her surname changes).

Before and after — CUSTOMER dimension (with effective dates):

Cust_Key Cust_ID Start_date End_date Marital_stat Cust_sname
12345 850002 01/03/2015 09/03/2018 single Jones
12347 850002 10/03/2018 (blank / current) married Charming

Step-by-step reading:

  1. Two rows exist for the same customer — same business key Cust_ID = 850002 but different surrogate keys (Cust_Key 12345 and 12347).
  2. The first row is closed with an End_date (09/03/2018); the new row starts the next day (10/03/2018) with an empty end date = current version.
  3. Why this works: old fact rows still point to Cust_Key 12345 (she was single when those sales happened), while new facts point to 12347 — so history by marital status is correct.
  4. The table structure on the slide: CUSTOMER(Cust_Key, Cust_ID, Eff_start_date, Eff_end_date, Cust_sname, Marital_stat, …) — the effective start/end dates support Type 2.

📌 Same event under Type 1 and Type 3 (added for comparison)

Strategy Result for customer 850002
Type 1 (overwrite) One row: Marital_stat = married, Cust_sname = Charming — "single" is gone; all past sales now appear to be to a married customer.
Type 2 (new record) Two rows as above — complete history.
Type 3 (alternate column) One row with extra columns, e.g., Marital_stat = married, Prev_marital_stat = single — only one previous value is kept.

When to use which (added): Type 1 for corrections (typos) where history doesn't matter; Type 2 when analysis by historical value matters; Type 3 when you only need "before vs after" comparison.

5. Loading Data into the ROLAP Structure

  • Distinguish between:
    1. Initial data load (first population of the warehouse), and
    2. Subsequent incremental loads (periodic additions/changes).
  • Slowly changing dimension handling (Type 1, 2, 3 above) applies during loading.

5.1 The SQL MERGE Statement (from the slide — used for initial and incremental loads)

MERGE INTO CUSTOMER C                          -- dimension table
USING (SELECT Cust_ID, ... FROM CUST_STG) S    -- staging table
ON ( (C.Cust_ID = S.Cust_ID) AND
     (C.Marital_Status = S.Marital_stat) )
WHEN MATCHED THEN
    -- a type 1 change
    UPDATE SET (what should change in C)
WHEN NOT MATCHED THEN
    -- a type 2 change on existing customer or a new customer
    INSERT VALUES (S.Cust_ID, S.Marital_stat, ...);

Step-by-step walkthrough:

  1. MERGE INTO CUSTOMER C — the target is the dimension table.
  2. USING (SELECT … FROM CUST_STG) S — the source is the staging table (data extracted from the operational system, Lecture 23's ETL).
  3. ON (C.Cust_ID = S.Cust_ID AND C.Marital_Status = S.Marital_stat) — decides whether a staging row "matches" an existing dimension row: same customer and same marital status.
  4. WHEN MATCHED THEN UPDATE — row already exists → overwrite attributes that should change (the slide labels this a Type 1 change).
  5. WHEN NOT MATCHED THEN INSERT — no row with that customer and that status → insert a new row. The slide labels this a Type 2 change on an existing customer, or a brand-new customer.
  6. Applying to the Single → Married example: the staging row (850002, married) does not match the existing (850002, single) row → falls to NOT MATCHED → INSERT → a new version is created (Type 2). A brand-new customer ID also doesn't match → also inserted.
  7. Why one statement for both loads: on the initial load the dimension is empty → everything is NOT MATCHED → inserted; on incremental loads it adds new rows and updates existing ones.

⚠️ Cautions (added — not on the slide): (a) because the ON condition includes Marital_Status, a "matched" row is one whose marital status is unchanged, so UPDATE there would be for other, non-tracked attributes (Type 1 corrections); a changed marital status never matches and is inserted. (b) A complete Type 2 load also needs to set the End_date of the old row (and give the new row a new surrogate key from the sequence) — typically with an additional UPDATE step. Check your practical/textbook for the exact pattern you must use.

6. OLAP Analysis for BI — Why SQL Needed Extensions

  • Limitation of basic SQL: it can't easily answer routine business queries such as:
    • Percentage change between this month and a year ago.
    • Moving averages (time series).
    • Cumulative sums and other statistical functions.
  • ANSI adopted a set of OLAP functions as an extension to SQL to enable these (and more) calculations that were previously impossible or impractical in SQL.
  • Standardisation history (slide): OLAP extensions were standardised through the SQL:1999 OLAP amendment and incorporated into SQL:2003; they introduced enhanced grouping operations and analytical functions including ranking and window calculations.
    • (Slide 12 separately says "Since SQL 2008 extensions" for CUBE/ROLLUP/GROUPING SETS — the lecture's dates are not fully consistent; remember the main point: they are standard SQL OLAP extensions, now widely supported.)

6.1 Analytical Capabilities

  1. Extended grouping: extensions to GROUP BY — ROLLUP, CUBE (and GROUPING SETS).
  2. Extended OLAP operators:
    • Windowing: cumulative and moving aggregations using SUM, AVG, MIN, COUNT over a range of rows.
    • Ranking: cumulative distributions, percent rank, N-tiles (quartiles, deciles, percentiles), RANK, DENSE_RANK.

7. Extended Grouping — CUBE, ROLLUP, GROUPING SETS

7.1 Traditional SQL (from the slides)

Manager's question: How much revenue did product X generate by province and by month this year?

SELECT   B.province, T.month, SUM(S.revenue) AS total_revenue
FROM     BRANCH B, TIME T, PRODUCT P, SALES S
WHERE    P.ProductName = 'Product X'
AND      T.year = 2026
AND      B.BranchKey  = S.BranchKey
AND      T.TimeKey    = S.TimeKey
AND      P.ProductKey = S.ProductKey
GROUP BY B.province, T.month;

Step-by-step walkthrough:

  1. The FROM clause lists the fact table (SALES) and three dimension tables.
  2. The three … Key = … Key conditions are the star-join (fact ↔ dimension via foreign keys).
  3. ProductName and year conditions filter the data.
  4. GROUP BY province, month produces one group type only: {province, month, SUM} — no subtotals. To get subtotals you'd need several separate queries combined with UNION — the problem the extensions solve.

7.2 Summary of the Three Operations (slide table)

Operation Purpose
CUBE Generates all possible combinations of grouping attributes
ROLLUP Generates hierarchical subtotals and a grand total
GROUPING SETS Generates only the explicitly specified groupings

7.3 GROUP BY CUBE (from the slide)

... GROUP BY CUBE (B.province, T.month);

Groups formed (slide): {province, month, SUM}, {province, SUM}, {month, SUM}, {all, SUM} — i.e., all 2² = 4 combinations.

7.4 GROUP BY ROLLUP (from the slide)

... GROUP BY ROLLUP (B.province, T.month);

Groups formed (slide): {province, month, SUM}, {province, SUM}, {all, SUM} — the hierarchy is rolled up from right to left: detail → province subtotal → grand total.

7.5 GROUP BY GROUPING SETS (from the slide)

... GROUP BY GROUPING SETS (
      (B.province, T.month),
      (B.province),
      ()
    );

Groups formed (slide): {province, month, SUM}, {province, SUM}, {all, SUM} — exactly the groupings listed; () = the grand total (empty grouping).

Observation (added): this GROUPING SETS list produces the same groups as ROLLUP (province, month). GROUPING SETS is the general form: you choose any groupings (e.g., omit some, or include (month) alone).

📌 Worked Example (added for step-by-step clarity) — the three operations on made-up data

Product X, 2026 — revenue (R millions) from the join:

province month revenue
Gauteng Jan 10
Gauteng Feb 20
KZN Jan 5
KZN Feb 15

ROLLUP (province, month) → 7 rows (NULL in a column means "all values / summarised over"):

province month SUM Meaning
Gauteng Jan 10 detail
Gauteng Feb 20 detail
Gauteng NULL 30 province subtotal
KZN Jan 5 detail
KZN Feb 15 detail
KZN NULL 20 province subtotal
NULL NULL 50 grand total

CUBE (province, month) → 9 rows = the 7 above plus the month-only subtotals:

province month SUM
NULL Jan 15 (10 + 5)
NULL Feb 35 (20 + 15)

GROUPING SETS ((province, month), (province), ()) → the same 7 rows as ROLLUP.

Row-count check: CUBE with 2 columns = 2² = 4 group types (detail, province, month, grand) → 4 + 2 + 2 + 1 = 9 rows.

Telling "real" NULLs from "summary" NULLs (added): the function GROUPING(column) returns 1 when the NULL in that column is a subtotal marker and 0 for ordinary data — useful for labelling rows such as "All provinces".

8. OLAP and Statistical Analysis — Windowing and Ranking

8.1 Windowing — Cumulative and Moving Aggregations

  • Windowing calculates cumulative and moving aggregations using functions such as SUM, AVG (moving average), MIN, COUNT over a range of rows.

Worked Example 1 — 3-Month Moving Average (slide table)

Month Jan Feb Mar Apr May Jun
Revenue 1m 4m 1m 2m 3m 4m
3-month moving average — — (6/3)m = 2m (7/3)m ≈ 2.33m (6/3)m = 2m (9/3)m = 3m

Step-by-step:

  1. March: average of Jan + Feb + Mar = (1 + 4 + 1) / 3 = 6/3 = 2.
  2. April: window slides forward one month: Feb + Mar + Apr = (4 + 1 + 2) / 3 = 7/3.
  3. May: Mar + Apr + May = (1 + 2 + 3) / 3 = 6/3.
  4. June: Apr + May + Jun = (2 + 3 + 4) / 3 = 9/3.
  5. Slide note: the first two months do not have three complete months of historical data, so no full 3-month average exists for them.

Worked Example 2 — Windowing in SQL (slide)

"Show the monthly figures and three-month moving averages and sums for property sales at branch office B003 for the first six months of 2020."

SELECT  yearMonth,
        SUM(saleAmount) AS monthlySales,
        AVG(SUM(saleAmount)) OVER (
            ORDER BY yearMonth
            ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
        ) AS threeMonthMovingAvg,
        SUM(SUM(saleAmount)) OVER (
            ORDER BY yearMonth
            ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
        ) AS threeMonthMovingSum
FROM    PropertySale
WHERE   branchNo = 'B003'
AND     yearMonth BETWEEN '2020-01' AND '2020-06'
GROUP BY yearMonth
ORDER BY yearMonth;

Step-by-step walkthrough:

  1. Inner SUM(saleAmount) with GROUP BY yearMonth — first computes monthly totals (this is ordinary aggregation).
  2. OVER ( … ) turns the outer AVG/SUM into window functions over those monthly totals (hence AVG(SUM(...)) — an aggregate of an aggregate).
  3. ORDER BY yearMonth inside OVER — sorts the rows chronologically so the "window" moves through time.
  4. ROWS BETWEEN 2 PRECEDING AND CURRENT ROW — the window frame: the current row plus the two rows before it (= 3 months).
  5. WHERE limits to branch B003 and the first six months of 2020.

Result (slide):

yearMonth monthlySales 3-month moving avg 3-month moving sum
2020-01 21,000 21,000 21,000
2020-02 35,000 28,000 56,000
2020-03 40,000 32,000 96,000
2020-04 42,000 39,000 117,000
2020-05 44,000 42,000 126,000
2020-06 43,000 43,000 129,000

Checking the numbers (added):

  • 2020-02: only two rows exist so far → avg (21,000 + 35,000)/2 = 28,000; sum = 56,000.
  • 2020-03: (21,000 + 35,000 + 40,000)/3 = 32,000; sum 96,000.
  • 2020-04: (35,000 + 40,000 + 42,000)/3 = 39,000; sum 117,000.
  • 2020-05: (40,000 + 42,000 + 44,000)/3 = 42,000; sum 126,000.
  • 2020-06: (42,000 + 44,000 + 43,000)/3 = 43,000; sum 129,000.

Difference between the two examples (added): the table in Example 1 leaves the first two months blank (not enough history), whereas the SQL frame in Example 2 uses whatever rows exist — so Jan shows its own value and Feb averages two months. Both are valid; know which behaviour the question wants.

8.2 Ranking Functions

  • Ranking functions compute the rank of a record compared to other records in the dataset, based on the values of a set of measures — e.g., RANK and DENSE_RANK. (Others: cumulative distribution, percent rank, N-tiles — quartiles, deciles, percentiles.)
  • Syntax:
RANK()        OVER (ORDER BY columnList)
DENSE_RANK()  OVER (ORDER BY columnList)
  • Note (slide): DENSE_RANK leaves no gaps in the ranking sequence when there are ties.

Worked Example — Ranking Branch Sales (slide)

"Rank the total sales of properties for branch offices in Pretoria."

SELECT  Branch.branchNo,
        SUM(saleAmount) AS sales,
        RANK()       OVER (ORDER BY SUM(saleAmount) DESC) AS Ranking,
        DENSE_RANK() OVER (ORDER BY SUM(saleAmount) DESC) AS DenseRanking
FROM    Branch
JOIN    PropertySale ON Branch.branchNo = PropertySale.branchNo
WHERE   Branch.city = 'Pretoria'
GROUP BY Branch.branchNo;

Note (added): the slide writes branchNo unqualified in SELECT/GROUP BY although both tables have that column; most DBMSs would report an ambiguous column error — qualify it (Branch.branchNo) as above.

Result (slide):

branchNo sales ranking dense_ranking
B009 120,000,000 1 1
B018 92,000,000 2 2
B022 92,000,000 2 2
B028 92,000,000 2 2
B033 45,000,000 5 3
B046 42,000,000 6 4

Step-by-step explanation:

  1. ORDER BY SUM(saleAmount) DESC — rank by total sales, highest first.
  2. B009 is the highest → rank 1 in both.
  3. B018, B022, B028 tie at 92,000,000 → all get rank 2 in both functions.
  4. RANK after a tie leaves a gap: three branches took ranks 2–4, so the next branch (B033) is rank 5, and B046 is 6.
  5. DENSE_RANK leaves no gaps: the next distinct value simply gets the next number → B033 = 3, B046 = 4.
Function Ties Number after a 3-way tie at 2
RANK same rank 5 (gap)
DENSE_RANK same rank 3 (no gap)

11.2 Homework (2) — SQL Tasks (suggested answers — added)

The slide asks for four statements. The answers below are suggested solutions using the hotel star schema from Section 2 (verify in your Oracle environment).

Task 1 — Create the TIME dimension with hierarchy DAY → MONTH → QUARTER → YEAR

(The slide's hierarchy text is missing one arrow: read it as DAY → MONTH → QUARTER → YEAR.)

CREATE TABLE TIME (
    Time_Key    NUMBER PRIMARY KEY,   -- surrogate key (from a sequence)
    Day_ID      DATE         NOT NULL,
    Month_ID    VARCHAR2(7)  NOT NULL,   -- e.g. '2026-11'
    Quarter_ID  VARCHAR2(7)  NOT NULL,   -- e.g. '2026-Q4'
    Year_ID     NUMBER(4)    NOT NULL
);

CREATE DIMENSION TIME_DIM
    LEVEL Day     IS TIME.Day_ID
    LEVEL Month   IS TIME.Month_ID
    LEVEL Quarter IS TIME.Quarter_ID
    LEVEL Year    IS TIME.Year_ID
    HIERARCHY Time_Rollup (
        Day CHILD OF Month CHILD OF Quarter CHILD OF Year
    );

Explanation: the table holds one row per day with the codes of the month, quarter and year it belongs to; the CREATE DIMENSION declares the four levels and the roll-up hierarchy (child → parent) from lowest (day) to highest (year). Month and quarter IDs include the year so that "Jan 2026" and "Jan 2027" are different members.

Task 2 — Total revenue per hotel per month with GROUP BY CUBE

SELECT   h.Hotel_ID, t.Month_ID, SUM(f.Revenue) AS total_revenue
FROM     OCCUPANCY_FACTS f
JOIN     HOTEL h ON f.Hotel_Key = h.Hotel_Key
JOIN     TIME  t ON f.Time_Key  = t.Time_Key
GROUP BY CUBE (h.Hotel_ID, t.Month_ID);

Values expected in the output:

Hotel_ID Month_ID Meaning
H1 2026-01 Revenue of hotel H1 in January 2026 (detail row)
H1 NULL Total for hotel H1 across all months
NULL 2026-01 Total for January across all hotels
NULL NULL Grand total (all hotels, all months)
  • CUBE produces all 4 combinations: (hotel, month), (hotel), (month), (grand total).

Task 3 — Successively rolled-up revenue per hotel per quarter with GROUP BY ROLLUP

SELECT   h.Hotel_ID, t.Quarter_ID, SUM(f.Revenue) AS total_revenue
FROM     OCCUPANCY_FACTS f
JOIN     HOTEL h ON f.Hotel_Key = h.Hotel_Key
JOIN     TIME  t ON f.Time_Key  = t.Time_Key
GROUP BY ROLLUP (h.Hotel_ID, t.Quarter_ID);

Values expected in the output:

Hotel_ID Quarter_ID Meaning
H1 2026-Q1 Revenue of H1 in that quarter (detail)
H1 NULL Subtotal for hotel H1 over all quarters
NULL NULL Grand total over all hotels and quarters
  • ROLLUP rolls up right to left: (hotel, quarter) → (hotel) → (grand total). There is no "all hotels per quarter" row (that would need CUBE). Column order matters: ROLLUP (Quarter_ID, Hotel_ID) would give quarter subtotals instead.

Task 4 — GROUPING SETS for (Hotel, month), (Room_type, month), (Hotel, Room_type, month)

SELECT   h.Hotel_ID, r.Room_Type, t.Month_ID, SUM(f.Revenue) AS total_revenue
FROM     OCCUPANCY_FACTS f
JOIN     HOTEL   h ON f.Hotel_Key = h.Hotel_Key
JOIN     RM_TYPE r ON f.Room_Key  = r.Room_Key
JOIN     TIME    t ON f.Time_Key  = t.Time_Key
GROUP BY GROUPING SETS (
            (h.Hotel_ID,  t.Month_ID),
            (r.Room_Type, t.Month_ID),
            (h.Hotel_ID, r.Room_Type, t.Month_ID)
         );

Values expected in the output:

Hotel_ID Room_Type Month_ID Meaning
H1 NULL 2026-01 Revenue of hotel H1 in Jan, all room types (set 1)
NULL Luxury 2026-01 Revenue of luxury rooms in Jan, all hotels (set 2)
H1 Luxury 2026-01 Revenue of luxury rooms at hotel H1 in Jan (set 3, the most detailed)
  • Each NULL marks the column not in that grouping. Only the three listed groupings appear — no grand total or other subtotals unless you add () to the list.

12. Questions & Memo

Section 2–3 — ROLAP

Q1: What is a surrogate key and why is it used in a data warehouse?

A1: A system-generated key (e.g., from a sequence) for dimension rows. It lets a dimension keep multiple historical versions of the same business entity (same business key, different surrogate keys), independent of source-system keys.

Q2: Which SQL statements create and load a ROLAP structure? Which is Oracle-specific?

A2: Create: CREATE SEQUENCE, CREATE TABLE, CREATE DIMENSION, CREATE MATERIALIZED VIEW. Load: MERGE, UPDATE/INSERT. CREATE DIMENSION is Oracle-specific.

Q3: Explain each clause of CREATE DIMENSION HOTELS_DIM (LEVEL, HIERARCHY, ATTRIBUTE … DETERMINES).

A3: LEVEL names a level and the column identifying it; HIERARCHY … CHILD OF … gives the roll-up path from lowest to highest level; ATTRIBUTE X DETERMINES (…) states that the level's key functionally determines the listed attributes.

Section 4 & 5 — Slowly Changing Dimensions and Loading

Q4: Why do dimension tables need a strategy for change?

A4: A warehouse stores history for a long period, while dimension attributes (e.g., a customer's marital status) change over time; the strategy decides whether and how history is kept.

Q5: Define Type 1, Type 2 and Type 3 changes.

A5: Type 1: overwrite the old value. Type 2: create a new record for the change (history preserved). Type 3: add an alternate attribute so old and new values are in the same record.

Q6 (Tracing): Customer 850002 (Cust_Key 12345, single, Jones, start 01/03/2015) marries on 10/03/2018 and becomes Mrs Charming. Show the Type 2 result.

A6: Close the old row (End_date 09/03/2018) and add a new row with a new surrogate key (12347), same Cust_ID 850002, start 10/03/2018, end blank (current), married, Charming.

Q7: What is the benefit of Type 2 for historical reporting?

A7: Earlier facts stay linked to the old row (customer was single then) and new facts to the new row, so analyses by historical attribute values remain correct.

Q8: Distinguish the initial load from incremental loads and explain how MERGE supports both.

A8: Initial load populates the empty warehouse; incremental loads add new/changed data periodically. MERGE updates matching rows and inserts non-matching ones, so on an empty dimension everything is inserted, and later loads apply updates and inserts.

Q9 (Tracing): In the slide's MERGE, why does a customer whose marital status changed go to WHEN NOT MATCHED?

A9: The ON condition requires both Cust_ID and Marital_Status to match; with a changed status, no existing row matches, so the INSERT branch creates a new row (a Type 2 change).

Section 6–8 — SQL OLAP Extensions

Q10: Name three business calculations that plain SQL struggles with and the SQL extensions that address them.

A10: Percentage change vs a year ago; moving averages; cumulative sums/statistics. Addressed by OLAP extensions: extended grouping (ROLLUP, CUBE, GROUPING SETS) and window and ranking functions.

Q11: Explain what groups CUBE, ROLLUP and GROUPING SETS produce for (province, month).

A11: CUBE: (province, month), (province), (month), grand total. ROLLUP: (province, month), (province), grand total. GROUPING SETS: only the listed groupings (e.g., (province, month), (province), ()).

Q12 (Calculation): Revenue: Gauteng-Jan 10, Gauteng-Feb 20, KZN-Jan 5, KZN-Feb 15. How many rows does GROUP BY CUBE (province, month) return and what are the month-only subtotals?

A12: 9 rows (4 detail + 2 province subtotals + 2 month subtotals + 1 grand total). Month subtotals: Jan 15, Feb 35; grand total 50.

Q13: How many rows does GROUP BY ROLLUP (province, month) return for the data in Q12?

A13: 7 (4 detail + 2 province subtotals [Gauteng 30, KZN 20] + grand total 50).

Q14: What does () mean inside GROUPING SETS?

A14: The empty grouping — i.e., the grand total over all rows.

Q15 (Tracing): Monthly revenue Jan–Jun is 1m, 4m, 1m, 2m, 3m, 4m. Compute the 3-month moving averages for March to June.

A15: Mar (1+4+1)/3 = 2m; Apr (4+1+2)/3 = 7/3 ≈ 2.33m; May (1+2+3)/3 = 2m; Jun (2+3+4)/3 = 3m.

Q16: Explain AVG(SUM(saleAmount)) OVER (ORDER BY yearMonth ROWS BETWEEN 2 PRECEDING AND CURRENT ROW).

A16: The inner SUM(saleAmount) (with GROUP BY yearMonth) gives monthly totals; the OVER clause orders the months and defines a window of the current row and the two preceding rows; AVG then averages those monthly totals over that window → a 3-month moving average.

Q17 (Tracing): Using the 2020 B003 table, what are the 3-month moving average and sum for 2020-04?

A17: (35,000 + 40,000 + 42,000)/3 = 39,000; sum = 117,000.

Q18 (Tracing): Branch sales: B009 120m; B018, B022, B028 each 92m; B033 45m; B046 42m. Give RANK and DENSE_RANK for B033.

A18: RANK = 5 (three branches tied at rank 2 occupy ranks 2–4, leaving a gap) and DENSE_RANK = 3 (no gaps).

Q19: Distinguish RANK from DENSE_RANK.

A19: Both give tied rows the same rank; RANK skips numbers after ties (gaps), DENSE_RANK does not.

Q20: Name three N-tile ranking measures and two examples of modern BI tools.

A20: Quartiles, deciles, percentiles (also cumulative distribution and percent rank). BI tools: Power BI, Tableau, Oracle Analytics Cloud (open source: Apache Superset).

Section 10 — OLAP Tool Categories

Q21: List the four OLAP tool categories and say which one this module's star schema implements.

A21: MOLAP, ROLAP, HOLAP, DOLAP. The star schema in relational tables implements ROLAP.

Section 11 — Homework-style Questions

Q22 (Code): Write a query giving revenue per hotel per quarter with successive roll-ups, and explain the NULL values.

A22: … GROUP BY ROLLUP (h.Hotel_ID, t.Quarter_ID). Rows: (hotel, quarter) detail; (hotel, NULL) = subtotal for that hotel over all quarters; (NULL, NULL) = grand total. NULL marks the level rolled up.

Q23 (Code): Write a GROUPING SETS query for (Hotel, month), (Room_type, month) and (Hotel, Room_type, month).

A23: See Task 4 (Section 11.2): GROUP BY GROUPING SETS ((h.Hotel_ID, t.Month_ID), (r.Room_Type, t.Month_ID), (h.Hotel_ID, r.Room_Type, t.Month_ID)) — each NULL indicates the column absent from that grouping.

Q24 (Scenario): A retailer wants for each province and quarter: revenue, subtotals per province, and a grand total; plus a ranking of provinces by total revenue. Outline the SQL features to use.

A24: Join the sales fact to the branch and time dimensions; use GROUP BY ROLLUP (province, quarter) for detail + province subtotals + grand total, and RANK() OVER (ORDER BY SUM(revenue) DESC) to rank provinces (applied to province-level totals, e.g., in a separate query or subquery on the province-level rows).
