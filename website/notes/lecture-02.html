1. Why Object-Relational? Arguments For and Against the Relational Model

1.1 Arguments Against the Relational Data Model

  • Relational DBMSs are satisfactory for normal/standard business applications — i.e., storing & querying business transactions data.
  • BUT: Relational DBMSs cannot support applications that need to store & query complex data — e.g., CAD, GIS.
    • CAD: Computer Aided Design.
    • GIS: Geographical Information Systems.
  • Illustration (from the slides): A simple Business invoice is easy for an RDBMS to represent (flat rows/columns), but CAD/GIS data (e.g., a spatial road network map, or an engineering design with thousands of interlinked parts) does not fit naturally into flat relational tables.

Example (added for clarity)

A GIS application must store a road's shape as a sequence of connected geographic coordinates, plus topological relationships to intersecting roads, all of which must be queried spatially ("which roads pass within 2 km of this point?"). Representing this purely relationally would require extremely complex, join-heavy schemas and cannot naturally express spatial operators (e.g., "intersects," "within") the way an extended, object-aware DBMS type system can.

1.2 Arguments For the Relational Data Model

  • The relational model is part of any real-world DB environment.
  • Businesses have made major investments in Relational DBs — switching away entirely is costly and risky.
  • Complex applications can be handled by extensions to the relational model (i.e., support for ORDBMS) — so the relational core doesn't need to be abandoned.
  • There is a smooth transition through upgrades to newer DBMS versions which are ORDBMS — existing relational applications keep working while new OO capabilities become available.
  • Database Market Share:
    • RDBMS: very large (billions of dollars).
    • ORDBMS: features are now mainstream, especially in open-source and hybrid systems.

Example (added for clarity)

A bank with decades of RDBMS-based transaction-processing infrastructure can upgrade to PostgreSQL (an ORDBMS) and continue running all existing relational SQL and applications unchanged, while gradually adopting new object-relational features (e.g., JSONB columns for flexible transaction metadata) only where genuinely useful — this "smooth transition" is a key argument for the object-relational approach over building a brand-new, incompatible OODBMS from scratch.

2. Introduction to ORDBMS

  • An ORDBMS extends the relational model with OO features, such as:
    • Classes & objects.
    • Aggregation & inheritance.
    • Polymorphism & dynamic binding, etc.
  • An ORDBMS bridges the gap between:
    • OO programming languages and RDBMS data.
    • OO data modeling and RDBMS.

Example (added for clarity)

A Java application using JPA-style objects (Country, City) can map those classes almost directly onto ORDBMS structures — e.g., a PostgreSQL CREATE TYPE structured type or table inheritance hierarchy — rather than needing to flatten the object graph entirely into plain relational tables, reducing the object-relational impedance mismatch (recall this concept from the OODBMS lectures).

4. Postgres — the Historical ORDBMS

  • Postgres ('Post Ingres') was a research DBMS designed to be a potential successor to INGRES.
  • The query language for Postgres was called postquel.
  • Postgres extended the Relational model to include:
    • Abstract Data Types (ADTs) — via DEFINE TYPE.
    • Data of type 'procedure' — via DEFINE PROCEDURE.
    • Operators and precedence + associativity of operators — via DEFINE OPERATOR.
  • Postgres supported OO constructs such as:
    • Inheritance.
    • Aggregation.
    • Attributes that reference tuples (objects) in other relations.

Example (added for clarity)

Using DEFINE TYPE, an early Postgres user might have defined a custom point ADT, and using DEFINE OPERATOR, could then define a custom ## operator meaning "distance between two points," so that queries could write p1 ## p2 — this is directly analogous to how modern PostgreSQL still supports geometric types and operators today (see Section 12), showing a direct lineage from Postgres's original ADT design to the modern product.

5. SQL:2016 — New Object-Oriented Features (Overview)

The SQL:2016 standard introduced the following new OO features:

  • Row types.
  • User-defined types (UDT) — distinct types, structured types.
  • Supertype/subtype relationship.
  • User-defined routines (UDR) — procedures, functions, methods, operators.
  • Collection types — arrays, sets, lists, and multisets.

Note: The SQL:2023 standard has additional OOP extensions beyond SQL:2016.

6. SQL:2016 Row Types

  • A Row type is a sequence of (field_name, data_type) pairs.
  • A column of a table can contain row values — i.e., a single column can itself be a "mini-row" of multiple sub-fields.
  • A complete row can be:
    • Stored in a variable.
    • Passed as an argument to a function.
    • Returned as a return value from a function call.

Conceptual Example — Branch with a Row-Typed Address Column (from the slides)

branchNo Address (is a row type)
street city postcode
B005 22 Deer Rd London SW14Eh

6.1 Coding Example 1 — Creating and Populating a Row-Typed Table

CREATE TABLE Branch (
    branchNo CHAR(4),
    address  ROW ( street   VARCHAR(25),
                    city     VARCHAR(15),
                    postcode VARCHAR(8) ) );

INSERT INTO Branch
    VALUES ( 'B005',
             ROW ('22 Roper street', 'Pretoria', '0002'));

Result:

branchNo Address (is a row type)
street city postcode
B005 22 Roper street Pretoria 0002

Step-by-step walkthrough:

  1. CREATE TABLE Branch declares a normal table with two "top-level" columns: branchNo and address.
  2. address ROW(...) — instead of address being a single scalar column, it is declared as a row type, itself containing three sub-fields: street, city, postcode.
  3. INSERT INTO Branch VALUES ('B005', ROW(...)) — the second value supplied is not a single scalar but a constructed ROW(...) value, matching the row type's structure exactly (street, city, postcode in order).
  4. Result: the single address column visually "contains" three sub-columns — this is not possible in a purely 1NF-compliant traditional relational table (recall Weakness 4, homogeneous data structure, from the OODBMS lectures).

6.2 Coding Example 2 (added for step-by-step clarity) — A Student Table with a Row-Typed ContactInfo

CREATE TABLE Student (
    studentNo CHAR(6),
    contactInfo ROW ( phone   VARCHAR(15),
                       email   VARCHAR(40),
                       address VARCHAR(50) ) );

INSERT INTO Student
    VALUES ( 'S12345',
             ROW ('012-555-1234', 'thabo@example.com', '10 Kudu St, Pretoria'));

Step-by-step walkthrough:

  1. contactInfo is declared as a row type with three sub-fields (phone, email, address).
  2. The INSERT supplies a ROW(...) constructor matching that structure exactly, in the same order as declared.
  3. Just like the Branch example, this lets one logical column hold a small structured record, keeping related contact details grouped together within a single table cell, rather than needing a fully separate joined table.

7. SQL:2016 User-Defined Types (UDTs)

UDTs are the SQL:2016 equivalent of the ADTs from the original postquel language (Section 4) — i.e., UDTs == ADTs of postquel.

7.1 What is a UDT?

  • A user-defined data type (UDT) is a data type derived from an existing data type.
  • A UDT may be:
    • a distinct (simple) type, or
    • a structured type.

7.2 Distinct (Simple) Types

  • A distinct type is equivalent to a domain in traditional relational theory.
  • Purpose:
    • Makes a distinction between the same underlying data type (e.g., two different VARCHAR(5) columns that should never be mixed up, like an owner number vs. a staff number).
    • Enforces type checking — the DBMS will not allow, e.g., an OwnerNoType value to be compared/assigned to a StaffNoType value even though both are internally VARCHAR(5).

7.3 Coding Example 1 — Distinct Types (from the slides)

CREATE TYPE OwnerNoType AS VARCHAR(5) FINAL;
CREATE TYPE StaffNoType AS VARCHAR(5) FINAL;
CREATE TYPE NameType    AS VARCHAR(15) FINAL;

Step-by-step walkthrough:

  1. CREATE TYPE OwnerNoType AS VARCHAR(5) FINAL; — declares a new distinct type OwnerNoType, whose underlying representation is VARCHAR(5).
  2. FINAL — this keyword means OwnerNoType cannot be used as a supertype — i.e., no further subtypes can be derived from it (see Section 8 for the alternative, NOT FINAL).
  3. StaffNoType and NameType are declared the same way, each also VARCHAR-based but logically distinct from one another and from OwnerNoType.
  4. Effect: even though OwnerNoType and StaffNoType are both textually VARCHAR(5), the DBMS treats them as incompatible types, catching logic errors (e.g., accidentally comparing an owner number to a staff number) at the type-checking level.

7.4 Coding Example 2 (added for step-by-step clarity) — Distinct Types for a Property System

CREATE TYPE PropertyNumberType AS VARCHAR(5) FINAL;
CREATE TYPE ClientNumberType   AS VARCHAR(5) FINAL;

Step-by-step walkthrough:

  1. Two distinct types are declared, both based on VARCHAR(5), exactly following the pattern of OwnerNoType/StaffNoType.
  2. Both use FINAL, meaning neither can act as a supertype for further subtyping.
  3. This prevents, for example, accidentally passing a ClientNumberType value into a function parameter expecting a PropertyNumberType, even though both are five-character strings underneath.

7.5 Structured Types

A structured UDT definition consists of:

  • Attribute definitions.
  • Routine declarations (methods).

7.6 Coding Example 1 — Structured Type Attribute Definitions (from the slides)

CREATE TYPE PersonType AS (
    dateOfBirth  DATE,
    gender       CHAR,
    fName        NameType   NOT NULL,
    lName        NameType   NOT NULL)
    .................
  • Here, dateOfBirth, gender, fName, lName are the attribute definitions of the PersonType structured UDT.

7.7 Structured Types — Full Definition with Methods and Modifiers

CREATE TYPE PersonType AS (
    dateOfBirth DATE  ....... )

    INSTANTIABLE
    NOT FINAL
    REF IS SYSTEM GENERATED
    INSTANCE METHOD age() RETURNS INTEGER;
    INSTANCE METHOD …………….
  • Stored attribute — the attribute definitions (e.g., dateOfBirth) hold the actual persisted data.
  • INSTANTIABLE — instances can be created of this type.
  • NOT FINAL — subtypes can be defined from this type.
  • REF IS SYSTEM GENERATED — declares that reference values (OID-like identifiers, see Section 9) will be generated automatically by the system.
  • INSTANCE METHOD age() RETURNS INTEGER; — declares a method (routine) belonging to instances of this type.

7.8 INSTANTIABLE and NOT FINAL — Creating Tables Based on UDTs

  • INSTANTIABLE
    • Specifies that the UDT is instantiable.
    • The user can then create one or more tables based on the UDT.
    • If the keyword INSTANTIABLE is left out, the UDT can be used only as an attribute data type — not as a basis for a table of objects.
  • NOT FINAL
    • Indicates that subtypes can be created for that type (see Section 8).

7.9 Coding Example 2 (added for step-by-step clarity) — Implementing a Method Body

CREATE TYPE PersonType AS (
    .................)
    INSTANCE METHOD age() RETURNS INTEGER;...

CREATE INSTANCE METHOD age ( )
    RETURNS INTEGER FOR PersonType
    BEGIN
        RETURN  /*val calculated from SELF.dateOfBirth*/
    END;

Step-by-step walkthrough:

  1. The method signature (INSTANCE METHOD age() RETURNS INTEGER;) is declared inside the CREATE TYPE statement — this only announces that the method exists, not what it does.
  2. The method implementation is provided separately: CREATE INSTANCE METHOD age() RETURNS INTEGER FOR PersonType — the FOR PersonType clause associates this implementation with the PersonType structured type.
  3. Inside BEGIN ... END, SELF refers to the specific PersonType instance the method is being called on — the body would compute an integer age from SELF.dateOfBirth (e.g., subtracting the birth date from the current date).
  4. Why this matters: this is the SQL:2016 realisation of the same idea as the Pilot class's addPoints() method from the OODBMS lectures — attaching custom, reusable behaviour directly to a data type, something a plain relational table cannot do.

8. SQL:2016 Supertypes & Subtypes (Inheritance)

  • The subtype is created as a new type that is similar but not identical to an already defined type.
  • The subtype then inherits all the functions of the predefined type, which is referred to as the supertype.

8.1 Coding Example 1 — Inheritance with UNDER (from the slides)

CREATE TYPE StaffType UNDER PersonType AS (
    staffNo    StaffNoType,
    position   VARCHAR(10) DEFAULT 'Assistant',
    salary     DECIMAL(7, 2),
    branchNo   CHAR(4)    )

    INSTANTIABLE
    NOT FINAL
    INSTANCE METHOD isManager()
        RETURNS BOOLEAN;

Step-by-step walkthrough:

  1. CREATE TYPE StaffType UNDER PersonType AS (...) — the UNDER keyword makes StaffType a subtype of PersonType (the supertype). StaffType automatically inherits PersonType's attributes (dateOfBirth, gender, fName, lName) and any methods (e.g., age()), without redeclaring them.
  2. StaffType then adds its own new attributes: staffNo, position (with a DEFAULT value of 'Assistant'), salary, branchNo.
  3. INSTANTIABLE and NOT FINAL apply here exactly as in Section 7.8 — instances of StaffType can be created, and further subtypes could still be derived from StaffType itself.
  4. INSTANCE METHOD isManager() RETURNS BOOLEAN; declares a new method specific to StaffType (not inherited from PersonType) — a Staff object can call .age() (inherited) and .isManager() (its own).

8.2 Coding Example 2 (added for step-by-step clarity) — A Second Subtype, ClientType

CREATE TYPE ClientType UNDER PersonType AS (
    clientNo   ClientNumberType,
    prefType   VARCHAR(10),
    maxRent    DECIMAL(7, 2) )

    INSTANTIABLE
    NOT FINAL
    INSTANCE METHOD isEligible(minBudget DECIMAL(7,2))
        RETURNS BOOLEAN;

Step-by-step walkthrough:

  1. Exactly like StaffType, ClientType is declared UNDER PersonType, so it inherits dateOfBirth, gender, fName, lName, and any PersonType methods (e.g., age()).
  2. New, ClientType-specific attributes are added: clientNo, prefType, maxRent.
  3. A new method, isEligible(...), is declared specifically for ClientType — demonstrating that two different subtypes of the same supertype can each add their own distinct methods, just as in ordinary OOP class inheritance (compare to the OODBMS lectures' discussion of "representation of inheritance relationships done through class definitions").

9. SQL:2016 Reference Types & Object Identity

9.1 What are Reference Types?

  • System generates references — the same meaning as: OODBMS OID (see the OODBMS lectures for a full treatment of OIDs).
  • Example of structured types with reference generation:
CREATE TYPE PersonType AS (
    dateOfBirth DATE  ....... )
    INSTANTIABLE
    NOT FINAL
    REF IS SYSTEM GENERATED
    INSTANCE METHOD age() RETURNS INTEGER; ...
  • A Reference type uniquely identifies a row within a table — similar to the OID of OODBs.

9.2 Object Identifiers Using Reference Types

  • A Reference type is used to create unique object identifiers (OIDs).
  • Options for generating them:
    • Can specify system-generated object identifiers.
    • Alternatively, can use a primary key as the OID, as in the traditional relational model.
  • Examples of the two syntax forms:
    • REF IS SYSTEM GENERATED
    • REF IS <OID_ATTRIBUTE> <VALUE_GENERATION_METHOD>;

9.3 Creation of Typed (UDT) Tables

CREATE TABLE Person OF PersonType
    REF IS personID SYSTEM GENERATED;
  • Rows are objects.
  • One column for every attribute in the UDT.
  • Cannot add any columns to this table (its structure is fixed by the UDT it is based on).

Result:

personID dateOfBirth fName lName
1 1/1/1965 John Smith

Step-by-step walkthrough:

  1. CREATE TABLE Person OF PersonType — creates a table whose row structure is exactly defined by the PersonType UDT — one column per PersonType attribute.
  2. REF IS personID SYSTEM GENERATED; — names the reference/OID column personID, and specifies it will be automatically generated by the system (rather than derived from a user-supplied primary key).
  3. Once created, every row in Person is treated as an object — it can be referenced elsewhere (see Section 9.4 below) via its personID.

9.4 Coding Example — Using Reference Types for Path Expressions Instead of Joins

CREATE TABLE PropertyForRent (
    propertyNo   PropertyNumber   NOT NULL,
    street       StreetType, .....
    personID     REF (PersonType) SCOPE  PERSON )

    REFERENCES ARE CHECKED ON DELETE CASCADE,
    PRIMARY KEY (propertyNo)  );
  • This lets us replace complex JOIN definitions in queries with much simpler path expressions.

INSTEAD OF a traditional JOIN:

SELECT P.street, S.fname, S.lname
FROM   propertyForRent P, Person S
WHERE  P.personID = S.personID

USE THE DEREFERENCING OPERATOR INSTEAD:

SELECT P.street, P.personID->fname, P.personID->lname
FROM   PropertyForRent P;

Note (from the slide): "This is a JOIN" — i.e., despite the simpler-looking syntax, the dereferencing form is conceptually still performing a join-like navigation under the hood, but expressed as object path navigation rather than an explicit relational WHERE join condition.

Step-by-step walkthrough:

  1. personID REF (PersonType) SCOPE PERSON — declares personID in PropertyForRent as a reference attribute, whose scope (the table it refers into) is PERSON. This is directly analogous to storing an OID as an attribute in the OODBMS relationship examples (recall Branch storing manager: OID6).
  2. REFERENCES ARE CHECKED ON DELETE CASCADE — a referential-integrity rule: if the referenced Person row is deleted, dependent rows/references are handled via cascade.
  3. Traditional JOIN form: requires listing two tables in the FROM clause (propertyForRent P, Person S) and an explicit WHERE P.personID = S.personID join condition.
  4. Dereferencing form: uses the -> operator to "walk across" the reference directly — P.personID->fname means "follow the reference stored in P.personID and get its fname attribute" — no second table needs to be named in the FROM clause, and no explicit join condition is written.
  5. Why this matters: this mirrors the exact same conceptual improvement discussed for OODBMSs (OID-based navigation eliminating joins) — SQL:2016 brings that same benefit into the relational/SQL world via reference types and the dereferencing operator.

10. From Postgres to PostgreSQL

  • Originally "Postgres," renamed "PostgreSQL" in 1996.
  • The query language postquel was replaced with SQL.
  • PostgreSQL uses a client/server model. A session consists of:
    1. A server process (called postgres):
      • Manages the database files.
      • Accepts connections to the database from client applications.
      • Performs database operations on behalf of the clients.
    2. Users' client (front end) applications:
      • Make requests for database operations.
  • PostgreSQL uses SQL + extensions for OOP as defined in SQL:2016 + other Postgres-specific features.

Example (added for clarity)

When a user opens pgAdmin 4 (a client application, see Section 11) and runs a query, pgAdmin sends the SQL text over a network connection to the running postgres server process, which parses, plans, and executes the query against the actual database files on disk, then sends the results back to pgAdmin for display — a direct illustration of the client/server session model described above.

13. PostgreSQL User-Defined Types: Enumerated Types

  • Enumerated types are data types that comprise a static, ordered set of values.
  • Similar to High-Level-Language (HLL) enum types.

13.1 Coding Example 1 — Defining and Using an Enum (from the slides)

CREATE TYPE mood AS ENUM ('sad', 'ok', 'happy');

CREATE TABLE person (
    name text, current_mood mood );

INSERT INTO person
    VALUES ('Cyril', 'happy');

SELECT * FROM person WHERE current_mood = 'happy';

Step-by-step walkthrough:

  1. CREATE TYPE mood AS ENUM ('sad', 'ok', 'happy'); — declares a new enumerated type mood, whose only legal values are the three listed strings, in this specific order (order matters for comparisons like < and > on enum values in PostgreSQL).
  2. CREATE TABLE person (name text, current_mood mood); — creates a table with a column, current_mood, typed as the custom mood enum, rather than a plain unrestricted text column.
  3. INSERT INTO person VALUES ('Cyril', 'happy'); — inserts a row; 'happy' is validated against the allowed enum values at insert time.
  4. SELECT * FROM person WHERE current_mood = 'happy'; — queries using the enum value directly in a WHERE clause, just like any other typed column.

13.2 Coding Example 2 (added for step-by-step clarity) — An Enum for Property Types

CREATE TYPE propertyType AS ENUM ('Flat', 'House', 'Studio');

CREATE TABLE PropertyForRent (
    propertyNo text,
    type propertyType );

INSERT INTO PropertyForRent
    VALUES ('PG4', 'Flat');

SELECT * FROM PropertyForRent WHERE type = 'Flat';

Step-by-step walkthrough:

  1. A propertyType enum restricts the legal values for a property's type column to exactly 'Flat', 'House', or 'Studio' — preventing typos or invalid categories (e.g., 'flatt') from ever being stored.
  2. The INSERT and SELECT statements follow the exact same pattern as the mood example — the enum type behaves like any ordinary typed column once declared.

14. PostgreSQL User-Defined Types: Composite Types

  • Composite types are similar to HLL record / struct types.
  • They represent a collection of field names and their corresponding data types, effectively mimicking the structure of a table row inside a single column.

14.1 Coding Example 1 — Defining and Using a Composite Type (from the slides)

CREATE TYPE inventoryItem AS (
    name        text,
    supplierID  integer,
    price       numeric);

CREATE TABLE StockOnHand (
    item  inventoryItem,  quantity  integer);

INSERT INTO StockOnHand VALUES
    ( ROW ('gismo', 42, 1.99), 1000);

Step-by-step walkthrough:

  1. CREATE TYPE inventoryItem AS (...) — declares a composite type with three fields: name (text), supplierID (integer), price (numeric).
  2. CREATE TABLE StockOnHand (item inventoryItem, quantity integer); — creates a table where the item column's type is the entire composite type — one column effectively holds a mini "sub-row."
  3. INSERT INTO StockOnHand VALUES (ROW('gismo', 42, 1.99), 1000); — the ROW(...) constructor supplies all three inventoryItem fields at once as the value for the item column, and 1000 is supplied separately for the plain quantity column.

14.2 Coding Example 2 — Querying Fields Inside a Composite Type (from the slides)

CREATE TYPE inventoryItem AS (
    name text, supplierID integer, price numeric);

CREATE TABLE StockOnHand (
    item inventoryItem, quantity integer);

SELECT (StockOnHand.item).name,
       (StockOnHand.item).price,
       StockOnHand.quantity
FROM StockOnHand
WHERE (StockOnHand.item).price > 0.99;

Step-by-step walkthrough:

  1. To access an individual field inside a composite-typed column, PostgreSQL requires the parenthesised dot-notation: (StockOnHand.item).name — the parentheses around StockOnHand.item are mandatory to disambiguate the composite field access from ordinary table.column syntax.
  2. (StockOnHand.item).name and (StockOnHand.item).price extract the name and price sub-fields respectively from the composite item column.
  3. StockOnHand.quantity is accessed normally, since quantity is a plain (non-composite) column.
  4. The WHERE (StockOnHand.item).price > 0.99 clause filters rows based on a field nested inside the composite column — something impossible in a strictly 1NF-atomic relational table without first normalising inventoryItem out into its own separate table.

15. PostgreSQL Arrays

  • PostgreSQL supports array types for all base and user-defined types.
  • Useful when a column needs to store multiple values of the same type.
  • Array elements may be of:
    • Any built-in type (e.g., integer, text, etc.)
    • A user-defined base type.
    • An enum type.
    • A composite type.

Further reading: data types supported in PostgreSQL are documented in Chapter 8 of the PostgreSQL user manual.

15.1 Coding Example 1 — Declaring an Array Column (from the slides, introductory version)

CREATE TABLE sales (id SERIAL PRIMARY KEY, item_prices NUMERIC[]);
INSERT INTO sales (item_prices) VALUES ('{12.99, 23.50, 8.99}');
SELECT item_prices[1] FROM sales;

Step-by-step walkthrough:

  1. item_prices NUMERIC[] declares a one-dimensional array of numeric values as a single column.
  2. The literal '{12.99, 23.50, 8.99}' uses PostgreSQL's curly-brace array literal syntax to insert three values into that single array column.
  3. item_prices[1] retrieves the first element of the array — note PostgreSQL arrays are 1-indexed by default, not 0-indexed.

15.2 Coding Example 2 — Declaring 1D and 2D Array Columns (from the slides, detailed version)

CREATE TABLE sal_Emp (
    name          text,
    payByQuarter  integer[ ],    /* 1D array  */
    schedule      text[ ][ ]   );  /* 2D array  */

16. PostgreSQL OOP Features: Table Inheritance

  • Tables can inherit from other tables — useful for modelling "is-a" relationships.
  • A subtable inherits columns and constraints (except primary keys) from its parent table.
  • In PostgreSQL, a table can inherit from one or more other tables (i.e., multiple inheritance is supported).

16.1 Coding Example 1 — Basic Table Inheritance (from the slides, introductory version)

CREATE TABLE vehicle (id SERIAL PRIMARY KEY, make TEXT, model TEXT);
CREATE TABLE car (doors INTEGER) INHERITS (vehicle);
  • car inherits the id, make, and model columns from vehicle, and adds its own doors column.

16.2 Coding Example 2 — Detailed Inheritance Example with Queries (from the slides)

CREATE TABLE CITIES (
    name        text,
    population  real,     /* in millions */
    area        int   );  /* in sq km    */

CREATE TABLE CAPITALS (
    state  char(2)  )
    INHERITS (CITIES);
  • ⇒ A row of CAPITALS inherits all columns (name, population, and area) from its parent, CITIES.
  • State capitals have an extra column, state.

Populating and querying:

INSERT INTO CITIES   VALUES ('Johannesburg', 2.5, 2500);
INSERT INTO CAPITALS VALUES ('Pretoria', 1.5, 900, 'GP');

-- e.g. list the names of all cities, including state capitals
SELECT * FROM CITIES;

-- e.g. list all the capitals
SELECT * FROM CAPITALS;

Results (from the slides' screenshots):

SELECT * FROM CITIES; →

name population area
Johannesburg 2.5 2500
Pretoria 1.5 900

SELECT * FROM CAPITALS; →

name population area state
Pretoria 1.5 900 GP

Step-by-step walkthrough:

  1. CITIES is created as a normal base table with three columns.
  2. CAPITALS INHERITS (CITIES) — CAPITALS automatically gains the name, population, and area columns from CITIES, and adds its own extra state column.
  3. Inserting into CAPITALS ('Pretoria', 1.5, 900, 'GP') supplies values for all four columns — the three inherited ones plus state.
  4. Crucially: SELECT * FROM CITIES returns both Johannesburg and Pretoria — because Pretoria, as a row in the child table CAPITALS, is considered to also be "a city" through inheritance. This is the object-relational realisation of OOP's "is-a" relationship: every CAPITALS row is also a CITIES row.
  5. SELECT * FROM CAPITALS returns only Pretoria (with its extra state column) — querying the child table directly does not pull in rows that exist only in the parent table (Johannesburg, which was inserted directly into CITIES, not CAPITALS).

Important caveat (explored further in Section 20.6): Triggers are NOT automatically inherited by child tables — this becomes a significant practical issue when trying to enforce a rule (e.g., "area must be positive") uniformly across both a parent and child table.

17. PostgreSQL User-Defined Functions

Content from Lecture 6, Lecture 7, and Lecture 8 on user-defined functions has been merged here into one complete section, since the lectures progressively build on the same material.

17.1 Motivation

  • PostgreSQL supports user-defined functions using SQL, PL/pgSQL, and other languages.
  • This encourages encapsulating logic inside the database (rather than solely in application code) — directly addressing Weakness 3 (Limited Operations) of plain RDBMSs discussed in the OODBMS lectures.
  • PostgreSQL allows user-defined functions to be written in languages besides SQL and C. These other languages are generically called procedural languages (PLs).

17.2 SQL:2016 / SQL/PSM Context

  • SQL Persistent Stored Modules (SQL/PSM) is the SQL standard's framework for procedural database programming.
  • It provides extensions to SQL that provide a (server-side) procedural language, used to write functions, stored procedures, and triggers that are stored on the DB server.
  • PostgreSQL implements procedural programming primarily through PL/pgSQL, which extends SQL with procedural constructs.
  • Databases (Relational / Object-Relational) from different suppliers provide their own version of SQL/PSM, e.g.:
    • ORACLE: the PL/SQL language.
    • PostgreSQL: PL/pgSQL.

17.3 Four Categories of User-Defined Functions

  1. Query language functions — SQL functions, written purely in SQL.
  2. Procedural language functions — functions written in, e.g., PL/pgSQL, PL/Tcl, PL/Perl, and PL/Python (see Chapters 41–43 of the Postgres User Manual for more).
  3. Internal functions.
  4. C-language functions.

17.4 Two Categories of SQL Functions

  1. Row functions — operate on values of a table row.
  2. Table functions — operate on a whole table; these produce a set of rows, made up of either:
    • base data types (scalar types), or
    • composite data types (table rows).

17.5 SQL Function Syntax

CREATE FUNCTION functionName( pmt1Type, pmt2Type, .... ) RETURNS returntype AS
$$
    SQL statement
$$ LANGUAGE SQL;
  • The $$ is a delimiter you use to indicate where the function definition starts and ends.

17.6 Coding Example 1 — populationDensity SQL Function (from the slides)

-- DROP FUNCTION populationDensity(real, integer);   -- if you need to
CREATE FUNCTION populationDensity(real, int) RETURNS int  AS
$$
    SELECT CAST ( (($1 * 1000000) / $2 ) AS int )
    AS populationDensity;
$$ LANGUAGE SQL;

SELECT   name, population, area,
         populationDensity( population, area )
FROM CITIES;

Result (from the slide's screenshot):

name population area populationdensity
Johannesburg 2.5 2500 1000
Pretoria 1.5 900 1667

Step-by-step walkthrough:

  1. CREATE FUNCTION populationDensity(real, int) RETURNS int AS ... — declares a new SQL function taking two unnamed positional parameters (a real and an int) and returning an int.
  2. $1 and $2 — inside the function body, positional parameters are referenced as $1 (the first parameter, real) and $2 (the second, int) — there are no named parameter variables in this simplest SQL-function form.
  3. (($1 * 1000000) / $2) — computes population density as (population in millions × 1,000,000) ÷ area in km², i.e., people per km².
  4. CAST ( ... AS int ) — converts the (possibly fractional) result to an integer, per the declared RETURNS int.
  5. $$ LANGUAGE SQL; — specifies the function body is written in plain SQL (not PL/pgSQL).
  6. Calling it: populationDensity(population, area) is used directly inside a SELECT list, just like a built-in function — for Johannesburg: (2.5 × 1,000,000) / 2500 = 1000; for Pretoria: (1.5 × 1,000,000) / 900 ≈ 1667.

17.7 Coding Example 2 (added for step-by-step clarity) — A Simple SQL Row Function for Salary Bonus

CREATE FUNCTION annualBonus(real) RETURNS real AS
$$
    SELECT $1 * 0.10;
$$ LANGUAGE SQL;

SELECT name, salary, annualBonus(salary) FROM Staff;

Step-by-step walkthrough:

  1. annualBonus(real) takes a single positional parameter ($1, expected to be a salary).
  2. The function body is a single SQL SELECT computing 10% of that salary.

CREATE FUNCTION functionname( pmttype1, pmttype2, … )
    RETURNS returntype AS
$$
    DECLARE    --comment 1: declare vars only if necessary
        var1   vartype1,      var2    vartype2, …. ;

17.9 Coding Example 1 — popDensity PL/pgSQL Function (from the slides)

CREATE FUNCTION popDensity(real, int) RETURNS int AS
$$
    DECLARE   density int;
    BEGIN
        density = CAST ( (($1 * 1000000) / $2 ) AS int );
        RETURN density;
    END;
$$ LANGUAGE plpgsql;

SELECT   name, population, area,  popDensity( population, area )
FROM CITIES;

Step-by-step walkthrough:

  1. DECLARE density int; — declares a local variable, density, of type int, used as intermediate storage inside the function body (something a plain SQL function cannot do).
  2. BEGIN ... END; — wraps the procedural logic block.
  3. density = CAST(...) — computes and assigns the population density into the local variable (identical formula to the SQL-function version in Section 17.6).
  4. RETURN density; — returns the computed local variable's value.
  5. Calling it: exactly the same as the SQL-function version (popDensity(population, area) inside a SELECT), and produces the same numeric results (1000 for Johannesburg, 1667 for Pretoria) — this demonstrates that PL/pgSQL functions and SQL functions can achieve the same simple result, but PL/pgSQL supports much richer procedural logic (variables, conditionals, loops), as shown next.

17.10 Coding Example 2 — is_big_city PL/pgSQL Function with Conditional Logic (from the slides)

-- Given the table:
CREATE TABLE cities ( name text, population real, area int );

-- and function:
CREATE FUNCTION is_big_city( integer ) RETURNS text AS
$$
    DECLARE   big text;
    BEGIN
        IF   $1   >=   1000   THEN
              big   :=   'YES';
        ELSE
              big   :=   'NO';
        END IF;
        RETURN   big;
    END;
$$ LANGUAGE plpgsql;

-- and query:
SELECT name, area, is_big_city(area) FROM CITIES;

Result (from the slide's screenshot):

name area is_big_city
Johannesburg 2500 YES
Pretoria 900 NO

Step-by-step walkthrough:

  1. DECLARE big text; — declares a local text variable to hold the eventual 'YES'/'NO' result.
  2. IF $1 >= 1000 THEN ... ELSE ... END IF; — a conditional construct (see Section 18 for the full syntax) that checks whether the input area parameter is at least 1000 (km²).
  3. big := 'YES'; — the := operator is the preferred assignment style in PL/pgSQL (equivalent to =, but stylistically preferred, per the slides).
  4. RETURN big; returns the computed classification.
  5. For Johannesburg (area = 2500), 2500 >= 1000 is true, so the function returns 'YES'. For Pretoria (area = 900), the condition is false, so it returns 'NO' — matching the screenshot exactly.

18.5 Coding Example 1 — FOREACH Over an Array: total_salary (from the slides)

-- Given:
CREATE TABLE salEmp ( name text, payByQuarter int[ ], .. );

-- and function:
CREATE FUNCTION total_salary( int[ ] )   RETURNS   int  AS
$$
    DECLARE   val int;   total int;
    BEGIN
        total = 0;
        FOREACH val IN ARRAY $1
        LOOP
            total = total + val;
        END LOOP;
        RETURN total;
    END;
$$ LANGUAGE plpgsql;

-- and query:
SELECT name, paybyquarter, total_salary(paybyquarter) FROM sal_Emp;

Sample data used with this example (from the slides):

INSERT INTO sal_Emp VALUES (
    'Adriaan',
    '{22000, 27000, 27000, 27000}',
    '{ { "breakfast", "consulting" } , {"lunch" , "meeting" } }');

INSERT INTO sal_Emp VALUES (
    'Katlego',
    '{30000, 35000, 35000, 35000}',
    '{ { "breakfast", "consulting" } , { "lunch", "meeting" } }');

Step-by-step walkthrough:

  1. DECLARE val int; total int; — two local variables: val (holds each array element in turn) and total (accumulates the sum).
  2. total = 0; — initialise the running total before looping.
  3. FOREACH val IN ARRAY $1 LOOP ... END LOOP; — iterates over every element of the input array parameter ($1, the employee's payByQuarter array), assigning each element to val in turn.
  4. total = total + val; — accumulates the running sum inside the loop body.
  5. RETURN total; — after the loop finishes, returns the final accumulated sum.
  6. Applied to the sample data: for Adriaan ({22000, 27000, 27000, 27000}), total_salary would compute 22000+27000+27000+27000 = 103000. For Katlego ({30000, 35000, 35000, 35000}), it would compute 30000+35000+35000+35000 = 135000.

18.6 Coding Example 2 (added for step-by-step clarity) — FOR Loop Counting Big Cities

CREATE FUNCTION countBigCities() RETURNS int AS
$$
    DECLARE
        rec RECORD;
        count int;
    BEGIN
        count := 0;
        FOR rec IN SELECT * FROM CITIES LOOP
            IF rec.area >= 1000 THEN
                count := count + 1;
            END IF;
        END LOOP;
        RETURN count;
    END;
$$ LANGUAGE plpgsql;

SELECT countBigCities();

Step-by-step walkthrough:

  1. DECLARE rec RECORD; count int; — rec is a special RECORD variable type able to hold an entire row of arbitrary structure (here, a row from CITIES); count is a simple integer accumulator.
  2. count := 0; initialises the counter.
  3. FOR rec IN SELECT * FROM CITIES LOOP ... END LOOP; — this demonstrates the FOR var IN listexpr LOOP construct being driven by a plain embedded SQL statement (Section 18.4) rather than a fixed list — rec takes on each row of the CITIES query result in turn.
  4. IF rec.area >= 1000 THEN count := count + 1; END IF; — reuses the IF/THEN construct (Section 18.2) inside the loop body to conditionally increment the counter.
  5. RETURN count; returns the final tally — using the CITIES data from Section 16.2 (Johannesburg area 2500, Pretoria area 900), this function would return 1 (only Johannesburg qualifies as "big").

19. PostgreSQL JSON and JSONB Support

  • PostgreSQL has first-class support for JSON and binary JSON (JSONB).
  • This allows storage, indexing, and querying of semi-structured data.

19.1 Coding Example 1 — Storing and Querying JSONB (from the slides)

CREATE TABLE orders (id SERIAL, order_data JSONB);
INSERT INTO orders (order_data) VALUES ('{"customer": "Alice", "items": ["Book", "Pen"]}');
SELECT order_data->'customer' FROM orders;

Step-by-step walkthrough:

  1. order_data JSONB — declares a column that stores JSON data in PostgreSQL's efficient binary JSON representation (JSONB), which supports indexing, unlike plain JSON type storage (which stores an exact text copy).
  2. INSERT ... VALUES ('{"customer": "Alice", "items": ["Book", "Pen"]}'); — inserts a JSON document directly as a string literal, which PostgreSQL parses and stores as JSONB.
  3. order_data->'customer' — the -> operator extracts the value at the 'customer' key from the JSON document, returning it as a JSON value ("Alice", still JSON-typed, including its quotes).

19.2 Coding Example 2 (added for step-by-step clarity) — Querying a Nested Array in JSONB

SELECT order_data->>'customer' AS customer_name,
       jsonb_array_length(order_data->'items') AS num_items
FROM orders
WHERE order_data->'items' ? 'Book';

Step-by-step walkthrough:

  1. ->> (double-arrow operator) extracts the 'customer' value as plain text (Alice, without surrounding quotes) — contrasted with the single-arrow -> used in Section 19.1, which returns a JSON-typed value.
  2. jsonb_array_length(order_data->'items') — a built-in JSONB function that returns the number of elements in the 'items' JSON array (here, 2: "Book" and "Pen").
  3. WHERE order_data->'items' ? 'Book' — the ? (existence) operator checks whether the JSON array (or object) contains the given string — here, filtering only orders whose items array contains 'Book'.
  4. This demonstrates PostgreSQL's ability to query inside semi-structured JSON data using ordinary SQL WHERE/SELECT clauses, without needing to pre-define a rigid relational schema for every possible JSON field.

20. PostgreSQL Triggers

20.1 What is a Trigger?

  • A trigger invokes a trigger function automatically when a specified database event occurs.
  • Most commonly, the event arises due to an operation — INSERT, UPDATE, DELETE, or TRUNCATE — on a database table.
  • A trigger may be defined as a BEFORE trigger or an AFTER trigger.
    • A BEFORE trigger executes before the specified operation.
    • An AFTER trigger executes after the specified operation.
  • A trigger may be used to:
    • Enforce some referential constraints.
    • Enforce complex constraints (business rules).
    • Audit changes to data.

20.2 SQL:2016 Summary Table Entry — Trigger

Activity Statement example
Special operations for changes to database data: Trigger — SQL (compound) statement executed automatically by DBMS as a side effect of a modification to a named table e.g. 1 CREATE TRIGGER InsertPropTable BEFORE INSERT ON PropertyForRent ..... e.g. 2 CREATE TRIGGER DeletePropTable AFTER DELETE ON PropertyForRent .....

20.3 General Trigger Syntax (PostgreSQL / SQL/PSM-style)

Refer to Chapter 37 of the PostgreSQL documentation for the complete syntax.

CREATE [ OR REPLACE ] [ CONSTRAINT ] TRIGGER name { BEFORE | AFTER | INSTEAD OF } { event [ OR ... ] }
    ON table_name
    [ FROM referenced_table_name ]
    [ NOT DEFERRABLE | [ DEFERRABLE ] [ INITIALLY IMMEDIATE | INITIALLY DEFERRED ] ]
    [ REFERENCING { { OLD | NEW } TABLE [ AS ] transition_relation_name } [ ... ] ]
    [ FOR [ EACH ] { ROW | STATEMENT } ]
    [ WHEN ( condition ) ]
    EXECUTE { FUNCTION | PROCEDURE } function_name ( arguments )

Where event can be one of:

  • INSERT
  • UPDATE [ OF column_name [, ... ] ]
  • DELETE
  • TRUNCATE

20.4 Trigger Function + Trigger — Basic Pattern

CREATE FUNCTION triggerfunction( ) RETURNS TRIGGER AS
$$
    DECLARE -- declare vars  if necessary
    BEGIN
        -- code to compute any required values goes here.
        RETURN NEW;
    END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER triggername   -- e.g. of a before trigger
    BEFORE tableoperation ON tablename
        --- table operation is INSERT or DELETE or UPDATE
    FOR EACH ROW
        -- enables access to the NEW and OLD table rows
    EXECUTE FUNCTION triggerfunction( );
  • RETURNS TRIGGER — a special return type indicating the function is intended to be used as a trigger function.
  • RETURN NEW; — in a BEFORE INSERT/BEFORE UPDATE trigger, returning NEW allows the (possibly modified) new row to proceed with the operation.
  • FOR EACH ROW — this trigger fires once per affected row and enables access to the NEW and OLD table rows inside the trigger function body.

20.5 More Detailed Trigger Function Syntax

CREATE FUNCTION triggerfunction() RETURNS TRIGGER AS
$$
    DECLARE
        --comment 1: declare vars  if necessary. var1 vartype1, var2 vartype2,..
    BEGIN
        -- comment 2: code to compute any required values goes here. In the code,
        -- use NEW.attribute1,.. to access values of new input row, e.g. for INSERT.
        -- use OLD.attribute1,... to access values of existing row in table, e.g. for UPDATE,
        -- DELETE

        IF (condition to test for unwanted situation) THEN
            RAISE EXCEPTION 'error message for exception';
        END IF;
        RETURN NEW;
    END;
$$ LANGUAGE plpgsql;
  • NEW.attribute — accesses attribute values of the new row being inserted/updated.
  • OLD.attribute — accesses attribute values of the existing row being updated/deleted.
  • RAISE EXCEPTION '...' — aborts the triggering operation and reports an error if a business-rule condition is violated.

20.6 Coding Example 1 — Validating Data with a BEFORE Trigger (from the slides)

-- Given the table created as:
CREATE TABLE cities (name text, population real, area int);

CREATE OR REPLACE FUNCTION check_valid_area() RETURNS TRIGGER AS
$$
    BEGIN
        IF (NEW.area <= 0) THEN
            RAISE EXCEPTION 'Invalid area value!';
        END IF;
        RETURN NEW;
    END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER valid_area
    BEFORE INSERT OR UPDATE ON Cities
    FOR EACH ROW
        EXECUTE FUNCTION check_valid_area();

Testing the trigger:

SELECT * FROM Cities;

INSERT INTO Cities
VALUES ('Durban', 4.7, -3000);   -- attempt with an invalid (negative) area

INSERT INTO Cities VALUES
('Durban', 4.7, 3000);           -- attempt with a valid (positive) area

SELECT * FROM Cities;

Results (from the slides' screenshots):

  • Before either insert: Cities contains Johannesburg (2.5, 2500) and Pretoria (1.5, 900).

  • INSERT INTO Cities VALUES ('Durban', 4.7, -3000); → fails with:

    ERROR: Invalid area value!CONTEXT: PL/pgSQL function check_valid_area() line 4 at RAISESQL state: P0001

  • INSERT INTO Cities VALUES ('Durban', 4.7, 3000); → succeeds, and SELECT * FROM Cities; now shows:

name population area
Johannesburg 2.5 2500
Durban 4.7 3000
Pretoria 1.5 900

Step-by-step walkthrough:

  1. check_valid_area() is a trigger function: IF (NEW.area <= 0) THEN RAISE EXCEPTION ... checks the new row's area value — if it is zero or negative, the whole operation is aborted with an error message.
  2. CREATE TRIGGER valid_area BEFORE INSERT OR UPDATE ON Cities FOR EACH ROW EXECUTE FUNCTION check_valid_area(); attaches this function as a BEFORE trigger on Cities, firing for every row on both INSERT and UPDATE operations.
  3. The first insert attempt (area = -3000) is blocked — the trigger fires before the row would be written, detects the invalid value, and raises an exception, so the row is never actually inserted.
  4. The second insert attempt (area = 3000) passes validation — the trigger returns NEW unchanged, allowing PostgreSQL to proceed with the actual insert.

20.7 Coding Example 2 — The Inheritance + Trigger Pitfall, and Its Solution (from the slides)

The Problem — triggers are NOT inherited by child tables:

CREATE TABLE Cities  (name text, population real, area int);
CREATE TRIGGER valid_area BEFORE INSERT OR UPDATE ON Cities .... ;

CREATE TABLE Capitals (state character(2)) INHERITS (cities);
INSERT ....

SELECT * FROM Cities;
SELECT * FROM Capitals;

INSERT INTO Capitals VALUES ('Upington', 0.5, -1000, 'NC');
SELECT * FROM Cities;
-- ***NOT GOOD***
-- ***SOLUTION??? ***

Observed result (from the slide's screenshot): despite Cities having the valid_area trigger, INSERT INTO Capitals VALUES ('Upington', 0.5, -1000, 'NC'); succeeds without error, and the invalid row (area = -1000) shows up in SELECT * FROM Cities; — because Upington was inherited into view via Capitals, but the valid_area trigger defined on Cities was never applied to INSERTs made directly on Capitals.

The Solution — explicitly create the trigger on the child table too:

CREATE TABLE Cities   (name text, population real, area int);
CREATE TABLE Capitals (state character(2)) INHERITS (cities);

-- So, create the trigger on Capitals AS WELL:
CREATE TRIGGER valid_area
    BEFORE INSERT OR UPDATE ON Capitals
    FOR EACH ROW
        EXECUTE FUNCTION check_valid_area();

DELETE FROM CAPITALS WHERE name = 'Upington';
INSERT INTO Capitals VALUES ('Upington', 0.5, -1000, 'NC');
-- Result: ERROR: Invalid area value! (same trigger function, now correctly applied)

SELECT * FROM Cities;
SELECT * FROM Capitals;

Confirmed via the slides' final example, applying triggers to both parent and child from the start:

CREATE TABLE cities   (name text, population real, area int);
CREATE TABLE Capitals (state character(2)) INHERITS (cities);

CREATE OR REPLACE FUNCTION check_valid_area() RETURNS TRIGGER AS
$$
    BEGIN    ....RETURN NEW;  END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER valid_area
    BEFORE INSERT OR UPDATE ON Cities
    FOR EACH ROW
        EXECUTE FUNCTION check_valid_area();

CREATE TRIGGER valid_area
    BEFORE INSERT OR UPDATE ON Capitals
    FOR EACH ROW
        EXECUTE FUNCTION check_valid_area();

NOTE (from the slides):

  1. TRIGGERS cannot be inherited.
  2. TRIGGER FUNCTIONS can be RE-USED (the same check_valid_area() function is attached to two separate triggers).
  3. The same name can be used for triggers on different tables (both triggers here are named valid_area, one on Cities, one on Capitals — no naming conflict, since trigger names are scoped per-table).

Step-by-step walkthrough:

  1. Recall from Section 16.2 that Capitals INHERITS (Cities), so column definitions (and ordinary constraints, excluding primary keys) flow down automatically — but this example demonstrates that triggers are a specific exception to that inheritance behaviour.
  2. Because the valid_area trigger was only ever explicitly attached ON Cities, any INSERT performed directly on Capitals (like the Upington row) never passes through that trigger's validation logic — even though, logically, Capitals rows are also Cities rows.
  3. The fix requires explicitly creating a second trigger, attached directly ON Capitals, reusing the exact same trigger function (check_valid_area()), so validation logic is written once but enforced on both tables.
  4. This reinforces the general principle: when using PostgreSQL table inheritance, any trigger-based business rule intended to apply to the whole hierarchy must be explicitly created on every table in that hierarchy, not assumed to propagate automatically like column definitions do.

20.8 Coding Example 3 — An AFTER DELETE Audit Trigger (from the slides)

CREATE TABLE deletedCities (
    name             text,
    population       real,
    area             integer,
    deleteDateTime   timestamp,
    deleteUserID     text    );

CREATE FUNCTION record_deleted_city() RETURNS TRIGGER AS
$$
BEGIN
    INSERT INTO DeletedCities
        SELECT OLD.*, now(), user; --user is current user
    RETURN OLD;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER audit_deleted_cities
    AFTER DELETE ON Cities
    FOR EACH ROW
        EXECUTE FUNCTION record_deleted_city();

Testing the trigger:

INSERT INTO Cities VALUES ('Cape Town', 2.0, 3500);
SELECT * FROM Cities;

DELETE FROM Cities
WHERE name = 'Cape Town';

SELECT * FROM DeletedCities;

Results (from the slide's screenshot):

After the insert, Cities contains (among others): Johannesburg (2.5, 2500), Durban (4.7, 3000), Cape Town (2, 3500), Pretoria (1.5, 900).

After the delete, SELECT * FROM DeletedCities; shows:

name population area deletedatetime deleteuserid
Cape Town 2 3500 2023-08-14 15:31:44.168757 postgres

Step-by-step walkthrough:

  1. deletedCities is a separate audit table, designed to record a historical log of deleted Cities rows.
  2. record_deleted_city() is an AFTER DELETE trigger function: INSERT INTO DeletedCities SELECT OLD.*, now(), user; — this copies all attributes of the just-deleted row (OLD.*), plus the current timestamp (now()) and the current database user (user), into the audit table.
  3. RETURN OLD; — in a DELETE trigger, the convention is to return OLD (the row that was deleted), rather than NEW (which doesn't exist for a delete operation).
  4. CREATE TRIGGER audit_deleted_cities AFTER DELETE ON Cities FOR EACH ROW EXECUTE FUNCTION record_deleted_city(); — attaches this as an AFTER trigger, meaning it runs after the actual delete has already taken place, for every row deleted.
  5. When Cape Town is deleted from Cities, the trigger automatically inserts a matching audit record into DeletedCities, capturing exactly when (2023-08-14 15:31:44.168757) and by whom (postgres) the deletion occurred — with no application code required to perform this logging; it happens entirely as a database-level side effect.

20.9 FOR EACH ROW vs. FOR EACH STATEMENT

Trigger Executes
FOR EACH ROW Once per affected row.
FOR EACH STATEMENT Once per SQL statement.

Example — FOR EACH STATEMENT Trigger (from the slides)

CREATE OR REPLACE FUNCTION audit_staff_insert()
RETURNS TRIGGER AS $$
BEGIN
    INSERT INTO StaffAudit
    VALUES (
        NEW.staffNo, NEW.fName, NEW.lName, current_user,
        now()
    );

    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER StaffAfterInsert
AFTER INSERT ON Staff
FOR EACH STATEMENT
EXECUTE FUNCTION audit_staff_insert();
  • Because this trigger is declared FOR EACH STATEMENT, it fires once for the whole INSERT statement, no matter how many rows that single statement inserts — not once per inserted row. (Note: within a FOR EACH STATEMENT trigger, NEW/OLD row-level values are not directly usable the way they are in FOR EACH ROW triggers, since there may be many affected rows; the slide's use of NEW.staffNo etc. here illustrates the intended single-row-insert use case.)

20.10 When Should I Use a Trigger?

Good uses:

  • Auditing changes.
  • Maintaining derived data.
  • Enforcing complex business rules.
  • Automatically recording timestamps.
  • Maintaining related tables.

Avoid triggers when:

  • A simple CHECK constraint is sufficient.
  • A foreign key can enforce the rule.
  • The behaviour belongs in application/business logic.
  • The trigger would make the database behaviour difficult to understand.

Example (added for clarity)

Enforcing "an employee's salary must be positive" is better done with a simple CHECK (salary > 0) constraint directly on the column — using a full trigger for this would be unnecessary overhead. In contrast, "automatically log every change to a Staff row, including who made it and when, into an audit table" (as in Section 20.8) is a good use of a trigger, since a CHECK constraint cannot express that kind of cross-table, timestamped side-effect logic.

22. Questions & Memo

Section 1 — Why Object-Relational?

Q1: According to the slides, why can't a plain RDBMS support applications like CAD or GIS, even though it is well-suited to standard business applications?

A1: RDBMSs are satisfactory for storing and querying standard business transaction data (e.g., invoices), but they cannot support applications that need to store & query complex data, such as CAD (Computer Aided Design) or GIS (Geographical Information Systems) data — this complex, structured, and often spatial data does not fit naturally into flat relational tables.

Q2: List the four arguments given in favour of retaining (and extending) the relational model rather than abandoning it entirely.

A2:

  1. The relational model is part of any real-world DB environment.
  2. Businesses have made major investments in relational DBs.
  3. Complex applications can be handled by extensions to the relational model (i.e., ORDBMS support).
  4. There is a smooth transition through upgrades to newer DBMS versions that are ORDBMS.

Section 2 — Introduction to ORDBMS

Q3: List the OO features that an ORDBMS adds to the relational model, and state the two "gaps" an ORDBMS bridges.

A3: An ORDBMS extends the relational model with classes & objects, aggregation & inheritance, and polymorphism & dynamic binding. It bridges the gap between (1) OO programming languages and RDBMS data, and (2) OO data modeling and RDBMS.

Section 4 — Postgres History

Q4: What was Postgres's original query language called, and what three extensions did Postgres make to the relational model?

A4: Postgres's original query language was called postquel. It extended the relational model to include: Abstract Data Types (ADTs) (via DEFINE TYPE), data of type 'procedure' (via DEFINE PROCEDURE), and operators and their precedence/associativity (via DEFINE OPERATOR).

Section 6 & 7 — Row Types and UDTs

Q5 (Code Tracing): Given CREATE TABLE Branch (branchNo CHAR(4), address ROW(street VARCHAR(25), city VARCHAR(15), postcode VARCHAR(8))); and INSERT INTO Branch VALUES ('B005', ROW('22 Roper street', 'Pretoria', '0002'));, what value would SELECT (address).city FROM Branch WHERE branchNo = 'B005'; return?

A5: 'Pretoria' — because the row type's city field was set to 'Pretoria' by the ROW(...) constructor at insert time, and (address).city extracts that specific sub-field from the row-typed address column.

Q6: Explain the difference between a "distinct type" and a "structured type" in SQL:2016 UDTs, and what FINAL means for a distinct type.

A6: A distinct (simple) type is equivalent to a domain — it makes a distinction between two uses of the same underlying data type (e.g., OwnerNoType vs. StaffNoType, both VARCHAR(5)) and enforces type checking between them, without adding any internal structure. A structured type consists of both attribute definitions and routine declarations (methods) — e.g., PersonType with fields like dateOfBirth plus a method like age(). FINAL on a distinct type means no subtypes can be derived from it.

Q7: What does INSTANTIABLE control, and what happens if it is omitted from a UDT definition?

A7: INSTANTIABLE specifies that instances of the UDT can be created, and that the user can create one or more tables based on that UDT. If INSTANTIABLE is left out, the UDT can only be used as an attribute's data type — it cannot serve as the basis for a table of objects.

Section 8 — Inheritance

Q8 (Code Tracing): Given CREATE TYPE StaffType UNDER PersonType AS (staffNo StaffNoType, position VARCHAR(10) DEFAULT 'Assistant', salary DECIMAL(7,2), branchNo CHAR(4)) INSTANTIABLE NOT FINAL INSTANCE METHOD isManager() RETURNS BOOLEAN;, which attributes/methods does a StaffType instance have, and where do they come from?

A8: A StaffType instance has: dateOfBirth, gender, fName, lName (inherited from the supertype PersonType, along with any PersonType methods such as age()), plus its own newly declared attributes staffNo, position, salary, branchNo, and its own newly declared method, isManager().

Section 9 — Reference Types

Q9: In SQL:2016, what is the relationship between a "reference type" and an OODBMS's OID?

A9: A reference type has the same meaning as an OODBMS's OID — it is a system-generated reference that uniquely identifies a row within a table, exactly analogous to how an OID uniquely identifies an object in an OODB.

Q10 (Code Tracing): Rewrite the following traditional JOIN query using the dereferencing operator, given PropertyForRent has a personID REF (PersonType) SCOPE PERSON attribute:

SELECT P.street, S.fname, S.lname
FROM propertyForRent P, Person S
WHERE P.personID = S.personID

A10:

SELECT P.street, P.personID->fname, P.personID->lname
FROM PropertyForRent P;

This uses the dereferencing operator (->) to navigate directly from P.personID's reference to the referenced Person object's fname and lname attributes, avoiding the need to name a second table in the FROM clause or write an explicit join condition — even though, conceptually, this is still a JOIN "under the hood."

Section 10 & 11 — PostgreSQL Basics and Setup

Q11: Name PostgreSQL's two-part client/server session model, and describe the responsibility of each part.

A11: (1) A server process (called postgres) — manages the database files, accepts connections from client applications, and performs database operations on behalf of clients. (2) Users' client (front end) applications — make requests for database operations (e.g., pgAdmin 4 sending SQL to the server).

Section 12–14 — Data Types

Q12: List at least five categories of built-in PostgreSQL data types mentioned in the slides.

A12: Any five of: Geometric Types, Text Search Types, XML Type, Composite Types, Arrays, Object Identifier Types, JSON Types, Numeric Types, Monetary Types, Character Types, Binary Data Types, Date/Time Types, Boolean Type, Enumerated Types, Network Address Types, Bit String Types.

Q13 (Code Tracing): Given CREATE TYPE mood AS ENUM ('sad', 'ok', 'happy'); and CREATE TABLE person (name text, current_mood mood);, would INSERT INTO person VALUES ('Bongani', 'furious'); succeed?

A13: No — it would fail, because 'furious' is not one of the values defined in the mood enum type ('sad', 'ok', 'happy'). PostgreSQL enforces that only the declared enum values are valid for a mood-typed column.

Q14: Explain why parentheses are required when selecting a field from a composite-typed column, e.g., (StockOnHand.item).name.

A14: The parentheses are required to disambiguate the expression — without them, PostgreSQL could not tell whether StockOnHand.item.name meant "the name field inside the composite item column of table StockOnHand" versus some other parsing of the dotted identifiers. Wrapping StockOnHand.item in parentheses first, then appending .name, tells PostgreSQL explicitly to treat (StockOnHand.item) as a single composite value before extracting its name field.

Section 15 — Arrays

Q15 (Code Tracing): Given payByQuarter integer[] with a stored value of {20000, 25000, 25000, 25000}, what does payByQuarter[1] return, and is PostgreSQL array indexing 0-based or 1-based?

A15: payByQuarter[1] returns 20000, the first element. PostgreSQL array indexing is 1-based by default (not 0-based, unlike many programming languages such as Java or Python).

Q16 (Code Tracing): Given schedule text[][] with dimensions [1:2][1:2] (confirmed via array_dims), what does schedule[1:1][1:2] return?

A16: It returns a slice of the array — specifically, row 1 across both columns (columns 1 to 2) — e.g., {{breakfast, consulting}}, matching Thando's first "time slot" pair of activities from the worked example.

Section 16 — Table Inheritance

Q17 (Code Tracing): Given CREATE TABLE CAPITALS (state char(2)) INHERITS (CITIES); with Johannesburg inserted directly into CITIES and Pretoria inserted into CAPITALS, what rows does SELECT * FROM CITIES; return, and what rows does SELECT * FROM CAPITALS; return?

A17: SELECT * FROM CITIES; returns both Johannesburg and Pretoria — because CAPITALS rows are also considered CITIES rows through inheritance (an "is-a" relationship), so querying the parent table pulls in matching child-table rows too (showing only the inherited columns: name, population, area). SELECT * FROM CAPITALS; returns only Pretoria (with its full column set, including state), since Johannesburg was never inserted into the CAPITALS child table.

Q18: What does the phrase "subtable inherits columns and constraints (except primary keys) from parent table" mean in practice?

A18: When a table is declared to INHERIT from a parent table, it automatically gains all of the parent's column definitions and most constraints (e.g., CHECK constraints, NOT NULL) — except for primary key constraints, which are not automatically inherited and would need to be redefined on the child table if desired.

Section 17 & 18 — User-Defined Functions

Q19: List the four categories of PostgreSQL user-defined functions, and the two categories of SQL functions specifically.

A19: The four categories of user-defined functions are: (1) Query language functions (SQL functions), (2) Procedural language functions (e.g., PL/pgSQL, PL/Tcl, PL/Perl, PL/Python), (3) Internal functions, (4) C-language functions. The two categories of SQL functions are: (1) Row functions (operate on values of a table row), and (2) Table functions (operate on a whole table, producing a set of rows).

Q20 (Code Tracing): Given CREATE FUNCTION populationDensity(real, int) RETURNS int AS $$ SELECT CAST((($1 * 1000000) / $2) AS int) AS populationDensity; $$ LANGUAGE SQL;, what would populationDensity(2.5, 2500) return, and what do $1 and $2 refer to?

A20: It would return 1000. $1 and $2 refer to the function's positional parameters — $1 is the first parameter (2.5, a real) and $2 is the second (2500, an int). The calculation is (2.5 × 1,000,000) / 2500 = 1,000,000 wait recompute: (2.5 × 1,000,000) = 2,500,000; 2,500,000 / 2500 = 1000.

Q21: What is the key structural difference between a plain SQL function and a PL/pgSQL function?

A21: A plain SQL function body is a single SQL statement (e.g., a SELECT), with no local variables or procedural control flow. A PL/pgSQL function body has a DECLARE section (for local variables) and a BEGIN ... END block, supporting full procedural programming constructs — assignment statements, IF/CASE conditionals, and various looping constructs (LOOP, WHILE, FOR, FOREACH).

Q22 (Code Tracing): Trace through the is_big_city(area) function from Section 17.10 for a city with area = 800. What is returned?

A22: 'NO' — because 800 >= 1000 is false, the ELSE branch executes, setting big := 'NO';, which is then returned by RETURN big;.

Section 18 — PL/pgSQL Programming Constructs

Q23: Name the assignment operator style described as "preferred" in PL/pgSQL, and give an example.

A23: The := operator is the preferred assignment style (e.g., big := 'YES';), although plain = (e.g., var1 = 10;) is also valid.

Q24 (Code Tracing): Given the total_salary(int[]) function from Section 18.5, trace through its execution for the input array {22000, 27000, 27000, 27000} (Adriaan's payByQuarter), and state the final returned value.

A24:

  1. total = 0; (initial value)
  2. FOREACH val IN ARRAY $1 LOOP iterates: val = 22000 → total = 0 + 22000 = 22000
  3. val = 27000 → total = 22000 + 27000 = 49000
  4. val = 27000 → total = 49000 + 27000 = 76000
  5. val = 27000 → total = 76000 + 27000 = 103000
  6. Loop ends; RETURN total; returns 103000.

Q25: Distinguish between FOREACH target IN ARRAY arrayexpr LOOP ... END LOOP; and FOR var IN listexpr LOOP ... END LOOP;.

A25: FOREACH ... IN ARRAY ... is specifically designed to iterate over the elements of an array value, assigning each element to the target variable in turn. FOR var IN listexpr LOOP is more general — it can iterate over a range or list expression (e.g., a numeric range, or the rows of a query result, as shown in the countBigCities() example), not specifically an array.

Section 19 — JSON/JSONB

Q26: What is the practical difference between the -> and ->> operators when querying JSONB data?

A26: The -> operator extracts a value from a JSON/JSONB document as a JSON-typed value (e.g., "Alice", retaining its JSON representation, including quotes for strings). The ->> operator extracts the same value as plain text (e.g., Alice, without quotes) — ->> is generally more convenient when you want to use the extracted value directly as a normal SQL string/text value.

Section 20 — Triggers

Q27: Define a BEFORE trigger and an AFTER trigger, and give one example use case for each type, drawn from the slides.

A27: A BEFORE trigger executes before the specified operation — e.g., the valid_area trigger in Section 20.6, which validates a new row's area value before allowing an INSERT/UPDATE to actually happen, so it can block invalid data. An AFTER trigger executes after the specified operation — e.g., the audit_deleted_cities trigger in Section 20.8, which records a log entry into DeletedCities after a row has already been removed from Cities.

Q28 (Code Tracing / Conceptual): Referring to Section 20.7, why did INSERT INTO Capitals VALUES ('Upington', 0.5, -1000, 'NC'); succeed even though the valid_area trigger (validating that area > 0) was already created on the parent table Cities, and Capitals INHERITS (Cities)?

A28: Because triggers are NOT automatically inherited by child tables in PostgreSQL, even though column definitions and most constraints are. The valid_area trigger was only ever explicitly attached ON Cities, so an INSERT performed directly on Capitals never passed through that trigger's validation logic. The fix requires explicitly creating a second, separate valid_area trigger directly ON Capitals, reusing the same check_valid_area() trigger function.

Q29: In the record_deleted_city() trigger function (Section 20.8), explain what OLD.*, now(), and user each represent, and why the trigger returns OLD rather than NEW.

A29: OLD.* represents all the column values of the row that was just deleted (there is no NEW row in a DELETE operation). now() returns the current timestamp, used to record when the deletion occurred. user returns the current database user executing the operation, used to record who performed the deletion. The trigger returns OLD because, by convention, DELETE triggers return the OLD (deleted) row — there is no NEW row to return in a delete operation.

Q30: Explain the difference between FOR EACH ROW and FOR EACH STATEMENT triggers, and give an example of when FOR EACH STATEMENT was used in the slides.

A30: A FOR EACH ROW trigger executes once for every row affected by the triggering statement (e.g., the valid_area trigger fires separately for each row being inserted/updated). A FOR EACH STATEMENT trigger executes only once per SQL statement, regardless of how many rows that statement affects. The slides used FOR EACH STATEMENT for the StaffAfterInsert trigger (audit_staff_insert()), which is intended to log a single audit entry for each INSERT statement issued against Staff.

Q31: According to the slides, list two situations where a trigger is a good choice, and two situations where triggers should be avoided.

A31: Good uses (any two): auditing changes, maintaining derived data, enforcing complex business rules, automatically recording timestamps, maintaining related tables. Avoid triggers when (any two): a simple CHECK constraint is sufficient, a foreign key can enforce the rule, the behaviour belongs in application/business logic, or the trigger would make the database behaviour difficult to understand.
