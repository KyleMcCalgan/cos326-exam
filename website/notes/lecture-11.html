2. Recap — Neo4j and Cypher

  • Cypher: Neo4j's graph query language:
    • Purpose-built for graph data; uses patterns to describe graph data.
    • Uses familiar SQL-like clauses.
    • Is declarative — describes what to do, not how.
  • A Neo4j graph consists of:
    • Nodes which store data as properties (simple key/value pairs, e.g., name: "Thandi", from: "Durban").
    • Relationships.
    • Optional components: constraints & indexes.
  • Applications should use explicit identifying properties where appropriate, and constraints can enforce uniqueness.
  • Each node also has an internal ID (the slide's figure shows [nodeID: 85] beside Thandi's node).

2.1 Nodes and Relationships — Reminder

  • Relationships connect nodes — "the real power" of a graph database is in connected data.
  • Relationships describe how records are related (e.g., FOLLOWS).
  • Relationships always have a direction and a type, and form patterns of data.
  • Relationship properties store information shared by the two nodes — in a property graph, relationships are data records that can also contain properties.

4. Writing Clauses

4.1 Summary Table

Writing clause Definition
CREATE Creating graph elements: nodes, relationships, constraints.
MERGE A combination of MATCH & CREATE that additionally lets you specify what happens if the data was matched or created.
SET Updating labels on nodes and properties on nodes and relationships.
DELETE Deleting graph elements: nodes and relationships.
REMOVE Removing properties and labels from graph elements.
FOREACH Updating commands on elements in a collection — a path, or a collection created by aggregation.
DETACH DELETE Deletes a node or set of nodes; all associated relationships are automatically deleted.

4.2 CREATE (1) — Many Nodes and Relationships at Once (from the slides)

CREATE
  (psT:Person { name: "Thandi", from: "Durban",    hobby: "singing" }),
  (psJ:Person { name: "Johan",  from: "Pretoria",  hobby: "surfing" }),
  (psN:Person { name: "Neo",    from: "Cape Town", hobby: "soccer"  }),
  (psT)-[:FOLLOWS { since: 2017 }]->(psJ),
  (psT)-[:FOLLOWS { since: 2016 }]->(psN),
  (psJ)-[:FOLLOWS { since: 2018 }]->(psT)

Step-by-step walkthrough:

  1. A single CREATE clause creates three Person nodes (variables psT, psJ, psN) and three FOLLOWS relationships.
  2. The variables are only valid within this statement; they let the relationship patterns point to the nodes just created.
  3. Relationship direction follows the arrow: (psT)-[...]->(psJ) = Thandi → Johan.
  4. Counts: 3 nodes, 3 relationships, 3 × 3 + 3 × 1 = 12 properties, 3 labels.
  5. Reminder (Lecture 17): CREATE does not check for existing data — re-running it creates duplicates.

4.3 CREATE (2) — Creating a Uniqueness Constraint (from the slides)

CREATE CONSTRAINT person_name_unique
FOR (psn:Person)
REQUIRE psn.name IS UNIQUE;

Step-by-step walkthrough:

  1. CREATE CONSTRAINT person_name_unique — creates a named constraint (the name person_name_unique is chosen by you).
  2. FOR (psn:Person) — applies it to nodes labelled Person.
  3. REQUIRE psn.name IS UNIQUE — no two Person nodes may share the same name.
  4. Result (slide screenshot): "Added 1 constraint."
  5. Effect: trying to create a second Person named "Thandi" now fails with an error — a safeguard against the duplicate problem of CREATE. It also makes name lookups efficient (uniqueness constraints are backed by an index).
  6. Relational analogy: like a UNIQUE constraint on a column.

4.4 SET — Updating Properties (from the slides)

Updating a node property

MATCH (psT)
WHERE psT.name = "Thandi"
SET psT.age = 20
RETURN psT
  1. MATCH … WHERE finds the Thandi node.
  2. SET psT.age = 20 adds the property age (or overwrites it if it already exists).
  3. RETURN psT shows the updated node — Thandi now has name, from, hobby, age: 20.

Updating a relationship property

MATCH (psN:Person)-[r:FOLLOWS]->(psT:Person)
WHERE psN.name = "Neo" AND psT.name = "Thandi"
SET r.since = 2018
RETURN psN, r, psT;
  1. The relationship is bound to a variable r inside square brackets [r:FOLLOWS].
  2. WHERE restricts the pattern to the pair Neo → Thandi.
  3. SET r.since = 2018 updates the relationship's property (not a node's).
  4. Key point ("BUT for relationships"): to update a relationship you must match the relationship with a variable, then SET on that variable.
  5. Caution (added): the pattern follows the arrow direction (Neo)-[:FOLLOWS]->(Thandi). In the Section 2.1 data, it is Thandi who follows Neo, so this exact query would only match if a Neo → Thandi relationship exists (in the slide's updated figure, Neo → Thandi appears with since: 2018). If a pattern finds nothing, SET changes nothing — check your direction.

SET can also add a label: MATCH (p {name:"Neo"}) SET p:Admin (added for completeness).

4.5 MERGE — Match or Create (from the slides)

MERGE (psT:Person { name: "Thandi" })
ON MATCH  SET psT.age = 21
ON CREATE SET psT.from = "Durban",
              psT.hobby = "singing",
              psT.age = 21
RETURN psT;

Step-by-step walkthrough:

  1. MERGE either matches an existing node and binds it, or creates a new node and binds it.
  2. The pattern in MERGE ({ name: "Thandi" }) is the identifying part — Neo4j looks for a Person with that name.
  3. ON MATCH SET … runs only if the node already existed → here, set age = 21.
  4. ON CREATE SET … runs only if the node had to be created → here, set from, hobby and age.
  5. You can use only ON CREATE, only ON MATCH, or both.
  6. Result with the slide's data: Thandi already exists, so ON MATCH runs → Thandi's age becomes 21 (final figure: name, from, hobby, age: 21). No duplicate is created.
  7. CREATE vs MERGE: CREATE always adds; MERGE is idempotent — running it repeatedly gives the same graph.

4.6 DELETE and DETACH DELETE

1. Delete a relationship (from the slides)

MATCH (psT:Person {name: "Thandi"})-[r:FOLLOWS]->(psN:Person {name: "Neo"})
DELETE r;
  • Finds the Thandi → Neo FOLLOWS relationship (bound to r) and deletes only that relationship — both nodes remain.
  • Inline properties: (psT:Person {name: "Thandi"}) is a shorter form of MATCH (psT:Person) WHERE psT.name = "Thandi".

2. Delete a node and its connected relationships (from the slides)

MATCH (p:Person {name: "Zorro"})
DETACH DELETE p;
  • DETACH DELETE removes the node and all relationships connected to it.
  • Important note on the slide: "DELETE cannot delete a node that still has relationships. DETACH DELETE removes the node and its connected relationships."
  • In the slide's graph, Zorro (from California, hobby swords) has a FOLLOWS relationship (since 2000) — so a plain DELETE p would fail with an error, while DETACH DELETE p succeeds.

3. Delete all Person nodes (from the slides)

MATCH (psn:Person)
DETACH DELETE psn;
  • Use with care: this deletes all Person nodes and their relationships.
  • SQL analogy: like DELETE FROM Person; but also removing every connected "foreign key row" automatically.

4.7 REMOVE — Removing Properties and Labels (from the slides)

MATCH (psZ:Person)
WHERE psZ.name = "Zorro"
REMOVE psZ.hobby
RETURN psZ
  • Removes the hobby property from Zorro (his node then has only name and from).
  • Note on the slide: "REMOVE removes a property; it does not delete the node."
  • REMOVE also removes labels: REMOVE psZ:Person (added).

4.8 SET vs REMOVE vs DELETE — Comparison (added for clarity)

Clause Acts on Effect on the node/relationship
SET Properties / labels Adds or changes a property or label
REMOVE Properties / labels Takes away a property or label — the element stays
DELETE Nodes / relationships Deletes the whole element (a node must have no relationships)
DETACH DELETE Nodes Deletes the node plus all its relationships

5. Reading Clauses

Reading clause Definition
MATCH Lets you specify the patterns Cypher will search for in the database.
OPTIONAL MATCH If no matches are found, uses NULLs for the missing parts of the pattern.
WHERE Filters the results of MATCH, OPTIONAL MATCH and WITH.
Aggregation clauses/functions Calculate aggregated data — much like SQL's aggregates and GROUP BY.
ORDER BY (General clause) sorts the output.

5.1 Patterns for MATCH

Pattern Meaning
MATCH (<var>) Any node
MATCH (<var>:<label>) A single node pattern with label <label>, assigning matches to <var>
MATCH (<var1>:<label>)-[:<relationship>]-(<var2>) Nodes connected by a relationship of the given type
MATCH (<var1> { <key>: <value> })-->(<var2>) --> specifies a path (any relationship, in that direction) from a node with that property

Direction cheat-sheet (added for clarity):

Pattern Meaning
(a)-[:FOLLOWS]->(b) a follows b (outgoing from a)
(a)<-[:FOLLOWS]-(b) b follows a (incoming to a)
(a)-[:FOLLOWS]-(b) Either direction (no arrowhead)
(a)-->(b) Any relationship type, a → b

5.2 Basic MATCH … RETURN (from the slides)

Sample graph for the following examples: nodes Thandi (Durban, singing, age 20/21), Johan (Pretoria, surfing), Neo (Cape Town, soccer) and Melanie (Joburg, dancing), with FOLLOWS relationships.

MATCH (psT:Person) RETURN psT;        // returns the NODES
MATCH (psT:Person) RETURN psT.name;   // returns only the NAMES
  • RETURN psT returns entire nodes (all their properties — shown as graph objects).
  • RETURN psT.name returns one property per node — a table column of names (Thandi, Johan, Neo, Melanie).
  • SQL analogy: SELECT * FROM Person vs SELECT name FROM Person.

5.3 MATCH & WHERE (from the slides)

e.g. 1 — Show Melanie's details

MATCH (psM)
WHERE psM.name = "Melanie"
RETURN psM.name, psM.from, psM.hobby
  • (psM) has no label → matches any node; WHERE filters to the one named Melanie.
  • Result: one row — Melanie | Joburg | dancing.

e.g. 2 — Find the people that Thandi follows

MATCH (psn:Person)-[:FOLLOWS]->(followed)
WHERE psn.name = "Thandi"
RETURN psn.name, followed.name
  • Result: rows pairing Thandi with each person she follows — e.g., (Thandi, Johan) and (Thandi, Neo).
  • Note the difference from Lecture 17: returning properties (psn.name, followed.name) rather than whole nodes gives a clean table.

5.4 MATCH & ORDER BY (from the slides)

MATCH (psn)
RETURN psn.name
ORDER BY psn.name
  • Returns all node names in sorted (ascending) order: Johan, Melanie, Neo, Thandi.
  • Add DESC for descending order: ORDER BY psn.name DESC (added).
  • SQL equivalent: SELECT name FROM ... ORDER BY name;

5.5 OPTIONAL MATCH (added for step-by-step clarity)

MATCH (p:Person)
OPTIONAL MATCH (p)-[:FOLLOWS]->(f)
RETURN p.name, f.name

Step-by-step walkthrough:

  1. MATCH (p:Person) finds every person.
  2. OPTIONAL MATCH tries to find who each person follows — but, unlike MATCH, a person with no outgoing FOLLOWS is NOT dropped; the missing part is filled with NULL.
  3. A person who follows nobody (e.g., Neo in the Section 2.1 data) still appears, as (Neo, null).
  4. SQL analogy: OPTIONAL MATCH ≈ a LEFT OUTER JOIN; plain MATCH ≈ an inner join.

6. Aggregation

  • Cypher performs grouping implicitly — based on the non-aggregated expressions returned alongside aggregate functions (there is no GROUP BY keyword).

6.1 Aggregation Functions (from the slides)

Function Example Purpose
Implicit "GROUP BY" MATCH (n {name:'A'})-->(x) RETURN n.name, count(x) n.name is the grouping key; count(x) is the aggregate
count RETURN count(*) Number of rows/matches
sum RETURN sum(n.property) Total (property must be numeric)
avg RETURN avg(n.property) Average
stdev RETURN stdev(n.property) Standard deviation
max RETURN max(n.property) Maximum
min RETURN min(n.property) Minimum
collect RETURN collect(n.property) Returns a collection (list) of values
DISTINCT RETURN count(DISTINCT b.name) Counts only unique values

6.2 Example 1 — Count the People Thandi Follows (from the slides)

MATCH (psT { name: "Thandi" })-[:FOLLOWS]->(followed)
RETURN psT.name, count(*) AS count_follows;

Result (slide screenshot):

psT.name count_follows
"Thandi" 2

Step-by-step walkthrough:

  1. The pattern matches two rows — (Thandi → Johan) and (Thandi → Neo).
  2. psT.name is non-aggregated, so it becomes the implicit grouping key.
  3. count(*) AS count_follows counts the rows in the group (2) and names the column with AS.
  4. SQL equivalent: SELECT t.name, COUNT(*) AS count_follows FROM … GROUP BY t.name;

6.3 Example 2 — Count the Relationships in the Graph, by Type (from the slides)

MATCH (psn)-[relation]->()
RETURN type(relation), count(*)

Step-by-step walkthrough:

  1. (psn)-[relation]->() matches every relationship in the graph: any start node, any relationship type (bound to relation), and an anonymous end node () (we don't need a variable for it).
  2. type(relation) is a function returning the relationship's type name (e.g., "FOLLOWS"); because it is non-aggregated it is the grouping key.
  3. count(*) counts how many relationships exist per type.
  4. Result shape: one row per relationship type — here all relationships are FOLLOWS, so a single row: "FOLLOWS" | <number of FOLLOWS relationships>.
  5. Tip: with 3 FOLLOWS relationships in the Section 2.1 graph the answer is "FOLLOWS" | 3; the larger slide graph (with Melanie's relationship added) would give a correspondingly larger count.

6.4 Example 3 — collect (from the slides)

MATCH (psn:Person)
RETURN collect(psn.name);

Result (slide screenshot): ["Thandi", "Johan", "Neo", "Melanie"]

Step-by-step walkthrough:

  1. MATCH finds all four Person nodes.
  2. collect(psn.name) gathers their names into one list (collection) in a single row/value — rather than one row per person.
  3. Compare: RETURN psn.name → 4 rows; RETURN collect(psn.name) → 1 row containing a list of 4 names.

Extra Examples (added for step-by-step clarity)

// How many people are there?
MATCH (p:Person) RETURN count(p) AS people;                      // 4

// Who does each person follow — as a list?
MATCH (p:Person)-[:FOLLOWS]->(f)
RETURN p.name, collect(f.name) AS follows;
// Thandi -> ["Johan","Neo"],  Johan -> ["Thandi"], ...

// Average age of people who have an age
MATCH (p:Person) WHERE p.age IS NOT NULL RETURN avg(p.age);
  • In the second query, p.name is the grouping key and collect(f.name) aggregates each person's followed people into a list.

6.5 Cypher Aggregation vs SQL (added for clarity)

Aspect SQL Cypher
Grouping Explicit GROUP BY Implicit — every non-aggregated item in RETURN is a grouping key
Count rows COUNT(*) count(*)
Unique count COUNT(DISTINCT x) count(DISTINCT x)
List of values STRING_AGG / ARRAY_AGG collect()
Filter on aggregate HAVING WITH … WHERE (pass the aggregate on with WITH, then filter)

8. Questions & Memo

Section 3 & 4 — CRUD and Writing Clauses

Q1: Map the four CRUD operations to Cypher clauses and to SQL statements.

A1: Create — CREATE, MERGE (SQL INSERT); Read — MATCH, OPTIONAL MATCH + RETURN (SQL SELECT); Update — SET, REMOVE (SQL UPDATE); Delete — DELETE, DETACH DELETE (SQL DELETE).

Q2: Define each writing clause: CREATE, MERGE, SET, DELETE, REMOVE, FOREACH, DETACH DELETE.

A2: CREATE — creates nodes, relationships, constraints. MERGE — match-or-create, with options for what to do on each outcome. SET — updates labels and properties on nodes/relationships. DELETE — deletes nodes and relationships. REMOVE — removes properties and labels. FOREACH — runs update commands on each element of a collection. DETACH DELETE — deletes a node and automatically all its relationships.

Q3: What does the following statement do, and what message would you expect? CREATE CONSTRAINT person_name_unique FOR (psn:Person) REQUIRE psn.name IS UNIQUE;

A3: It creates a constraint named person_name_unique ensuring no two Person nodes have the same name; Neo4j reports "Added 1 constraint." Attempting to create a duplicate name afterwards fails.

Q4 (Code Tracing): Explain each line: MATCH (psT) WHERE psT.name = "Thandi" SET psT.age = 20 RETURN psT.

A4: Line 1 binds any node to psT; line 2 restricts it to the node named "Thandi"; SET psT.age = 20 adds/overwrites the age property; RETURN psT displays the updated node (now with age: 20).

Q5 (Code Tracing): How do you update a property of a relationship? Write a query that changes the year Thandi started following Neo to 2020.

A5: Bind the relationship to a variable in the pattern, then SET its property:

MATCH (:Person {name:"Thandi"})-[r:FOLLOWS]->(:Person {name:"Neo"})
SET r.since = 2020
RETURN r;

Q6 (Code Tracing): Explain the result of the following when Thandi already exists with age: 20, and when she does not exist at all: MERGE (psT:Person {name:"Thandi"}) ON MATCH SET psT.age = 21 ON CREATE SET psT.from = "Durban", psT.hobby = "singing", psT.age = 21 RETURN psT;

A6: Exists: ON MATCH runs → age becomes 21; other properties are unchanged and no new node is created. Does not exist: a new node is created and ON CREATE runs → it gets from: "Durban", hobby: "singing", age: 21.

Q7: Compare CREATE and MERGE.

A7: CREATE always creates new data (running it twice duplicates it); MERGE matches if the data exists, otherwise creates, so repeated runs do not create duplicates, and it supports ON MATCH / ON CREATE actions.

Q8: What is the difference between DELETE and DETACH DELETE? Why would MATCH (p:Person {name:"Zorro"}) DELETE p fail in the lecture's graph?

A8: DELETE removes a node only if it has no relationships; DETACH DELETE removes the node and all connected relationships. Zorro has a FOLLOWS relationship (since 2000), so a plain DELETE fails — DETACH DELETE is required (or delete the relationship first).

Q9: Write a query to delete only the FOLLOWS relationship from Thandi to Neo, leaving both nodes intact.

A9:

MATCH (:Person {name:"Thandi"})-[r:FOLLOWS]->(:Person {name:"Neo"})
DELETE r;

Q10: What does MATCH (psn:Person) DETACH DELETE psn; do, and why is it dangerous?

A10: It deletes every Person node and all their relationships — effectively wiping the people data from the graph, and it cannot be undone without a backup.

Q11: What does REMOVE psZ.hobby do, and does it delete the node?

A11: It removes the hobby property from Zorro's node; the node is not deleted (and its other properties/relationships remain).

Q12: Distinguish SET, REMOVE and DELETE.

A12: SET adds or changes properties/labels; REMOVE takes away properties/labels (the element stays); DELETE deletes the entire node or relationship.

Section 5 — Reading Clauses

Q13: What is the difference between RETURN psT and RETURN psT.name?

A13: RETURN psT returns whole nodes (with all properties); RETURN psT.name returns only the name property of each matched node, as a table column.

Q14: What does the pattern MATCH (n) match? And MATCH (n)-->(m)?

A14: (n) matches any node (no label restriction). (n)-->(m) matches any relationship, in the arrow's direction, from node n to node m (a path of length one).

Q15 (Code Tracing): What does MATCH (psn:Person)-[:FOLLOWS]->(followed) WHERE psn.name = "Thandi" RETURN psn.name, followed.name return?

A15: One row per person Thandi follows, pairing her name with theirs: (Thandi, Johan) and (Thandi, Neo).

Q16: What does MATCH (psn) RETURN psn.name ORDER BY psn.name return?

A16: All the names, sorted ascending (alphabetically): Johan, Melanie, Neo, Thandi.

Q17: Explain OPTIONAL MATCH and its SQL analogy.

A17: If no match is found, OPTIONAL MATCH returns NULL for the missing parts of the pattern instead of discarding the row — like a LEFT OUTER JOIN.

Section 6 — Aggregation

Q18: How does Cypher decide how to group results, given it has no GROUP BY keyword?

A18: It groups implicitly by the non-aggregated expressions returned alongside the aggregate functions (e.g., in RETURN n.name, count(x), n.name is the grouping key).

Q19: List eight aggregation functions given in the lecture.

A19: count, sum, avg, stdev, max, min, collect, and DISTINCT (e.g., count(DISTINCT b.name)).

Q20 (Code Tracing): What does MATCH (psT {name:"Thandi"})-[:FOLLOWS]->(followed) RETURN psT.name, count(*) AS count_follows; return?

A20: A single row: "Thandi" | 2 — she follows two people (Johan and Neo).

Q21: Explain MATCH (psn)-[relation]->() RETURN type(relation), count(*).

A21: It matches every relationship in the graph, returns each relationship's type name via type(relation) and counts how many exist per type (grouping by the type).

Q22 (Code Tracing): What is the difference between MATCH (p:Person) RETURN p.name and MATCH (p:Person) RETURN collect(p.name)?

A22: The first returns one row per person (4 rows); the second returns a single row containing a list of all names: ["Thandi", "Johan", "Neo", "Melanie"].

Q23: Write a query returning, for each person, how many people they follow.

A23:

MATCH (p:Person)-[:FOLLOWS]->(f)
RETURN p.name, count(f) AS follows

(Grouping key: p.name. People who follow nobody do not appear, because MATCH drops them — use OPTIONAL MATCH to include them with a count of 0.)

Q24: Write a query listing all names of people in the graph in one list, sorted alphabetically.

A24:

MATCH (p:Person)
WITH p ORDER BY p.name
RETURN collect(p.name)

Section 7 — Movie Graph Homework

Q25 (Code Tracing): Explain MATCH (people:Person)-[relatedTo]-(:Movie {title: "Cloud Atlas"}) RETURN people.name, type(relatedTo), relatedTo;

A25: It finds every Person connected, by any relationship type and in either direction, to the Movie titled "Cloud Atlas" (the movie node is anonymous — no variable). It returns each person's name, the relationship type as text (e.g., ACTED_IN, DIRECTED, PRODUCED) and the relationship itself.

COS 326 — Neo4j & Cypher Study Cheat Sheet

Based on Lectures 17–18 and everything we've discussed, including node creation, matching patterns, relationships, variables, properties, MERGE, and how queries return results.

1. Understanding Neo4j's structure

Neo4j is a graph database, meaning that rather than storing information in tables, it stores information using nodes and relationships.

Component Purpose Example
Node Represents an entity A student named John
Label Categorises a node :Student, :Module
Property Stores data inside a node {name: "John", age: 21}
Relationship Connects two nodes [:ENROLLED_IN]
Relationship property Stores information about a connection [:ENROLLED_IN {year: 2026}]
Variable Temporary reference to a matched or created node s, john, m

Node syntax

(variable:Label {property: value})

Examples:

()                               // Anonymous node
(s)                              // Node assigned to variable s
(s:Student)                      // Student node
(s:Student {name: "John"})       // Student named John
(s:Student {name: "John", age: 21})

Important discoveries:

  • Nodes do not require properties, labels or relationships.

  • Properties are key-value pairs stored inside the nodes.

  • Labels help categorise nodes but aren't unique identifiers.

  • Variables are temporary names used within a query.

  • Neo4j nodes have internal identifiers, even without properties.

2. Creating nodes and relationships

Creating nodes

CREATE (john:Student {name: "John", age: 21})

This creates a Student node with two properties.

Creating multiple nodes and relationships

3. Relationships and direction

Relationships have types and directions.

Syntax Meaning
(a)-[:FRIENDS_WITH]->(b) A has an outgoing friendship relationship to B
(a)<-[:FRIENDS_WITH]-(b) B has an outgoing friendship relationship to A
(a)-[:FRIENDS_WITH]-(b) Match friendship in either direction
(a)-[r:FRIENDS_WITH]->(b) Store the relationship in variable r
(a)-[r]->(b) Match any outgoing relationship type
(a)--(b) Match any relationship in either direction

An important distinction: Although friendships are logically mutual, Neo4j does not automatically treat directed FRIENDS_WITH relationships as bidirectional.

For example:

MATCH (s:Student {name: "Sarah"})-[:FRIENDS_WITH]-(friend)
RETURN friend.name

Result:

friend.name
John
Mike

Removing the arrowhead allows Neo4j to match either direction.

4. MATCH — Finding existing patterns

MATCH searches the graph for nodes and relationships that satisfy a specified pattern.

Basic MATCH

MATCH (s:Student)
RETURN s.name, s.age

Result:

s.name s.age
John 21
Sarah 22
Mike 20

Finding a specific student

Both queries are equivalent.

Using WHERE:

MATCH (s:Student)
WHERE s.name = "John"
RETURN s

Putting the condition directly inside MATCH:

MATCH (s:Student {name: "John"})
RETURN s

For simple equality conditions, you do not need WHERE.

Finding connections

MATCH (s:Student {name: "John"})
      -[:FRIENDS_WITH]->(friend)
RETURN friend.name

Result:

friend.name
Sarah

Here:

  • s represents John.

  • friend is a variable that Neo4j binds to matching destination nodes.

  • The relationship pattern tells Neo4j what connections to follow.

  • RETURN determines which information to display.

5. Understanding properties and RETURN

Properties are accessed using:

variable.property

For example:

RETURN s.name, s.age

These are the actual property keys stored inside the node.

Expression Meaning
s Entire node
s.name Value of the node's name property
s.age Value of its age property
m.code Module's code property
r.since Value of the relationship's since property

Example:

MATCH (s:Student)-[:ENROLLED_IN]->(m:Module)
RETURN s.name, m.code

Result:

s.name m.code
John COS326
Sarah COS326
Sarah COS301
Mike COS301

Important: Returning s gives the entire node, while returning s.name retrieves only the name. If a requested property is missing, its value is null.

6. Variables are not permanent identifiers

Consider:

CREATE (john:Student {name: "John"})

The variable john only exists within that query.

This means running another query:

MATCH (john)-[:FRIENDS_WITH]->(friend)
RETURN friend

does not automatically refer to the John created earlier.

Instead, john is a new variable that can match any node with the specified relationship.

To specifically identify John:

MATCH (john:Student {name: "John"})
      -[:FRIENDS_WITH]->(friend)
RETURN friend
Component Persisted in the database?
Variable john No
Label Student Yes
Property name: "John" Yes
Relationship FRIENDS_WITH Yes

7. Matching more complex relationships

You can chain multiple relationship patterns together.

Question: Which modules are studied by Sarah's friends?

MATCH (s:Student)-[:FRIENDS_WITH]-(f:Student)
      -[:ENROLLED_IN]->(m:Module)
WHERE s.name = "Sarah"
RETURN f.name, m.code

Result:

f.name m.code
John COS326
Mike COS301

Notice:

  • FRIENDS_WITH is matched in either direction.

  • ENROLLED_IN is still directional.

  • Neo4j finds the complete chain before returning the matching values.

The labels and relationship types define the structure we want; variables are bound to the nodes satisfying that structure.

8. Multiple MATCH clauses and multiple results

Multiple MATCH clauses build on existing matches. The second MATCH uses variables bound by the first.

Suppose we have three different students named Emma:

CREATE
  (:Student {name: "Emma", age: 19}),
  (:Student {name: "Emma", age: 22}),
  (:Student {name: "Emma", age: 25})

Query all Emmas

MATCH (s:Student {name: "Emma"})
RETURN s.name, s.age

Result:

s.name s.age
Emma 19
Emma 22
Emma 25

All matching nodes are returned, not just the first.

Multiple MATCH clauses

Suppose Emma (19) studies COS326, Emma (22) studies COS301 and COS326, and Emma (25) studies nothing.

MATCH (s:Student {name: "Emma"})
MATCH (s)-[:ENROLLED_IN]->(m:Module)
RETURN s.age, m.code

Result:

s.age m.code
19 COS326
22 COS301
22 COS326

Key observations:

  • The first MATCH finds all three Emmas.

  • The second MATCH searches for matching relationships for each Emma.

  • Emma (25) disappears because she has no matching enrolment.

  • Emma (22) produces two rows because she is enrolled in two modules.

OPTIONAL MATCH

To include students even when they have no enrolments:

MATCH (s:Student {name: "Emma"})
OPTIONAL MATCH (s)-[:ENROLLED_IN]->(m:Module)
RETURN s.age, m.code

Now Emma (25) also appears, with null for m.code.

MATCH OPTIONAL MATCH
Removes rows without a complete match Retains rows with null for missing parts
Similar to SQL inner joins Similar to SQL left outer joins

9. MERGE — Match or create

MERGE combines the behaviour of matching and creating.

MERGE (s:Student {name: "John"})

  • If a matching John exists, Neo4j uses that node.

  • If no matching John exists, Neo4j creates one.

Unlike CREATE, running the same MERGE repeatedly does not normally create a new matching node each time.

ON MATCH SET vs ON CREATE SET

MERGE (s:Student {name: "John"})
ON MATCH SET s.age = 25
ON CREATE SET s.age = 18
RETURN s
Situation What happens
John already exists ON MATCH SET executes; age becomes 25
John doesn't exist ON CREATE SET executes; John is created with age 18

Important: MERGE itself doesn't update other properties. The SET clauses perform those updates.

You can use either branch, both branches, or neither.

What if there are duplicate Johns?

If multiple nodes already match:

MERGE (s:Student {name: "John"})
ON MATCH SET s.age = 25

Neo4j matches all qualifying Johns, and each gets updated.

MERGE does not automatically remove existing duplicates.

Uniqueness constraints

To ensure students have unique student numbers:

CREATE CONSTRAINT student_no_unique
FOR (s:Student)
REQUIRE s.studentNo IS UNIQUE

This prevents two Student nodes from having the same non-null studentNo.

A constraint is particularly useful when MERGE should identify exactly one student. Unlike a node's temporary variable name, a stored student number can serve as a permanent identifier.

10. Updating and deleting data

Clause Purpose Example
SET Add or change properties SET s.age = 22
SET Add a node label SET s:Graduate
REMOVE Remove properties REMOVE s.age
REMOVE Remove a label REMOVE s:Graduate
DELETE Delete a node or relationship DELETE r
DETACH DELETE Delete a node and all its relationships DETACH DELETE s

Update John's age

MATCH (s:Student {name: "John"})
SET s.age = 23
RETURN s

Update a relationship property

MATCH (a:Student {name: "John"})
      -[r:FRIENDS_WITH]->
      (b:Student {name: "Sarah"})
SET r.since = 2024
RETURN r

Here, r is the variable referencing the relationship. Relationships can have properties just like nodes.

Delete only a relationship

MATCH (:Student {name: "John"})
      -[r:FRIENDS_WITH]->
      (:Student {name: "Sarah"})
DELETE r

Both students remain; only their specified relationship is removed.

Delete a connected node

MATCH (s:Student {name: "John"})
DETACH DELETE s

This deletes John and every relationship connected to his node.

A normal DELETE s fails if John still has relationships.

11. Aggregation functions

Cypher supports aggregation similar to SQL, but does not require an explicit GROUP BY clause.

Function Purpose Example
count() Count matching values or rows count(s)
sum() Add numeric values sum(s.age)
avg() Calculate average avg(s.age)
min() Minimum value min(s.age)
max() Maximum value max(s.age)
stdev() Standard deviation stdev(s.age)
collect() Combine values into a list collect(s.name)
DISTINCT Remove duplicate results or values count(DISTINCT s.name)
type() Retrieve relationship type as text type(r)

Example: Count enrolments per module

MATCH (s:Student)-[:ENROLLED_IN]->(m:Module)
RETURN m.code, count(s) AS total
ORDER BY total DESC

Result from the original example graph:

m.code total
COS326 2
COS301 2

Because m.code is returned alongside count(s), Neo4j implicitly groups the results by module code.

Collect values into a list

MATCH (s:Student)
RETURN collect(s.name) AS names

Result (order not guaranteed):

["John", "Sarah", "Mike"]

Rather than three rows, this produces one row containing a list.

12. Additional clauses to recognise

Clause Purpose Example
WHERE Filter matches WHERE s.age > 20
RETURN Select results to display RETURN s.name
AS Rename an output expression RETURN s.name AS student
ORDER BY Sort results ORDER BY s.age DESC
DISTINCT Remove duplicate result rows RETURN DISTINCT s.name
WITH Pass intermediate results to the next part of a query WITH s, count(m) AS total
FOREACH Apply updates to items in a collection FOREACH (x IN nodes \\| SET x.active = true)

Example using WITH:

MATCH (s:Student)-[:ENROLLED_IN]->(m:Module)
WITH s, count(m) AS total
WHERE total > 1
RETURN s.name, total

Returns students enrolled in more than one module.

14. Most important things you've established

  1. Nodes don't need properties, but properties make them easier to identify and query.

  2. Labels categorise nodes; properties contain their actual data.

  3. Variables are temporary and do not persist between separate queries.

  4. MATCH searches for patterns, not merely individual nodes.

  5. WHERE is optional when you can put an equality condition directly inside a pattern.

  6. Relationships have directions, but queries can ignore direction by removing the arrowhead.

  7. RETURN node.property accesses the stored property, while RETURN node returns the full node.

  8. Multiple matches produce multiple rows, including when multiple nodes share the same property values.

  9. Successive MATCH clauses build on previous matches, so one starting node can lead to several result rows.

  10. MERGE matches or creates, while ON MATCH SET and ON CREATE SET determine which properties to update on each outcome.

  11. MERGE does not guarantee uniqueness by itself; use constraints on appropriate identifying properties.

  12. SET modifies properties, REMOVE removes properties, and DELETE removes graph elements.

  13. DETACH DELETE also removes connected relationships.

  14. Cypher aggregation groups implicitly according to the non-aggregated expressions returned alongside aggregate functions.

The central concept to remember for your test is:

Cypher describes a graph pattern → Neo4j finds every matching combination → WHERE filters those combinations → RETURN determines what information you see.

For writing operations, use CREATE to add new graph elements, MATCH with SET to update existing ones, and MERGE when you want matching-or-creation behaviour.
