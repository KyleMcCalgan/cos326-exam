Question 11 markObject ODBMSPDF p.3 ↗

You want to create a bi-directional relationship between Student and Course entities, where each student can enroll in multiple courses, and each course can have multiple students. Which annotations and configurations would you use to define the relationship on both sides?

@Entity
public class Student {
    @Id
    private Long id;
    private String name;
    // Which annotation would go here?
    private List<Course> courses;
}

@Entity
public class Course {
    @Id
    private Long id;
    private String title;
    // Which annotation would go here?
    private List<Student> students;
}
  1. @OneToMany on both courses in Student and students in Course.
  2. @ManyToMany on courses in Student and @ManyToOne on students in Course.
  3. @ManyToMany(mappedBy = "students") on courses in Student and @ManyToMany on students in Course.
  4. @ManyToMany on courses in Student and @ManyToMany(mappedBy = "courses") on students in Course.
Show answer Study answer

d. Many students to many courses is @ManyToMany on both sides. One side owns the relationship; the other side uses mappedBy naming the field on the owning side. Here Student owns courses and Course points back with mappedBy = "courses".

Option a is wrong because @OneToMany on both sides is not a many-to-many. Option b mixes many-to-many with many-to-one. Option c is also a structurally valid bidirectional mapping (Course would own it), but d matches the natural reading that a student enrols in courses.

Question 21 markObject relational DBMSPDF p.3 ↗

A PL/pgSQL function calculate_discount applies a discount to a total amount based on customer type. It accepts customer_id and total_amount as inputs and returns the discounted total. Given the code below, how should you structure the conditional statement to apply a 10% discount for 'VIP' customers and no discount for others?

CREATE OR REPLACE FUNCTION calculate_discount(customer_id INT, total_amount NUMERIC)
RETURNS NUMERIC AS $$
DECLARE
    customer_type VARCHAR;
    discounted_amount NUMERIC;
BEGIN
    -- Fetch customer type
    SELECT type INTO customer_type FROM customers WHERE id = customer_id;

    -- Apply discount if customer is 'VIP'
    -- Which code from the options correctly applies the discount?
$$ LANGUAGE plpgsql;
  1. IF customer_type = 'VIP' THEN discounted_amount := total_amount * 0.9; ELSE discounted_amount := total_amount; END IF;
  2. CASE customer_type WHEN 'VIP' THEN discounted_amount := total_amount * 0.9; ELSE discounted_amount := total_amount; END CASE;
  3. IF customer_type := 'VIP' THEN discounted_amount := total_amount * 0.9; ELSE total_amount;
  4. IF customer_type = 'VIP' discounted_amount := total_amount * 0.9; ELSE total_amount;
Show answer Study answer

a. PL/pgSQL conditionals are IF cond THEN ... ELSE ... END IF;, comparison uses = and assignment uses :=.

Options c and d are syntactically wrong: neither has END IF, both leave a bare total_amount; in the ELSE branch, c uses the assignment operator := inside the condition, and d omits THEN.

Option b is also legal PL/pgSQL (a simple CASE statement ending in END CASE;). The expected answer is a, the standard IF form, but if your answer key says otherwise, trust the key.

The multiplication sign in the printed options was lost in text extraction and has been restored as *.

Question 31 markSemi-structured data & XMLPDF p.4 ↗

You need to create an XML output that combines the first_name and last_name of employees in a Staff table, with each full name appearing under an XML tag <FullName>. Which statement would achieve this?

  1. SELECT xmlelement(NAME "FullName", xmlcombine(first_name, last_name)) FROM Staff;
  2. SELECT xmlelement(NAME "FullName", xmlconcat(first_name, last_name)) FROM Staff;
  3. SELECT xmlelement(NAME "FullName", concat(first_name, last_name)) FROM Staff;
  4. SELECT xmlelement(NAME "FullName", xmlattributes(first_name || ' ' || last_name)) FROM Staff;
Show answer Memo

c. concat() builds the text that becomes the element's content, so xmlelement wraps it in <FullName>.

xmlcombine does not exist. xmlconcat concatenates XML values, not ordinary name strings. Option d puts the name in an attribute rather than in the element content.

Nuance: option c joins the two names with no space. A natural full name would use concat(first_name, ' ', last_name).

Question 61 markNeo4jPDF p.5 ↗

Given the following Cypher query executed in Neo4J:

CREATE
  (s1:Student { name: "Ndivhuwo", grade: "A" }),
  (s2:Student { name: "Marlize", grade: "B" }),
  (s3:Student { name: "Katlego", grade: "A" }),
  (s1)-[:FRIEND_WITH]->(s2),
  (s2)-[:FRIEND_WITH]->(s3),
  (s1)-[:FRIEND_WITH]->(s3);

Which Cypher query will return the names of all students who have an "A" grade and are friends with "Ndivhuwo"?

  1. MATCH (ndivhuwo:Student { name: " Ndivhuwo " })-[:FRIEND_WITH]->(friend:Student { grade: "A" }) RETURN friend.name;
  2. MATCH (ndivhuwo:Student { name: " Ndivhuwo " })-[:FRIEND_WITH]->(friend) WHERE friend.grade = "A" RETURN friend.name;
  3. MATCH (ndivhuwo:Student { name: " Ndivhuwo " })-[:FRIEND_WITH*]->(friend:Student { grade: "A" }) RETURN friend.name;
  4. MATCH (ndivhuwo:Student { name: " Ndivhuwo " })-[:FRIEND_WITH]-(friend:Student { grade: "A" }) RETURN friend.name;
Show answer Memo

The conceptual answer is a one-hop outgoing FRIEND_WITH pattern filtered on grade A (options a and b are equivalent):

MATCH (:Student {name: "Ndivhuwo"})-[:FRIEND_WITH]->(f:Student {grade: "A"})
RETURN f.name;

Result: Katlego. The WHERE form WHERE f.grade = "A" is equally valid.

Paper caveat: every printed option writes the name with spaces inside the literal (" Ndivhuwo "), which would not match "Ndivhuwo" under exact equality. Use the pattern above, not the padded literal.

Question 71 markNeo4jPDF p.6 ↗

You have a social network graph with nodes representing people and KNOWS relationships between them. You want to find the shortest connection path between "Alice" and "Simphiwe" to see if they are indirectly connected through other friends. Which query would find the shortest possible path between "Alice" and "Simphiwe" in terms of relationship hops, regardless of relationship direction?

  1. MATCH p = shortestPath((alice:Person { name: "Alice" })-[:KNOWS*]-(simphiwe:Person { name: "Simphiwe" })) RETURN p
  2. MATCH p = allShortestPaths((alice:Person { name: "Alice" })-[:KNOWS*]-(simphiwe:Person { name: " Simphiwe" })) RETURN p
  3. MATCH p = shortestPath((alice:Person { name: "Alice" })-[:KNOWS*1..3]-(simphiwe:Person { name: " Simphiwe" })) RETURN p
  4. MATCH p = shortestPath((alice:Person { name: "Alice" })-[:KNOWS*..3]-(simphiwe:Person { name: "Simphiwe" })) RETURN p
Show answer Memo

a. shortestPath returns one minimum-hop path, [:KNOWS*] allows any length, and no arrow means direction is ignored.

Suppose in JPQL you need to query Order entities with a status equal to "shipped". Is "shipped" considered a literal or a variable in the query? Based on your answer write the JPQL query snippet to achieve this. (3 Marks)

Show answer Study answer

"shipped" is a literal: a fixed string value written directly in the query. A variable would be a named parameter such as :status (or positional ?1) bound at run time.

SELECT o FROM Order o WHERE o.status = 'shipped'

Parameterised alternative: SELECT o FROM Order o WHERE o.status = :status with setParameter("status", "shipped"). JPQL string literals use single quotes.

Question 224 marksObject relational DBMSPDF p.10 ↗

Differentiate between the third-generation database manifesto and the third manifesto (4 Marks).

Show answer Study answer

Third-generation database system manifesto (Stonebraker and others, 1990): the next generation should extend relational systems with a richer type system (objects, inheritance, rules) while keeping non-procedural access and data independence, and be open to other languages and tools. It is object-friendly and accepts evolution of the relational model.

The Third Manifesto (Date and Darwen): insists that database systems stay strictly grounded in relational theory with a sound, strongly typed foundation. Types and relations are kept separate; it rejects treating a class as a relation, and rejects object identifiers and pointers as part of the model.

Contrast: the first accepts object-oriented extensions to the relational base; the second argues those extensions undermine the relational model and that the right answer is a purer relational model with proper types.

The course notes only list these manifestos (with a one-line contrast); the detail above is written from general knowledge. Check it against your lecture slides before relying on it.

db.orders.aggregate([
  {

    $group: {

Question 267 marksBig data & data miningPDF p.12 ↗

(a) Compare and contrast parallel relational DBMSs and the MapReduce/Hadoop systems (4 Marks)

(b) Elaborate on at least two ways to describe the knowledge discovered during data mining (no one word answers). (3 Marks)

Show answer Study answer

(a) Parallel relational DBMS: SQL over structured, schema-defined data, with relational query optimisation, parallel query execution and transactional consistency.

Hadoop/MapReduce: distributed computation over partitioned files. Mappers emit intermediate key-value pairs and reducers aggregate per key. It tolerates node failures on commodity clusters and suits large batch jobs over varied, often unstructured, input.

Contrast: the parallel DBMS gives declarative SQL, schemas and strong consistency but is costlier to scale; MapReduce gives cheap scale-out and flexibility but you write the processing logic yourself and it is batch-oriented.

(b) Knowledge discovered by data mining can be described as, for example:

  • Association rules: rules of the form X ⇒ Y with support and confidence, such as customers who buy bread also buy milk.
  • Classification hierarchies: a tree (such as a decision tree) that assigns items to classes using their attributes, for example approving or rejecting a loan.
  • Clustering: grouping records into clusters of similar items without predefined classes.
  • Sequential patterns and patterns within time series: events that follow each other over time, such as what a customer buys after a first purchase.

Part (a) draws on your memo's summary of this question; part (b) uses the five types of discovered knowledge from your Lecture 22 notes.

Question 284 marksObject ODBMSPDF p.12 ↗

Study the following scenario and the following question:

You are building a system for an online marketplace where each Product can be sold by multiple Sellers, and each Seller can sell multiple Products. You need to ensure that the relationship is bidirectional so that you can easily navigate from either Product to Seller or from Seller to Product.

(a) How would you implement this bi-directional relationship using JPA annotations, ensuring that both entities maintain a reference to each other without causing issues like infinite loops during serialization? (3 Marks)

Show answer Study answer

This is a many-to-many relationship. One side owns it with @ManyToMany (and a @JoinTable); the other side is the inverse with @ManyToMany(mappedBy = ...). Both sides hold a collection of the other.

@Entity
public class Product {
    @Id @GeneratedValue
    private Long id;
    private String name;

    @ManyToMany
    @JoinTable(name = "product_seller",
               joinColumns = @JoinColumn(name = "product_id"),
               inverseJoinColumns = @JoinColumn(name = "seller_id"))
    private List<Seller> sellers = new ArrayList<>();
}

@Entity
public class Seller {
    @Id @GeneratedValue
    private Long id;
    private String name;

    @ManyToMany(mappedBy = "sellers")
    @JsonIgnore
    private List<Product> products = new ArrayList<>();
}

Avoiding the infinite loop: serialising Product writes its sellers, each of which writes its products, and so on. The example uses Jackson @JsonIgnore on the seller-side collection to omit that property from JSON and break the cycle. It does not remove the JPA relationship, but it affects JSON input as well as output. Alternatively use object identity or purpose-built DTOs. The annotations @JsonManagedReference and @JsonBackReference are unsuitable here: Jackson specifies that the back-reference property cannot be a collection. These JSON annotations are not JPA annotations. Also override toString, equals and hashCode without the opposite collection.

Keep both sides in sync with helper methods such as addSeller() that update both collections.

Write a query to extract the total purchase amount from the purchaseHistory XML field for each customer using the xpath() function. [5 Marks]

Show answer Memo

xpath() returns an XML array. Expand it with unnest() and cast the text to a number before summing.

SELECT c.customerId, c.customerName,
       SUM((x.amount_xml::text)::numeric) AS totalPurchaseAmount
FROM CustomerSales AS c
CROSS JOIN LATERAL unnest(
    xpath('/PURCHASES/PURCHASE/AMOUNT/text()', c.purchaseHistory)
) AS x(amount_xml)
GROUP BY c.customerId, c.customerName
ORDER BY c.customerId;

C002Bob Smith120.00

A customer with no purchase nodes would be dropped by the cross join; use LEFT JOIN LATERAL ... ON true to keep them.

Show answer Study answer

(a) Follow the same pattern as the HOTELS_DIM example: a TIME table, then a dimension with four levels and a hierarchy from the lowest level up.

CREATE TABLE TIME (
    Day_ID INT PRIMARY KEY, Day_date DATE,
    Month_ID INT, Month_name VARCHAR(20),
    Quarter_ID INT, Quarter_name VARCHAR(10),
    Year_ID INT, Year_num INT
);

CREATE DIMENSION TIME_DIM
    LEVEL Day     IS TIME.Day_ID
    LEVEL Month   IS TIME.Month_ID
    LEVEL Quarter IS TIME.Quarter_ID
    LEVEL Year    IS TIME.Year_ID
    HIERARCHY Time_Rollup
    (Day CHILD OF Month CHILD OF Quarter CHILD OF Year)
    ATTRIBUTE Day     DETERMINES Day_date
    ATTRIBUTE Month   DETERMINES Month_name
    ATTRIBUTE Quarter DETERMINES Quarter_name
    ATTRIBUTE Year    DETERMINES Year_num

(b) This assumes a fact table REVENUE(Hotel_ID, Day_ID, Revenue) (the question does not name one).

SELECT h.Hotel_name, t.Month_name, SUM(r.Revenue) AS total_revenue
FROM REVENUE r
JOIN HOTEL h ON r.Hotel_ID = h.Hotel_ID
JOIN TIME  t ON r.Day_ID   = t.Day_ID
GROUP BY CUBE (h.Hotel_name, t.Month_name);

CUBE returns every combination of the two grouping columns:

  • (hotel, month): revenue for each hotel in each month.
  • (hotel, NULL): each hotel's total across all months.
  • (NULL, month): each month's total across all hotels.
  • (NULL, NULL): the grand total.

The NULLs mark the column that has been rolled up in that row.
