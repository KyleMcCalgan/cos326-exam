A2. Worked memorandum — MongoDB

A1 memo [1]

B. Collection. A database contains collections; a collection contains documents. A row belongs to the relational model; a node belongs to a graph database.

A2 memo [2]

  • find(filter) returns a cursor over all matching documents, which can be iterated with hasNext() and next().
  • findOne(filter) returns one matching document (or null if there is none), rather than a cursor.

A3 memo [3]

db.projects.find(
  { status: 'active', budget: { $gt: 100 } },
  { _id: 0, name: 1, budget: 1 }
).sort({ budget: -1 })

Expected rows, in order: CoralAI 150, AquaScan 120, DeepDrone 110. The first argument filters, the second controls returned fields, and -1 in sort means descending. _id: 0 excludes the normally displayed identifier.

A4 memo [2]

AquaScan, CoastLab, MarineHub (alphabetically ascending). The dotted field 'lead.city' reaches inside lead; it is not the same as querying a top-level city field.

A5 memo [3]

db.projects.updateMany(
  { status: 'paused' },
  { $set: { status: 'review' } }
)

2 documents: _id 2 and 6. updateMany affects all matching documents; $set updates just status. updateOne would affect only one matching document.

A6 memo [3]

db.projects.updateOne(
  { name: 'AquaScan' },
  { $set: { 'lead.city': 'Pretoria' } }
)
db.projects.findOne({ name: 'AquaScan' })

The result still contains lead.name: 'Lebo'; using $set with dot notation changes only the nested city. Avoid $set: { lead: { city: ... } }, which would replace the whole embedded lead document.

A7 memo [3]

  • (a): _id 1 and 4. The array may have one element above 8 and a different element below 6. The qualifying arrays are [5,9] and [4,9]. For example, in [5,9], 9 > 8 and 5 < 6 are both true, even though no single element satisfies both.
  • (b): no matches. $elemMatch requires a single rating simultaneously >8 and <6, which is impossible.

Exam trap: $elemMatch means one element satisfies every stated condition, not every element in the array satisfies the conditions.

A8 memo [4]

  • (a) _id: 1, 2, 3, 6, 7. Independent dotted predicates may be satisfied by different documents inside the reviews array. _id:1 contains a QA review (with passed:false) and a Security review (with passed:true), so it satisfies the two independent predicates.
  • (b) _id: 2, 3, 6, 7. $elemMatch requires one review with both by:'QA' and passed:true; _id:1 does not have such a review.

A9 memo [2]

db.projects.find({ ratings: [5, 9] }) // exact array and exact order: _id 1
db.projects.find({ ratings: 9 })      // any array element equals 9: _id 1, 4, 5, 7

An equality query using an entire array is order-sensitive; equality to a scalar can match an element of an array.

A10 memo [3]

db.projects.aggregate([
  { $group: { _id: '$team', totalBudget: { $sum: '$budget' } } },
  { $sort: { totalBudget: -1 } }
])
_id totalBudget Calculation
Ocean 310 120 + 80 + 110
AI 240 150 + 90
Web 200 70 + 130

_id: '$team' is the grouping key, not the document's own _id field.

A11 memo [5]

db.projects.aggregate([
  { $match: { status: 'active', budget: { $gte: 100 } } },
  { $group: {
      _id: '$team',
      numberOfProjects: { $sum: 1 },
      totalBudget: { $sum: '$budget' }
  } },
  { $sort: { totalBudget: -1 } }
])

Expected:

{ _id: 'Ocean', numberOfProjects: 2, totalBudget: 230 }
{ _id: 'AI',    numberOfProjects: 1, totalBudget: 150 }

Only _id 1, 3, and 5 survive $match. Ocean has two of them (120+110), AI has one (150), and Web has none. The order of pipeline stages matters: group after filtering if you only want qualifying records included in the totals.

A12 memo [3]

const c = db.projects.find()
while (c.hasNext()) printjson(c.next())

hasNext() checks whether another document remains and next() retrieves it, advancing the cursor. Once the loop exhausts c, c.toArray() produces an empty array because it only collects remaining results. To iterate again, create a fresh cursor with another find().

A13 memo [3]

db.projects.createIndex({ description: 'text' })
db.projects.find({ $text: { $search: 'coral' } })

Matches: CoralAI (_id:3) and ReefVision (_id:7). A classic $text query requires a text index. A collection has at most one classic text index, but it may cover multiple string fields.

A14 memo [4]

db.projects.aggregate([
  { $match: { $text: { $search: 'coral' } } },
  { $group: { _id: null, combinedBudget: { $sum: '$budget' } } }
])

Expected: { _id: null, combinedBudget: 240 } because 150+90=240. $match with $text must be the first stage of the aggregation pipeline. _id:null groups the matched documents into a single result group.

A15 memo [2]

An index can speed up lookups and sorting by avoiding unnecessary document scanning; indexes take storage and must be maintained on inserts/updates, which adds write overhead. A single compound text index may include multiple string fields, e.g. { name:'text', description:'text' }, while a second independent classic text index on the same collection is not permitted.

  (s2:Student {studentNo:'S2', name:'Bongani', city:'Durban'}),
  (s3:Student {studentNo:'S3', name:'Chloe',   city:'Pretoria'}),
  (s4:Student {studentNo:'S4', name:'David',   city:'Cape Town'}),
  (s5:Student {studentNo:'S5', name:'Esha',    city:'Durban'}),

  (c3:Course {code:'COS301', title:'Software Engineering', credits:32}),

  (s1)-[:ENROLLED_IN {mark:65}]->(c2),
  (s2)-[:ENROLLED_IN {mark:58}]->(c1),

  (s3)-[:ENROLLED_IN {mark:82}]->(c1),

  (s1)-[:FOLLOWS {since:2024}]->(s3),

B2. Worked memorandum — Neo4j / Cypher

B1 memo [1]

B. Node label. s is a query variable, Student is the node label, and name is a property. Relationship types appear inside relationship brackets, e.g. [:ENROLLED_IN].

B2 memo [2]

Bongani
Chloe

The arrow -> starts at Amina and follows only outgoing FOLLOWS relationships. Bongani's and Chloe's incoming relationships to Amina are different edges and do not make additional outgoing matches for Amina. The sorting instruction places Bongani before Chloe.

B3 memo [3]

MATCH (s:Student)
WHERE s.city = 'Pretoria'
RETURN s.name AS name, s.studentNo AS studentNo
ORDER BY name

Expected: (Amina,S1), (Chloe,S3). Equivalent property-map filtering MATCH (s:Student {city:'Pretoria'}) ... is also valid.

B4 memo [3]

MATCH (s:Student {name:'Amina'})-[:ENROLLED_IN]->(c:Course)
RETURN c.code AS code
ORDER BY code

Expected: COS326, COS332. (s)-[:ENROLLED_IN]->(c) respects that enrolment edges point from Student to Course.

B5 memo [3]

MATCH (s:Student)-[e:ENROLLED_IN]->(c:Course {code:'COS326'})
WHERE e.mark >= 75
RETURN s.name AS name, e.mark AS mark
ORDER BY mark DESC

Expected: (Chloe,82), (Amina,78). The other COS326 marks are 58 and 55, so those students are filtered out. e is the relationship variable, and e.mark reads the relationship property.

B6 memo [4]

MATCH (c:Course {code:'COS326'})
CREATE (f:Student {studentNo:'S6', name:'Farah', city:'Pretoria'})
CREATE (f)-[:ENROLLED_IN {mark:77}]->(c)
RETURN f.name AS student, c.code AS course

MATCH locates the existing course first. The first CREATE adds Farah; the second adds only the enrolment to the previously bound c. Do not use CREATE (c:Course {code:'COS326'}), which would make a second course node.

B7 memo [2]

MATCH (s:Student {studentNo:'S3'})
SET s.city = 'Johannesburg'

SET creates or updates the specified property on the matched node. A RETURN is optional for a write-only query.

B8 memo [3]

MATCH (s:Student {studentNo:'S1'})-[e:ENROLLED_IN]->(c:Course {code:'COS326'})
SET e.mark = 80
RETURN e.mark AS newMark

Result: 80. Updating s.mark or c.mark would modify a node, not the enrolment relationship where marks are stored.

B9 memo [3]

MATCH (d:Student {name:'David'})
REMOVE d.city
RETURN d

The David node remains with studentNo and name; his ENROLLED_IN relationship to COS332 also remains. REMOVE removes properties or labels, whereas DELETE removes graph elements.

B10 memo [3]

MATCH (a:Student {name:'Amina'})-[r:ENROLLED_IN]->(c:Course {code:'COS332'})
DELETE r

Only one relationship is deleted. Both Amina and COS332 remain, as do her other enrolment and follows relationships.

B11 memo [3]

MATCH (d:Student {studentNo:'S4'})
DETACH DELETE d

David has an outgoing ENROLLED_IN relationship to COS332. Plain DELETE d cannot delete a node with existing relationships; DETACH DELETE removes the node and its connected relationships. COS332 itself remains.

B12 memo [3]

MERGE (c:Course {code:'COS344'})
ON CREATE SET c.title = 'Graphics', c.credits = 16
RETURN c

MERGE matches an existing pattern or creates it if absent; CREATE creates a new pattern every time the statement is run. Nuance: for reliable global uniqueness of a course code, a corresponding uniqueness constraint should be defined; MERGE alone is not a substitute for one in concurrent writes.

B13 memo [4]

MATCH (s:Student)
OPTIONAL MATCH (s)-[:FOLLOWS]->(f:Student)
RETURN s.name AS name, count(f) AS followsCount
ORDER BY name
name followsCount
Amina 2
Bongani 1
Chloe 1
David 0
Esha 0

OPTIONAL MATCH leaves unmatched students in the intermediate result with f = null; count(f) counts non-null matched f nodes, giving zero for David and Esha. Using a mandatory second MATCH would omit those students.

B14 memo [5]

MATCH (s:Student)-[e:ENROLLED_IN]->(c:Course)
RETURN c.code AS code,
       count(s) AS studentCount,
       avg(e.mark) AS avgMark
ORDER BY code
code studentCount avgMark Arithmetic
COS301 2 80 (72+88)/2
COS326 4 68.25 (78+58+82+55)/4
COS332 2 69.5 (65+74)/2

Why no GROUP BY? Cypher groups implicitly by the non-aggregated return expression c.code. count(s) counts matched enrolments; avg(e.mark) aggregates marks from the relationships.

B15 memo [5]

MATCH (a:Student {studentNo:'S1'})-[:ENROLLED_IN]->(c:Course)<-[:ENROLLED_IN]-(other:Student)
WHERE other.studentNo <> a.studentNo
RETURN DISTINCT other.name AS name
ORDER BY name

Expected: Bongani, Chloe, David, Esha.

Step by step: Amina belongs to COS326 and COS332. COS326 connects her to Bongani, Chloe, and Esha; COS332 connects her to David. The two-edge pattern meets at the same c. The WHERE removes Amina herself, and DISTINCT prevents duplicate names if a student shares more than one course.

C2. Worked memorandum — XQuery / FLWOR

C1 memo [2]

  • for $s in ... iterates over sequence items, binding $s to each in turn and generating tuples.
  • let $x := ... binds an expression's whole value/sequence without iterating through that sequence's members.
  • return is required; where and order by are optional. A FLWOR begins with at least one for or let clause in the lecture's presentation.

C2 memo [2]

/STAFFLIST/STAFF[@branchNo = 'B003']/NAME/LNAME/text()

Expected: Kruger, Bakwena. @branchNo reaches the attribute on each STAFF element. /STAFF/branchNo instead searches for a child element named branchNo, which does not exist in this dataset.

where $s/SALARY > 28000
order by xs:decimal($s/SALARY) ascending
return string($s/NAME/FNAME)

Expected sequence: Thando, James. The matching salaries are 30000 and 34000. Numeric casting in the sort makes the intended numeric ordering explicit. return produces strings rather than the original <FNAME> elements.

return

C8 memo [3]

C9 memo [5]

for $b in distinct-values(doc('staff_list.xml')//@branchNo)
let $staff := doc('staff_list.xml')//STAFF[@branchNo = $b]
order by $b ascending
return
  <BRANCH>
    <BRANCHNO>{string($b)}</BRANCHNO>
    <AVGSALARY>{avg($staff/SALARY)}</AVGSALARY>
  </BRANCH>
Branch Staff salaries Average
B002 30000 30000
B003 27000, 25000 26000
B004 34000 34000

for iterates over unique branches. let binds all matching staff for the current branch. avg() is the XQuery aggregate function, not MongoDB's $avg. XQuery's numeric functions can atomize/cast the numeric-looking salary elements; in more strongly typed input, an explicit conversion such as xs:decimal(...) may be necessary.

C10 memo [4]

for $b in distinct-values(doc('staff_list.xml')//@branchNo)
let $staff := doc('staff_list.xml')//STAFF[@branchNo = $b]
where every $s in $staff satisfies (xs:decimal($s/SALARY) >= 27000)
order by $b
return string($b)

Expected: B002, B004. Branch B003 fails because Lerato's 25000 is less than 27000, even though Marlize earns 27000. every requires all members of the sequence to satisfy the predicate. Do not confuse it with some (at least one member).

C12 memo [4]

return
  <STAFFNOK>
    <STAFF>{string($s/NAME/FNAME)}</STAFF>

C13 memo [3]

for $m in doc('modules.xml')/MODULES/MODULE
order by xs:integer($m/CREDITS) descending,
         string($m/@code) ascending
return string($m/@code)

Expected order: COS301, COS326, COS332, STK120. First compare credits (32, 16, 16, 12); only the two 16-credit modules require the second key (code ascending). @code reads an XML attribute, while CREDITS is a child element.

C14 memo [2]

  • = is a general comparison: with sequences, it can succeed when at least one pair of values compares equal.
  • eq is a value comparison: it expects at most one atomic value on each side, so a sequence containing multiple salaries causes a dynamic error.

Therefore SALARY eq 30000 is not always safe if the path can return multiple SALARY elements. For untyped XML there may also be data-type conversion differences between general and value comparisons; xs:decimal(SALARY) eq 30000 is suitable when exactly one numeric salary is expected.

C15 memo [5]

<HIGH_EARNERS>{
  for $s in doc('staff_list.xml')/STAFFLIST/STAFF
  where xs:decimal($s/SALARY) > 27000
  order by xs:decimal($s/SALARY) descending
  return
    <PERSON branch="{string($s/@branchNo)}">
      <FIRST>{string($s/NAME/FNAME)}</FIRST>
      <SALARY>{string($s/SALARY)}</SALARY>
    </PERSON>
}</HIGH_EARNERS>

Expected:

<HIGH_EARNERS>
  <PERSON branch="B004"><FIRST>James</FIRST><SALARY>34000</SALARY></PERSON>
  <PERSON branch="B002"><FIRST>Thando</FIRST><SALARY>30000</SALARY></PERSON>
</HIGH_EARNERS>

The outer XML constructor gives one root element; the FLWOR creates one <PERSON> per qualifying staff member. Marlize (27000) is excluded because the condition is strictly greater than, not greater-than-or-equal. order by controls child order and {...} inserts evaluated values into XML elements and attributes.
