Mark-saving habits (grounded in ST1 feedback): Write an exact requested expression rather than an explanation; check whether the question wants a whole node/document or just a field; include every condition (e.g., active AND depth > 4000 was a missed condition in ST1); and complete the whole statement, not just the calculation. 2. XML / XQuery — Lectures 11–12

2.1 FLWOR: the template to memorise

for $s in //STAFF                  (: iterates over matching nodes :)
let $salary := $s/SALARY           (: binds a value; no extra iteration :)
where $salary > 15000             (: filters the tuples :)
order by $s/STAFFNO ascending     (: sorts the output :)
return $s/NAME                    (: returns a node/sequence :)
Clause / symbol Essential distinction / typical trap
for $x in ... One binding per item: iterates
let $x := ... Binds an expression/result; does not itself iterate
where Filters the current sequence of variable bindings
order by ... ascending/descending Sorts before return
return Required in FLWOR; constructs the result
//STAFF Staff elements anywhere under current context
/STAFF/NAME Child-path navigation (context matters)
@branchNo Selects an attribute, not an element
text() Selects a text node rather than the element node
{ expression } Evaluates/inserts XQuery data inside a constructed XML element
$S vs $s XQuery variables are case-sensitive

Lecture 11, example: Names of staff in branch B004 whose salary exceeds 15,000:

for $S in //STAFF
where $S/SALARY > 15000 and $S/@branchNo = "B004"
return $S/NAME

How to derive it: (1) identify the repeating element STAFF; (2) filter on the STAFF element because both salary and branch belong to it; (3) project the required NAME, not the full staff record.

2.2 Aggregates, distinct values, some / every

Lecture 11: Average salary for every branch

for $B in distinct-values(//@branchNo)
let $avgSalary := avg(//STAFF[@branchNo = $B]/SALARY)
return
  <BRANCH>
    <BRANCHNO>{$B}</BRANCHNO>
    <AVGSALARY>{$avgSalary}</AVGSALARY>
  </BRANCH>
  • distinct-values(//@branchNo) → one value for each unique branch number.
  • //STAFF[@branchNo = $B] → staff at the current branch.
  • avg(.../SALARY) → average across that branch's staff salary elements.
  • return → builds one <BRANCH> result per branch.

Lecture 11: Branches where at least one salary > 15,000

for $B in distinct-values(//@branchNo)
let $S := //STAFF[@branchNo = $B]
where some $sal in $S/SALARY satisfies ($sal > 15000)
return <BRANCHNO>{$B}</BRANCHNO>
Qualifier Meaning Memorise
some $x in ... satisfies (...) At least one satisfies Existential
every $x in ... satisfies (...) All satisfy Universal
distinct-values(...) Removes duplicates Unique groups / IDs
avg(...), sum(...) Aggregate numeric values Apply to the filtered sequence

2.3 Joining XML documents / correlated subqueries

Lecture 11: Staff plus next-of-kin, joined on STAFFNO:

for $S in //STAFF, $NOK in //NOK
where $S/STAFFNO = $NOK/STAFFNO
return <STAFFNOK>{$S/NAME, $NOK/NAME}</STAFFNOK>

Walkthrough: enumerate candidate staff and NOK pairs → retain pairs with matching STAFFNO → construct XML for each match. A nested for $NOK ... inside the outer return is an alternative correlated subquery from the lecture.

Practice fill-in: for $x in //STAFF ... return $x/NAME gives one result per STAFF; let $x := //STAFF ... binds the whole sequence. Swapping for and let can change both the result's shape and number of iterations.

2.4 SQL/XML and PostgreSQL XML

Requirement Exact form from Lecture 12 Remember
XML-typed column staffData XML Native XML data type
XML from scalar SQL value xmlelement(NAME staffname, fName) Creates an element
XML attribute xmlattributes(branchNo AS "branchNo") Goes inside xmlelement
Whole table as XML table_to_xml('numbers', false, false, '') Maps rows to XML
Table's XSD table_to_xmlschema('numbers', false, false, '') Produces XML Schema
Query results as XML query_to_xml('SELECT ...', false, false, '') Maps SQL query results
Query results as XSD query_to_xmlschema('SELECT ...', false, false, '') Produces result schema
XPath on XML column xpath('/STAFF/STAFFNO', staffData) Returns an xml[] array
Values instead of tags xpath('/STAFF/STAFFNO/text()', staffData) Selects text nodes (still xml[])
XML array → rows unnest(xpath('/STAFF/STAFFNO/text()', staffData)) Expands XPath matches

Lecture 12: Generate one XML staff element with an attribute:

SELECT xmlelement(
  NAME staff,
  xmlattributes(branchNo AS "branchNo"),
  concat(fName, lName)
) AS staffXMLCol
FROM Staff;

Lecture 12: Retrieve the XML staff number via SQL:

SELECT docNo,
       unnest(xpath('/STAFF/STAFFNO/text()', staffData)) AS StaffNumber
FROM XMLStaff;

Four XML storage approaches — MCQ material: 1. Whole XML document in one column (simple insertion/retrieval; parsing cost for fine queries); 2. shredded across columns/tables (index fields, reconstruct hierarchy); 3. schema-independent representation (e.g., DOM-derived model); 4. parsed/internal XML representation. Related PostgreSQL server functions: pg_ls_dir('.') lists server-side directory entries, pg_read_file('...') reads a file accessible to the server, and CAST(pg_read_file('...') AS xml) makes it XML-typed. These are privilege-restricted and not client-PC file access.

Possible fill-in traps: xpath(...) ≠ XQuery FLWOR; PostgreSQL's xpath() returns an array, even if one element matched; XMLATTRIBUTES creates an attribute, while XMLELEMENT creates an element; RETURN in XQuery is not the same as Cypher's RETURN syntax in every context.

3. Big Data and NoSQL — Lecture 13 (concept questions)

3.1 Five Vs and NoSQL model identification

V Meaning Scenario keyword
Volume Quantity/scale of data Terabytes, petabytes
Velocity Speed of arrival/processing Streaming telemetry
Variety Different data forms JSON, video, tables, text
Value Useful insight/business benefit Recommendations and patterns
Veracity Accuracy/reliability Noisy/untrustworthy sensors
Model Core shape Best fit / example from lectures
Key–value Key → value Fast key lookup; Redis / DynamoDB
Document BSON/JSON-like field–value documents Nested data, flexible fields; MongoDB
Wide-column Rows keyed and organised by column families Large distributed tabular-like workload; Cassandra / HBase
Graph Nodes + relationships + properties Social connections, recommendations; Neo4j
Time series Timestamped events in time order Sensor readings / price history

CAP theorem — likely recognition question: C = consistency, A = availability, P = partition tolerance. During a network partition, a replicated distributed system cannot guarantee both strong consistency and availability. This is a trade-off under partition—not a claim that a system may possess only two useful qualities at all times. Eventual consistency means replicas may disagree temporarily but converge once updates propagate (subject to the system's assumptions).

Reading topic mentioned in Lecture 13: PACELC extends the discussion: if there is a Partition, trade off Availability/Consistency; Else (no partition), consider Latency/Consistency. Label this as reading-extension material, rather than a detailed lecture worked example.

4. MongoDB — Lectures 14–16 (highest-density command section)

4.1 CRUD / filtering / output syntax

Use db.<collection>.<method>(...) in mongosh. Query field values are documents, not SQL strings.

use mydb                             // mongosh helper
show collections                     // mongosh helper

db.students.insertOne({name: "Neo", mark: 78, active: true});
db.students.insertMany([{name: "A", mark: 45}, {name: "B", mark: 80}]);

db.students.find({mark: {$gt: 60}});              // mark > 60
db.students.find({active: true, mark: {$gte: 70}}); // implicit AND
db.students.find({$or: [{mark: {$lt: 50}}, {mark: {$gt: 90}}]});
db.students.find({mark: {$in: [45, 80]}});

db.students.find({mark: {$gte: 70}}, {name: 1, _id: 0})
           .sort({name: 1});                    // projection + ascending sort

db.students.updateOne({name: "Neo"}, {$set: {mark: 82}});
db.students.updateMany({active: true}, {$set: {status: "approved"}});
db.students.deleteOne({name: "A"});
db.students.deleteMany({active: false});
Meaning Syntax Trap
equals {x: 3} Equality usually no $eq required
greater / greater-or-equal $gt / $gte gt not >, >= within query document
less / less-or-equal $lt / $lte Distinct from $gt
not equals $ne Different from $not
OR $or: [{...}, {...}] Array of alternatives
IN list $in: [a, b] Alternatives for one field
projection include/exclude {name: 1, _id: 0} 1 include, 0 exclude, _id exception
sorting .sort({name: 1}) 1 ascending, -1 descending
update property {$set: {mark: 82}} Forgetting $set changes semantics
update one vs all updateOne / updateMany updateOne is not multi: true
remove one vs all deleteOne / deleteMany deleteMany({}) deletes all documents

BSON / concepts: Database → collections → documents → fields. MongoDB documents are stored in BSON; _id uniquely identifies documents and is commonly an ObjectId when autogenerated. Date is suitable for application date/time; Timestamp is primarily an internal MongoDB BSON type. An embedded document is not the same as an ObjectId.

4.2 Nested documents, arrays, cursors — common traps

Lecture 15 examples:

// Nested fields: access: {level: 5, group: "dev"}
db.users.find({"access.level": 5});
db.users.find({access: {level: 5, group: "dev"}});
// First checks one nested field; second compares the embedded document as a whole.

// Given ratings: [5, 8, 9]
db.inventory.find({ratings: [5, 8, 9]}); // exact array AND order
db.inventory.find({ratings: 5});         // any array element equals 5

db.inventory.find({ratings: {$gt: 5, $lt: 9}});
// Two different elements MAY fulfil these two conditions.

db.inventory.find({ratings: {$elemMatch: {$gt: 5, $lt: 9}}});
// ONE SAME element must be >5 AND <9; for [5,8,9], 8 works.

// Given memos: [{memo: "on time", by: "shipping"}, ...]
db.inventory.find({"memos.by": "shipping"});
db.inventory.find({"memos.0.by": "shipping"}); // specifically first element

Practice trap: Array [5, 9] satisfies {ratings: {$gt: 5, $lt: 9}} via different values (9 and 5) but does not satisfy $elemMatch with both strict conditions. This is a particularly good select-all / predict-the-output question.

Cursor (Lecture 15):

const c = db.users.find();
while (c.hasNext()) printjson(c.next());
// Or: const result = db.users.find().toArray(); printjson(result[0]);

hasNext() tests for another result; next() consumes a result; toArray() materialises the remaining results. JavaScript arrays start at index 0.

4.3 Aggregation pipeline — MUST be able to build and trace

Lecture 15 dataset (total 7 blog documents):

Title Individual likes Group sum
NoSQL 400 400
MongoDB 100, 150, 50 300
Neo4j 50, 150, 250 450

Lecture: Group totals, retain totals greater than 300, sort ascending:

db.blogs.aggregate([
  {$group: {_id: "$title", num_likes: {$sum: "$likes"}}},
  {$match: {num_likes: {$gt: 300}}},
  {$sort: {num_likes: 1}}
]);

Trace it as the examiner might: 1. $group creates {_id: "NoSQL", num_likes: 400}, {_id: "MongoDB", num_likes: 300}, {_id: "Neo4j", num_likes: 450}. 2. $match keeps only 400 and 450. 300 does not pass $gt: 300. 3. $sort ascending returns NoSQL (400), Neo4j (450) in that order.

Alternative Lecture query: only Neo4j, then total:

db.blogs.aggregate([
  {$match: {title: "Neo4j"}},
  {$group: {_id: "$title", num_likes: {$sum: "$likes"}}}
]); // Neo4j, 450
Stage/operator Function Common error
$match Filter documents in current pipeline stage Before grouping filters original docs; after grouping filters aggregates
$group Group by _id expression "$title" field reference, not literal "title"
$sum: "$likes" Sum likes $sum: 1 counts records instead
$avg, $min, $max Numeric aggregates Put inside accumulator in $group
$sort: {field: -1} Descending order -1 descending; 1 ascending

4.4 Indexing, text searches, design and applications

db.blogs.createIndex({title: 1});                 // ascending index
db.blogs.createIndex({title: 1, likes: -1});      // compound index
db.blogs.find({title: "Neo4j"}).explain("executionStats");

db.blogs.createIndex({comments: "text"});       // prerequisite for $text
db.blogs.find({$text: {$search: "NoSQL"}});      // usually case-insensitive
db.blogs.createIndex({"$**": "text"});          // wildcard TEXT index alternative

Text-in-aggregation (Lecture 16):

db.blogs.aggregate([
  {$match: {$text: {$search: "NoSQL"}}}, // must be first for $text
  {$group: {_id: null, totalLikes: {$sum: "$likes"}}}
]); // Lecture dataset: totalLikes = 550

Why 550? Matching comments from NoSQL (400), MongoDB (100) and Neo4j (50) → 400 + 100 + 50 = 550. A text index is required. A collection supports at most one text index, although that index can include several fields. A wildcard text index makes indexing broader and can cost storage/write performance. Do not create both of the text indexes shown above on the same collection; treat them as alternative configurations.

Design questions: Embed when child data belongs to the parent and is normally read together (e.g., account contact details); reference for shared entities, complex many-to-many data or large/unbounded child collections. Lecture 15 highlights the 16 MiB document limit. Indexes improve reads/sorts but add storage and write overhead.

Lecture 16 client-app details: mongosh uses JavaScript functions (function computeTotalLikes(dbName, colName, blogTitle) {...}); .mongoshrc.js can load helper functions on shell start. In Java, MongoClient → MongoDatabase → MongoCollection via the MongoDB Java Driver (Maven/Gradle preferred). A client-side JS shell function is not the same as a PL/pgSQL database trigger.

5. Graph databases / Neo4j — Lectures 17–18

5.1 Graph basics: short conceptual marks

  • G = (V, E): V vertices/nodes, E edges/relationships. Weighted directed edge: (v_i, v_j, w); weight might be distance/cost.
  • Directed edge A → B is not the same as B → A. Path = sequence connected by edges; cycle = starts and ends at same vertex, without repeating other vertices.
  • Neo4j node: properties such as {name: "Thandi"}; a node can have labels such as :Person (a classification, not a property).
  • Neo4j relationship: directed, has a type (:FOLLOWS), may have properties (since: 2017). Cypher can match a relationship without specifying direction, but every stored relationship has direction.
  • Cypher is declarative and expresses graph patterns; it is not SQL table-join syntax.

5.2 Cypher patterns and CRUD — memorise punctuation

// CREATE THREE NODES AND THREE DIRECTED RELATIONSHIPS (Lecture 18 example)
CREATE
  (t:Person {name: 'Thandi', from: 'Durban'}),
  (j:Person {name: 'Johan', from: 'Pretoria'}),
  (n:Person {name: 'Neo', from: 'Cape Town'}),
  (t)-[:FOLLOWS {since: 2017}]->(j),
  (t)-[:FOLLOWS {since: 2016}]->(n),
  (j)-[:FOLLOWS {since: 2018}]->(t);

// READ: who does Thandi follow?
MATCH (p:Person)-[:FOLLOWS]->(f:Person)
WHERE p.name = 'Thandi'
RETURN f.name;

// UPDATE NODE PROPERTY
MATCH (p:Person {name: 'Thandi'})
SET p.age = 21
RETURN p;

// UPDATE RELATIONSHIP PROPERTY
MATCH (t:Person {name: 'Thandi'})-[r:FOLLOWS]->(n:Person {name: 'Neo'})
SET r.since = 2020
RETURN r;

Trace: The CREATE sample has 3 Person nodes and 3 FOLLOWS relationships. The read query returns Johan, Neo (order unspecified without ORDER BY); it does not return Thandi because Johan → Thandi points the opposite way.

Cypher What it does Critical distinction
CREATE (p:Person {...}) Always creates matching new data Running again can make duplicates unless constraints prevent it
MERGE (p:Person {name: 'Thandi'}) Match pattern or create if absent Supports ON CREATE SET / ON MATCH SET
MATCH (p:Person) Bind matching labelled nodes p is a variable, Person a label
MATCH (a)-[:FOLLOWS]->(b) Follow outgoing directed edges Swapping (a) and (b) changes meaning
OPTIONAL MATCH Try pattern and permit null missing matches Unlike ordinary MATCH, does not drop every unmatched row
WHERE Filter matched rows Use property with p.name
RETURN p vs RETURN p.name Node vs scalar property Distinct output types
SET p.age = 21 Add/update property Not the same as REMOVE
REMOVE p.hobby Remove property only Does not remove node
DELETE r Delete relationship Does not delete connected nodes
DELETE p Delete unconnected node Fails if node still has relationships
DETACH DELETE p Delete node and attached relationships Destructive
ORDER BY p.name ASC Sort rows No implicit guaranteed order

MERGE template (Lecture 18):

MERGE (p:Person {name: 'Thandi'})
ON MATCH SET p.age = 21
ON CREATE SET p.from = 'Durban', p.age = 21
RETURN p;

Uniqueness constraint (Lecture 18):

CREATE CONSTRAINT person_name_unique
FOR (p:Person)
REQUIRE p.name IS UNIQUE;

Delete only the relationship vs delete a person:

MATCH (t:Person {name: 'Thandi'})-[r:FOLLOWS]->(n:Person {name: 'Neo'})
DELETE r;

MATCH (p:Person {name: 'Thandi'})
DETACH DELETE p;

5.3 Cypher aggregation — likely count/output questions

Given the three-edge sample above (before any DELETE or subsequent modification):

MATCH (p:Person {name: 'Thandi'})-[:FOLLOWS]->(f)
RETURN count(f) AS peopleFollowed;   // 2

MATCH (p:Person)-[:FOLLOWS]->(f)
RETURN p.name AS person, count(f) AS total;
// Thandi: 2; Johan: 1 (Neo omitted: no outgoing FOLLOWS)

MATCH (p:Person)
RETURN collect(p.name) AS names;     // list of three names; order unspecified

MATCH (a)-[r]->(b)
RETURN type(r) AS relationType, count(*) AS total;
// FOLLOWS: 3
Function Result
count(*) / count(f) Number of matching rows / non-null f values
sum(p.x), avg(p.x) Sum / average numeric properties
min(p.x), max(p.x) Min / max
collect(p.name) A list of values
count(DISTINCT p.name) Count distinct values
RETURN p.name, count(f) Implicit grouping by p.name; no explicit GROUP BY

Common predict-the-output trap: A query with MATCH (p)-[:FOLLOWS]->(f) excludes a person with zero matching outgoing relationships. To preserve such a person in the result, start with MATCH (p:Person) and then use OPTIONAL MATCH (p)-[:FOLLOWS]->(f) before counting.

6. Practice 20-mark integrated scenario — model of the ST1 essay format

Practice prediction — not an actual past/future question. An ocean-research company keeps mission summaries in XML, underwater-vehicle telemetry in MongoDB, and links between vehicles and research stations in Neo4j. The following three subtasks intentionally follow ST1's multi-technology style.

(a) XML/XQuery — 6 marks

Question: Given <missions><mission base="DUR"><missionCode>M1</missionCode><depth>4500</depth></mission>...</missions>, write an XQuery that returns the code of each mission based at DUR deeper than 3000 metres, ordered by code, wrapped in <code> elements.

for $m in /missions/mission
where $m/@base = "DUR" and $m/depth > 3000
order by $m/missionCode ascending
return <code>{$m/missionCode/text()}</code>

Marks to secure: correct path and for (1); correct attribute (@base) (1); correct depth condition (1); ordering (1); correct element construction (2).

(b) MongoDB — 7 marks

Question: Collection readings holds documents {vehicle: "A1", temperature: 2, depth: 4200}. Return average temperature per vehicle for readings deeper than 3000m; keep only vehicles with average temperature below 5; sort vehicle IDs ascending.

db.readings.aggregate([
  {$match: {depth: {$gt: 3000}}},
  {$group: {_id: "$vehicle", averageTemp: {$avg: "$temperature"}}},
  {$match: {averageTemp: {$lt: 5}}},
  {$sort: {_id: 1}}
]);

Marks to secure: correct aggregate([ ... ]) (1); original-document $match (1); $group field reference _id: "$vehicle" (1); $avg (2); post-group $match (1); $sort (1).

(c) Neo4j — 7 marks

Question: Create vehicles A1 and A2, station DUR and directed REPORTS_TO relationships. Then return all vehicle IDs reporting to DUR; count them.

CREATE (a:Vehicle {vehicleId: 'A1'}),
       (b:Vehicle {vehicleId: 'A2'}),
       (s:Station {code: 'DUR'}),
       (a)-[:REPORTS_TO]->(s),
       (b)-[:REPORTS_TO]->(s);

MATCH (v:Vehicle)-[:REPORTS_TO]->(s:Station {code: 'DUR'})
RETURN v.vehicleId ORDER BY v.vehicleId;

MATCH (v:Vehicle)-[:REPORTS_TO]->(s:Station {code: 'DUR'})
RETURN count(v) AS vehicleCount;
// vehicle IDs A1, A2; count 2

Marks to secure: correctly labelled nodes/properties (2); correctly directed edges (2); correct MATCH pattern and property filter (1); projection (1); aggregate count (1).
