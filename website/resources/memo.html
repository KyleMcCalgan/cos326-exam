2024 Q32 — HeritageSA graph scenario (7 marks) · paper pp. 15–16

(a) Add annual visitor counts to sites:

MATCH (sRobbenIsland:Site {name: "Robben Island"})
SET sRobbenIsland.visitorsPerYear = 300000
RETURN sRobbenIsland;

MATCH (sApartheidMuseum:Site {name: "Apartheid Museum"})
SET sApartheidMuseum.visitorsPerYear = 150000
RETURN sApartheidMuseum;

(b) People honoured in Apartheid Museum and year:

MATCH (p:Person)-[r:HONOURED_IN]->(:Site {name: "Apartheid Museum"})
RETURN p.name, r.year;

Expected names Nelson Mandela (2001) and Desmond Tutu (2010).

(c) Heritage sites linked to Cape Town:

MATCH (:City {name: "Cape Town"})-[:HAS_SITE]->(s:Site)
RETURN s.name;

Expected: Robben Island. The HAS_SITE edge is directed City → Site. s.name is a stored node property; r.year is a stored relationship property.

2023 Q32 — People/departments graph (7 marks) · paper p. 18

Given Mpho (33), Tebatso (28), Aviwe (24), James (33); WORKS goes from Aviwe → Accounting, Tebatso → HR, Mpho → HR; James → Mpho is MARRIED.

(a) Change Aviwe’s age to 25:

MATCH (p:Person {name: "Aviwe"})
SET p.age = 25
RETURN p;

(b) Count relationships in the graph:

MATCH ()-[r]->()
RETURN count(r) AS relationshipCount;

Expected 4 (one MARRIED, three WORKS).

MATCH (p:Person)

After (a), result (33 + 28 + 25 + 33)/4 = 29.75; before the update, it is 29.5. The order of answering the subquestions matters if you execute the updates.

Expected: Tebatso, Mpho (order unspecified).

MERGE / ON MATCH / ON CREATE — lecture-relevant, not a verified standalone past-paper question

MERGE (s:Student {studentNo: "123"})
ON CREATE SET s.name = "Emma", s.age = 19
ON MATCH SET s.lastSeen = date()
RETURN s;
  • MERGE searches for the whole pattern and creates it if missing.
  • ON CREATE SET executes only when newly created.
  • ON MATCH SET executes only when matched.
  • If duplicate matches already exist, MERGE does not clean them up; use uniqueness constraints on identifiers where appropriate.
  • Repeating MATCH (s:Student {name: "Emma"}) can yield multiple Emmas, each potentially producing multiple rows from connected relationships.

2. MongoDB (L14–16)

2024 Q31 — WildlifeSA practical (7 marks) · paper pp. 14–15

The supplied sighting uses a date string formatted YYYY-MM-DD, not a BSON Date. Answers below preserve that source representation.

(a) Species and location only, January 2024:

db.getSiblingDB("conservationDB").animalSightings.find(
  { date: { $gte: "2024-01-01", $lt: "2024-02-01" } },
  { _id: 0, species: 1, location: 1 }
)

For ISO-formatted date strings, lexicographic range comparison works. If date were stored as a BSON Date, use ISODate(...) bounds instead.

(b) All fields, ranger Nomsa Khumalo:

db.getSiblingDB("conservationDB").animalSightings.find({
  "ranger.name": "Nomsa Khumalo"
})

(c) Delete all Impala sightings:

db.getSiblingDB("conservationDB").animalSightings.deleteMany({species: "Impala"})

The source explicitly equates “not endangered” with the given species: "Impala" filter; do not generalise the deletion to all unlabelled species.

2022 Q32 — Food ratings arrays (6 marks) · paper pp. 19–20

(a) Exact array [5, 8, 9] in this order:

db.getSiblingDB("foods").myfavourites.find({ratings: [5, 8, 9]})

Expected documents cake and steak (IDs 5 and 8).

(b) Array contains 5 anywhere:

db.getSiblingDB("foods").myfavourites.find({ratings: 5})

All four source documents contain 5.

(c) At least one SAME element is greater than 5 and less than 9:

db.getSiblingDB("foods").myfavourites.find({
  ratings: { $elemMatch: { $gt: 5, $lt: 9 } }
})

Expected cake, biscuits and steak, which contain 8. Chicken only has [5,9], so does not match. $elemMatch is essential to bind both conditions to a single array element.

2024 Q24 — Orders aggregation (7 marks) · paper p. 11

(a) A collection is a group of MongoDB documents (BSON documents) in one database, analogous to a relational table but normally schema-flexible. Each document contains fields and values, and may contain embedded documents and arrays.

(b) The supplied pipeline:

db.orders.aggregate([
  { $match: { status: "completed" } },
  { $group: {
      _id: "$customerId",
      totalAmount: { $sum: "$amount" },
      totalOrders: { $count: {} }
  }},
  { $sort: { totalAmount: -1 } }
])
  1. $match retains completed orders only.
  2. $group groups by customer ID, sums spending and counts orders.
  3. $sort orders customers by total spending descending.
  4. Each output document contains _id (customer ID), totalAmount and totalOrders.

Important nuance: $count: {} is a valid group accumulator in supported MongoDB versions; $sum: 1 is the common alternative taught in L15. No numeric output can be calculated because this question does not provide actual order records.

Lecture 16 — Mongo shell functions (supplement to past questions)

function totalLikes(dbName, collectionName, title) {
  const col = db.getSiblingDB(dbName).getCollection(collectionName);
  const results = col.aggregate([
    {$match: {title: title}},
    {$group: {_id: "$title", total: {$sum: "$likes"}}}
  ]);
  while (results.hasNext()) printjson(results.next());
}

getSiblingDB() selects another database without changing the db variable; col stores the collection reference; results stores a cursor. Mongosh JavaScript functions are not automatically server-side database functions. A Java application normally uses the MongoDB Java driver, not a mongosh-defined JavaScript function.

3. XQuery and FLWOR (L11)

2022 Q31 — Students and third-year modules (3 marks) · paper pp. 18–19

The requested query lists names of students studying third-year modules and aged under 22. The sample uses a student element with module attribute such as COS314, <name>, <age>.

for $s in //student
where starts-with(string($s/@module), "COS3")
      and number($s/age) < 22
return $s/name

Assumption: In this module’s sample, third-year modules are represented by COS3xx codes. If the XML separately defines a year attribute or other module classification, filter that explicit field instead. starts-with(..., "COS3") is a reasonable interpretation of the given module-code convention, not a general rule for every university.

2022 Q3 — Staff in ascending staff-number order · paper pp. 4–6

A complete valid FLWOR form:

for $s in //STAFF
let $num := $s/STAFFNO
let $fn := $s/NAME/FNAME
let $ln := $s/NAME/LNAME
order by $num ascending
return
  <STAFFDATA>
    <STAFFNO>{data($num)}</STAFFNO>
    <FNAME>{data($fn)}</FNAME>
    <LNAME>{data($ln)}</LNAME>
  </STAFFDATA>

Critical rule: $s/STAFFNO starts from the current staff element; /STAFFNO incorrectly starts at the document root. for loops over nodes; let binds a value/sequence; order by sorts; return constructs result XML.

2023 Q3 — Customers above credit limit · paper pp. 4–5

for $c in //CUSTOMER
where number($c/CREDLIMIT) > 10000
return (
  $c/ACCOUNTNO,
  $c/NAME,
  $c/CREDLIMIT
)

The source has customers James Brown (30000) and Lebogang Tshabalala (12000), so both satisfy the filter. A valid FLWOR clause uses for $c in, XPath /, and where ... > 10000 (not malformed slashes or literal $ signs in paths).

2022 Q11 — Distinct branches with salary predicate · paper p. 11

The paper gives a query shaped like:

for $b in distinct-values(//@branchNo)
let $staff := //STAFF[@branchNo = $b]
where some $salary in $staff/SALARY
      satisfies ($salary > 15000)
return <BRANCHNO>{$b}</BRANCHNO>

Meaning: For each distinct branch number, retrieve its staff, keep branches with at least one salary over 15,000, and return that branch once. some ... satisfies is an existential condition, not “all staff.”

4. PostgreSQL XML (L12)

2024 Q30 — Sum customer XML purchase amounts (5 marks) · paper pp. 13–14

Each purchaseHistory has multiple PURCHASE/AMOUNT elements. xpath() returns an XML array; expand it using unnest() and convert text values to numbers before summing.

SELECT c.customerId, c.customerName,
       SUM((x.amount_xml::text)::numeric) AS totalPurchaseAmount
FROM CustomerSales AS c
CROSS JOIN LATERAL unnest(
    xpath('/PURCHASES/PURCHASE/AMOUNT/text()', c.purchaseHistory)
) AS x(amount_xml)
GROUP BY c.customerId, c.customerName
ORDER BY c.customerId;

Expected:

customerId customerName totalPurchaseAmount
C001 Alice Johnson 350.00
C002 Bob Smith 120.00

CROSS JOIN LATERAL applies unnest(xpath(...)) independently to each customer's XML, producing one numeric amount per purchase. For customers without any purchase nodes this query returns no row; use a LEFT JOIN LATERAL if zero-purchase customers must remain.

2024 Q3 — Create FullName XML · paper pp. 4–5

Correct functional form:

SELECT XMLELEMENT(NAME "FullName", concat(first_name, ' ', last_name))
FROM Staff;

The paper’s closest listed option is C (xmlelement(NAME "FullName", concat(first_name,last_name))), but that version produces joined words without an inserted space. If a natural full name needs a space, explicitly include ' '. XMLCONCAT concatenates XML values, not ordinary name strings.

2024 Q23 — XML catalog XPath · paper p. 10

(a) Select names of products whose category is Electronics:

/catalog/product[category = 'Electronics']/name

Result: <name>Laptop</name>.

(b) Select all products in either category:

Both Book and Laptop products match. text() could be appended if the question asks for text rather than elements.

2020 Q39 / 2021 Q38 — XMLStaff XPath · 2020 pp. 11–12 · 2021 pp. 13–14

Useful correct patterns for the staff XML column:

-- Return STAFFNO element(s), as xml[]
SELECT xpath('/STAFF/STAFFNO', staffData) FROM XMLStaff;

-- Text node instead of the element tag
SELECT xpath('/STAFF/STAFFNO/text()', staffData) FROM XMLStaff;

-- Attribute rather than child element
SELECT xpath('/STAFF/@branchNo', staffData) FROM XMLStaff;

-- Convert the array of matches into result rows
SELECT unnest(xpath('/STAFF/STAFFNO/text()', staffData)) FROM XMLStaff;

xpath() returns xml[]. The root is /STAFF when each column value stores one <STAFF> element; if the column stores an entire <STAFFLIST> document, use /STAFFLIST/STAFF/... instead.

2020 Q3 — Store XML as a column · paper pp. 1–2

Description: Store the whole XML document/fragment as the value of a column (often a native xml type) in one or more rows.

Strengths: easy and fast to insert the whole document; straightforward to retrieve intact; preserves hierarchical structure; good when documents are mostly read or archived as whole units.

Weaknesses: difficult or inefficient to search individual inner fields repeatedly; document parsing overhead; small internal updates can require replacing the entire document; ordinary relational indexes on internal XML elements are not directly available.

2020 Q31 / 2021 Q34 — XML shredding · 2020 p. 8 · 2021 pp. 11–12

Shredding decomposes an XML tree into table rows/columns (often one row per repeated element). Advantage: ordinary SQL queries/indexes can target individual values. Disadvantages: additional schema design and hierarchy/order metadata may be needed to reconstruct XML; updates to hierarchical structures can be more involved.

2023 Q23/Q30; 2022 Q23 — XML-related questions

  • 2023 Q23, pp. 11–12: Distinguish well-formed XML, hierarchy and path navigation from table storage. Use the document's exact root/element names.
  • 2023 Q30, pp. 15–16: XSD describes structure and types. A simple type contains scalar content; a complex type contains child elements/attributes; minOccurs/maxOccurs constrain cardinality; DTD is less expressive about data types.
  • 2022 Q23, pp. 13–14: For STAFFLIST, STAFF is a repeated element, branchNo is an attribute (@branchNo), and STAFFNO/SALARY are elements.

2024 Q26 — Parallel relational DBMS vs Hadoop/MapReduce (only partial L13 overlap) · paper p. 12

  • Parallel RDBMS: SQL, structured data, relational optimisation, parallel query execution, relational consistency/transactions; traditionally schema-oriented.
  • Hadoop/MapReduce: distributed computation over partitioned datasets; mapper generates intermediate pairs and reducers aggregate per key; tolerates node failures and commodity clusters; suited to large batch processing and varied input formats.

7. Revision rules and identified exam pitfalls

Topic Exam-safe rule
Cypher (x:Label {key:value}) Variable x, label Label, property filter key:value; x does not persist between queries.
Cypher direction -> and <- matter; -[:TYPE]- matches either direction.
Cypher rows MATCH returns all matching combinations; another MATCH may produce more rows or eliminate rows with no continuation.
OPTIONAL MATCH Keeps unmatched outer rows and supplies nulls.
Cypher SET / MERGE SET adds/updates; MERGE matches-or-creates; ON MATCH SET and ON CREATE SET are conditional branches.
DELETE A connected node needs DETACH DELETE (or relationship deletion first).
Cypher aggregation Nonaggregated RETURN expressions determine grouping; count(r) counts matched relationship values.
MongoDB find() find(filter, projection); projection 1 includes and 0 excludes, except _id:0 can accompany inclusions.
MongoDB nested data Dot notation: "ranger.name". Arrays: ratings: 5 means an array contains 5.
$elemMatch Combines conditions on the same array element.
Aggregation $match filters, $group computes output with _id, $sort uses fields available after grouping.
MongoDB $ in strings "$likes" reads a field; "likes" is literal text.
MongoDB shell function Lives in current mongosh session or script / .mongoshrc.js and is not automatically a database-stored server procedure.
XPath @ vs / @branchNo accesses an attribute; /SALARY accesses an element.
PostgreSQL xpath() Returns xml[] even for one matching node; unnest() expands it into rows.
FLWOR for vs let for iterates over items; let binds expression/sequence; where, order by, return are clauses.
Whole-XML vs shredded Whole XML retains document form; shredded storage exposes inner fields in ordinary columns.
Past paper fidelity Several uploaded papers contain spelling, spacing and syntax mistakes in sample code/options. Prioritise valid database syntax and mention ambiguities rather than copying errors.
